## 0. 五条结论先说

1. **依赖方向是单向的**：`app → board → soc → arch`，`drivers / subsys` 再依赖 `soc / arch / HAL`。上层可以换，下层不能反向依赖。
2. **板级定义住在上游树里**：`west\zephyr\boards\espressif\esp32s31_function_coreboard\`（15 个文件）——**主仓库的 git 看不到它**，它提交在 zephyr 克隆的 `pr-s31` 分支上。这是这套仓库最特殊的结构，也是最大的一处风险（§9-1）。
3. **树外模块现在落了 5 个**：`west.yml` 声明 **70** 个项目，磁盘上有 **7** 条路径（`zephyr` 自身 + `hal_espressif` + `hal_stm32` + `cmsis_6` + `mbedtls` + `tf-psa-crypto` + `mcuboot`），其余 **63** 个没拉。不是缺配置：ESP32 那条线只做 S3/S31 + Wi-Fi/BLE/crypto；STM32 那条线为了 F411/F103 拉了 `hal_stm32` 与 `cmsis_6`；`mcuboot` 是为了 OTA 双槽。**这五个模块现在全部是按 `west.yml` revision 落地的真 git 仓**（§7.3）。
4. **"组件层"你有自己的，而且长出来了**：`applications\common\`（`store` / `breath_sync` / `ota_engine` + `test\` + 两个 `dtsi`）就是自建的跨工程共用层，`applications\_template\` 是新建工程骨架。这层是唯一能让 **14 个工程**不各写一份的东西（§8）；`s3_wifi_portal` 内部还按 L0/L1/L2 分了层（§3.1）。
5. **Kconfig 是"开关决定代码在不在"**：一个符号没打开，它下面整棵子树（含 `default y` 的驱动）都不会实例化，结果不是"功能没了"，而是**链接期 undefined reference `__device_dts_ord_NN`**。这是读懂依赖树最实用的一条（§5、§6 有实例）。

## 1. 依赖方向（同一棵树，两个方向看）

**向下 = 依赖**（app 需要谁才能编出来）：

```
applications\esp32s31\korvo_sys         ← 你的代码（只认 API 头 + devicetree）
├── boards\<board>.overlay      ← 板级差异（引脚/外设节点）
├── prj.conf                    ← 打开哪些 Kconfig 符号
└── CMakeLists.txt              ← find_package(Zephyr)
        │
        ├── board: boards\espressif\esp32s31_function_coreboard\
        │     └── soc: soc\espressif\esp32s31\
        │           └── arch: arch\riscv\
        ├── drivers: drivers\*（102 组，按 devicetree 节点实例化）
        ├── subsys: subsys\*（54 组）
        ├── lib: lib\*（14 组，含 libc 选择）
        └── modules: ESP32 线 → hal_espressif（HAL + blob） / tf-psa-crypto / mbedtls
                     STM32 线 → hal_stm32（Cube HAL/LL） / cmsis_6（core_cmN.h）
                    └── SDK 1.0.1（gcc / binutils / newlib / openocd，三个目标）
```

**向上 = 提供**（谁被谁用，从硅片往上）：

```
芯片 (ESP32-S31 / ESP32-S3 / STM32F411 / STM32F103)
└── SDK 工具链 + HAL（ESP32 走 hal_espressif；STM32 走 hal_stm32 + cmsis_6）
    └── arch（RISC-V / Xtensa / ARM Cortex-M：上下文切换、异常、MPU）
        └── soc（时钟树、中断控制器、内存布局 dtsi/defconfig）
            └── drivers（uart / gpio / i2c / spi / wifi / pwm / crypto …）
                └── subsys（console / shell / logging / settings / net / usb …）
                    └── app（你的 main.c；s3_wifi_portal 再往下分 L0/L1/L2）
```

一句话记：**换芯片只动下面四层，换工程只动最上面一层**。这就是 Zephyr 跨芯片的机制本体。

## 3. 三层各自负责什么（横向对照表）

| 层 | 在哪 | 只做一件事 | 依赖谁 | 被谁依赖 |
|---|---|---|---|---|
| **app** | `applications/<family>/<app>/` | 业务逻辑 + 打开符号 + 板级差异 | board / subsys / lib | 无（最上层） |
| **board** | `zephyr\boards\espressif\<板>\` | 引脚、外设节点、flash 分区、板级默认 | soc | app |
| **soc** | `zephyr\soc\espressif\<soc>\` | 时钟/中断/内存映射/多核 | arch + hal | board / drivers |
| **arch** | `zephyr\arch\{riscv,xtensa}\` | 上下文切换、异常、MPU、启动 | hal + SDK | soc |
| **drivers** | `zephyr\drivers\*` | 把 devicetree 节点变成可用设备实例 | soc / arch / hal | subsys / app |
| **subsys** | `zephyr\subsys\*` | 协议栈与服务（shell/log/net/usb/settings…） | drivers / lib / modules | app |
| **lib** | `zephyr\lib\*` | 纯算法与 libc 适配 | 无（或 libc） | 所有上层 |
| **modules** | `west\modules\…` | 厂商 HAL、加密、blob 库 | SDK | drivers / subsys |
| **SDK** | `C:\Users\xiao1\zephyr-sdk-1.0.1` | 交叉编译器与运行时 | 硬件 | 全部 |

### 3.1 app 层内部还有两层：L0/L1/L2 与 `applications\common`

"app 只有一层"是旧认知。`s3_wifi_portal` 拆完以后，**app 内部自己也是一棵树**，且这条约束是物理的（L2 编译时看不到 L1 的头文件）：

```
applications\esp32s3\s3_wifi_portal\src\
├── main.c        ← 217 行：初始化 + 事件分派 + 时间线（只 include L1/L2 的对外头）
├── l0\           ← 最底层：协议/搬运（ota.c/h 的升级状态机、ops.c 的文件搬运）
├── l1\           ← 中间层：对外的"面"（http_core 路由、api_*、page 资源、shell_cmds、selftest）
└── l2\           ← 业务策略：cred / wifi_scan / portal_ap / wifi_link / time_sync / netcheck / led_status / dns_hijack
```

依赖方向：**L0 ← L1 ← L2 ← main**，`L2` 不许 include `L1`（物理隔离已实证：`fatal error: http_core.h: No such file or directory`）。
跨工程复用的部分再往上一格 —— `applications\common\include\ota_engine.h` 提供"OTA 协议层"（后端表 + `begin` 三态），
`applications\esp32s3\s3_wifi_portal\src\l0\ota.c` 只是它的**平台适配器**。机制与判据见
`应用层分层改造教程-s3_wifi_portal.md`（§5 四问判据、§11 静态库裁符号事故）。

## 4. 一次构建把这棵树串起来的顺序

### 4.1 CMake 阶段（`west build --cmake-only`，约 25 s）

```
app\CMakeLists.txt
└── find_package(Zephyr HINTS $ENV{ZEPHYR_BASE})
    ├── 读 board.yml → 定 SoC 与两个核
    ├── 收集 arch/  soc/  drivers/  subsys/  lib/  各自 CMakeLists
    ├── 收集每个 module 的 zephyr/module.yml（cmake/kconfig 入口）
    └── 生成 build\<…>\ 下的 CMakeCache / Kconfig / 编译数据库
```

### 4.2 Kconfig 合并（**优先级从低到高**，后者覆盖前者）

| 顺序 | 来源 | 本项目实例 |
|---|---|---|
| 1（最低） | 各 `Kconfig` 文件里的 `default` | `CRYPTO_ESP32 default y`（但被 `if CRYPTO` 包住，要上层打开才生效） |
| 2 | **板级 `*_defconfig`** | `esp32s31_function_coreboard_hpcore_defconfig` |
| 3 | **`prj.conf`** | `CONFIG_CRYPTO=y`、`CONFIG_WIFI_NM=y` … |
| 4（最高） | 命令行 `-DEXTRA_CONF_FILE` / fragment | `build.ps1 -ExtraConfFile <file>` |

### 4.3 devicetree 合并（同样从低到高）

| 顺序 | 来源 | 说明 |
|---|---|---|
| 1（最低） | `soc\espressif\<soc>\*.dtsi` | SoC 级外设与中断号 |
| 2 | 板级 `.dts` + `-pinctrl.dtsi` | 引脚怎么接、flash 分区表 |
| 3 | **`applications/<family>/<app>/boards\<board>.overlay`** | 本工程要开哪些节点（`status = "okay"`） |
| 4（最高） | `-DEXTRA_DTC_OVERLAY_FILE` | `build.ps1 -ExtraDtcOverlay <file>` |

> `applications\common\korvo_board.dtsi` / `korvo_i2c.dtsi` 不在 Zephyr 的合并链里——它们是**被 overlay 用 `#include` 拉进来的**，所以效果等价于第 3 层的一部分。

### 4.4 编译阶段（`ninja -j8`）

```
ninja → SDK gcc（riscv64 / xtensa）
      → 每个 .c 一条 cc1（Windows 上单次 ~123 ms，进程开销占一半）
      → 链接 → zephyr\zephyr.elf / .bin / .map
```

## 5. 实例 A：`korvo_sys`（S31，最小系统 + 三个驱动）

`prj.conf` 只写了 11 个符号，但每个符号下面是一棵子树：

```
CONFIG_CONSOLE=y ─┐
CONFIG_SERIAL=y  ├→ subsys\console + drivers\uart\uart_esp32 → 板级 uart0 节点
CONFIG_UART_CONSOLE=y ┘
CONFIG_SHELL=y → subsys\shell → SHELL_BACKEND_SERIAL → 复用上面那条 console
CONFIG_LOG=y   → subsys\logging → 后端自动挑 console
CONFIG_HWINFO=y        → drivers\hwinfo（hwinfo_esp32 默认 y）→ 复位原因/器件 ID
CONFIG_SENSOR=y        → drivers\sensor\coretemp → 要求 overlay 里 coretemp 节点 okay
CONFIG_ENTROPY_GENERATOR=y → drivers\entropy（trng0 板级已 okay）
CONFIG_WATCHDOG=y      → drivers\watchdog\wdt_esp32（**必须先开 WATCHDOG**，否则 WDT_ESP32 的 default y 不生效）
CONFIG_CRYPTO=y        → drivers\crypto（AES/SHA；整个 `drivers/crypto/Kconfig` 被 `if CRYPTO` 包住）
```

**为什么这条链值得记**：`CONFIG_CRYPTO` 忘写时，编译能过 configure，**链接期**才报
`undefined reference to __device_dts_ord_46`（aes）/ `_71`（sha）。这是"Kconfig 树决定代码是否存在"的直接证据——不是运行时找不到设备，是那台设备根本没被编译进去。

## 6. 实例 B：`s3_wifi_portal`（S3，网络栈整条链）

```
app（s3_wifi_portal：main.c 只做事件分派；L2 业务策略；L1 HTTP/页/命令面；L0 升级状态机）
├── applications\common\include\ota_engine.h ← 跨工程复用的 OTA 协议层（与本工程的 l0\ota.c 适配器对接）
├── CONFIG_NETWORKING + NET_IPV4/TCP/UDP/SOCKETS + DHCPv4
│   └── subsys\net\（核心）→ L2: drivers\wifi\esp32（offloaded）
│         └── modules\hal\espressif\zephyr\blobs\lib\esp32s3\
│               libnet80211.a(1.45 MB) libpp.a(0.71 MB) libcore.a  libcoexist.a
│               ＋ wpa_supplicant（net/lib）→ 加密原语走 modules\crypto\tf-psa-crypto
├── CONFIG_HTTP_SERVER → subsys\net\lib\http\server（19 条 HTTP_RESOURCE_DEFINE 在这里注册）
├── CONFIG_MDNS_RESPONDER + DNS_RESOLVER → subsys\net\lib\dns
├── CONFIG_WIFI_NM + WIFI_USAGE_MODE_STA_AP → 新版 Wi-Fi 管理层
├── CONFIG_FLASH/NVS/SETTINGS/SETTINGS_NVS → subsys\fs\nvs + subsys\settings
│   └── CONFIG_WIFI_CREDENTIALS → 官方凭据库（SSID/密码落 NVS）
└── CONFIG_LED_STRIP → drivers\led_strip（WS2812 @ GPIO48，走 RMT）
```

这一条链横跨了**四层**：app → subsys（net/http/dns/settings）→ drivers（wifi/flash/led_strip）→ modules（hal_espressif blob + tf-psa-crypto）。S3 是主干分支，这条链是完整的；S31 因为 Wi-Fi 驱动在 PR 里，同一套 app 的可用性见 `平台现状与坑.md`。

> **和旧版最大的差别**：以前"app"就是一个 `main.c`；现在 app 内部按 L0/L1/L2 分了层（§3.1），
> 且 `HTTP_RESOURCE_DEFINE` / `SHELL_CMD_REGISTER` / `K_THREAD_DEFINE` 这些"只注册不被引用"的对象
> 必须住进 **OBJECT 库**（`$<TARGET_OBJECTS:…>`）才不会被链接器静默裁掉 —— 这是 2026-11-16 那次事故的正面结论，
> 写进了 `AGENTS.md` §1 与教程 §11。

| 项目 | 路径 | 提供什么 | 谁需要它 |
|---|---|---|---|
| `hal_espressif` | `modules\hal\espressif` | ESP32 全家族 HAL + **9 个 blob 库**（在 `zephyr\blobs\lib\esp32s3\`：`libnet80211` 1.45 MB、`libpp` 0.71 MB、`libbtdm_app` 1.54 MB、`libmesh` 1.00 MB、`libcoexist` 110 KB、`libphy` 257 KB、`libespnow` 66 KB、`libbtbb` 23 KB、`libcore` 4.8 KB） | Wi-Fi / BLE / RF 驱动 |
| `hal_stm32` | `modules\hal\stm32` | STM32Cube 全系列 HAL/LL + `stm32cube\common_ll` 的统一入口 + `dts\st\f4\`、`dts\st\f1\` 引脚库 | F411 / F103 的 SoC 支撑（**真 git 仓 @2fd0502，稀疏检出 F1/F4**，见 7.3） |
| `cmsis_6` | `modules\hal\cmsis_6` | CMSIS Core 设备头（`core_cm4.h` 给 F4、`core_cm3.h` 给 F1） | 所有 ARM 芯片 |
| `mbedtls` | `modules\crypto\mbedtls` | TLS | HTTPS/MQTT-TLS、WPA 部分原语 |
| `tf-psa-crypto` | `modules\crypto\tf-psa-crypto` | PSA Crypto API | 4.x 的 wpa_supplicant、硬件加密 |
| `mcuboot` | `bootloader\mcuboot` | 双槽 bootloader + `imgtool` | S3 的 OTA 换槽/回滚 |

`Get-ChildItem modules -Recurse -Depth 4 -Filter module.yml` 现在有 **5 个**（`hal\espressif`、`hal\stm32`、`hal\cmsis_6`、`crypto\mbedtls`、`crypto\tf-psa-crypto`；mcuboot 在 `bootloader\` 下另有自己的 `module.yml`）——**"有 module.yml 才算 Zephyr 模块"**，这是判断一个第三方树能不能被 `CONFIG_*` 打开的唯一标准。

### 7.2 没拉的 63 个，按用途归组（不用逐个记）

| 组 | 数量 | 代表 | 拉了会解锁什么 |
|---|---|---|---|
| 其他厂商 HAL | 29 | `hal_nordic` `hal_xtensa` `cmsis` `libmetal` … | 换别家芯片才有意义；STM32 那份（`hal_stm32`）和 `cmsis_6` 已经拉了 |

**这张表的用法**：想加一项新能力（屏幕、文件系统、OTA），先看它在哪一组，`west update <项目名>` 拉下来，再看它的 `module.yml` 会不会要求额外 Kconfig —— 而不是直接写 `CONFIG_LVGL=y` 然后奇怪为什么编不过。

这五个模块以前有的是**补文件补出来的**（不是 git 仓）。2026-11-16 晚已全部按 `west.yml` 的 revision 换成真仓，`west update` 认得它们了：

| 模块 | 现状 | 后果 |
|---|---|---|
| `hal_stm32` | 真 git 仓，`HEAD = 2fd0502dd5…7229`（= `west.yml` 钉的 revision）；**无 blob 克隆 + 稀疏检出**：工作区里齐全的是根文件、`zephyr\`、`stm32cube\common_ll\`、`stm32cube\stm32f1xx\`、`stm32cube\stm32f4xx\`、`dts\`，其它系列（F0/F7/H7/U5…）的 blob 没下载 | 编 F103/F411 没有任何影响（双板 `-Pristine` 复编 `17104 B` / `19940 B`，烧录与串口也补跑过）；真要用别的系列，git 会按需补 blob，或显式 `git sparse-checkout disable` 补齐 |

## 8. 你自建的"组件层"：`applications\common\` + `applications\_template\`

Zephyr 树内不提供"跨工程共用业务代码"的容器，这层必须自己做。现在这一层有 **5 样东西**，按"机制 vs 策略"分得很清楚：

| 形态 | 文件 | 被谁用 | 作用 | 属于 |
|---|---|---|---|---|
| **共用源码·存储** | `applications\common\src\store.c` + `include\store.h` | `korvo_apps`、`korvo_nvs`（CMake 里显式 `target_sources`） | settings/NVS 的键值封装，芯片无关 | 机制 |
| **共用源码·呼吸同步** | `applications\common\src\breath_sync.c` + `include\breath_sync.h` | 多机同步呼吸灯（见 `同步呼吸灯规则.md`） | 把"绝对 UTC 锚点 + 相位"算成亮度，跨芯片/跨灯型一致 | 机制 |
| **共用源码·OTA 协议层** | `applications\common\src\ota_engine.c` + `include\ota_engine.h`（+ `test\test_ota_engine.c`） | `s3_wifi_portal` 的 `src\l0\ota.c` 作为平台适配器调用 | 后端表 + `begin` 三态（`<0` 失败 / `0` 全量 / `>0` 续传偏移）+ `err_msg`/`err_token`；**只做协议，不碰 flash** | 机制 |
| **共用 dtsi** | `applications\common\korvo_board.dtsi`（PA_CTRL / WS2812@GPIO37 / adc0）、`korvo_i2c.dtsi`（SDA=IO0 / SCL=IO1） | `korvo_apps` / `korvo_lab` / `korvo_periph` / `korvo_shell` 的 overlay 里 `#include` | 板级差异只写一份，14 个工程不重复 | 机制 |
| **骨架** | `applications\_template\`（CMakeLists / prj.conf / presets / `boards\` / `src\`） | 新建工程时复制 | 保证新工程天然满足 `build\` 落点与 overlay 命名 | 机制 |

**判据（这一层到底该放什么）**：放"**机制**"——多工程会重复、且改漏会出错的东西（键值封装、OTA 协议、灯效同步）；
不放"**策略**"——某个工程独有的玩法（配网页长什么样、扫不扫 AP、连哪个 SSID）。策略留在 app，机制才下沉。
一旦某样东西开始出现"只有 A 工程用得上、但 B 工程也顺手抄了一份"的苗头，就是该下沉的信号。

这一层不叫 module（没有 `module.yml`），也不叫 snippet —— 但它解决的是同一个问题：**同一份配置/代码在多个 app 间复用**。真要升级成 Zephyr 原生可移植形态，只有两条路：把 `store.c` / `ota_engine.c` 那套做成带 `module.yml` 的独立模块（可被 `CONFIG_*` 打开），或把"常用 Kconfig 组合"做成 snippet（`west build -S` 一句话套用）。

## 9. 结构风险与边界（诚实清单）

| # | 风险 | 证据 | 影响 / 建议 |
|---|---|---|---|
| 1 | **板级定义不在主仓库的 git 里** | `west\zephyr` 的 `git log -- boards/espressif/esp32s31_function_coreboard` → `34e025569`；主仓库 `git status` 看不到这 15 个文件 | 重新 clone Zephyr / 换分支 → 板子直接编不出来。备份或在主仓库留一份（取舍见 `工程结构与可迁移性.md`） |
| 2 | **blob 的位置容易搞错** | 真 blob 在 `modules\hal\espressif\zephyr\blobs\lib\esp32s3\`（9 个 .a）；而 `modules\hal\espressif\lib\esp32s3\` 是**空目录**（旧 `fetch_s3_blobs.ps1` 的目标路径） | 现在 blob 随模块自带，不再需要手动 fetch；清掉空目录或在 `tools\README.md` 标注"旧布局" |
| 3 | **S31 依赖未合并的 PR 分支** | `VERSION 4.5.99` + 分支 `pr-s31` | 换回 main 就编不出 S31；S3 工程不受影响（主线可用） |
| 4 | **模块只有 5 个** | §7.1 | 想要屏幕/文件系统，先 `west update`，否则 `CONFIG_*` 写了也不存在。盘上这 5 个（`hal_espressif`/`hal_stm32`/`cmsis_6`/`mbedtls`/`tf-psa-crypto`）现在都是标准仓、`west update` 认得（§7.3） |
| 5 | **`applications\common` 靠相对路径引用** | `../../common`、`../../../common/korvo_board.dtsi` | 目录再搬一次就断，且 `check-layout.ps1` 不查这类断链（只查产物落点） |
| 6 | **F1/F4 的厂商模块不在 git 里** | `applications\stm32f1`、`applications\stm32f4` 已入库，但 `west\modules\hal\stm32\stm32cube\stm32f1xx\` 等被 `.gitignore` 覆盖 | 换机 clone 后直接编 F103/F411 会报 `Cannot find source file stm32f1xx_hal.c` / `core_cm3.h`。先跑 `tools\pull-stm32-modules.ps1`（或照教程 15 第二/三篇手工复原） |
| 7 | **`build\esp32s3\s3ota` 体积大（241.9 MB）** | 里面是 sysbuild 目录 + 20 个 `fw_v*.signed.bin` | 不纳库、不影响巡检；若要给仓库瘦身需连 `build_ota.ps1` 的路径一起改 |
