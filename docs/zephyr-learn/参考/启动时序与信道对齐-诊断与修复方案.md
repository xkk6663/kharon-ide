# s3_wifi_portal 启动时序与信道对齐：诊断、修复与验收

> 状态：**已落地并真机验收**（v142 诊断 → v143–v148 实施，5 次 OTA 上板）。
> 对象：`applications\esp32s3\s3_wifi_portal`，ESP32-S3，mcuboot 双槽。
> 核查日期：2026-11-16
>
> 阅读顺序：§0 结论 → §8 实施与验收（含每档改动的真机数据）→ §10 遗留项。
> §1–§7 保留的是**改造前**的实测证据与代码定位，是"为什么要这么改"的依据，不随版本更新。

## 0. 结论（先看这三句）

1. **"重启后很久才通"不是 HTTP 慢，是"没有 IP"**。HTTP server 在 `t≈2.7 s` 就已经起来（`t=3.2 s` 的机上自检拿到了 200）。真正卡住的是 STA：改造前实测 **boot → 拿到 IP = 19.3 s**，其中 6.4 s 与网络无关（固定 `k_msleep` + 串行自检）、3.6 s 是**一次必然失败的首连 + 3 s 退避**、9.1 s 是第二次连接自己扫信道+关联+DHCP。**改造后实测 5.8 / 7.7 / 8.7 / 11.2 / 12.7 / 13.9 s**（6 次冷启动），剩下的大头是驱动自己全信道扫描（~10 s），属物理成本。
2. **信道死锁的种子不是"拿不到扫描结果"，而是"拿到之后再也不松手"**：`ap_retarget()` 会把 `g_ap_params.channel` 永久钉在某个具体信道，而 `enable_softap()` 只在第一次（`ssid == NULL`）才初始化参数，之后再也不会恢复到 `WIFI_CHANNEL_ANY`。一旦 AP 被钉住，STA 连另一个信道上的网络就是 `status 4`（ASSOC_EXPIRE），而这时唯一的自救入口是"再扫一次"，扫描入口又只挂在 HTTP 上。**改造后 AP 只报真实信道、auto 不再被判成 mismatch，失败时会自己扫/搬信道；真机已跑到 `channel mismatch: ap pinned ch=9, "SCAUNET" ch=3 -> reopen AP` 并成功搬过去。**
3. **成本很低**：改动全在 `src\*.c`，不动 `prj.conf`、不动 overlay，**增量编译 29.5–40 s**。只有一次例外：目录改名/CMake 缓存失效导致 v147 那次全量（708.6 s），不是改动本身的性质。

## 1. 实测证据（先有数据，再谈修法）

### 1.1 一次冷启动的完整时间线

抓取方式：`kernel reboot cold`（shell 命令）+ 串口 80 s 全量记录，日志在 `logs\boot-probe3.log`。

| 时刻 | 事件 | 说明 |

| `2.096 s` | `SoftAP "S3-Portal" is up` | **`k_msleep(2000)` 结束后**才开 AP |
| `2.104 s` | `DHCPv4 server up on 192.168.4.1` | AP 侧可用 |
| `3.217 s` | 自检 `GET /api/wifi -> 200` | **HTTP server 此时已可用** |
| `3.247 / 3.262 / 3.276 s` | 自检 `/api/shell`、`/api/ota/slots`、`/api/drops` 全 `404` | **不是故障，见 §6** |
| `4.791 s` | 自检 `/api/saved -> 200` | |
| `6.305 s` | 自检 `/generate_204 -> 302` | captive 兜底正常 |
| `6.337 s` | `ota: nonce restored: 1794832740` | settings 读完 |
| `6.360 s` | `boot #145 ... previous run dirty` | NVS 启动计数 |
| `6.514 s` | `wifi_credentials: 2 saved network(s)` | 凭据表就绪 |
| `6.558 s` | `connecting to "Power" ...` | **第一次真正发起连接** |
| `7.172 s` | `connect failed, status 1` | **0.61 s 就被判失败** |
| `10.205 s` | `auto reconnect attempt 2/3` | 3 s 盲退避后重试 |
| `10.210 s` | `connecting to "Power" ...` | 第二次 |
| `19.304 s` | `net_dhcpv4: Received: <hub-ip>` | **boot → IP = 19.3 s** |
| `19.310 s` | `STA got IP` + scope 自检 `dev` 通过 | 局域网侧真的通了 |
| `19.483 s` | `SNTP ok`（127 ms） | 对时成功 |
| `20.123 s` | `net check: online (200)` | 出网自检通过 |

**时间预算**（19.3 s 花在哪）：

| 段 | 时长 | 与网络有关？ | 可压缩性 |
|---|---|---|---|
| 启动 → AP 起来 | 2.1 s | 有必要（驱动初始化），但用盲等不是事件等 | 可改成事件驱动，省 1–2 s |
| AP → 连接发起（自检 + 读 NVS） | 4.4 s | **完全无关** | 可挪到连接之后，近乎全免 |
| 首连失败 | 0.61 s | 是 | 见 §3 |
| 盲退避 | 3.0 s | 是（`AUTO_RETRY_DELAY_MS`） | 首连失败可降到 0.3–1 s |
| 第二次连接 + DHCP | 9.1 s | 是（驱动自扫 13 信道 + 关联 + DHCP） | 只有"先知道信道"才能省掉自扫 |

> 注：`35 s` 这个数字本轮没有复现，也没有日志留证。19.3 s 是可复现的现状值；差异可能来自当时热点 DHCP 更慢、或者客户端轮询到一个已失效的旧 IP（见 §7.1）。

### 1.2 历史证据：`status 4` 真的出现过

设备自己的事件账本（`/api/wlog`，boot 日志里回放了 16 条）：

```
kind=3 ssid=501A  sc=4  at up=27s     ← CONN_FAIL
kind=3 ssid=501A  sc=4  at up=33s
kind=3 ssid=501A  sc=4  at up=38s
kind=3 ssid=Power sc=4  at up=52s
```

`kind=3` = 连接失败，`sc=4` = ESP reason 4 = **ASSOC_EXPIRE（关联超时）**。这正是"单射频 + AP 停在别的信道"的典型码。

### 1.3 现场信道分布（`/api/scan`，2026-11-16）

| SSID | RSSI | 信道 |
|---|---|---|
| **Power**（当前连的） | −13 | **1** |
| SCAUNET | −54 | 3 |
| Redmi K60 | −61 | 11 |
| 其他两条 | −59 / −67 | 2 / 3 / 11 |

关键结论：**Power 在信道 1**，正好和 SoftAP 上电默认（auto → ch1）撞在一起。所以"上电第一次连接"其实**不是**信道问题；而历史那几次 `status 4`，发生在**用户从网页点了一个不同信道的网络**的时候。

## 2. 代码路径：三个缺陷分别落在哪一行

### D1 —— 连接被排在 6.4 s 的串行工作之后（`src\main.c`）

```c
k_msleep(2000);            // :158  盲等驱动，非事件驱动
enable_softap();           // :160
start_dns_hijack();        // :163
http_server_start();       // :165
k_msleep(500);             // :174
http_self_test("/api/wifi");        // 3 次自检 + 3 次 k_msleep
...
k_msleep(1500); http_self_test("/api/saved");    // :181-182
k_msleep(1500); http_self_test("/generate_204"); // :183
dns_self_test();                                   // :184
settings_subsys_init(); settings_load();           // :187-195
ops_boot_init(); cred_migrate_legacy();            // :199-202
ota_srv_start();                                   // :206
link_boot_autoconnect();                           // :209  ← 连接在最后
```

`link_boot_autoconnect()` 之前那 4.4 s 里，**没有一件事是连接的前置条件**。自检是"验证 AP 网段的 HTTP"，跟 STA 出不出得去无关；`settings_load()` 只要在连接前面就行，不需要排在自检后面。

### D2 —— 首连必然失败一次（`src\l2\wifi_link.c`）

```
6.558  connecting to "Power"
7.172  connect failed, status 1     ← 0.61 s
```

`connect_work_handler()`（`:347`）在发起前只做一件事：看 `ap_channel_of_ssid(g_ssid)`（`:360`）。上电时**扫描缓存是空的**（`wifi_scan.c` 的 `g_ap_count == 0`），所以 `target_ch == 0` → 不做对齐 → 直接 `NET_REQUEST_WIFI_CONNECT`，`params.channel = WIFI_CHANNEL_ANY`（`:387`）。

在这块板子上，AP 刚起来 4 s、单射频还在 AP 上，这个请求会在 0.6 s 内被驱动以 `status 1`（UNSPECIFIED）打回。**它不是信道问题**（Power 就在 ch1），而是"WI-Fi 刚进 APSTA、STA 还没扫过任何东西就要求关联"。重试一次就成功了 —— 说明路径本身没问题，问题只是"白打一次 + 白等 3 s"。

### D3 —— 信道被钉死后不松手，且失败后不重扫

三处，缺一不可：

**(a) 钉住**（`src\l2\portal_ap.c`）

```c
g_ap_params.channel = g_ap_retarget_channel;   // :183  ap_reopen_handler
enable_softap();                               // :192
```
`enable_softap()`（`:133`）里参数只初始化一次：
```c
if (g_ap_params.ssid == NULL) { ... g_ap_params.channel = WIFI_CHANNEL_ANY; }  // :143-151
```
此后**任何路径都不会把它改回 `ANY`**。所以只要发生过一次 `ap_retarget(6)`，AP 就永远在 6。

**(b) 依赖缓存**（`ap_channel_of_ssid()`，`:63`）—— 只读 `wifi_scan.c` 的缓存；缓存被 `scan_cache_reset()` 清空（每次 `wifi_scan_start()` 都清）、或者扫描被连接打断没收到 `SCAN_DONE`，`target_ch` 就是 0 → 不做对齐 → 直接拿"钉住的 AP 信道"去连别的信道 → `status 4`。

**(c) 失败不重扫**（`connect_failed_now()`，`wifi_link.c:291`）—— 失败后只会：`AUTO_RETRY_MAX` 次 → 换下一条已保存网络 → 全失败就 `LINK_IDLE`。**从头到尾没有"再扫一次"或"把 AP 挪到目标信道"的动作**。`status 4` 时盲重试只会重复失败，这就是"死锁"的完整闭环：

```
AP 钉在 ch1 ──连 ch11 的网──▶ status 4
      ▲                          │
      │                          ▼
   不解除                   只盲退避（不重扫）
      │                          │
      └────── 想再扫？入口只有 HTTP ◀── 没 IP 就打不开 /api/scan/start
```

顺带一个**纯浪费**：`cur_ch == 0`（AP 处于 auto）时，代码把它当"不一致"处理（`:366` 注释明确这么写的）→ 只要缓存里有目标信道，就必然触发 `ap_retarget` → AP 关 900 ms 再开 1500 ms（`:189-194`），**2.4 s 白等 + 已连的手机被踢**。而 ESP-IDF 的语义是 `ap.channel = 0` 时 SoftAP **自动跟随 STA 信道**，这次 retarget 在多数情况下是多余的。

## 3. 驱动侧事实（决定方案能怎么设计）

| 事实 | 出处 | 对我们的意义 |
|---|---|---|
| `wifi_iface_status` 查 **STA** 返回的是 `ap_info.primary`，即**真实关联信道** | `west\zephyr\drivers\wifi\esp32\src\esp_wifi_drv.c:2100` | 现在能读到真实信道，但代码没读 |
| 查 **AP** 返回的是 `conf.ap.channel`（配置值），配 0 就回 0 | 同文件 `:2124-2131` | 印证 `portal_ap.c` 里"AP 查不到真实信道"的注释是对的 |
| `params->channel == WIFI_CHANNEL_ANY` → `wifi_config.sta.channel = 0`，由驱动自己扫 | 同文件 `:1555-1557` | 现状首连就是这条路（自扫 13 信道，~9 s） |
| AP 配置 channel 0 = auto，IDF 会跟随 STA 信道 | ESP-IDF APSTA 既定行为 + 上表驱动映射 | P1 方案的前提（需真机对照验证，见 §5） |
| 连接时若 pin 了 BSSID/channel，会关掉 BSS transition | 同文件 `:1764` | 我们只 pin channel，代价是不能漫游换 AP |

## 4. 修复方案（P0 / P1 / P2，按"收益 ÷ 风险"排序）

### P0-1 把连接从启动尾部挪到前面（省 ~4 s，风险最低）

- **改哪**：`src\main.c`
- **怎么改**：`settings_subsys_init/settings_load` → `ops_boot_init` → `cred_migrate_legacy` → `ota_srv_start` → **`link_boot_autoconnect()`** 连续排完；把 5 个 `http_self_test()` 与 `dns_self_test()` 挪到 `link_boot_autoconnect()` 之后（它们只验 AP 网段，晚点做不影响）。
- **预期**：连接发起从 `6.56 s` 提前到 ~`2.5 s`；IP 从 19.3 s → **~15 s**。
- **风险**：低。自检日志的先后顺序会变（读日志的人要注意）。`settings_load` 仍是 OTA/连接的前置，顺序不动。
- **验收**：`boot → connecting` 时间戳 < 3 s。

### P0-2 首连不再白打一次（省 ~3.6 s）

两种做法，二选一（建议先做 (b)，因为 (a) 的根因还没坐实）：

- **(a) 等 AP 真正稳定再连**：`enable_softap()` 之后不靠 `k_msleep`，改成在 `NET_EVENT_WIFI_AP_ENABLE_RESULT` 回调里再 `link_boot_autoconnect()`（`main.c:69` 的 case 已经有这个事件）。代价是链路依赖事件而非时序，更干净。
- **(b) 首连失败退避从 3 s 降到 0.5 s**：`portal_cfg.h` 加 `AUTO_RETRY_FIRST_MS 500`，只在 `g_auto_attempts == 1`（第一次）时用它，其余仍用 3 s。**这是纯止损，不解决根因**，但 0.5 s 足够覆盖驱动"刚进 APSTA"的窗口。
- **预期**：省 3.0 s（(b)）或省掉整个失败（(a)，但要真机确认 status 1 是不是 AP 未稳定导致）。
- **风险**：低；(b) 若根因不是"AP 未稳定"，只是把 3 s 变成 0.5 s，仍在 1 次失败后成功。

### P0-3 失败时"先扫再对齐"，而不是盲退避（治死锁，必须做）

- **改哪**：`src\l2\wifi_link.c`（`connect_failed_now()` / `connect_work_handler()`）、`src\l2\wifi_scan.c`（加一个 `scan_cache_age_ms()`）
- **怎么改**：
  1. `wifi_scan.c` 记下"最后一次 `SCAN_DONE` 的时刻"，暴露 `scan_last_done_ms()`；
  2. `connect_work_handler()` 判断：`ap_channel_of_ssid(g_ssid) == 0` **或** 缓存年龄 > 60 s → 先 `wifi_scan_start()`，并 `k_work_reschedule(&connect_work, 1500)` 自己重入（最多等 `scan_is_active()` 到期，25 s deadline 已有），本轮不发起 CONNECT；
  3. `connect_failed_now()` 在 `status == 4`（也含 `1`）时，先把"缓存标旧"（置一个 `g_channel_stale = true`），下一次尝试因此走第 2 步的扫描分支。
- **预期**：`status 4` 从"每次都 4、直到放弃"变成"扫一次 → 对齐 → 连上"；最坏情况多花一次扫描（~10 s），但不再是死循环。
- **风险**：中。扫描会短暂打断 AP 客户端（单射频固有代价）；要防抖 —— **每轮重试最多扫一次**，用计数器而不是"每次都扫"。
- **验收**：手工复现"AP 在 ch1、目标在 ch11"（连 `Redmi K60`），日志应出现 `scan → ap ch 11 → connected`，且 `wlan0` 最终 `state=connected`。

### P1 AP 信道策略：auto 就是"跟随"，不该被判成 mismatch（省 2.4 s + 手机不被踢）

- **改哪**：`src\l2\portal_ap.c`（`ap_current_channel()` / `connect_work_handler()` 的判定）
- **怎么改**：
  1. `ap_current_channel()` 改成"STA 已连接时优先返回 STA 的真实信道（`wifi_iface_status.channel`，见 §3），否则返回配置值"；
  2. `connect_work_handler()` 的判定改为：**只有 `cur_ch != 0 && cur_ch != target_ch` 才 retarget**；`cur_ch == 0`（auto）视为"会自己跟上"，不再主动重启 AP；
  3. 成功连上之后把 `g_ap_params.channel` 恢复成 `WIFI_CHANNEL_ANY`（只在"下一次需要 pin"时才重新 pin）。
- **预期**：从"每换一次网络就让 AP 重启 2.4 s、手机掉线重连"变成"AP 自己跟过去"。
- **风险**：中高。前提是 IDF 的 "ap.channel == 0 跟随 STA" 在本板子上成立 —— **必须先做一次对照实验**（见 §5），不成立就回退到 P0-3 的方案（保留 retarget，但保证失败会重扫）。

### P2 可观测性与工具（不加功能，但以后不用猜）

1. **`/api/status` 加 `channel`**（`ap`=配置值 / `sta`=真实信道 / `src`=从哪儿读的）。现在只能靠 `ap_current_channel()` 猜，它只会回 0 或配置值。落点：`src\l1\api_wifi.c:110` 的 `status_handler` + `wifi_link.c` 加一个只读 getter。
2. **boot 日志加一行耗时**：`STA got IP` 处打印 `boot→ip = %u ms`，以后再有人报"很久才通"，直接看串口就行。
3. **抓启动时序的工具收编**：本轮用的临时脚本（开串口 → 发 `kernel reboot cold` → 记 80 s）建议正式化成 `tools\boot_capture.py COM11 80 logs\boot.log`。注意：**原生 USB-Serial-JTAG 的 RTS 复位脉冲在这块板上不生效**（本轮实测：uptime 从 28 s 连续跑到 46 s，根本没重启），必须走 shell 命令。
4. **OTA/工具默认 host 换成 `s3portal.local`**：见 §7.1，硬编码 IP 会因为 DHCP 换址而"看起来连不上"。

## 5. 需要真机验证的两个假设（方案的前提）

| # | 假设 | 怎么验（10 分钟内） | 若不成立的后果 |
|---|---|---|---|

## 6. 附带发现：自检里那三条 404 不是故障

`t=3.2 s` 自检 `/api/shell`、`/api/ota/slots`、`/api/drops` 全部 404，容易误判成"接口没注册"。实际是**设计如此**：

```c
/* http_core.h:36-45 */
#define DEV_GUARD()                                        \
	do {                                               \
		if (client_side_ap(client)) {              \
			response_ctx->status = HTTP_404_NOT_FOUND; /* 装成不存在 */ \
```

自检从 `192.168.4.1`（AP 侧）发请求，而这三个是"开发者接口，AP 侧一律 404"。从局域网侧（`<hub-ip>`）请求同一批接口，实测全是 `200`（本轮验证：`/api/drops`、`/api/ota/slots`、`/api/shell`、`/api/boot`、`/api/wlog` 均 200）。

**建议**：把这三条自检从 `http_self_test()`（AP 侧）挪到 `http_self_test_scope()` 那套"用 STA IP 发"的逻辑里，或者干脆删掉 —— 现在它们在启动日志里制造 3 条假 404，掩盖真问题。

## 7. 环境侧的两个坑（不属于固件 bug，但会让人以为固件坏了）

### 7.1 DHCP 池换址导致的"假离线"

本轮实测：板子与 PC 在同一个热点下**交换过地址**——上一轮板子 `10.115.126.239` / PC `<hub-ip>`，本轮重启后板子 `<hub-ip>` / PC `10.115.126.239`。用硬编码 IP 的脚本/网页会打到"自己"或打到旧地址，表现就是"连不上"，而设备其实好好的。

**已经可用的解法**：mDNS 生效中 —— `s3portal.local` 解析到 `<hub-ip>`，`http://s3portal.local/api/status?k=...` 直接 200。工具（`tools\ota_push.py` 等）与人工调试都应改用 hostname。

### 7.2 板子是"software reset"就算 dirty

`/api/boot` 显示 `boot.n=145 crash=6 clean=false`：每次 `kernel reboot cold`、每次 OTA 的 `/api/ota/reboot` 都会把 dirty 标志留下，被计成"异常退出"。这会让 `clean` 长期为 false，失去诊断价值。要不要在收尾时区分"主动重启"和"掉电"，是另一个待拍板项。

### 8.4 两次真实故障与最终定稿（这一段比方案本身重要）

- **故障 A（我自己引入的）**：v144 把 `wifi_scan_start()` 直接放在系统工作队列里调用，而 `net_mgmt(NET_REQUEST_WIFI_SCAN)` 在 ESP32 驱动里是**阻塞**的（全信道 ~10 s）→ 单线程系统工作队列被冻住，LED/RSSI/重试全停、串口日志 18 s 左右静默。
  **修法**：新增独立 `align_scan_wq` 只跑扫描，系统队列不再被占。
- **故障 B（换网路径）**：v145 加了"换网先 DISCONNECT 再连"。真机切到不存在的 `501A` → `connect failed, status 4` → 500 ms 后立刻再发 CONNECT → **HTTP 与串口同时失联，设备彻底卡死，只能 USB 复位**（`logs\hang-test.log` 101–104 行）。
  **修法**：删掉那条 DISCONNECT 路径，并在 `connect_work_handler` 原位留注释说明为什么不做；`connect_failed_now()` 的对齐阶梯**只在 `g_auto_reconnect`（开机自动重连）时生效**，运行期（网页换网 / 掉线）完全回退到改造前行为（3 s 退避 + `wifi_rssi()!=0` 就把状态拉回 connected）。
- **阶梯的三档**（每个"开机重连周期"最多走一遍，`ALIGN_STEP_MAX=2`）：
  1. `g_align_step==0`：只重试不扫。`status==1` 等 `AUTO_RETRY_FIRST_MS`(0.5 s)，`status==4` 等 `AUTO_RETRY_DELAY_MS`(3 s)——避免刚超时完又立刻发 CONNECT。
  2. 缓存里知道目标信道且 `pinned==0||pinned!=target` → `ap_retarget(target)`。
  3. 缓存里没有目标 → `scan_invalidate()` + `align_scan_wq` 扫一次 + `align_work` 每 1 s 查 `scan_is_active()`（最多等 `ALIGN_SCAN_WAIT_MS`）后再提交连接。

## 10. 还没解决、需要拍板的

1. **boot → IP 仍有 5.8–13.9 s 的抖动**：全部来自驱动自己做的那次全信道扫描（~10 s）+ 关联 + DHCP。要再压只有两条路，且都有副作用：(a) 连接前预热扫描（省 3–5 s，但要占 10 s 射频、可能延迟 SoftAP 就绪）；(b) 缩短首个 `k_msleep(2000)`（实测只省 1–2 s，且要改成轮询接口就绪）。我倾向都不做。
2. **dirty 计数**（§7.2）：主动重启（`kernel reboot cold`、OTA 的 `/api/ota/reboot`）也被记成异常退出，`clean` 长期 false。要不要区分"主动重启 / 掉电"未定。
3. **`POST /api/ota/reboot` 的鉴权没摸清**：`X-Key: <REDACTED-PSK>` 实测 401，本轮一律用串口 `kernel reboot cold` 切槽。要修的话得先查 `ota` 那边对 `X-Key`/PSK 的判定优先级。
4. **`portal apch` 是诊断命令，不是产品功能**：它只改 RAM 里的 `g_ap_params.channel`，重启即失效；保留它的理由是本轮验证信道搬运全靠它，删掉以后下次想复现这个现场就得再写一遍。
5. **`tools\` 里的临时脚本尚未收编**：本轮所有抓启动的脚本都在 `%TEMP%`（`bootcap.py` / `sendcmd.py` / `cmdseq.py` / `retarget.py`），建议正式化为 `tools\boot_capture.py`，但本轮没做。
