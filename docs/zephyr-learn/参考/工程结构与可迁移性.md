# 工程结构与可迁移性

> 回答两个问题：
> 1. 为什么我们的目录不像「`boards/` + `CMakeLists.txt` + `CMakePresets.json` + `prj.conf` + `src/`」那种标准例程？
> 2. 以后换别的芯片，这套东西能搬过去多少？

---

## 一、先分清三种目录，别拿一种当"标准"

Zephyr 世界里同时存在三种合法布局，长得完全不一样，混在一起对比就会得出"我们做错了"的错误结论。

### A. 树内 sample（`zephyr/samples/basic/blinky/`）

```
blinky/
├── CMakeLists.txt
├── prj.conf
└── src/main.c
```

**没有 `boards/`**。因为它用的是 Zephyr 树里**已经存在的板级定义**（`zephyr/boards/<arch>/<board>/`）。这是最常见的形态，`samples/` 下几百个例子全是这样。

### B. 独立应用 + 树外板级（截图里那个 `blinky-led`）

```
blinky-led/
├── boards/arm/st_h743_board/      ← 板级定义搬到自己仓库里
│   ├── board.cmake
│   ├── board.yml
│   ├── Kconfig.st_h743_board
│   ├── Kconfig.defconfig
│   ├── st_h743_board.dts
│   ├── st_h743_board-pinctrl.dtsi
│   ├── st_h743_board_defconfig
│   └── support/openocd.cfg
├── CMakeLists.txt
├── CMakePresets.json
├── prj.conf
└── src/main.c
```

这个结构的**关键不是 `boards/`，而是"板级定义归谁维护"**：它把板级从 Zephyr 树里"摘"出来，放进自己的仓库。Zephyr 通过 `BOARD_ROOT` 认这种布局（`west build --board-root <dir>` 或 `$env:BOARD_ROOT`）。

它为什么这么做：**自己的板不打算往上游合，或者上游不收**。板子的 dts/Kconfig 自己拿着，永远能编。

### C. 本项目（独立应用，板级仍在上游树里）

```
zephyr-learn/
├── applications/esp32s31/korvo_sys/
│   ├── CMakeLists.txt      ← 3 行（find_package Zephyr + project + target_sources）
│   ├── prj.conf
│   ├── app.overlay         ← 本工程特有的 dts 片段（Zephyr 会自动找目录下的 *.overlay）
│   └── src/main.c
└── west/zephyr/boards/espressif/esp32s31_function_coreboard/   ← 板级在 PR 树里
```

**这是 A 的变体加了一层 overlay**，不是野路子。区别只有一条：板级定义**我们没有自己拿**，用的是 PR #119851 里那块 `esp32s31_function_coreboard`（同芯片、不同板）。

## 二、一个 Zephyr 应用的"最小合法集"只有三样东西

```cmake
# CMakeLists.txt —— 全文就 3 行
cmake_minimum_required(VERSION 3.20.0)
find_package(Zephyr REQUIRED HINTS $ENV{ZEPHYR_BASE})
project(korvo_sys)

target_sources(app PRIVATE src/main.c)
```

| 必需 | 作用 | 缺了会怎样 |
|---|---|---|
| `CMakeLists.txt` | 让 CMake 找到 Zephyr、声明目标是 `app` | `west build` 报 "not a Zephyr application" |
| `prj.conf` | Kconfig 应用配置（可为空文件） | 能用，但全用默认值（常常连 console 都没） |
| `src/` | 源码 | 链接出来是空程序 |

**其余全部是可选的便利设施**：

| 可选 | 什么时候需要 |
|---|---|
| `boards/`（树外板级） | 板级要自己维护（不打算合上游，或上游没收） |
| `app.overlay` / `<board>.overlay` | 板级定义不是你要的那块板，要补/改几个节点 |
| `CMakePresets.json` | 给 VS Code / CLion 用，或用 `cmake --preset` 而不是 `west build` |
| `support/`（如 `openocd.cfg`） | 烧录/调试器配置需要定制 |
| `sysbuild.cmake` | 需要多镜像（bootloader + app） |

所以截图里那个仓库"看起来标准"，是因为它**同时**选择了"自带板级"和"自带 IDE 预设"。我们只选择了"自带 overlay"，所以少了两个目录 —— **少的是可选项，不是必需品**。

## 三、我们为什么没建 `boards/`（四个理由）

### 理由 1：差异小到 overlay 就能表达

Korvo-1 这块板相对 PR 里那块 coreboard，真正需要改的只有 5 处：

| # | 差异 | 表达方式 |
|---|---|---|
| 1 | RGB LED 在 GPIO37，走 RMT 的 `pulse_io` | `app.overlay` 加 `rmt_korvo` 节点 + `led-strip` 别名 |
| 2 | 功放使能在 GPIO7 | overlay 加 `gpio-leds` 的 `pa_ctrl` |
| 3 | 四个功能键共 IO42（ADC 电阻梯） | overlay 打开 `&adc0` / `&adc1` |
| 4 | 片上温度传感器默认关 | overlay `&coretemp { status = "okay"; }` |
| 5 | 看门狗节点默认关 | overlay `&wdt0 { status = "okay"; }` |

把板级整套搬进仓库，是为了改**几十行 dts + 一整份 Kconfig**；而这里只要**十几行 overlay**。用大炮打蚊子。

### 理由 2：搬过来就要和 PR 同步

PR #119851 会 rebase。如果板级在 `zephyr/boards/` 里，`git pull` 就自动跟着更新；如果复制一份到自己仓库，每次上游改了 SoC dtsi、改了 `Kconfig`、改了 `board.cmake` 的 flash runner，你都要**手工 diff 两份**。这是典型的"双份真相"陷阱。

> **2026-11-19 补充（替代 11-16 的 boards_local 方案）**：运行时真相仍然只有一份，住在自研板 module `zephyr_modules\elab-boards\boards\espressif\esp32s31_function_coreboard\`。这 15 个文件只活在没有上游跟踪的 PR 分支 commit（`34e025569`）里，所以做成独立 module：`west update` 不会冲掉，`kharon deps --check` 只读校验。**不再有 `boards_local\` 副本，也不再需要 `bootstrap.ps1` 往 zephyr 树里拷文件。**

### 理由 3：学习目标不在板级移植

这个项目的定位是"学 Zephyr"，重点在 devicetree / Kconfig / device model / 子系统。**写一份合法的板级定义**是 SoC 移植的活（还要写 binding、pinctrl、flash runner），属于另一个课题。现在做，等于把 80% 的时间花在跟学习目标无关的地方。

### 理由 4：overlay 本身就是最该练的技能

`app.overlay` 是 Zephyr 里**最常用、最该练熟**的东西——几乎所有真实项目都在用（板子不完全匹配、要加自己的外设节点）。这五个工程正好把 overlay 的五种典型用法都练了一遍：加别名、加新节点、改 `status`、改 `chosen`、引用 SoC 节点补属性。

## 四、代价（必须诚实列出来）

| # | 代价 | 具体表现 |
|---|---|---|
| 1 | 没有 `-b korvo1` 这种板名 | 只能用 `-b esp32s31_function_coreboard/esp32s31/hpcore`，别人看到会以为你烧错了板 |
| 2 | 每个 app 重复同样的 overlay 片段 | `korvo_apps` 和 `korvo_sys` 都写了 `&coretemp`；四个工程都写了 `rmt`/`gpio-leds`（改一处要改四处） |
| 3 | `west boards` 里看不到 Korvo-1 | 板级清单来自 `boards/` 树和 `BOARD_ROOT`，我们两处都没有 |
| 4 | 板级跟着 PR 走，不可控 | PR rebase 改坏了 dts，我们只能等或自己打 patch |
| 5 | 没有 `CMakePresets.json` | 换 IDE（VS Code 的 Zephyr 插件）时要手工配一遍参数 |

第 2 条是目前**唯一真正影响维护**的：`korvo_lab` / `korvo_apps` / `korvo_sys` 三份 overlay 有重叠。要不要抽公共片段，取决于还想加几个工程（见第六节判据）。

## 五、可迁移性评估（换成别的芯片能搬多少）

先分清"层"，因为不同层的可迁移性差了一个数量级。

| 层 | 换芯片要做什么 | 可复用度 | 说明 |
|---|---|---|---|
| **应用逻辑**（线程、状态机、帧调度、HSV、shell 命令骨架） | 改 DT 引用、改物理量换算 | **≈70%** | 三角波包络、25 fps 的 40 ms 调度、整数 HSV→RGB、`compute_frame` 这套跟芯片无关 |
| **板级**（dts / overlay / pinctrl / 引脚号） | 全部重写 | **0%** | 这是物理事实：换芯片=换外设基地址、换引脚复用、换时钟树 |
| **构建配置**（`prj.conf`） | 按新树改符号 | **≈60%** | `CONFIG_WATCHDOG`（本树）vs `CONFIG_WDT`（上游）；`ESP32_TEMP` 依赖 `!SOC_SERIES_ESP32`；`DT_HAS_*` 全变 |
| **工具脚本**（`serial_cmd.py` / `read_serial.py`） | 改串口号/波特率 | **≈100%** | 纯 pyserial，与芯片无关 |
| **环境**（`config/host.<profile>.profile.yaml` + `host.local.yaml`） | 改 SDK / 工具链 2–3 行 | **≈95%** | `kharon env` 重新生成 PATH；`TOOLCHAIN_HOME`、`CROSS_COMPILE`、`ZEPHYR_BASE` 由 profile/provider 收口 |
| **教程与方法论**（判据、坑、验证方式） | 不改 | **100%** | "dts 节点 + 驱动文件 + Kconfig 三个条件"这套判据对所有 Zephyr 移植都成立 |

### 5.1 具体到"换成截图里那块 STM32H743"

假设你以后加一块 STM32H743 的板（就是图里那个 `st_h743_board`），需要动的只有这些：

1. **新建板级**：`boards/arm/st_h743_board/`，7 个文件（`board.yml`、`Kconfig.<board>`、`*_defconfig`、`<board>.dts`、`-pinctrl.dtsi`、`board.cmake`、`support/openocd.cfg`）。
2. **换工具链**：`CROSS_COMPILE=.../arm-zephyr-eabi-`，或直接用 Zephyr SDK（`ZEPHYR_TOOLCHAIN_VARIANT=zephyr`）。
3. **建新工作区**：`west init` 一个新的（或同一工作区 `west.yml` 加 `BOARD_ROOT`）。
4. **改 `prj.conf`**：把 `CONFIG_WATCHDOG` 换回 `CONFIG_WDT`、删掉 `ESP32_TEMP` 相关、`CONFIG_WS2812_STRIP_PULSE_IO` 可能要换成 STM32 的 SPI/定时器方案。
5. **改 overlay**：全部重写（引脚号、外设节点名都不同）。
6. **应用代码**：把 `DT_NODELABEL(...)` / `DT_ALIAS(...)` 换成新板的标签，把"IO42 的 mV 窗口"换成新板按键的实际分压。

结论：**换芯片时"手感"能搬，代码只能搬一半，配置得重写，硬件描述必须重写。** 这不是本项目的缺陷，而是嵌入式工程的常态——Zephyr 帮你统一的是 API 和构建体系，不是引脚。

> **2026-11-16 实测校准（这一节原来只是预测）**：STM32 那条线已经真的走过两遍 ——
> ESP32 → STM32F411（教程 15 第二篇）、STM32F411 → STM32F103（教程 15 第三篇）。预测里漏掉的**两层**：
>
> | 预测里没写的 | 实测代价 |
> |---|---|
> | **工具链目标**：SDK 默认只有 riscv64 + xtensa，ARM 要单独补 `arm-zephyr-eabi` 目标（79 MB 的 7z） | 装一次，之后四块板共用一个 SDK |
> | **厂商 HAL 模块**：`modules\hal\stm32` + `cmsis_6` 不存在 → `Cannot find source file stm32f4xx_hal.c` / `core_cm4.h` | 这是"板级目录只描述引脚，不提供寄存器"的直接后果 |
> | **烧录探针**：板级 `support\openocd.cfg` 是 ST-Link 专用，DAP-Link 必须另写一份（`cmsis-dap` + `swd`） | 每个 STM32 系列一份、只差 `target/stm32f*x.cfg` 那一行 |
>
> 另外 F103 还多一层：**同一家厂商换系列**（F4 → F1）时，`stm32cube\<系列>\`、`core_cmN.h`、`dts\st\<系列>\` 的 pinctrl、`common_ll` 的 LL shim 分支**全部要再来一遍** —— "换系列"和"换厂商"在模块层面是同一种工作。

### 5.2 真正能跨芯片复用的东西（价值最大的部分）

| 可复用 | 为什么值钱 |
|---|---|
| `app` 命令分层（`app rgb` / `app key` / `sys info`） | 这套 shell 组织方式在任何 Zephyr 项目上都能直接套 |
| 线程 + 帧率调度（40 ms / 栈 2048 / 优先级 7） | `k_thread` + `k_sleep` 的用法与 SoC 无关 |
| "先 `device list` 看 Zephyr 认到什么，再写代码"的排查顺序 | 这是方法论，比代码值钱 |
| "改 overlay 必须 `-p always`"、"`__device_dts_ord_NN` 未定义=驱动没进镜像" | 换个 SoC 一样会踩 |
| `logs/` 里每次实测的串口原文 | 可复现的基准，出问题能对比 |

## 六、想升级成截图那种结构，值不值得

### 判据（满足任意两条就值得做）

1. 工程数 ≥ 3 且 overlay 有重复片段（现在已满足：3 个）
2. 想让别人（或半年后的自己）用 `-b korvo1/esp32s31` 一条命令就编
3. 想脱离 PR 树固定板名，不怕上游 rebase
4. 要把这块板当"长期实验台"，而不是"学完就换"

### 迁移步骤（5 步，约半天）

```powershell
# 1. 在项目里建树外板级根
mkdir C:\Users\xiao1\Desktop\ELAB\kharon-ide\boards\riscv\korvo1

# 2. 抄 PR 板级做底子（只抄需要的，不整套复制）
#    esp32s31_function_coreboard_hpcore.dts / -pinctrl.dtsi / _defconfig / board.cmake
#    改名为 korvo1.dts / korvo1-pinctrl.dtsi / korvo1_defconfig

# 3. 新增 board.yml
@'
board:
  name: korvo1
  full_name: ESP32-S31-Korvo-1
  vendor: espressif
  socs:
  - name: esp32s31
'@ | Set-Content -LiteralPath ...\boards\riscv\korvo1\board.yml -Encoding utf8

# 4. 把三份 app.overlay 里重复的片段（rmt/GPIO37、pa_ctrl/GPIO7、adc0/1、coretemp、wdt0）
#    合并进 korvo1.dts，app 里的 overlay 只留本工程特有的部分

# 5. 编译时指定板级根
$env:BOARD_ROOT = "C:\Users\xiao1\Desktop\ELAB\kharon-ide"
west build -b korvo1/esp32s31 ...
```

### 收益 vs 成本

| | 收益 | 成本 |
|---|---|---|
| 短期 | `-b korvo1/esp32s31` 语义清楚；overlay 去重 | 半天工作量；10 个文件要维护 |
| 长期 | 脱离 PR rebase 风险；能对外交付 | 上游改 SoC dtsi 后要手工同步（回到"双份真相"） |

**我的建议**：现在**不做**。理由是第五条判据还没满足——PR rebase 时跟着上游走反而更省事。等你要"把这套东西给别人"或"再加第三个需要相同外设的项目"时再做，那时收益才真正超过成本。

## 四、实测回填：这套布局真的跨了一次芯片（教程 15 组）

前面几节都是推演。教程 15 组把其中一条做了真机验证：**同一份 `applications\esp32s31\korvo_apps`，只靠 `boards\esp32s3_devkitc_esp32s3_procpu.overlay` 加一层，就编出了 ESP32-S3 的固件并跑通。**

| 问题 | 实测答案 |
|---|---|
| 应用源码要改吗？ | `main.c` / `store.c` / `prj.conf` / `CMakeLists.txt` **都是同一份文件**。改动只在应用里加了"能力探测"（见下），不是为了 S3 才写的分支 |
| 板子差异放哪？ | **只放一个文件**：`applications\esp32s31\korvo_apps\boards\esp32s3_devkitc_esp32s3_procpu.overlay`（删 `pa-ctrl` 别名、WS2812 改到 GPIO48、控制台切 `usb_serial`、打开 `rmt`/`adc0`/`adc1`） |
| 分区表要补吗？ | **不用**。S3 默认分区表自带 `storage`（`0x3b0000` / 192 KB），`store.c` 一字未改 |
| 板级目录要搬进仓库吗？ | **暂时不用**，还是第三节那条结论。但这次实测补了一条判据：**当你的应用要支持第 3 块板、且板级 overlay 开始重复时，就该考虑搬了** |
| 最不能复用的是哪层？ | 仍然是工具链（RISC-V ↔ Xtensa 两套 SDK），其次是"SoC 属性"（ADC 17 位 vs 12 位）。两者都不是代码问题，是物理事实 |

**顺带修正了一个此前的判断**：原文里写过"换板可能要自己补分区表 overlay"。实测证明不需要——S3 的默认分区表已经带 `storage`。这条差异记在这里，免得以后按旧笔记多干半天活。

**新增的一条经验（不属于目录结构，但同样影响可迁移性）**：板级差异有三类，处理手法各不相同——设备有没有（dts 别名 + `DT_HAS_ALIAS`）、参数范围不同（运行时问驱动，如 ADC 分辨率）、物理接法不同（overlay 改一行 pinmux）。把这三类混在一起用 `#ifdef` 处理，是"越加板越乱"的根源。

**第五类差异（教程 16 组补的，会直接把你卡住）**：`boards\<board>.overlay` 与 `app.overlay` **互斥**，板级 overlay 一旦存在，`app.overlay` 就整段不生效。

- 依据：`zephyr\cmake\modules\configuration_files.cmake:75-89` —— 先找 `socs\<soc>.overlay`、再找 `boards\<board>.overlay`，命中即定下 `DTC_OVERLAY_FILE`；`NAMES "app.overlay"` 只是最后的兜底。
- 症状：`korvo_sys` 在 S3 上链接失败 `__device_dts_ord_48 undeclared`，因为 `app.overlay` 里那句 `&coretemp { status = "okay"; }` 没被执行，节点仍是 `disabled`。
- 判据（一条命令）：`Select-String -Path build-*\CMakeCache.txt -Pattern "^DTC_OVERLAY_FILE"` —— 它只会给你**一个**文件。
- 处理：加板级 overlay 时，把 `app.overlay` 里"这块板也必须成立"的段落搬过去；确实要两个文件都生效，就显式 `-DDTC_OVERLAY_FILE="a.overlay;b.overlay"`（分号分隔 + 正斜杠）。

这条也顺带解释了另一个现象：`korvo_apps` 在 S3 上 `app.overlay` 里的 `pa_ctrl`、`rmt` pinctrl 其实都没生效——之所以没出问题，是因为板级 overlay 把该补的都补了一遍。**"看起来能用"和"真的生效"是两件事。**
