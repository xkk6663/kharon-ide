# 编译速度优化（Windows 实测）

> **现状校准（2026-11-19）**：数字与结论来自 2026-11 的 S3 `hello_world` 实测，仍有参考价值；
> 但路径口径已变：`.venv` → `.deps\venv`，`.tools` → `.deps\tools`，
> `env.ps1` → 优先用 `.\scripts\kharon-env.ps1`（`kharon env` 生成），
> 旧 `tools\zephyr\env.ps1` 仍可 fallback。ccache 目录现为 `.deps\ccache`。

> 目标不是"听起来更快"，而是**给你这台机器上的真实数字、真实瓶颈、以及可直接用的加速开关**。
> 所有数字都是本机（Ryzen 9 7940H，8 核 16 线程 / NVMe SSD / 15.2 GB RAM / Windows）实测，被测对象是 S3 的 `samples\hello_world`（257 个构建步骤），构建目录全新。

## 一、先给结论

| 场景 | 实测 | 说明 |
|---|---|---|
| **干净全量**（默认并行，257 步） | **216.7 s** | 最慢的一种，改 dts / prj.conf、换 board 都会落到这里 |
| CMake configure（不含编译） | **25.1 s** | Python Kconfig + devicetree 处理，纯串行，每 10 次构建都要付一次 |
| 无改动重建（no-op） | **1.64 s** | 正常，这条不需要优化（分层后的 `s3_wifi_portal` 实测 **0.82 s**） |
| 改一个 `.c` 的增量（hello_world 口径） | **6.59 s** | 7 步：编译 + 静态库 + 3 次链接（`s3_wifi_portal` 分层后是 **10.5–11.0 s**，见 §四） |
| 单次极小文件编译 | **123 ms** | Linux 同机通常 25~40 ms，差距就在这 |
| 单次 `cmd.exe` 启动 | **47 ms** | 进程创建本身就要钱，Zephyr 一次构建起几百个进程 |

三条可以直接落地的结论：

1. **不要把 `-j` 开到 16/18。** 本机 `-j18` 直接把提交内存打光，`cc1.exe: out of memory allocating 1052671 bytes`，构建中途失败。**用 `-j8`**。
2. **开 ccache。** 同一份代码第二次、第三次全量构建，命中缓存后只剩链接时间（当前由 `kharon env` 注入 ccache 配置，`kharon build` 生效；旧 `tools\zephyr\env.ps1` / `tools\zephyr\build.ps1` 也支持）。
3. **增量其实很快**，6.6 秒。真正浪费时间的是"随手改 overlay / prj.conf 触发全量"——把这类改动攒一起改。

## 二、Windows 为什么慢（不是 CPU 的问题）

CPU 是 8 核 16 线程 Zen4，NVMe 固态，硬件不背这个锅。慢在四处：

| 原因 | 证据 | 影响 |
|---|---|---|
| **每次起进程的固定开销** | 同一个极小 `.c` 编译 123 ms，其中真正编译只有几十 ms；`cmd /c echo` 起进程 47 ms | 257 步 × 若干进程，累计就是几十秒 |
| **Defender 实时扫描** | `MsMpEng.exe` 常驻，`RealTimeProtectionEnabled = True`；从未加过排除项 | 每个新写入的 `.o` / `.d` / `.a` 都被扫一遍 |
| **大量小文件的元数据开销** | 实测删一个 build 目录要数分钟（几万个文件） | `-p always`（先删后建）代价极高；复制的对象是整棵构建树 |
| **内存/提交空间不足** | 编译时可用提交内存一度只剩 **0.63 GB**（上限 61 GB、页文件 46 GB、物理剩 1.99 GB） | 并行度一高就 OOM，编译器内部频繁换页，表现为"慢" |

### 那个 OOM 的原文（值得记住）

```
FAILED: .../esp_clk_tree_common.c.obj
cc1.exe: out of memory allocating 1052671 bytes
```

`cc1` 只要 1 MB 都拿不到，说明不是单个文件太大，而是**整机提交内存见底**。这种失败不是"代码有问题"，降并行度就恢复。

## 三、Linux 会快多少（诚实的说法）

- **同硬件原生 Linux，通常快 2~4 倍**（干净全量 200 多秒 → 60~100 秒量级）。原因是 fork/exec 便宜、没有 Defender、ext4 处理小文件快得多。这是经验区间，**本机没有 Linux 环境，我没法给你实测数字**，所以不写成"实测"。
- **WSL2 能用，但必须把源码放 ext4**（`~/zephyr-learn`），**不要放 `/mnt/c/...`**：跨 9P 文件系统比 Windows 本机还慢，这是最常见的"WSL 反而更慢"的原因。
- 你现在不必换系统。**先把 `-j8` + ccache + Defender 排除做上**，Windows 下的体验就能接受；真要追极限，再考虑 WSL2。

## 四、已经为你做好的三件事

### 1. `kharon env` / 旧 `env.ps1` 都带 ccache 与并行度

```powershell
$ccache = "$root\.deps\tools\ccache\ccache-4.14.3-windows-x86_64"
$env:PATH = "...;$ccache;..."
$env:CCACHE_DIR    = "$root\.deps\ccache"      # 固定在项目内，便于统计/清理
$env:CCACHE_MAXSIZE = "3G"
$env:CCACHE_COMPRESS = "1"
$env:ZEPHYR_BUILD_JOBS = "8"              # 内存吃紧时降到 6
```

ccache 4.14.3 已装在 `\.deps\tools\ccache\`（走 `gh-proxy` 镜像下的 1.76 MB zip，解压后用 python 校验过 `testzip() = None`）。

### 2. 构建入口：`kharon build`（旧 `tools\zephyr\build.ps1`）

```powershell
# 当前入口：工程 yaml 里已带 ccache / 并行度
.\kharon.cmd build -p <project>

# 旧入口仍然可用：一条命令 = 配置 + 构建 + 计时（+ 可选烧录）
.\tools\zephyr\build.ps1 -App applications\esp32s31\korvo_sys -Board esp32s3_devkitc/esp32s3/procpu -BuildDir build\esp32s3\korvo_sys\s3-debug

# 带 overlay（S3 的 Wi-Fi 控制台切换就是靠这个）
.\tools\zephyr\build.ps1 -App west\zephyr\samples\net\wifi\shell -BuildDir build\samples\esp32s3\shell\default `
  -ExtraDtcOverlay applications\esp32s3\korvo_wifi\boards\esp32s3_devkitc_esp32s3_procpu_usb_serial.overlay

# 构建 + 烧录
.\tools\zephyr\build.ps1 -App applications\esp32s31\korvo_sys -BuildDir build\esp32s3\korvo_sys\s3-debug -Flash -Port COM11

# 不想用缓存（做对照实验时）
.\tools\zephyr\build.ps1 -App applications\esp32s31\korvo_sys -BuildDir .build\esp32s31\korvo_sys\noccache -NoCcache
```

输出形如：

```
OK  configure=25.1s  build=xx.xs  total=xx.xs  bin=xxxxxx B
```

> 为什么不用 `west build` 直接带 `-j`？因为 west 把并行度透传给 ninja 的行为跟版本有关，容易踩坑；封装脚本里 **显式调 ninja** 最稳，也顺便能计时。

### 4. ccache 效果：拿一个真实编译边单独测（单个文件，冷/热对比）

方法：从 `build\samples\esp32s3\peripheral\default\compile_commands.json` 里取一条真实编译命令（`esp_clk_tree_common.c`，带完整 Zephyr + ESP HAL 头文件路径），输出重定向到临时目录，分别测「裸 gcc」「ccache 冷（miss）」「ccache 热（hit）」：

| 方式 | 耗时 | 说明 |
|---|---|---|
| 裸 gcc（无缓存） | **3447 ms** | 这个大文件真实编译成本 |
| ccache 冷（第一次，miss） | 6118 ms | 编译 + 写缓存，**比裸编还慢**（要算哈希、压缩存盘） |
| ccache 热（第二次，hit） | **191 ms** | 直接取缓存对象 |
| ccache 热（第三次，hit） | 214 ms | 稳定在这个量级 |
| **加速比** | **约 18×** | 同一文件、同一参数 |

> 测量时机器上还有另一个编译在跑（CPU 49~67%），所以绝对毫秒数偏大；但**比值是可信的**：命中的代价 ≈ 起进程 + 查缓存，和文件大小、头文件深度无关。
> 脚本：`tools\ccache_micro.py`；统计：`ccache --show-stats`（本次 `Direct: 2 / 2 (100%)`，说明命中走的是直接模式，没有退化成预处理模式）。

**这意味着什么**：全量 257 步里，重复构建（换构建目录、`-p always`、改 board 后再回来）只要参数一致就能几乎全部命中。你越是频繁"推倒重来"，ccache 越值钱。

**但第一次不要期待变快**：miss 时 ccache 要把预处理结果算哈希、压缩存盘，实测单文件比裸编还慢（3447 → 6118 ms）。全量构建的第一轮大概会多花 30%~80%，收益从第二轮开始。

> **诚实标注**：全量"无缓存 vs 有缓存"的两次干净构建对照，没能在这台机器上跑完——期间一直有另一条编译任务占用 50%~65% CPU，测出来的绝对值会被污染（我实测同一份构建从 216 s 掉到 9 分钟只走到 99/257 步）。因此本表只保留**同一时刻、同一台机器、同一参数**的单文件对照，比值可信、绝对值偏大。等机器完全空闲时可以自己复现（命令见第七节）。

### 3. 语义化的增量策略

| 你改了什么 | 会发生什么 | 建议 |
|---|---|---|
| `src\main.c` | 编译 1 个文件 + 链接，**6.6 s**（hello_world 口径） | 随便改，随便编 |
| **`s3_wifi_portal` 里任何一个 `.c`**（分层后） | **10.5–11.0 s**：OBJECT 库 + 4 个 target 多了几步链接；no-op 仍只 0.82 s | 见下方"分层后的重测" |
| `prj.conf` / `*.conf` | **全量重配置 + 全量重编**（分钟级） | 攒着一起改 |
| `*.overlay` / dts | **全量**（devicetree 变了，`autoconf.h`/`devicetree_generated.h` 全失效） | 一次改完再编 |
| 换 `-b` board | 必须新构建目录 | 用不同 `-d`，不要复用 |

> **分层后的重测（2026-11-16，`s3_wifi_portal`，`-j8`）**：no-op **0.82 s** / 改 L2 文件 **11.02 s** /
> 改 `main.c`（217 行）**10.93 s** / 改 `applications\common\ota_engine.c` **10.53 s**。
> 结论：**拆分让单文件变短，但没有让整体增量变快**——多的那 3~4 s 花在分 target 的额外链接步骤上。
> 拆分的收益在"改一处只影响一层、编译单元只重编一个"，不在秒数。原始对照表见
> `应用层分层改造教程-s3_wifi_portal.md` §9。

## 五、还能再快的手段（按性价比排序）

### ① Defender 排除构建目录（要管理员，收益大）

Windows 安全中心 → 病毒和威胁防护 → 管理设置 → 排除项 → 添加文件夹：

```
C:\Users\xiao1\Desktop\ELAB\kharon-ide\build
C:\Users\xiao1\Desktop\ELAB\kharon-ide\.deps\ccache
C:\Users\xiao1\Desktop\ELAB\kharon-ide\west
C:\Users\xiao1\zephyr-sdk-1.0.1
```

一行到位（管理员 PowerShell，脚本会自动枚举上述目录，Defender 排除项不支持通配符）：

```powershell
pwsh -File .\tools\zephyr\defender_exclude.ps1
```

或手工：

```powershell
Add-MpPreference -ExclusionPath "C:\Users\xiao1\Desktop\ELAB\kharon-ide\.deps\ccache"
Add-MpPreference -ExclusionPath "C:\Users\xiao1\zephyr-sdk-1.0.1"
```

> 我这边查不到当前排除项（提示 `Must be an administrator to view exclusions`），所以**没有替你改**。这一步需要你自己用管理员权限确认一次。

### ② 不要用 `-p always`

它先删整棵构建树再重建。Windows 上删几万个小文件本身就要几分钟。需要干净构建时优先**换一个新的 `-d` 目录**，而不是删旧目录；旧目录攒多了再一次性清。

### ③ 内存

- 编译时把常驻大户（Steam、多个豆包窗口、壁纸引擎）关掉，`-j8` 更稳。
- 物理内存 15.2 GB 属于够用但紧；页面文件已经是 46 GB，别再调小。
- 如果 `-j8` 仍偶发 OOM，降到 `-j6`，并用 `ZEPHYR_BUILD_JOBS` 统一控制。

### ④ 构建产物瘦身

- `CONFIG_LOG` / `CONFIG_SHELL` / `CONFIG_NET` 这类"大子系统"在练习工程里按需开，编译时间和镜像大小都会明显下降。
- 不要把 `CONFIG_*` 全开会把构建步骤从 257 步抬到 600+ 步（Wi-Fi sample 就是 613 步）。

## 六、一次真实事故：`.venv` 被沙箱回收（这个坑比速度更重要）

**现象**：所有 `west build` 立刻失败：

```
west.exe : did not find executable at
'C:\Users\xiao1\AppData\Local\Doubao\User Data\sandbox_runtime\bases\772984f6...\python\python.exe'
```

**根因**：项目 `.venv` 当初是用沙箱自带的 Python **3.13.16** 创建的，`pyvenv.cfg` 里 `home` 指向沙箱路径；沙箱回收后 base interpreter 没了，venv 里的 `python.exe` / `west.exe` 全是死链。

**修复**（已执行）：

```powershell
# 旧 venv 保留改名，不直接删
Move-Item .venv .venv-broken-3.13

# 用系统 Python 重建
& "C:\Users\xiao1\AppData\Local\Programs\Python\Python312\python.exe" -m venv .venv
.\.venv\Scripts\python.exe -m pip install -U pip -i https://pypi.tuna.tsinghua.edu.cn/simple
.\.venv\Scripts\python.exe -m pip install west esptool -i https://pypi.tuna.tsinghua.edu.cn/simple
.\.venv\Scripts\python.exe -m pip install -r west\zephyr\scripts\requirements.txt -i https://pypi.tuna.tsinghua.edu.cn/simple
```

验证：

```
West version: v1.5.0
west build -d build\samples\esp32s3\peripheral\default  →  ninja: no work to do.  (2.1 s)
```

**教训**：项目 venv 的 base interpreter 必须是稳定路径（系统 Python）。自检一行就够：

```powershell
.\\.venv\\Scripts\\python.exe -c "import sys;print(sys.executable)"
```

# 干净全量（不带缓存）

## 七点一、这套实验用的是哪些脚本

都是**测量工具**，不会让编译本身变快；真正让编译变快的是 `env.ps1` 里的 ccache + `-j8`，加上 ①的 Defender 排除。留着它们的意义是：以后换机器 / 换 SDK / 换 `-j`，能用同一套口径重测、对比。

| 脚本 | 干什么 | 输出 |
|---|---|---|
| `tools\zephyr\defender_exclude.ps1` | 一条命令加 Defender 排除（`build\`、`.ccache`、`west`、SDK），要管理员 | 控制台打印 added/skipped |
| `tools\zephyr\build.ps1` | 旧构建入口（当前优先 `kharon build`），默认带 ccache 与 `-j8`，`-NoCcache` 可关 | 终端耗时行 |
| `tools\speed_full.ps1` | **最正式的一次**：先 `ccache -C/-z` 清零 → S1 冷缓存 → S2 热缓存全量对照 | `logs\speed-full.txt` |
| `tools\speed_bench.ps1` | 第一版：默认并行(18) / `-j8` / ccache 首编 / ccache 二编四组 | `logs\speed-report.txt` |
| `tools\speed_bench2.ps1` | 第二版：同上四组，改用 `Stopwatch` 计时（去掉 `Measure-Command` 的管道开销），逐行追加 | 同上 |
| `tools\speed_bench3.ps1` | 第三版精简：`-j8` 下"无缓存 vs 有缓存"三组 + bin 体积 | `logs\speed-r.txt` |
| `tools\ccache_micro.py` | 单文件微基准：裸编 / 冷 / 热 / 再热，算加速比 | 终端（第四节那张表就是它出的） |

`speed_bench.ps1/2/3` 是同一实验的三代草稿（参数逐渐收敛），**要用请直接用 `speed_full.ps1`**；前三份保留只为对照"当时怎么测的"。

> 注意：这三个 bench 脚本的临时构建目录写在 `build\_scratch\` 下（speed-A…D / r1…r3 / s1…s2），不占正常产物的位置；跑完想回收就整目录删 `build\_scratch`。
