# 构建入口与产物规则（唯一入口）

> **现状校准（2026-11-19）**：当前唯一推荐入口是 `kharon build -p <project>`；
> `tools\zephyr\build.ps1` 仍保留，作为“直接给 `-App` 路径”的旧入口（适合临时工程）。
> 两者都把产物守在同一棵 `build\` 下。

> 这篇回答两个问题：**"东西应该怎么编？"** 和 **"产物会落到哪里？"**
> 结论一句话：`kharon build` 是当前入口，产物只准落在 `build\` 下，裸敲 `west build` 会被兜进 `build\_unsorted\`（等于自报违规）。

## 一、一条链路

```
kharon env（生成 scripts\kharon-env.ps1：工具链 / CCACHE / SDK / west）
        │
        ▼
[当前入口] kharon build -p <project> [--clean]
        │                          └─ 工程 yaml 推算：build\<芯片>\<工程>\<配置>
        ▼
build\<芯片>\<工程>\<配置>\  →  zephyr\zephyr.bin / zephyr.elf / zephyr.map（ARM 另有 zephyr.hex）
        │
        ▼
ESP32：kharon flash -p <project>（或 west flash -d 同一目录 --esp-device COMx）
ARM  ：kharon flash -p <project>（内核按工程 yaml 走 openocd + DAP-Link cfg）
        │
        ▼
logs\<证据>.txt   +   docs\（把结论写进对应那一层）
```

**旧入口 `tools\zephyr\build.ps1`** 仍然可用：`-App <工程> -Board <板> [-Flash]`，
产物同样落 `build\<芯片>\<工程>\<配置>`；它按 `-Board` 推断烧录方式
（`esp32*` → esptool，`stm32|blackpill` → OpenOCD）。**日常优先 `kharon`**，别两套混用。

源码层 → 构建层 → 文档层，三层的对应关系是固定的：

| 层 | 位置 | 职责 |
|---|---|---|
| 源码层 | `applications/<family>/<app>\` + `projects/kharon/<project>.yaml` | 一个工程 = `CMakeLists.txt` + `prj.conf` + `src\`（+ `boards\*.overlay`）；工程名与目录名逐字一致 |
| 构建层 | `build\<芯片>\<工程>\<配置>\` | 一个目录 = 一个工程 + 一块板 + 一套配置，**不可复用** |
| 文档层 | `docs\`（教程 / 课程同款 / 参考 / 变更记录） | 结论、证据、决策 |

## 二、入口排序，只有一个算数

| 入口 | 谁在用 | 产物落点 | 状态 |
|---|---|---|---|
| `kharon build -p <project>` | 人、脚本、当前文档 | `build\<芯片>\<工程>\<配置>`（工程 yaml 推算） | ★ **当前入口** |
| `tools\zephyr\build.ps1 -App <工程> -Board <板>` | 旧脚本、临时工程 | 同上（`-App` 推算） | 兼容保留，日常不优先 |
| `CMakePresets.json`（`cmake --preset` / CLion / VS Code） | IDE | `../../../build\<芯片>\<工程>\${presetName}`（`_template` 是 `../../`） | 允许（同一棵树） |
| 裸 `west build`（不写 `-d`） | 手滑 | `build\_unsorted\<app>\` | **违规兜底**，巡检会报 |

旧 `build.ps1` 会**拒绝**落在 `build\` 之外的 `-BuildDir`：

```
throw "Build dir must be under <root>\build (got: …). Use -AllowOutsideBuild only for a throwaway experiment."
```

`-AllowOutsideBuild` 是留给"临时试一下"的逃生舱，正常流程不要碰。

## 三、裸 `west build` 为什么也进 `build\`

`west\.west\config` 里钉了一行格式串：

```ini
[build]
dir-fmt = {west_topdir}/../build/_unsorted/{app}
```

`west` 在没给 `-d` 时会按这个格式串算目录（`scripts\west_commands\build_helpers.py:189` 的 `find_build_dir`，最后一步 `os.path.abspath`）。展开结果（本机实测模拟）：

```
korvo_sys   -> C:\Users\xiao1\Desktop\ELAB\kharon-ide\build\_unsorted\korvo_sys
hello_world -> C:\Users\xiao1\Desktop\ELAB\kharon-ide\build\_unsorted\hello_world
```

三个要点：

1. **用 `{west_topdir}/../` 而不是相对路径** —— 相对写法会跟着当前工作目录跑（在 `west` 里跑就落到 `west\build\`，在仓库根跑就落到仓库根），只有锚在工作区根才恒定。
2. **为什么不用它直接生成 `build\<芯片>\<工程>\<配置>`** —— `dir-fmt` 的占位符只有 `{west_topdir} {source_dir} {source_dir_workspace} {app} {board}`（`build.py:503-508`），而 `{board}` 是 `esp32s31_function_coreboard/esp32s31/hcore` 这种带斜杠的三段式，塞进去会变成一长串多级目录，且**提取不出"芯片"这一层**。所以"按芯片分目录"只能由脚本或 preset 算。
3. **落 `_unsorted` 而不是报错** —— 直接让 `west build` 失败太粗暴（有人就是想临时编一下 sample）；落到 `_unsorted` 既不污染仓库根、又留下痕迹，`build/` 本来就被 `.gitignore` 排除，清起来一条命令。

## 四、目录命名规则

```
build\
├─ esp32s31\<工程>\<配置>\     例：korvo_sys\s31-debug、korvo_apps\s31-release
├─ esp32s3\<工程>\<配置>\      例：s3ota\、s3_wifi_portal\（本机这两份没带 `default` 段；`build.ps1` 默认会建 `\<工程>\default`，一个构建目录=一个缓存，别混用）
├─ stm32f4\<工程>\<配置>\     例：f411_breath\default、f411_hwpwm\default（ARM，Zephyr SDK 的 arm-zephyr-eabi）
├─ stm32f1\<工程>\<配置>\     例：f103_breath\default（F1 系列单独一层，不与 F4 混放）
├─ samples\<芯片>\<样例>\<配置> 上游 sample：hello_world\default、shell\default
├─ _scratch\                   实验临时的构建目录（编译速度 bench 用，可整删）
└─ _unsorted\<app>\            裸 west build 的落点（出现即说明有人绕过入口）
```

两条硬约束：

- **一个构建目录 = 一个工程 + 一块板**。换板或换工程必须换目录（`build.py:645-652` 会直接拒绝"这个目录编的是 A 板，你却给了 B 板"）。所以 `<配置>` 段是必需的，`s31-debug` / `s3-debug` 不是装饰。
- **`_` 开头只给系统用**：`_scratch`（bench 临时目录，可整删）、`_unsorted`（违规落点，出现即待清理）。用户自己的配置名不许用 `_` 开头，否则巡检和清理脚本无法区分。（`_legacy` 归档层已于 2026-11-15 删除。）

## 五、巡检（唯一可执行的判据）

```powershell
pwsh -File .\tools\check-layout.ps1
```

它读文件、不编译、不删东西，检查五件事：

| # | 检查 | 不合格意味着 |
|---|---|---|
| 1 | `applications\**\build` 不存在 | 有人把产物编回工程目录里 |
| 2 | 仓库根没有 `build-*` | 又回到了扁平老布局 |
| 3 | `west\build-*` 不存在 | 产物落在 west 工作区里 |
| 4 | 每个 `CMakeCache.txt` 的 `APPLICATION_SOURCE_DIR` 指向本仓库的 `applications\` 或 **west 工作区内**（`west\`，含 sysbuild 自己的 `zephyr\share\sysbuild\template` 与 `mcuboot\boot\zephyr` 子缓存），且源码目录真实存在 | 构建目录指向了已删除/仓库外的源码 |
| 5 | 每个 `CMakePresets.json` 的 `binaryDir` 落在 `build\` 下（缺省的子 preset 靠 `inherits`，不算错） | preset 会把产物编进工程目录 |

本机当前结果（2026-11-16 清理后）：

```
== 目录巡检 ==
checks passed: 5/5   caches: 7   presets: 10
OK: 布局合规
```

> 2026-11-16 之前这项长期是 **3/5**：一条是 `applications\esp32s3\s3_wifi_portal\build`（裸 `west build` 落点），
> 已删除；另一条是 `build\esp32s3\s3ota` 下 sysbuild 的两个子缓存指向上游 `sysbuild\template` 与 `mcuboot\boot\zephyr`，
> 那**本来就是 sysbuild 的正常形态**，是判据太窄 —— 规则 [4] 已放宽到"整个 west 工作区"。数字也相应从 30 个 cache 降到 7 个（空目录清掉了）。

`WARN` 里出现 `build\_unsorted` 就说明有人绕过入口，看一眼是谁的目录，确认无用后 `Remove-Item -Recurse build\_unsorted`。

## 六、改回来（回滚）

```powershell
# 取消 dir-fmt 兜底，回到 west 默认（产物落在当前目录的 build\）
cd west
west config --delete build.dir-fmt

# 取消 build.ps1 的收口守卫
git restore tools\zephyr\build.ps1
```

`dir-fmt` 只存在 `.west\config`（`west\` 整个目录不纳入版本库），所以删掉即可，不影响仓库历史。

## 七、新增工程时照这个顺序

1. `Copy-Item applications\_template applications\<family>\<新工程> -Recurse`
2. 改工程内的 `CMakePresets.json` 落点（`../../build/<family>/_template/...` → `../../../build/<family>/<新工程>/...`），目录名与工程名逐字一致
3. 在 `projects/kharon/<新工程>.yaml` 登记工程（板、通道、烧录参数）
4. 跑 `pwsh -File .\tools\zephyr\check-layout.ps1`，5/5 过了再开始写代码
5. 构建：`.\kharon.cmd build -p <新工程>`（旧入口：`.\tools\zephyr\build.ps1 -App .\applications\<family>\<新工程> -Board <板>`）

## 八、清理 `build\`：一条命令，且不进回收站

```powershell
pwsh -File .\tools\zephyr\clean-builds.ps1                 # 干跑：列出每个构建目录 + 最后构建时间，标 keep / DELETE
pwsh -File .\tools\zephyr\clean-builds.ps1 -Delete         # 删掉超过 7 天没动过的
pwsh -File .\tools\zephyr\clean-builds.ps1 -Delete -KeepDays 3
pwsh -File .\tools\zephyr\clean-builds.ps1 -Delete -All    # 除 -Protect 外全删
```

"最后构建时间"取构建目录里 `build.ninja` / `.ninja_log` / `CMakeCache.txt` 的最后写入时间，**不看目录 mtime**（Windows 上目录 mtime 不可靠）。构建目录的识别口径是"`build\` 下第一个带 `CMakeCache.txt` 的目录"，所以 sysbuild 的子缓存不会被重复计数；`_scratch` / `_unsorted` 整层按 `_` 规则单独处理。

三条硬约束（脚本里是 throw / 白名单，不是建议）：

1. **只删 `<root>\build` 之内的路径**，其它一律拒绝；
2. **默认干跑**，不加 `-Delete` 一个文件都不动；
3. **`-Protect` 保护正在用的目录**，`build.ps1` 每次把当前的 `-BuildDir` 传进去。

### 为什么不写 `Remove-Item`，更不能走资源管理器

2026-11-18 的事故：一次清 `build\` 产生 **113 万个回收站条目 / 52 GB**，资源管理器打开回收站直接卡死（要枚举的条数太多），最后只能提管理员权限、用内核递归删除补完。细节见 `docs\zephyr-learn\变更记录\构建产物清理-2026-11-18.md`。

2026-11-19 实测补了一条更硬的事实：**本机对 `Desktop\` 下的删除做了拦截**。`[System.IO.Directory]::Delete`、`cmd rd /s /q`、`cmd del` 三种方式删 `Desktop\ELAB\dsh-elab-flow` 里的东西，回收站条目都会增加、空间不释放；同样的调用在 `%TEMP%` 下则不产生条目。所以"`.NET Delete` 本来就不进回收站"在这台机器上**不成立**。

脚本因此改成分两步删：

1. `[System.IO.Directory]::Move($target, "$env:TEMP\elab-prune-<时间戳>-<随机>\<guid>")` —— 同卷 rename 是纯元数据操作，不是删除，回收站零增长；
2. 再在 `%TEMP%` 里 `[System.IO.Directory]::Delete($staged, $true)` —— `%TEMP%` 内的删除不被拦截。

`Move` 失败时（例如 TEMP 被指到别的卷）回落到直接 Delete，并在摘要里单独计数、提示你去看回收站。实测（2026-11-19）：一个含 `CMakeCache.txt` 的测试构建目录被删除，回收站条目 25 → 25。

其余约定：

- `build.ps1` 构建成功后自动调用一次（`-KeepDays 7 -TriggerFreeGB 25 -Quiet`）：**只有 C 盘剩余低于 25 GB 才真的干活**，平时零成本；`-NoPrune` 可关；
- 仓库根的 `.vscode\settings.json` 已设 `files.enableTrash: false`（需重载窗口生效），IDE 里删文件也不进回收站。

> 跑 `kharon` / `build.ps1` 请用 **pwsh 7**：`kharon env` 生成的脚本与旧 `tools\zephyr\env.ps1` 都是 UTF-8（含中文），Windows PowerShell 5.1 按 ANSI 读会乱码并解析失败。
