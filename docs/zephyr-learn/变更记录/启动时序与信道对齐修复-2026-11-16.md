# 启动时序与信道对齐修复（2026-11-16）

> 一句话：**应用层没加功能，只把"什么时候开始连"和"失败了怎么救"两件事做对了** ——
> 冷启动 `boot → 拿到 IP` 从 **19.3 s** 降到 **5.8–13.9 s**（中位 ~9 s），
> 单射频下"AP 被钉在错信道 → `status 4` → 越连越死"的那条链条被拆掉，
> 网页切到不存在的网络也不再能把整台设备卡死。
> 完整诊断、方案与验收数据见 [`..\参考\启动时序与信道对齐-诊断与修复方案.md`](../参考/启动时序与信道对齐-诊断与修复方案.md)。

## 1. 这轮不做什么

- **不加功能**，不改 `prj.conf`、不改 overlay、不改分区表 —— 所以除 v147 因 CMake 缓存失效全量一次外，其余都是 29.5–40 s 的增量。
- **不碰 OTA 与分层结构**：这一轮只动 `wifi_link.c` / `portal_ap.c` / `wifi_scan.c` / `main.c` / `selftest.c` / `api_wifi.c` / `portal_cfg.h`，目录结构沿用上一轮的 L0/L1/L2。

## 2. 两个问题的根因（诊断结论）

1. **"重启后很久才通"不是 HTTP 慢，是没有 IP。** 改造前 19.3 s 的预算是：6.4 s 与网络无关的固定等待（`k_msleep` + 串行自检把连接排在最后）+ 0.6 s 必然失败的首连 + 3 s 盲退避 + 9.1 s 第二次连接自己扫信道/关联/DHCP。
2. **`status 4` 的死锁是三个缺陷叠出来的**：`ap_reopen_handler` 把 AP 信道永久钉住且永不恢复 `WIFI_CHANNEL_ANY`；AP 处于 auto 时 `ap_current_channel()` 恒为 0，于是"0 != 目标"永远成立（要么白踢手机，要么判不出真错）；失败后只会盲退避/换网，从不重扫、不搬信道 —— 而扫描入口只挂在 HTTP 上。

## 4. 两次真实事故（这才是这轮最该留下的东西）

- **事故 A：把扫描放进系统工作队列 = 冻住整个应用。** `net_mgmt(NET_REQUEST_WIFI_SCAN)` 在 ESP32 驱动里是阻塞的（全信道约 10 s），系统工作队列是单线程，一冻就把 LED、RSSI 采样、重试全停了，串口日志 18 s 左右静默，现象和"死机"一模一样。修法：单开一条 `align_scan_wq`（2048 栈，`K_PRIO_PREEMPT(2)`），扫描只在这条队列里跑。
- **事故 B：失败后立刻再发 CONNECT，会把整台设备卡死。** 真机切到不存在的 `501A` → `status 4` → 500 ms 后重试 → HTTP 与串口同时失联，`crash` 计数不涨、`boot` 计数不涨（说明是真 hang 不是复位），只能 USB 复位。修法：删掉"换网先 DISCONNECT"那条改动；对齐阶梯**只在开机自动重连时生效**，运行期回到改造前的"3 s 退避 + 有 RSSI 就把状态拉回 connected"。

## 5. 验收（三条都能复现）

| 断言 | 结果 | 证据 |
|---|---|---|
| `boot → IP` 明显变短 | 19 304 ms → 5 773 / 7 726 / 8 713 / 11 232 / 12 747 / 13 872 ms | `logs\boot-probe3..9.log` |
| 网页切到不存在的网络不再卡死 | 35 s 内每 2 s 都能 poll，链路保持在原网络，切回 0.1 s 生效 | `logs\switch147.log` |
| 信道搬运分支真的会动 | `channel mismatch: ap pinned ch=9, "SCAUNET" ch=3 -> reopen AP` → AP 搬到 ch3 | `logs\retarget1.log` |

未验到的一项：**开机时"必须走扫描档"的组合**没能造出来——这块板的 boot target 永远是"最后连上的那条"，而屋里只有一条有密码的网络；塞假凭据只能走到扫描档的前半程。详情见参考文档 §8.5。
