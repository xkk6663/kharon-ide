# 仓库精简 + STM32F103 入库 + 两份 README 重写（2026-11-16）

> 一句话：**代码没动一行，仓库里"只干过一次活的脚本"和"编错地方的产物"清掉了**；
> 34 个死脚本退场、`tools` 从 69 支降到 36 支、布局巡检从 3/5 变成 **5/5·0 WARN**，
> 根 `README.md` 与 `tools\README.md` 各重写一遍，顺手把一直在工作区外面漂着的 F103 工作线并进版本库。

## 1. 为什么做这一轮

上一轮（`7a9c90c`）把 `s3_wifi_portal` 的 4399 行单文件拆成 L0/L1/L2 之后，仓库里留下了两笔账：

1. **一次性脚本沉淀**。OTA 调试期为了"改一行看一次结果"，往 `tools\` 里塞了三十来个 `_patch_*.py` / `*_probe.py`，
   每个都只服务过某一次实验。它们跟着仓库走，后果是 `tools\` 里真正的入口（`build.ps1` / `ota_push.ps1` /
   `check-layout.ps1`）被人一眼看不出来，新人要在一堆 `_hang_probe` 里找入口。
2. **产物落错位置**。有人绕过 `build.ps1` 直接在 `apps\esp32s3\s3_wifi_portal` 里跑了裸 `west build`，
   `build\` 下还留着几个空目录壳。布局巡检因此长期挂着 FAIL，**"3/5" 变成了一种背景噪音**，
   真出现新违规时反而没人察觉。

加上用户明确要求"F103 也要入库、一次性脚本删掉、不用的脚本和产物也删掉、精简仓库重写 README"，
这一轮就按这四件事做。

## 2. 判定"死脚本"的判据（不是拍脑袋）

写了一个引用关系扫描（`tools\` 里 69 个 `*.py|*.ps1|*.js`，逐个在**全仓库**（含 `docs\`、`apps\`、`AGENTS.md`）
里搜文件名，排除它自己那一行），判据是两条同时成立：

- 除自己以外，**全仓库零引用**；
- **不在** `tools\README.md` 的索引表里（索引是"有人还在用它"的人工证据）。

得到 33 个零引用；再补一条**链式失效**：`serial_capture.py` 本身只被已判死的脚本引用，一起删。
最终 **34 个**。

删之前每个都 `git ls-files --error-unmatch` 确认过受版本控制 —— 这一步不是为了流程好看，
而是保证**全部可恢复**（见第 6 节）。

## 3. 删了什么

### 3.1 34 个零引用脚本（全部 `.py`）

| 类别 | 名单 | 它们服务过的场景 |
|---|---|---|
| OTA 非对称调试探针（11） | `ota_auth_probe` `ota_gate_probe` `ota_reboot_auth_probe` `auth_probe` `_nonce_debug` `_fix_nonce_file` `_reason_probe` `_reason_probe2` `_reboot_probe` `_hang_probe` `_drop_probe` | 排查"为什么带 nonce 的升级包被拒 / 为什么卡在 85%" |

**统一理由**：这些脚本的价值是"当时那一次的观测结果"，结果已经写进了教程与变更记录；
脚本本身换个日期就跑不出同样的输出（版本号、端口、nonce 都变了），留着只会误导。

## 4. 两处"巡检误报"的修法

`tools\check-layout.ps1` 改了三处，都是**判据错，不是缓存脏**：

| # | 问题 | 改法 |
|---|---|---|
| 1 | `$allowedTop` 没有 `stm32f1`，新芯片的 `build\stm32f1\` 被记"层级不合规" | 白名单加 `stm32f1` |
| 2 | [4] 判据原为"源码在 `apps\` 或上游 `samples\`"，把 **sysbuild 的合法子缓存**判成 FAIL：`build\esp32s3\s3ota` 的 `mcuboot` 子缓存指向 `zephyr\share\sysbuild\template` 与 `bootloader\mcuboot\boot\zephyr` | 判据放宽为"`apps\` 或**整个 west 工作区**（`zephyr-s31\`）内的真实目录" |
| 3 | 头部注释还写着旧判据 | 同步 |

修完实测：

```
== 目录巡检 ==
checks passed: 5/5   caches: 7   presets: 10
OK: 布局合规
```

> 这里刻意没有选"删掉 s3ota 缓存来凑 5/5"。**巡检是为开发服务的，判据错了就改判据** ——
> sysbuild 子缓存本来就是这种形状，删一次缓存只是把问题推迟到下次 `build_ota`。

## 6. 怎么把删掉的东西拿回来

删前都在 `HEAD` 里（`7a9c90c`），一条命令恢复单支：

```powershell
git show HEAD~1:tools/_hang_probe.py > tools/_hang_probe.py
```

整轮回滚：`git revert <本次提交>`（纯删除 + 两份 README，回滚无冲突风险）。
