# 16 · ESP32-S3 还能干什么：能力地图与开工顺序

> 这篇不是"参数罗列"，而是**判断一个外设能不能在本机上真跑起来**的方法：看三层证据（dts 节点 → 驱动源码 → 外部硬件），三层缺一层就做不成。最后给一条按"能立刻验证"排序的开工路线。

---

## 一、判断一个外设"能不能做"的三层证据

以 I2S 为例，三层缺一不可：

| 层 | 查什么 | 本机怎么查 | S3 的结果 |
|---|---|---|---|
| ① devicetree | 有没有节点、`compatible` 是什么、`status` 是 okay 还是 disabled | `Select-String ...\dts\xtensa\espressif\esp32s3\esp32s3_common.dtsi -Pattern "i2s@"` | ✅ `i2s0: i2s@6000f000`、`i2s1: i2s@6002d000`，`compatible="espressif,esp32-i2s"`，**默认 `status="disabled"`** |
| ② 驱动 | 树里有没有这个 `compatible` 的驱动 `.c`，Kconfig 有没有门控 | `Get-ChildItem zephyr\drivers -Recurse -Filter "*esp32*"` | ✅ `drivers\i2s\i2s_esp32.c` |
| ③ 硬件 | 板子上有没有这段模拟电路 / 接插件 | 用户告知 + 丝印 | ❓ 最小板只有排针，**要自己接 I2S 麦克风或功放** |

再看 Wi-Fi 这个例子（**它一开始是最像"做不了"的那个**）：

| 层 | 结果 |
|---|---|
| ① dts | ✅ `wifi: wifi { compatible = "espressif,esp32-wifi" }`，板级 dts 里 `&wifi { status = "okay"; }`（devkitc 板级 dts 直接打开了，不用自己写 overlay） |
| ② 驱动 | ✅ `drivers\wifi\esp32\`（Kconfig 要求 `DT_HAS_ESPRESSIF_ESP32_WIFI_ENABLED` + `ZEPHYR_HAL_ESPRESSIF_MODULE_BLOBS`） |
| ③ 二进制库 | 🟡→✅ **一开始缺，后来补齐了**：`modules\hal\espressif\zephyr\blobs\lib\esp32s3\` 里 9 个 `.a` 是空的（`zephyr\esp32s3\` 只有 `src\` / `src\linker\`，没有 `libnet80211*` / `libbtdm_app*`），必须从乐鑫的 blob 仓库按 `module.yml` 里的 url + sha256 拉下来 |

第 ③ 层补齐之后，Wi-Fi 的 `wifi scan` 扫到了 **11 个 AP**，BLE 的 `bt_enable()` 返回 0 并 `Advertising successfully started`，PC 侧用 bleak 扫到了广播（RSSI -32 ~ -40，带 180D/180F/1805 三个标准服务 + 一个自定义 UUID）。完整过程见 **第 17 组《S3 无线能力：Wi-Fi 与 BLE》**。

> 结论写法建议：以后别人问你"S3 能不能跑 Wi-Fi"，答案不是"能"或"不能"，而是"**节点、驱动、blob、板级配置四层都齐，才叫能**"。前两层在这棵树上一直是齐的，卡住的只是第③层和第④层（后者指控制台/quirks 这类板级细节）。

| **LCD_CAM（摄像头/并口屏）** | `lcd_cam@60041000` | `video\video_esp32_dvp.c`、`mipi_dbi\mipi_dbi_esp32.c` | 摄像头/屏 | 🟡 |
| **RMT RX**（红外/脉冲解码） | 同 `rmt@60016000` | `pulse_io\pulse_io_esp32_rmt_rx.c` | 红外接收头 / 信号源 | 🟡 只用了 TX |
| **UART1 / UART2** | `uart1@60010000`、`uart2@6002e000` | `serial\uart_esp32.c` | USB-TTL 模块 | 🟡 |
| **PSRAM** | `psram0 { compatible="espressif,esp32-psram" }`（**默认 okay**） | — | 模组是否焊了 PSRAM | ⚠️ **物理未知**，别直接开 |
| **Wi-Fi（STA 扫描 / 连接 / APSTA 配网）** | `wifi`（板级 dts `status="okay"`） | `drivers\wifi\esp32\` + 9 个 blob | 无（板载天线） | ✅ 已实测：`wifi scan` 扫到 11 个 AP；`applications\esp32s3\s3_wifi_portal` 里 APSTA + DHCP server + mDNS + HTTP 配网页 + 连真实路由器拿到 `10.168.1.226`（见第 17 组） |
| **BLE（peripheral 广播）** | `esp32_bt_hci`（默认 disabled，需 overlay 打开） | `bluetooth\hci\hci_esp32.c` + `libbtdm_app.a` 等 blob | 无（板载天线） | ✅ 已实测：控制器 MAC `f0:9e:9e:0e:f4:c2`、`Advertising successfully started`、PC 侧扫到广播 |

**怎么读这张表**：

- ✅ 的四行是这台机器上**已经有串口原文**的；
- 🟡 的是"软件层齐了，缺一根线/一个模块"——最容易上手；
- 🔵 的是"还要自己在 overlay 里把 `status` 打开，并补 Kconfig"，属"会做但没做"；
- ⛔ 的是"缺不可替代的二进制资产"，靠改代码解决不了。

## 三、系统层在 S3 上的实测（本组新增证据）

`applications\esp32s31\korvo_sys` 同一份代码，S3 构建 `FLASH: 145908 B / 8388352 B / 1.74%`（S31 上 145280 B，差 628 B 全是板级/控制台差异）。

复位后的启动原文（`logs\serial-s3-sys.txt`）：

```
rst:0x15 (USB_UART_CHIP_RESET),boot:0xb (SPI_FAST_FLASH_BOOT)
*** Booting Zephyr OS build 34e025569cbb ***
=== Korvo-1 sys ===
sys info | sys temp 3 | sys rand 4 | sys dev
```

四条命令全部有输出：

```
>>> sys info
[info] 复位原因位图 = 0x00000000
[info] 复位原因 = UNKNOWN
[info] 器件 ID = f0:9e:9e:0e:f4:c0 (len=6)
[info] 运行时长 = 1908 ms
[info] Zephyr 版本 = 4.5.99
[info] 板 = esp32s3_devkitc/esp32s3/procpu

>>> sys temp 3
[temp] 采样 3 次
[temp] 31.29 °C
[temp] 31.29 °C
[temp] 31.29 °C

>>> sys rand 4
[rand] 从硬件熵源取 4 组
[rand] 0x6cdb6976 0x6660b6a6
[rand] 0x15b51584 0xfb2065db
[rand] 0x7f132d26 0x0a5c2f78
[rand] 0x5180e6dc 0x930495fc

>>> sys dev
[dev] coretemp  = coretemp@60008800 (ready=1)
[dev] watchdog0 = watchdog@6001f048 (ready=1)
[dev] 说明：只读设备状态，不安装超时（安装后停止喂狗会复位板子）
```

三个值得注意的点：

1. **`复位原因 = UNKNOWN`，位图 0x0**：S3 的 hwinfo 驱动对 `USB_UART_CHIP_RESET`（`rst:0x15`，来自 USB-Serial-JTAG 的复位请求）没有归类，返回 0。**这不是驱动坏了**，是"这一类复位没有被映射到标准枚举"。同一条代码在 S31 上能给出具体原因——这就是芯片差异在"系统层"留下的痕迹。
2. **温度稳定在 31.29 °C**：三次采样一模一样，因为这颗片上温度传感器分辨率本来就粗（它测的是芯片结温，不是环境温度）。想验证它真的在变，得给它加热/跑满载。
3. **`器件 ID` 是 6 字节 MAC**：`f0:9e:9e:0e:f4:c0`，来自 eFuse 出厂 MAC，两片板不会重复。

## 四、开工顺序建议（按"能不能立刻验证"排序）

> 排序原则：**能在 30 分钟内用串口看到数字变化**的排前面。需要买模块、需要焊线的排后面。

### 第 0 步：硬件加密（已完成，零外设、自带标准答案）

- 为什么它排在最前：不需要任何器件，答案写在标准里（SHA-256("abc") / AES-128 ECB 的 NIST 向量），算错就是 FAIL，没有"大概对"。
- 结果：**四组 KAT 全 PASS**，SHA 33.5 MB/s、AES 复用会话 5.6 MB/s。详见 `硬件加密加速.md`。
- 学到的抽象：**会话式 API**（begin → compute/op → free）+ **驱动自述能力（hwcaps）**。

### 第 1 步：LEDC PWM（不需要任何外接硬件）

- 节点 `ledc0@60019000` 默认 disabled → overlay 打开，`pinctrl` 选一个**空闲且能输出**的脚（IO48 已被 WS2812 占用，建议用排针上的 IO1/IO2 之类，**先查最小板丝印确认那个脚确实引出**）。
- 驱动是 `pwm_led_esp32.c`，API 是标准 `pwm_set_cycles()`。
- 验证点：`pwm` shell 命令（`CONFIG_PWM_SHELL=y`）能设占空比；接个 LED 看亮度。
- 学到的抽象：**PWM 子系统**（`pwm_dt_spec` + `pwm_set_cycles`），和 GPIO 完全不同的编程模型。

### 第 2 步：PCNT 计数（用 IO45 按键当脉冲源！）

这是最取巧的一步：**不需要外部信号发生器**。

- 节点 `pcnt@60017000` 默认 disabled；驱动是 `sensor\espressif\pcnt_esp32\pcnt_esp32.c`——注意它是**挂在 sensor 子系统下的**（`sensor_channel_get(..., SENSOR_CHAN_ROTATION)`），不是独立 counter API。
- 把 PCNT 的输入脚也指到 IO45（和 gpio-keys 共用一根脚是允许的：一个走中断，一个走边沿计数），每按一次键就是一个边沿。
- 验证点：`sensor` shell 或自定义命令里读计数，按 5 次应得 5 左右（去抖会吃掉抖动边沿）。
- 学到的抽象：**同一根引脚可以被两个驱动同时"观察"**，这是 Zephyr 设备模型和裸机思维最大的区别之一。

### 第 3 步：I2S（S3 独有能力，要一个 I2S 麦克风）

- 这是全篇最值得做的一项：**Korvo-1 的 S31 树里根本没有 i2s 节点**，所以"音频"这件事在 S3 上是**新增**能力，不是平移。
- 节点 `i2s0@6000f000` 自带 `dmas = <&dma 2>, <&dma 3>`，说明走 GDMA；驱动 `i2s_esp32.c` 支持 `I2S_DIR_RX`。
- 需要：INMP441（I2S MEMS 麦克风）或 MAX98357A（I2S 功放）+ 三根线（BCLK/LRCLK/DIN）。
- 验证点：先做"录音到缓冲区，算一个 RMS 值打出来"——**不接 SD 卡也能验证链路**，对着麦克风说话 RMS 会变。
- 学到的抽象：**DMA + 块设备 API**（`i2s_configure` / `i2s_buf_read`），这是从"寄存器级"跨到"流水线级"的门槛。

### 第 4 步：TWAI / CAN（要一个收发器）

- `chosen { zephyr,canbus = &twai }` 已经写好，说明这棵树的 CAN 支持是"一等公民"。
- 需要：SN65HVD230 之类 3.3 V 收发器 + 120 Ω 终端电阻（自测可以单节点 + 环回模式 `CAN_MODE_LOOPBACK`，**不用第二块板**）。
- 验证点：环回模式下自发自收，`can` shell 能打出帧。
- 学到的抽象：**CAN 子系统**（`can_send` / `can_add_rx_filter_msgq`）。

### 第 5 步：SD 卡（要卡座）

- `sdhc@60028000` 默认 okay，驱动 `sdhc_esp32.c`；接上后能挂 FAT（`CONFIG_FAT_FILESYSTEM_ELM`）。
- 这一步的价值不在 SD 本身，在于**文件系统**：`fs` 子系统 + `disk` 子系统，和第 14 组的 NVS 是两套完全不同的持久化。

### 第 6 步：USB-OTG（把这块板变成一个 USB 设备）

- 节点 `usb_otg@60080000`，`snps,dwc2` IP；Zephyr 侧走 `udc` + `usbd` 框架，可以做 CDC（虚拟串口）或 HID。
- ⚠️ **踩点提前说**：USB-OTG 和 USB-Serial-JTAG 共用 PHY。切到 OTG 后，**你现在用的 COM11 会消失**，日志要看 OTG 枚举出来的那个新串口。所以这一步一定要"先把日志改到 uart0 + CP2102 或先写好 USB CDC 描述符"，否则会陷入"没日志→不知道有没有枚举成功"的死循环。
- 学到的抽象：**USB device 类框架**（描述符 + 类注册 + 端点回调）。

### 不建议现在动的

| 项 | 为什么 |
|---|---|
| PSRAM | 节点默认 okay 但**物理上有没有 PSRAM 取决于模组型号**；贸然启用会在启动阶段崩，且崩在 C 库初始化里，极难查 |
| deep_sleep / `sys_poweroff` | 属于"会复位/关机"的操作，本教程只写原理（见第 14 组），不做现场演示 |
| WDT 超时 | 装超时后停止喂狗会复位板子，违反本项目"不做复位类演示"的约定 |

## 六、自检

2. `i2s0` 节点里 `dmas = <&dma 2>, <&dma 3>` 说明了什么？为什么这条信息决定了"能不能做实时音频"？
3. 为什么 `pcnt` 的驱动放在 `drivers\sensor\espressif\pcnt_esp32\`，而不是 `drivers\counter\`？这对你写应用有什么影响（提示：API 是哪个子系统的）？

5. 如果要在 S3 上做 USB HID，为什么"先把日志挪走"是第一步而不是最后一步？
