# 硬件加密加速：把"跑起来了"变成"算对了"

> 本文是第 16 组的第三篇。前两篇是 `GPIO按键与输入子系统.md`、`S3能力地图.md`。
> 这篇解决一个很实际的问题：**加密这种东西，没有仪器、没有第二个实现，你怎么知道自己跑对了？**
> 答案不是"跑通不报错"，而是**已知答案测试（KAT）**——拿标准里写死的向量去对。

---

## 一、为什么选这一块作为下一个能力

`S3能力地图.md` 里 AES/SHA 那一行原来标的是 🟡（"节点 okay、驱动在、还没写示例"）。它在候选里排第一，不是因为它最花哨，而是因为它**天然自带验收标准**：

| 能力 | 验收需要什么 | S3 最小板上现实吗 |
|---|---|---|
| LEDC / PWM | 示波器，或接个 LED 看亮度 | 要器件 |
| PCNT | 脉冲源 + 跳线 | 要接线 |
| I2S | 麦克风/喇叭/codec | 要器件 |
| SDHC | TF 卡 | 要卡 |
| CAN | 第二个 CAN 节点或环回线 | 要接线 |
| **AES / SHA** | **一个标准测试向量** | **纯软件，零外设** |

硬件加密的"对错"是绝对的：SHA-256("abc") 的答案全世界只有 `ba7816bf…15ad` 这一个。算错一个 bit 就是 FAIL，没有"大致正确"这种中间态。这就让它成了**最便宜的一次"真·实机验证"**——正好补上第 15 组留下的"只验到设备就绪"的欠账模式。

## 二、三层证据：这次一层都没省

### 第 1 层：dts 节点是否 okay

```dts
/* zephyr\dts\xtensa\espressif\esp32s3\esp32s3_common.dtsi */
aes: aes@6003a000 {
	compatible = "espressif,esp32-aes";
	reg = <0x6003a000 0x1000>;
	clocks = <&clock ESP32_AES_MODULE>;
	status = "okay";                 /* 默认就是 okay，不用 overlay 打开 */
};
sha: sha@6003b000 {
	compatible = "espressif,esp32-sha";
	reg = <0x6003b000 0x100>;
	clocks = <&clock ESP32_SHA_MODULE>;
	status = "okay";
};
```

两个节点都在 `esp32s3_common.dtsi`（SoC 级），**不需要写任何 overlay**。这一点和 coretemp 不同：coretemp 在板级 dts 里是 disabled，必须 overlay 打开；AES/SHA 出厂就是 okay。

### 第 2 层：驱动在，但**没有被编进去**（这是本篇的坑）

```
zephyr\drivers\crypto\crypto_esp32_aes.c
zephyr\drivers\crypto\crypto_esp32_sha.c
zephyr\drivers\crypto\Kconfig.esp32
```

`Kconfig.esp32` 里 `config CRYPTO_ESP32` 是 `default y`，看起来"开箱即用"。但它被包在一个 `if` 里：

```kconfig
# drivers\crypto\Kconfig 的最外层
if CRYPTO
source "drivers/crypto/Kconfig.esp32"
...
endif
```

**`if CRYPTO` 不成立，整个文件都不参与解析**，`default y` 也就无从生效。结果就是：dts 有节点、源码有驱动、Kconfig 写着 default y，编译却链接失败：

```
app/libapp.a(main.c.obj):(.literal.aes_ecb_block+0x8): undefined reference to `__device_dts_ord_46'
app/libapp.a(main.c.obj):(.literal.sha256_once$constprop$0+0x4): undefined reference to `__device_dts_ord_71'
```

修法只有一行（`applications\esp32s31\korvo_sys\prj.conf`）：

```conf
CONFIG_CRYPTO=y
```

> 这个错误的形态值得记住：**`__device_dts_ord_NN` 未定义 = "你引用了这个设备，但没有任何驱动为它 `DEVICE_DT_INST_DEFINE`"**。第 16 组第一篇踩过一次（`gpio-keys` 子节点），第 15 组踩过一次（`korvo_sys` 的 coretemp）。三次同一个签名、三个不同原因：子节点没有驱动 / overlay 没生效 / Kconfig 门没开。

### 第 3 层：算出来的字节对不对（KAT）

这一层才是真的"验证"。

## 三、Zephyr crypto API 是"会话式"的（和 mbedTLS 的直觉不一样）

很多人第一次看 `include\zephyr\crypto\crypto.h` 会懵：没有 `mbedtls_sha256(...)` 那种一把梭的接口，取而代之的是：

```
begin_session(dev, &ctx, algo)   ← 建会话：算法、模式、密钥、能力标志
        ↓
compute / block_op(&ctx, &pkt)   ← 干活：一次或多次，pkt 里放 in/out 缓冲
        ↓
free_session(dev, &ctx)          ← 释放：把驱动里的会话槽还回去
```

结构上分成两层：

```
你的 app
  │  struct hash_ctx  ← 会话参数（flags 由 app 填，drv_sessn_state 由驱动填）
  │  struct hash_pkt  ← 这一次的 IO（in_buf / in_len / out_buf）
  ▼
crypto.h 的 inline 封装（hash_begin_session / hash_compute）
  ▼
crypto_driver_api 的函数指针（驱动注册的那几个）
  ▼
crypto_esp32_sha.c → HAL → SHA 寄存器
```

三个"必须照驱动说的填"的地方，填错就是 `__ASSERT` 当场挂：

| 字段 | SHA 驱动要求 | AES 驱动要求 | 依据 |
|---|---|---|---|
| IO 缓冲 | `CAP_SEPARATE_IO_BUFS`（**不能** INPLACE） | INPLACE 或 SEPARATE 都行 | `crypto_esp32_sha.c:359` 返回 `CAP_SEPARATE_IO_BUFS \| CAP_SYNC_OPS` |
| 同步/异步 | `CAP_SYNC_OPS` | `CAP_SYNC_OPS` | 同上 |
| 密钥类型 | — | `CAP_RAW_KEY`（裸密钥） | `crypto_esp32_aes.c:74` |
| IV 前缀 | — | `CAP_NO_IV_PREFIX` | 同上 |

实测拿到的 hwcaps 能直接印证：

```
[sha] 设备=sha@6003b000 驱动 hwcaps=0x30
[aes] 设备=aes@6003a000 驱动 hwcaps=0x13a
```

`0x30` = `CAP_SEPARATE_IO_BUFS | CAP_SYNC_OPS`；`0x13a` = `CAP_RAW_KEY | CAP_INPLACE_OPS | CAP_SEPARATE_IO_BUFS | CAP_SYNC_OPS | CAP_NO_IV_PREFIX`。**先 `crypto_query_hwcaps()` 打印一遍，再填 flags**，比读源码猜快得多——这也是命令里第一行就打 hwcaps 的原因。

## 四、代码：两个命令，四个断言

### 4.1 `sys sha`——两次 KAT + 一次吞吐

```c
static int sha256_once(const uint8_t *in, size_t len, uint8_t *out)
{
	struct hash_ctx ctx = {
		.flags = CAP_SEPARATE_IO_BUFS | CAP_SYNC_OPS,   /* 照驱动 hwcaps 填 */
	};
	struct hash_pkt pkt = {
		.in_buf = in, .in_len = len, .out_buf = out,
	};
	int ret = hash_begin_session(sha_dev, &ctx, CRYPTO_HASH_ALGO_SHA256);

	if (ret != 0) {
		return ret;
	}
	ret = hash_compute(&ctx, &pkt);
	(void)hash_free_session(sha_dev, &ctx);   /* 失败也要还会话槽 */
	return ret;
}
```

两个 KAT 是故意的组合：

- `SHA-256("abc")` → `ba7816…15ad`：验证**普通消息 + 多轮压缩**。
- `SHA-256("")` → `e3b0c4…b855`：验证**空输入**。空输入是最容易写错的一条路——padding 长度、块边界、`in_len = 0` 时驱动会不会直接返回，全在这 0 字节里暴露。只测 "abc" 很可能会漏掉空消息分支。

吞吐测试用 16 KB 静态缓冲 × 循环次数，用**硬件周期**换算（不用 ms，1 ms 的粒度对 64 KB 太快了）：

```c
t0 = k_cycle_get_32();
for (int i = 0; i < loops; i++) { sha256_once(sha_buf, sizeof(sha_buf), sha_out); }
t1 = k_cycle_get_32();
bps = (uint64_t)bytes * sys_clock_hw_cycles_per_sec() / (t1 - t0);
```

### 4.2 `sys aes`——加、解、两种吞吐

NIST/FIPS-197 附录 B 的向量：

```
key = 000102030405060708090a0b0c0d0e0f
pt  = 00112233445566778899aabbccddeeff
ct  = 69c4e0d86a7b0430d8cdb78070b4c55a
```

```c
ret = cipher_begin_session(aes_dev, &ctx, CRYPTO_CIPHER_ALGO_AES,
                           CRYPTO_CIPHER_MODE_ECB, optype);
ret = cipher_block_op(&ctx, &pkt);      /* ECB 用 block_op，CBC 用 cbc_op */
(void)cipher_free_session(aes_dev, &ctx);
```

**加密算一遍对期望值，解密再把密文还原回明文**——两条路径都要过。只测加密的话，`decrypt` 分支（驱动里是另一套 handlér 和另一条 HAR 流程）完全是黑盒。

吞吐故意测**两种姿势**：

| 姿势 | 含义 |
|---|---|
| 每块开关会话 | 循环里 `aes_ecb_block()`，每次都 begin/free |
| 复用会话 | begin 一次 → N 次 `cipher_block_op()` → free 一次 |

## 五、实测原文（COM11，S3，`logs\serial-s3-sha.txt`）

构建：`FLASH: 147876 B / 8388352 B / 1.76%`（比加加密前的 145908 B 多 **1968 B**）。
`CONFIG_CRYPTO=y` 之后 0 warning。

```
=== Korvo-1 sys ===
sys info | sys temp 3 | sys rand 4 | sys dev
sys sha 8 | sys aes 1000（硬件加密，已知答案自检）

>>> sys sha 4
[sha] 设备=sha@6003b000 驱动 hwcaps=0x30
[sha] ab    = ba7816bf8f01cfea414140de5dae2223b00361a396177a9cb410ff61f20015ad
[sha] KAT("abc")   PASS
[sha] empty = e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855
[sha] KAT("")      PASS
[sha] 吞吐 65536 B / 468706 cyc = 33557581 B/s（约 32771 KB/s，4 次 × 16384 B）

>>> sys aes 2000
[aes] 设备=aes@6003a000 驱动 hwcaps=0x13a
[aes] 明文  = 00112233445566778899aabbccddeeff
[aes] 密文  = 69c4e0d86a7b0430d8cdb78070b4c55a
[aes] 期望  = 69c4e0d86a7b0430d8cdb78070b4c55a
[aes] KAT(encrypt) PASS
[aes] KAT(decrypt→明文) PASS
[aes] 每块开关会话：2000 块 / 2678449 cyc = 2867331 B/s（约 2800 KB/s）
[aes] 复用会话：    2000 块 / 1340634 cyc = 5728632 B/s（约 5594 KB/s）
[aes] 结论：会话开关本身比一次块运算还贵，高频小块要用长会话
```

### 读数怎么解释

- **33.5 MB/s 的 SHA**：S3 主频 240 MHz，`468706 cyc` 处理 64 KB ≈ 1.95 ms。硬件 SHA 每周期能吃多个字节，所以速率远超 CPU 逐字节软件实现（软件 SHA-256 在 240 MHz 上典型只有几 MB/s）。这不是"优化了"，是**换了个执行单元**。
- **AES 复用会话 5.6 MB/s，每块开关 2.8 MB/s**：正好 2 倍。说明 `begin/free` 的开销 ≈ 一次 16 B 块运算的耗时。这个数字很反直觉（直觉上"建会话"应该很便宜），原因是驱动每次 begin 都要：申请会话槽 → 配寄存器 → 展开密钥（AES key schedule 是 10 轮运算）。**所以"小块高频"场景（比如逐包加密的 BLE/Matter 帧）必须复用会话**，否则一半时间花在钥匙上。
- **两个 hwcaps 值**：`0x30` / `0x13a`，和上一节的表对得上——这就是"驱动自述能力"的意义：不用读源码，程序自己告诉你该怎么填 flags。

## 六、坑表（本篇新增）

| # | 坑 | 症状 | 判据 / 修法 |
|---|---|---|---|
| 1 | 以为 `CRYPTO_ESP32 default y` 就够了 | 链接期 `undefined reference to __device_dts_ord_46/71` | `drivers\crypto\Kconfig` 整个被 `if CRYPTO` 包住 → `prj.conf` 加 `CONFIG_CRYPTO=y` |
| 2 | 照 mbedTLS 的直觉找"一把梭"接口 | 找不到 `crypto_hash_sha256()` 这种函数 | Zephyr crypto 是**会话式**：begin → compute/op → free |
| 3 | SHA 用 INPLACE 缓冲 | `hash_begin_session` 里 `__ASSERT(flags != 0)` 挂 | SHA 驱动只给 `SEPARATE_IO_BUFS`；先 `crypto_query_hwcaps()` 再填 |
| 4 | 拿 ms 算吞吐 | 数字全是 0 或抖得没意义 | 用 `k_cycle_get_32()` + `sys_clock_hw_cycles_per_sec()` |
| 5 | 只测 `SHA("abc")` | 空输入分支的 bug 测不出来 | 加 `SHA("")` 这条 KAT |
| 6 | 小块高频也每块开关会话 | 吞吐只有一半 | 复用会话（本篇实测 2x 差距） |
| 7 | shell 里 `snprintf` 拼 hex 用 80 字节缓冲 | 摘要最后 1–2 个字符被截断 | 缓冲留够（本篇改 128，且判据用 `sizeof - 3`） |

## 七、和 Korvo-1（ESP32-S31）的关系

| | Korvo-1 | ESP32-S3 最小板 |
|---|---|---|
| aes / sha 节点 | 需要确认（第 17 组待勘） | `esp32s3_common.dtsi` 里 okay |
| 驱动 | `crypto_esp32_*.c` 同一份 | 同一份 |
| Kconfig | `CONFIG_CRYPTO=y` 同样必须加 | 同样 |
| 代码 | `cmd_sha` / `cmd_aes` 一字不改 | 一字不改 |
| 验收 | KAT 同样 PASS 才算通 | KAT PASS |

**这里体现的正是"跨芯片可迁移"的正确形态**：应用层只依赖 `zephyr,crypto` 这套 API 和 `DT_NODELABEL(sha)`，换芯片只换 dts 与 Kconfig 门，业务代码零改动。

一个诚实的边界：**S31 上的 AES/SHA 还没实测**。本篇只验证了 S3。Korvo-1 不在线，`korvo_sys` 在 S31 上的加密命令要等下次上板再补——所以这一节写的是"应该一样"，不是"已经一样"。
