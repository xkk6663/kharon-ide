# 17.6 OTA 断点续传：段锚点 + 回读校验

> 这是 `embedded-ota-pipeline` 里的**可选档**，本工程做它的理由很具体：
> 830 KB 的镜像在 50 KB/s 下要传 ~17 s，只要中途断一次，之前的全白费。
>
> 本篇按"约束 → 设计 → 协议 → 实机数据 → 踩过的坑"讲。

## 1. 核心约束：哈希是流式的，跨重启不能"续累积"

这是整个设计的起点：

- 正常全量下载时，整包 SHA-256 与写入**同序**累积，零额外 IO；
- 但一旦进程重启/连接断开，那个哈希上下文就没了。**不可能**"上次算到 40%，这次接着算"——
  数据不是连续的，上下文也不是可序列化的。

所以只剩两条路：

| 策略 | 代价 |
|---|---|
| A. 续传后**回读**已写区间重算 | 1–2 s 回读（本机实测 225 ms / 256 KB） |
| B. 放弃整包摘要，只信启动前镜像校验 | 丢掉 S2 的"是不是我批准的那个文件" |

本工程选 A，并加段锚点把"断在哪"精确到 256 KB。

## 2. 断点记录：`struct rb_rec`（NVS 键 `s3ota/rb`）

```c
#define RB_MAGIC 0x52415442u        /* "RATB" */
#define RB_SEG   (256u * 1024u)
#define RB_MAXSEG 6

struct rb_rec {
    uint32_t magic;
    uint32_t total;                  /* 整包大小 */
    uint32_t ver;                    /* 目标版本 */
    uint32_t rw;                     /* 已确认写入偏移（段边界） */
    uint32_t seg_done;               /* 已完成段数 */
    uint8_t  sha[32];                /* 期望整包摘要 */
    uint8_t  seg[RB_MAXSEG][32];     /* 每段摘要 */
};                                   /* ≈248 B */
```

设计取舍：

- **只落段边界**：`rw` 永远是 `seg_done * RB_SEG`。段内断掉就回退到上一段边界重写，
  最多丢 256 KB（约 5 s）。这比"记录任意偏移"省掉一整套一致性难题。
- `RB_MAXSEG 6` × 256 KB = 1536 KB，刚好盖住槽上限（1344 KB）。
- 记录里存**期望摘要**，不存"已算出的摘要"——后者跨重启不可信。

## 3. stale 校验：`rb_check()`

加载/使用前必须逐条过：

1. `magic` 对不对；
2. `total` 是否等于本次请求的 size；
3. `ver` 是否等于本次请求的版本；
4. 期望 `sha` 是否等于本次 `X-Sha256`；
5. `rw` 是否对齐到 `RB_SEG`；
6. `seg_done` 是否 ≤ `RB_MAXSEG` 且与 `rw` 自洽。

任一条不符 → 丢记录、走全量，并打日志：

```
resume requested but record unusable, fallback to full
```

## 4. 续传握手（向后兼容，协议版本不变）

`OTA_PROTO_VER` 仍是 2：**不带 `X-Resume` 的旧端行为完全不变**。

```
客户端: POST /ota  … + X-Resume: 1        （先只发头，不发 body）
设备  : 有可用记录 → 206 Partial Content
                     X-Resume-Offset: <rw>
                     Connection: keep-alive
        无可用记录 → 200 {"resume":0}
           （客户端收到 200 就按全量发）
设备  : 回读 [0, rw) 复算段摘要，逐段比对记录 → 打
        resume accepted: off=… seg=… (readback verified, …ms)
```

握手阶段设备做的事（`rb_readback_verify()`）：

- `flash_area_read()` 按 4096 B 分块读 `[0, rw)`；
- 每 256 KB 收一段 `setup/update/finish`，与 `g_rb.seg[]` 逐段比；
- 同时把这些字节**喂进整包哈希** `g_hseg`，这样续传结束后整包摘要仍然闭合；
- `img_start` 用 `g_fctx.stream.offset - g_fctx.flash_area->fa_off` 动态反推，
  不写死 4 KB —— 原因见 17.7（OFFSET 模式的特殊基址）。

为什么必须回读而不能"信记录"：记录在 NVS、镜像在 image 槽，**两个区域掉电不同步**。
可能出现"记录说写了 512 KB，实际只落了 400 KB"。回读是唯一便宜的真相来源。

## 5. 把流状态复位对（这里差一点写出致命 bug）

续传开始时三个字段必须同步设：

```c
g_fctx.stream.bytes_written = off;
g_fctx.stream.erased_up_to   = off;   /* 关键：不设会重新擦掉已写好的开头 */
g_fctx.stream.buf_bytes      = 0;
```

`erased_up_to` 漏设的后果：写第一块时按"从 0 开始"再擦一遍扇区，把刚回读校验过的数据擦掉 ——
**校验通过、下载成功、启动变砖**，而且日志里一切正常。这种 bug 只能靠"回读后再校验一次"和
"续传完做整包摘要"两层兜住。

吞吐打点的分母也换成增量：

```c
clen = expect_size - start_off;   /* 不是整包 size，否则续传吞吐虚高 */
timing dl=… verify=… total=… throughput=… size=… resumed=1 off=262144
```

`verify` 里把回读 + 回读校验的耗时（`t_rb`）一起算进去，否则会低估续传成本。

## 6. 实机验收（完整证据链）

### 6.1 造断点

```powershell
& "$root\.venv\Scripts\python.exe" "$root\tools\ota_drop.py" 10.168.1.226 "$root\build\esp32s3\s3ota\fw_v112.signed.bin" --version 112 --drop-bytes 400000
```

设备侧（串口）：

```
resume checkpoint: seg=1 off=262144
ota fail: peer closed mid-transfer (short body) (errno -104)
```

`400000` 落在第 2 段中间 → 记录只认到 `262144`（段边界），这就是"最多丢 256 KB"的体现。
**失败会保留记录**，这是设计（用户主动取消才算放弃）。

### 6.2 续传

```powershell
& "$root\.venv\Scripts\python.exe" "$root\tools\ota_push.py" 10.168.1.226 "$root\build\esp32s3\s3ota\fw_v112.signed.bin" --version 112 --resume
```

上位机：

```
resume  : 设备接受续传，从 262144 / 859460 (30%) 开始
  sent …          # 只发剩余 597316 B
--- client side: 11.79 s, 49 KB/s ---
device accepted: image written + sha256 verified + upgrade flag set
```

设备侧串口原文（`logs\serial-resume-run.log`）：

```
resume accepted: off=262144 seg=1 (readback verified, 225 ms)
ota start: ver=112 size=859460 nonce=6 force=0 resumed=1 off=262144
resume checkpoint: seg=2 off=524288
resume checkpoint: seg=3 off=786432
expected-sha256 MATCH (07bcae10…)
timing dl=11286 verify=- total=- throughput=51KB/s size=859460 resumed=1 off=262144
whole-sha256 MATCH (859460 bytes)
timing dl=11286 verify=661 total=11979 throughput=48KB/s size=859460 resumed=1 off=262144
ota ready: slot1 written + verified, upgrade flag set
```

三个关键点：

- `resumed=1 off=262144`：续传被真的接受；
- `whole-sha256 MATCH`：回读 + 增量累积拼出的整包摘要闭合 —— 说明回读那 256 KB 与后续数据接上了；
- 回读只花 225 ms，相对于 11.8 s 的下载可以忽略。

### 6.3 重启生效

```powershell
& "$root\.venv\Scripts\python.exe" "$root\tools\ota_reboot.py" 10.168.1.226 8080 --key <REDACTED-PSK>
```

`/api/status`：

```json
"ota":{"local_ver":112,…}   "boot":{"n":29,"clean":true,"rst":"software"}
```

### 6.4 记录是否已清

升级成功路径调了 `rb_clear()`。验证方式：带 `X-Resume: 1` 只发头，看回 206 还是 200。

```powershell
& "$root\.venv\Scripts\python.exe" "$root\tools\ota_resume_probe.py" 10.168.1.226 "$root\build\esp32s3\s3ota\fw_v112.signed.bin" 112 force
```

```
HTTP/1.1 200 OK
结论: 无可用记录（升级成功后已清空 → 正确）
```

为什么脚本要第 4 个参数 `force`：版本门禁在握手之前（17.5 第 3 节），同版本探测不带 force 会先吃 409。

## 7. 踩过的两个坑

### 7.1 `g_rb_valid` 没置真 → 握手永远回 200（同一运行期内）

第一次实现时，续传握手**恒回 `200 resume:0`**，即使刚造完断点。

根因：新建记录时只写了 `g_rb` 的字段，**没有** `g_rb_valid = true`。该标志原本只在
"从 settings 加载"时置真，于是同一运行期内 `rb_check()` 永远为假。

修法：建记录处 + `seg_feed()` 落记录处都补 `g_rb_valid = true`。

教训：这类 bug 的表现是"功能整体不生效"，很容易被误判成"协议写错了"。

### 7.2 验证时忘了"板子跑的还是旧固件"

第二次测试仍回 200，当时以为还有 bug。真实原因：修复只编进了 **slot1**，
板子还在跑 slot0 的旧代码。**必须先进新固件再测新逻辑**。

正确顺序：旧固件 → 全量推新版 → 重启 → 新固件 → 造断点 → 续传 → 重启验证。

## 8. 边界与未做

- 服务端忽略 Range 直接回 200 的情形已处理（按全量）；
- **没有**做"续传记录与版本无关地跨版本复用"：`ver` 变了直接丢记录；
- **没有**做断电掉电测试（`references\acceptance.md` 里的 P0 项还没跑）；
- 一次只允许一个 OTA 会话（`:8080` 是单线程），续传期间别人连不上。
