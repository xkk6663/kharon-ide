# 17.3 SNTP 对时与 HTTP 出网自检

> 这两件事解决同一个疑问：**"板子是真连上网了，还是只连上了路由器？"**
> 前者要能解析 DNS、能出公网、能对时；后者只要 AP 给了 IP 就算"已连接"。

## 1. 为什么配网门户一定要有"出网自检"

`state:"connected" + ip:"10.168.1.x"` 只证明四件事：扫描到 AP、关联成功、DHCP 拿到地址、ARP 通。
它**不证明**：

- 路由器有没有真的把包转出去（上游断了、需要 Web 认证的热点）；
- DNS 能不能解析（很多"连上了但网页打不开"就是这个）；
- 板子的时钟对不对（TLS 握手、证书校验、日志时间戳都依赖它）。

所以 `/api/status` 里单独给了三组字段：`netcheck/netrc/netdone`、`dns/dnsip`、`sntp/sntpsrv`。

## 2. DNS 自检

做法：连上之后主动解析一个固定域名（本项目用 `captive.apple.com`，它同时被 captive 检测用），
把结果记进 `dns`（0 成功）/`dnsip`（解析到的地址）。

串口实测：

```
[00:00:06.231,000] <inf> portal: dns self-test: captive.apple.com -> 192.168.4.1
```

注意这里解析到 `192.168.4.1` —— 那是因为板子自己是 DNS 劫持者（captive portal 需要），
在 **AP 模式**下这是预期行为。STA 模式下应该解析到公网地址（实测 `dnsip:"203.107.6.88"`）。
看日志时先确认当前是哪种模式，别把 captive 劫持当成"DNS 坏了"。

## 3. HTTP 出网自检

做法：用 Zephyr 的 HTTP client 发一个 GET，把返回状态码记进 `netcheck`，整段耗时记进 `netrc`（ms），
成功一次后 `netdone=1`，不再重复跑。

串口实测：

```
[00:00:06.222,000] <inf> portal: self-test: GET /generate_204 -> "HTTP/1.1 302"
```

返回 302 是正常的：这类探测地址在"需要登录的热点"上就是返回重定向。
判据应该写成 **"拿到了一个合法 HTTP 响应"**，而不是"必须 200"。

一个踩过的坑：`CONFIG_HTTP_CLIENT_BUFFER_SIZE` 这个配置项在本版树里**不存在**，
想调缓冲要去看 `CONFIG_HTTP_CLIENT_*` 的实际符号，别凭记忆写。

## 4. SNTP 对时

- 客户端在连上 STA、拿到 IP 后启动，成功后 `/api/status` 里 `sntp=0`，`sntpsrv` 显示对时服务器。
- 页面上直接显示 `clock:"18:05:32"`，和 17.1 里的状态条同一行。
- 对时**不影响 OTA 的防重放**：OTA 只靠 nonce 严格递增，不靠时间新鲜度。
  原因很实在 —— 板子不保证每次开机都已完成对时，用时间窗会冒出无法解释的 `stale`。
  这条与 `embedded-ota-pipeline` 的 `security.md` 一致：「时间新鲜度仅在设备时钟可信时启用」。

## 5. 验收

```powershell
& "$root\.venv\Scripts\python.exe" -c "import json,urllib.request;d=json.load(urllib.request.urlopen('http://10.168.1.226/api/status?k=<REDACTED-PSK>',timeout=10));print('clock',d['clock'],'netcheck',d['netcheck'],'dns',d['dns'],d['dnsip'],'sntp',d['sntp'],d['sntpsrv'])"
```

判据：

| 字段 | 正常值 | 异常时先查什么 |
|---|---|---|
| `clock` | 与手机时间接近 | SNTP 没起来 / UDP 123 被墙 |
| `netcheck` | 200/204/302 之类合法码 | 路由器上游、热点认证 |
| `netrc` | 几十到几百 ms | 特别大说明链路差 |
| `dns` | 0 | DNS 没解析成功；确认不是在 AP 模式下看 |
| `sntp` | 0 | 服务器地址、UDP 是否被拦 |
