# 17.7 Flash 布局与 mcuboot 换槽（4 MB / ESP32-S3）

> 这一篇回答两个问题：**"双分区是谁画的？"** 和 **"换槽到底用的哪种模式？"**
> 两个问题的答案都和"想当然"不一样，而且都影响 OTA 代码（尤其续传的回读基址）。

## 1. 真实分区表（从构建产物读出来，不是抄文档）

来源：`zephyr\dts\vendor\espressif\partitions_0x0_amp_4M.dtsi`，
实际生效值可在 `build\esp32s3\s3ota\s3_wifi_portal\zephyr\zephyr.dts` 里核对。

| 分区 | 偏移 | 大小 | 用途 |
|---|---|---|---|
| `mcuboot` | `0x0` | 64 KB | bootloader |
| `sys` | `0x10000` | 64 KB | 系统参数 |
| `image-0` | `0x20000` | **1344 KB** (`0x150000`) | 主镜像槽 |
| `image-1` | `0x170000` | **1344 KB** (`0x150000`) | OTA 镜像槽 |
| `image-0-appcpu` | `0x2c0000` | 448 KB | 协处理器镜像 |
| `image-1-appcpu` | `0x330000` | 448 KB | 协处理器镜像 |
| `image-0-lpcore` | `0x3a0000` | 32 KB | LP 核心 |
| `image-1-lpcore` | `0x3a8000` | 32 KB | LP 核心 |
| `storage` | `0x3b0000` | 192 KB | NVS（口令 / nonce / 断点 / WiFi 凭据） |
| `coredump` | `0x3ff000` | 4 KB | 崩溃现场 |

**没有 scratch，没有 otadata。** 双槽是板级分区表自带的，本工程一行分区代码都没写。

这条很值得记住：看到"我有双分区"就以为"我做了双分区方案"，其实是板级 dts 送的。
要改槽大小，改的是分区表 dtsi，不是 `ota.c`。

## 2. 换槽模式：写的是 MOVE，编进去的是 OFFSET

这是本轮最有价值的一次"证据对账"。

### 2.1 现象

`applications\esp32s3\s3_wifi_portal\mcuboot.conf` 里明明写着：

```conf
CONFIG_BOOT_SWAP_USING_MOVE=y
```

但构建产物里：

```
CONFIG_BOOT_SWAP_USING_OFFSET=y
CONFIG_BOOT_SWAP_USING_MOVE is not set
CONFIG_BOOT_SWAP_USING_SCRATCH is not set
```

即**整份文件都没生效**。

### 2.2 证据链

1. 构建系统里 mcuboot 这一层的 `CMakeCache.txt`：

   ```
   CONF_FILE = boot/zephyr/prj.conf ; socs/esp32s3_procpu.conf
   ```

   —— 里面**没有** app 的 `mcuboot.conf`。`mcuboot.conf` 只对"把 mcuboot 当主工程编"的情形有效。

2. 真正说话的是 sysbuild 强制写入的文件：

   ```
   FORCED_CONF_FILE = build\...\mcuboot\zephyr\.config.sysbuild
   ```

   内容含 `OFFSET=y / MOVE=n / SCRATCH=n / UPGRADE_ONLY=n / PREFER_MOVE=y / SIGNATURE_TYPE_RSA=y`。

3. 根因在 sysbuild 自己的 Kconfig 默认值：

   ```
   west\zephyr\share\sysbuild\images\bootloader\Kconfig:33-46
   choice MCUBOOT_MODE  →  默认 SWAP_USING_OFFSET
   ```

4. 旁证：同一个文件里写 `MCUBOOT_LOG_LEVEL_INF=y`，实际编出 `CONFIG_MCUBOOT_LOG_LEVEL_OFF=y`
   （值是 soc fragment 的）。整份文件都在"看起来生效、实际没生效"的状态。

### 2.3 修正（行为不变，只把真相写进配置）

- `sysbuild.conf` 加显式项 + 证据注释：

  ```conf
  # 换槽模式只能在 sysbuild 层决定；改 mcuboot.conf 无效（见 docs 17.7）
  SB_CONFIG_MCUBOOT_MODE_SWAP_USING_OFFSET=y
  ```

- `mcuboot.conf` 整份重写成说明文件：本文件在此树不生效 + 真正的开关在哪 + 怎么核对。
- 重编 rc=0，镜像 858628 B 未变 —— 证明"只是把隐式默认显式化"。

## 3. OFFSET 模式对代码的两个硬影响

### 3.1 镜像从槽的**第二个扇区**开始写

`zephyr\subsys\dfu\img_util\flash_img.c` 在 `CONFIG_MCUBOOT_BOOTLOADER_MODE_SWAP_USING_OFFSET` 下：

```c
fa_off + fs_size      /* fs_size = 4 KB，即从槽基址 + 一个扇区起写 */
```

并且要求**第一个扇区为空**。`flash_img_check()` 里的 `fac.off` 用
`boot_get_image_start_offset()`，与写入基址保持一致。

所以"镜像在槽里的起始偏移 = 槽基址 + 4 KB"。这就是 17.6 里回读基址要这么算的原因：

```c
img_start = g_fctx.stream.offset - g_fctx.flash_area->fa_off;
```

写死 `+4096` 也能跑，但一旦换模式就静默错位 —— 动态反推更安全。

### 3.2 bootloader 日志默认看不到 swap 决策

实际编译值 `CONFIG_MCUBOOT_LOG_LEVEL_OFF=y`，所以串口里能看到的：

```
<inf> mcuboot_util: Image index: 0, Swap type: none
```

这行是 **app 侧** mcuboot 模块打的，不是 bootloader 打的。别把它当成"bootloader 选择了不换槽"。

判断"换槽到底成没成"，用应用层证据：

- `/api/status` 的 `ota.local_ver` 变了；
- `boot.rst:"software"` + `clean:true`；
- 串口启动段的 `local_ver 112`。

## 4. 为什么"没有自动回滚"是这套布局的结构性结果

| 条件 | 现状 |
|---|---|
| 是否进自证窗口 | 否，`BOOT_UPGRADE_PERMANENT` 直接转正 |
| 能否写运行槽 trailer | 否，XIP，`boot_write_img_confirmed()` 恒 -5 |
| 有 scratch 分区吗 | 没有（所以只能用 OFFSET/MOVE 这类原地搬） |
| 掉电时谁保证一致 | 没有任何保证，靠 S2 阻断坏包 |

结论（与 17.5 第 6 节一致）：**能升，不能自动回**。要真回滚，得改 mcuboot 策略 + 处理 XIP
写 trailer 的限制，属于独立课题。

## 5. 自己核对这套东西的三条命令

```powershell
# 1. 看实际生效的分区
Select-String -LiteralPath "$root\build\esp32s3\s3ota\s3_wifi_portal\zephyr\zephyr.dts" -Pattern "image-0|image-1|storage|coredump" | Select-Object -First 12

# 2. 看 mcuboot 真实配置
Select-String -LiteralPath "$root\build\esp32s3\s3ota\mcuboot\zephyr\.config" -Pattern "BOOT_SWAP_USING|MCUBOOT_LOG_LEVEL|SIGNATURE_TYPE"

# 3. 看谁强制了这些值
Select-String -LiteralPath "$root\build\esp32s3\s3ota\mcuboot\zephyr\.config.sysbuild" -Pattern "SWAP_USING|MCUBOOT_MODE"
```

判据：`.config` 是"编进去的"，`.config.sysbuild` 是"sysbuild 强加的"，
`mcuboot.conf` / `prj.conf` 只是"申请"。三者不一致时，**以 `.config` 为准**。
