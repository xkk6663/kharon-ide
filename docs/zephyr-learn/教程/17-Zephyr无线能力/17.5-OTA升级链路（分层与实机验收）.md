## 2. 协议：一个 POST，三个必填 + 一个有条件的头

```
POST /ota  HTTP/1.1
Host: <ip>
Content-Length: <size>
X-Version: 112
X-Nonce: 6
X-Force: 0
X-Sha256: <hex>
X-Auth: <hex>            # HMAC-SHA256
X-Resume: 1              # 可选，见 17.6
```

`X-Auth` 的规范化串（**两端逐字一致**，这是 S3 最容易翻车的地方）：

```
"%u|%u|%s|%u|%d"  →  ver|size|sha256|nonce|force
```

重启请求用另一个串：`"reboot|<nonce>"`。

判据：

- 字段顺序固定、`|` 分隔、不 trim、不大小写归一；
- `force` 归一成 `0/1` 数字（C 侧用 `atoi`，Python 侧用 `int(bool)`，两边是同一种语义）；
- 长度上界固定（`OTA_HDR_MAX 1536`），超长直接拒，不截断 —— 截断会算出一个"合法"的错误摘要。

## 3. 门禁顺序（每一步对应一个拒绝码）

这是实机验证过的顺序，**顺序本身是设计**：

1. 缺 `X-Version`/`X-Sha256` → `400 ERR missing header: …`
2. 鉴权失败 → `401 ERR auth failed`
3. 体积超槽 → `413 ERR image too large for slot`
4. nonce 不递增 → `403 ERR nonce replay (last=…)`
5. 版本未变新且未 force → `409 ERR version X not newer than Y`
6. 然后才是续传握手（17.6）

实测记录（`logs\ota-gate-probe.log` / `logs\ota-auth-probe.log`）：

| 请求 | 响应 |
|---|---|
| 不带 `X-Sha256` | `400 ERR missing header: X-Sha256` |
| 不带 `X-Auth` | `401 ERR missing auth header` |
| 同 nonce 重发 | `403 ERR nonce replay` |
| 版本相同、无 force | `409 ERR version 112 not newer than 112` |
| 全部正确 | `200 {"ok":true,"reboot":false}` |

为什么门禁放在握手之前：**未授权或降级的请求，连"设备有没有断点"都不该被告知**。
副作用是：想用探测脚本验"断点记录是否已清"，同版本必须带 `force`（见 17.6 第 6 节）。

## 4. 完整升级流程（代码怎么跑）

```
遇到 POST /ota
  → 解析头 + 校验（上面 6 步）
  → (可选) 续传握手，得到 start_off
  → 打开 slot1：flash_img_init()
  → 循环 recv：攒 OTA_CHUNK，满一块 → 段哈希 + 整包哈希 + 按扇区写
  → 收满 size：expected-sha256 比对（不符 → fail，不切槽）
  → flash_img_check()：镜像格式自校验
  → boot_request_upgrade(BOOT_UPGRADE_PERMANENT)
  → 打 timing，返回 200 {"ok":true}
```

几个必须记住的实现点：

- **哈希是流式的**：`psa_hash_setup/update/finish`，与写入同序累积，零额外 IO；
- 失败路径要 `psa_hash_abort(&g_hseg)`，否则下一次请求会拿到脏上下文；
- `boot_request_upgrade` 之后立刻 `rb_clear()`（有断点记录时必须清，见 17.6）；
- `g_ota.st` 只在 `RECV`/`VERIFY` 阶段翻 `fail`：`ready` 是"镜像已校验待重启"，
  不能被一个乱发的探测请求改成 `fail`。

## 5. 打点与实测数据

### 5.1 页面驱动的真浏览器升级（2026-11-16，v126 → v127）

串口/接口都验过之后，最后一步是**用页面自己点一次**。上一版卡在"产品内置浏览器与局域网隔离"，
这一版换成桌面 Chrome（局域网可达）：

| 步骤 | 现场 |
|---|---|
| 打开 `http://10.115.126.239/?k=<REDACTED-PSK>` | 开发者台，`已连接 / Power / 10.115.126.239` |
| 选文件 | `fw_v127.signed.bin`（869140 B，`1.127.0.0`） |
| 点「上传」 | JS `prompt` 问版本，默认 `127` |
| 传输 | `板端 126 · 待装 127`、`recv94% (821178/869140 B)` |
| 完成 | `slot1 已写入：期望摘要 + Flash 回读都通过（22.8 s，sha=54314c077bda…）`、`ready100%` |
| 切槽 | 页面同一个接口 `POST :8080/api/ota/reboot` → 约 22 s 后 `/api/status` 返回 `local_ver=127` |

截图：`img-ota-page-lan-success.png`（本目录）。这条证据的意义不只是"能点"，而是
**页面用纯 JS 算的整包 SHA-256 和设备端流式 SHA 逐字节一致**，S2 的闭环在真实浏览器里成立了。

另外，`:8080` 现在按来源判身份：AP 侧直接**拒绝连接**（不是拒绝请求），
避免手机白传 850 KB、也避免半截固件写进备用槽。详见
[17.10 第 7 节](17.10-页面受众分离（用户配网页与开发者台）.md)。

### 5.2 打点原文与读法

串口原文（v112 全量升级）：

```
ota start: ver=112 size=859460 nonce=6 force=0 resumed=0 off=0
expected-sha256 MATCH (07bcae10…)
timing dl=11286 verify=661 total=11979 throughput=48KB/s size=859460 resumed=0 off=0
whole-sha256 MATCH (859460 bytes)
ota ready: slot1 written + verified, upgrade flag set
```

读法（`references\pipeline.md` 的判据表）：

- `dl/total = 11286/11979 ≈ 94%` → **链路主导**，继续调 Flash 没意义；
- 想再快就动传输层（chunk / 窗口 / NODELAY），不是动擦写；
- `verify` 只有 661 ms（本机 FLASH 读回很快），所以 `resumed` 场景的回读成本也可以接受。

## 6. 回滚：诚实地说没有

- `boot_request_upgrade(BOOT_UPGRADE_PERMANENT)`：直接永久转正，**不进自证窗口**；
- `ota_confirm_if_healthy()` 是空实现；
- `boot_write_img_confirmed()` 恒返回 -5：ESP32 是 XIP，写"运行中的槽"的 trailer 会 -EIO。

结论：**升级失败不会自动回退**，只能再 OTA 一版旧固件。要真回滚得改 mcuboot 的
`PREFER_*` 策略并处理 XIP 限制，属于下一步，不是现在。

缓解措施（已经在做的）：切槽前必须过 S2（整包摘要 MATCH）+ 镜像自校验，
所以"坏包被切上去"这条路基本堵住了；剩下的是"镜像能启动但业务坏了"这种，理论风险仍在。

```powershell
& "$root\.venv\Scripts\python.exe" "C:\Users\xiao1\.workbuddy\skills\embedded-ota-pipeline\scripts\check_fw_size.py" "$root\build\esp32s3\s3ota\fw_v112.signed.bin" --slot 0x150000 --margin 0x10000
```

注意 `--slot` 用的是**槽大小 0x150000**（1344 KB），不是整个 Flash。

## 9. 归属：为什么 `X-Key` 和 `X-Auth` 两个入口

- 页面（浏览器里算 HMAC 麻烦）走 `X-Key: <口令>`；
- 脚本走 `X-Auth`（HMAC）。
两条都在 401 那道门里收口，属于开发期便利，量产应只留 HMAC + 真正密钥体系。
