# 17.8 故障排查实录（栈溢出、编译内存、几个"假 bug"）

> 这一篇按"现象 → 排查路径 → 根因 → 修法"写，都是本项目真实发生过的。
> 排障的价值不在结论，而在**下次遇到同类现象时先查哪一步**。

## 1. Telnet 一连就卡死：其实是 LED 线程栈溢出

### 现象

TCP 三次握手成功，然后**板子整个卡死**（页面打不开、串口也不出东西），不是"Telnet 连不上"。

### 排查路径（这次的关键是"先看串口，再连 Telnet"）

1. 串口监视先跑起来（`tools\zephyr\serial_monitor.py COM11 115200`，`dsrdtr=False`），
   落盘到 `logs\serial-*.log`；
2. 从另一台机器/脚本连 `telnet 10.168.1.226 23`；
3. 串口里看到的是**栈溢出诊断**（`fatal error: stack overflow`），不是 Telnet 的错。

### 根因

LED/WS2812 驱动那条线程的栈开得太小，平时勉强够用；一旦多出一个 Telnet 会话（
shell 后端 + 网络栈都要占栈），调度切到这条线程时就踩穿。
换句话说：Telnet 只是**触发者**，不是原因。

### 修法

把 LED 线程栈调大（`K_THREAD_DEFINE` 的栈尺寸参数），之后 Telnet 稳定。
串口证据留在 `logs\serial-led-fix.log`。

### 结论（值得背下来的那条）

> 网络"卡死"先查**栈和内存**，别先怀疑 TCP。
> Zephyr 的栈溢出诊断会打 `fatal error: stack overflow`，但要能看到它 ——
> 所以"先串口监视、再连远端"这个顺序不能反。

## 2. 编译反复失败、还"累计内存不清理"

### 现象

`west build` 到一半失败，重跑还是失败；关掉终端再开能过一次，之后又不行。
体感像"编译器内存越用越多"。

### 真相

不是编译器泄漏，是 **Windows 侧的 commit 内存不够**：Zephyr 的构建在
`--sysbuild` 下会并发起很多 cc1（每个都是独立进程），每个 cc1 加上 CMake、
ninja、python 的常驻，一起顶到系统 commit 上限。**上一个进程组的残留**（失败的
ninja/cc1 没退干净）会让下一次更难成功。

### 处置

| 做法 | 效果 |
|---|---|
| 把并发降到 6（`CMAKE_BUILD_PARALLEL_LEVEL=6`） | 稳定通过 |
| 失败后确认没有残留 cc1/ninja 进程 | 否则重跑等于叠罗汉 |
| 日志全量落盘再 grep（`*> logs\build-xxx.log`） | 看真正的第一条 error，不被后续噪声带跑 |

本项目固定用法：

```powershell
$root = "C:\Users\xiao1\Desktop\ELAB\kharon-ide"
. "$root\env.ps1"; $env:CCACHE_NOCOMPRESS = "1"; $env:CMAKE_BUILD_PARALLEL_LEVEL = "6"
& "$root\.venv\Scripts\west.exe" build --sysbuild -b "esp32s3_devkitc/esp32s3/procpu" -d "$root\build\esp32s3\s3ota" "$root\applications\esp32s3\s3_wifi_portal" *> "$root\logs\build-112.log"
```

顺便澄清三个"写错参数"的坑：

- `west build -t configure` 这个 target **不存在**；
- `west build ... -j N` 是错写法，并发走环境变量；
- `--sysbuild` 必须显式写，否则 mcuboot 那一层不会按预期生成。

### 为什么"别的编译器不这样"

GCC/Clang 单进程编译时内存是**峰值高、占用短**；这里是**大量并发进程同时峰值**，
而且 Windows 的 commit 计费比 Linux 更严格（overcommit 策略不同）。
所以同样的机器编 Linux 内核没事，编 Zephyr sysbuild 会卡 —— 是并发模型差异，不是编译器坏。

## 3. `mcuboot.conf` 写了不生效（配置层面的"假 bug"）

现象：改了 `mcuboot.conf`，行为没变化。
根因与证据链见 17.7 第 2 节。这里只留一条操作规则：

> 改配置后，**去 `.config` 里 grep 你改的那个符号**，确认它真的变了。
> 只改了源文件就当生效，是这个项目里最贵的一类时间浪费。

## 4. `.ota_nonce` 被写成带 BOM 的 UTF-8

### 现象

脚本读 nonce 报 JSON 解析失败 / 第一次字符不是数字。

### 根因

旧版 PowerShell 的 `Set-Content -Encoding utf8` 会写 BOM。Python 的 `json.load`
遇到 BOM 会报 `Unexpected UTF-8 BOM`。

### 修法

- 写入用无 BOM（pwsh 7 的 `-Encoding utf8` 已经不带 BOM，或直接 `[IO.File]::WriteAllText`）；
- 读取统一 `encoding="utf-8-sig"`，两种都能吃。

## 5. 页面里的 SHA-256 和 Python 算的不一样

页面要在浏览器里算整包摘要（OTA 上传前）。早期用了一份手写 JS，结果和
`hashlib.sha256` 对不上。

修法：写 `tools\sha_golden_test.py` + 用 node 跑同一段 JS，对**空串 / "abc" / 真实固件**
三组逐字节比对，过了才继续。这就是 skill 里说的 "跨语言 golden vector" 的必要性。

遗留：这条**纯 JS 实现还没有在真浏览器里点过一次完整 OTA**（产品浏览器与局域网隔离），
目前只有 node + python 的等价性证明。

## 6. 串口日志文件读不出来（进程占用）

### 现象

`Get-Content` 返回空、`[IO.File]::ReadAllText` 报 IOException "正由另一进程使用"。

### 根因

`serial_monitor.py` 运行期间以独占方式持有日志文件。

### 修法

先停监视任务（`TaskStop`），再读文件。想边跑边看，就让监视脚本自己 tee/滚动写多个文件，
或者读它自己的 stdout 而不是同一个文件句柄。

## 7. 打不开 COM11 / 一打开板子就复位

- 串口监视与 `west flash` **不能同时占 COM11**；
- 打开 COM 会触发 DTR/RTS，本板带自动下载电路 → **一打开就复位**。
  这就是为什么 `serial_monitor.py` 里要 `dsrdtr=False`。

## 8. 三个"看起来在工作"的假象（2026-11-16 新增）

### 8.1 `settings_save_one` 写了，但没人读

症状：`/api/wlog` 永远只有本次运行的事件，重启即空；NVS 里明明有 `wlog/blk`。

根因：只声明了 `settings_save_one("wlog/blk", ...)`，**没有 `SETTINGS_STATIC_HANDLER_DEFINE`**。
`settings_save_one` 负责写，`settings_load` 走的是 handler 表 —— 没人认领这个子树，读回自然什么都没有。

判据：写 NVS 的代码必须是「写 + 注册 handler + 启动日志证明 restore」三件套，
只看"保存成功返回 0"是不够的。

### 8.2 C 里手写整页 HTML/JS：编译通过 ≠ 页面正确

症状：手机打开配网页报 `SyntaxError: Unexpected token e in JSON at position 1`。

根因：HTML 属性引号 + JS 字符串引号 + JS 里再拼 HTML，三层叠加全靠 `\"` 转义，
某一处多数/少数一个反斜杠，**C 编译器完全不会报**（它只看到一串合法字面量），
JS 字符串在 `data-c='"+` 处被切断，后半句变成裸标识符。

修法：页面单独存 `.html`，用脚本生成 C 头文件，并把 `<script>` 抽出来过 `node --check`。
详见 [17.10 第 6 节](17.10-页面受众分离（用户配网页与开发者台）.md)。

### 8.3 新 Chrome 实例里页面 fetch 私网端口必然失败

症状：用 CDP 起一个全新 profile 的 Chrome，页面加载正常、状态卡片也有数据，
但一点「上传」就 `TypeError: Failed to fetch`；同一台机器上 Python 直连 `:8080` 一切正常。

根因：Chrome 130+ 的**本地网络访问策略**。页面是非安全上下文（http）→ 访问私网地址的端口，
首次需要用户授权；用户平时那个 profile 早已点过"允许"，所以旧 profile 能过、全新 profile 不过。
`--disable-features=LocalNetworkAccessChecks` 在当前版本上没能绕过去。

判据：遇到"浏览器说 fetch 失败、命令行却通"的情况，先分三层：
DNS/路由（用 Python 打一次）→ CORS 预检（看 `OPTIONS` 响应头）→ 浏览器策略（换 profile 复现）。

## 9. 一个方法论收尾

这个项目里最常出现的错觉是「功能写好了但不生效」，而真实原因分布是这样的：

| 类别 | 例子 | 先查什么 |
|---|---|---|
| 配置没生效 | `mcuboot.conf`、`CONFIG_HTTP_SERVER_CAPTURE_HEADERS` | `.config` 里 grep 符号 |
| 跑的还是旧固件 | 续传恒回 200 | `ota.local_ver` / 串口 `local_ver` |
| 状态标志没置 | `g_rb_valid` | 加一行日志证明分支进了 |
| 资源不够 | 栈溢出、commit 内存 | 串口诊断、线程列表、并发数 |

四条里有三条**不需要改代码，只需要加一条可验证的观测**。
