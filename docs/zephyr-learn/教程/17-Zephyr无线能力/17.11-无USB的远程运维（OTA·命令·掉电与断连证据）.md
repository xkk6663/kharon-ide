# 17.11 无 USB 的远程运维：OTA、命令、掉电与断连证据

> 场景：板子只接了电源，**USB 线拔掉**，人不在板子旁边。
> 问题是：还能升级固件吗？还能查"它上次为什么重启/断网"吗？
>
> 结论先说：
>
> - **能**：局域网 HTTP（`:8080` OTA + `:80` 调试台）覆盖升级、远程命令、状态、断连账本。
> - **但有一个坑能把它彻底锁死**：`X-Nonce` 用毫秒时间戳会被 32 位 `strtoul` 饱和成 `UINT32_MAX`，
>   之后任何请求都 `403 replay` —— 远程升级永久失效，只能靠 USB 救。本轮就撞上了，见第五节。
> - 掉电本身**不可能**在断那一刻写日志；能拿到的是"下次上电时"的复位原因 + 上次运行时长。
>   本轮的实测证据：`rst=poweron`、`previous run dirty`、`last_up=66s`。

---

## 一、先把"没有串口还能做什么"列清楚

| 能力 | 接口 | 无 USB 时可用 | 说明 |
|---|---|---|---|
| 看状态 | `GET /api/status?k=` | ✅ | SSID/IP/RSSI/uptime/OTA 阶段/启动计数 |
| 看断连账本 | `GET /api/wlog?k=`、`/api/drops?k=` | ✅ | 掉线当下就写 NVS，重启后仍可查 |
| 看启动与复位原因 | `GET /api/boot?k=` | ✅ | `rst` / `last_up` / `crash` / `clean` |
| 执行板端命令 | `GET /api/shell?cmd=<...>&k=` | ✅ | `portal status`、`kernel uptime` 等 |
| 扫描 / 连网 / 断开 | `/api/scan`、`/api/connect`、`/api/disconnect` | ✅ | 但 `portal drop` 会让本次 HTTP 请求超时 |
| 升级固件 | `POST :8080/ota` + 头 | ✅（前提：nonce 没被污染） | 见第三、五节 |
| 切槽重启 | `POST :8080/api/ota/reboot` | ✅ | 客户端必然看到连接被切断 |
| 看串口原始日志 | COM11 | ❌ | 这就是为什么要"账本落 NVS" |
| 改口令 | `GET /api/pw?...&k=` | ✅ | 改完要用新口令 |

本轮实测（板子 USB 已拔、只接电源）：

```json
# GET /api/shell?cmd=portal status&k=<REDACTED-PSK>
{"ok":true,"out":"\nstate=2 ssid=\"Power\" ip=10.115.126.239 rssi=-22 reconnects=0 uptime=228s\n"}
```

**这条就说明了整件事**：没有串口，一样能在 228 秒的运行期里问出"连着谁、信号多少、活多久"。

## 二、远程 OTA 的协议形状（不是"上传一个文件"那么简单）

```
POST http://<板子IP>:8080/ota
Content-Type: application/octet-stream
X-Version : 130            # 目标版本，必须 > 板端 local_ver（除非 force）
X-Nonce   : 1794759862     # 严格递增，持久化在 NVS（防重放）
X-Force   : 0              # 只允许越过"版本不升"，越不过 size/nonce/完整性
X-Sha256  : <整包 sha256>  # 期望摘要，设备端算完必须与它一致
X-Key     : <REDACTED-PSK>    # 口令，来自 auth/pw

body: 整个 signed.bin（约 850 KB）
```

设备端的门禁顺序（拒绝码就是排障索引）：

| # | 检查 | 失败返回 | 真因 |
|---|---|---|---|
| 1 | `X-Key` | 401 `{"err":"need key"}` | 口令不对，或 `k=` 被别的参数吃掉（见 17.4 §1.1） |
| 2 | 连接来源 | 直接关连接 | 从 `192.168.4.x` 来的，AP 侧不给 OTA（17.10 §7） |
| 3 | 镜像头/size | 400/413 | 不是 mcuboot 镜像，或超过槽容量 |
| 4 | `X-Nonce` 递增 | 403 `{"err":"replay"}` | nonce ≤ 上次；**毫秒时间戳会把它锁死** |
| 5 | 版本门禁 | 409 `oldver` | 目标版本不比板端大，且没带 `force` |
| 6 | 整包 SHA | 400 `badauth`/`sha` | 期望摘要与实收字节不一致 |
| 7 | 写槽 + 回读 | 500 | Flash 写入或回读比对失败，**不切槽** |

只有 7 全过，才置升级标记；`POST /api/ota/reboot` 才真正切槽。

## 三、一次标准的远程升级（脚本版）

`tools/remote_ota.py` 就是这条链的自动化：**只用 HTTP，不碰串口**。

```powershell
$root = "C:\Users\xiao1\Desktop\ELAB\kharon-ide"
& "$root\.venv\Scripts\python.exe" "$root\tools\remote_ota.py" `
    --ip 10.115.126.239 --key <REDACTED-PSK> `
    --bin "$root\build\esp32s3\s3ota\fw_v130.signed.bin" --version 130
```

它做的事：

1. `GET /api/status` 取基线（`local_ver`、槽位、`uptime`）；
2. 本地算整包 `sha256`，`nonce = int(time.time())`（**秒**，不是毫秒）；
3. `POST :8080/ota` 开一个线程传，主线程**同时轮询 `/api/status` 的 `ota.pct`** 打印进度
   （不依赖服务端流式响应，也不需要长连接）；
4. 收到 `{"ok":true}` 后 `POST :8080/api/ota/reboot`，客户端超时是预期（板子立刻复位）；
5. 轮询 `local_ver` 变成目标版本即判 PASS。

为什么"上传"和"重启"要分成两个请求：上传只负责**写备用槽 + 回读校验**，
重启才切槽。分开之后，"传完了但还没切"是一个可观察的中间态（`ota.stage=ready`），
排障时能直接区分"传坏了"和"切槽失败"。

## 四、掉电能不能留证据：能，但是"事后记账"

物理事实：**断电那一刻，芯片没有任何机会写 flash**。所以"掉电日志"只能是下次上电时的结论。

可用的证据链（都在 NVS）：

| 证据 | 来源 | 本轮实测值 | 含义 |
|---|---|---|---|
| `boot.dirty` | `boot/dirty` 只有干净退出才清 0 | `false`（dirty） | 上次**没有**走正常关机/重启路径 |
| `boot.rst` | `esp_reset_reason()` | `poweron` | 上电复位：拔电重插或首次上电 |
| `boot.last_up` | 运行期每 60 s 落一次 | `66` 秒 | 上次跑到 66 秒就没了（粒度 ±60 s） |
| `boot.crash` | 只在 panic/看门狗/欠压/毛刺时 +1 | `6` | 真崩溃计数，被烧录/按键骗不到 |

```
{"boot":{"n":85,"crash":6,"last_up":26,"clean":false,"rst":"poweron","rstc":1}, ...}
```

这四行就是"偶尔掉电"的全部可取证内容。要更细就得外部手段（示波器看 3V3、串口抓最后一行）。

v130 起，这类事件会**额外写一条账本记录**（`kind=4`），这样它和断连事件在**同一条时间线**上。
拔电重插之后，`GET /api/wlog?k=` 的真实返回（该记录在**紧接着又一次 OTA 升级之后仍然存在**）：

```json
{"t":6,"k":4,"dr":0,"rc":0,"sc":1,"rssi":0,"hold":56,"ssid":"poweron"}
```

同一时刻的 `/api/drops`：

```json
{"total":16,"conn":10,"disc":1,"fail":4,"abn_boot":1,
 "last_drop":{"t":97,"held_s":0,"dr":2,"drtxt":"User request","rssi":-30,"ssid":"Power"},
 "last_fail":{"t":9,"sc":3,"rssi":0,"ssid":"Power"}}
```

读法：

- `k=4` = 上次不是干净退出；
- `ssid` 字段这里存**复位原因文本**（poweron / brownout / panic …）；
- `sc` 存复位枚举原值（`1` = POWERON），字符串映射漏了也还有数字；
- `hold` = 上次运行了多少秒（这一条是 `56`，与 `boot.last_up` 同源）；
- `abn_boot` = 账本里 `kind=4` 的条数，用来回答"这台板子被拔过几次电"。

**刻意不记** `software` / `ext_pin` / `usb` / `jtag`：那些是烧录、按复位键、插拔 USB、软重启，
记进去只会把真掉电淹掉。

### 4.1 顺带修的第三个"看起来在工作"

写进 NVS 了、`/api/wlog` 却读不到 `hold`，原因不在存储而在**输出缓冲**：

```c
static char g_wlog_json[920];   // 16 条 × 约 130 B ≈ 2.1 KB，装不下
```

数组满了 `snprintf` 就不再追加，JSON 停在半截（实测末尾是 `{"t":12,"k":1`），
前端 `JSON.parse` 直接抛错——现象看起来像"设备没记这条"，实际是"记了但没吐全"。
修法两件：缓冲区扩到 `2176`，并把 `conn_s` 以 `hold` 字段输出。

判据写法：**"字段能查到"才算交付**。只写 `settings_save_one` 不注册读回 handler，
或者写了却被缓冲截断，两种都表现为"远程查不到"，排障时不要再往 flash 那边找。

## 五、本轮撞上的真坑：一个毫秒时间戳把远程升级锁死

### 5.1 现象

板子 USB 已拔，纯局域网升级 v130：

```
baseline: local_ver=128 stage=idle
upload: POST :8080/ota  nonce=1794759862 ver=130
reply  : HTTP 403 {"ok":false,"err":"replay"}
RESULT: FAIL (未写入，槽位内容不变)
```

槽位没动（`slot0=1.128`、`slot1=1.126`），运行中的固件完好——**门禁按设计生效了**，
但"replay"这个理由明显不对：这台板子上一小时才升过一次，nonce 是新的秒级时间戳。

### 5.2 根因

页面早期实现的签名头是：

```js
'X-Nonce': String(Date.now())      // 1.78e12，毫秒
```

设备端解析：

```c
return (uint32_t)strtoul(v, NULL, 10);   // 32 位平台上 > ULONG_MAX → 饱和成 UINT32_MAX
```

于是 `g_nonce_last = 4294967295` 被持久化。之后比较是 `nonce <= last` 就拒，
**任何 32 位整数都不可能大于它** —— 远程升级从此永久 403，只有 USB 能救。

串口日志早就写了这一行，只是当时没意识到它是"死锁"：

```
<inf> ota: nonce restored: 4294967295
```

### 5.3 修法（v130 已包含）

1. **发起端改秒**：页面与脚本统一 `Math.floor(Date.now()/1000)` / `int(time.time())`；
2. **设备端判脏**：读到 `UINT32_MAX` 视为被毫秒时间戳污染，直接归零并告警
   （饱和值不可能来自合法的秒级时间戳，判据是充分的）；
3. **`nonce == 0` 单独报**：返回 400 `nonce missing or 0`，别让"没带头"伪装成"重放"。

```c
if (g_nonce_last == UINT32_MAX) {
	LOG_WRN("nonce stored as UINT32_MAX (poisoned by ms timestamps), reset to 0");
	g_nonce_last = 0;
}
```

### 5.4 代价：这一版必须靠一次 USB（已完成）

这是"鸡生蛋"：修复在 v130 里，而 v130 传不上去（403）。所以处理顺序只能是：

1. **插一次 USB，把 v130 直烧进 slot0**（`Wrote 869844 bytes` + `Hash of data verified`）；
2. v130 一启动，自愈逻辑就生效，串口留下这行证据：

```
<wrn> ota: nonce stored as UINT32_MAX (poisoned by ms timestamps), reset to 0
<inf> ops: wlog: restored 11 event(s), head=11
<inf> ops: boot #83, rst=other, previous run dirty (last_up=56s, abnormal_crashes=6)
```

3. 拔掉 USB，之后**每次升级都是纯远程**（实测见 5.5）。

这条正好写进 checklist：**任何持久化的单调计数器，都要写清"单位"和"饱和后怎么恢复"**，
否则它会在某一天变成一个不可远程修复的死锁。

### 5.5 修好之后：一次完整的无 USB 远程升级（实测）

板子在 v130（USB 已拔），本地只构建出 v131 的 `signed.bin`，然后一条命令：

```powershell
& "$root\.venv\Scripts\python.exe" "$root\tools\remote_ota.py" `
    --ip 10.115.126.239 --key <REDACTED-PSK> `
    --bin "$root\build\esp32s3\s3ota\fw_v131.signed.bin" --version 131
```

```
baseline: local_ver=130 stage=idle slot0=0
image   : fw_v131.signed.bin 869844 B sha=6b2ed5ce36baaaf5...
upload: POST :8080/ota  nonce=1794760287 ver=131
   recv 5% (48777/869844 B)
   recv 24% (216672/869844 B)
   recv 50% (437802/869844 B)
   recv 74% (646647/869844 B)
   ready 100% (869844/869844 B)
reply  : HTTP 200 {"ok":true,"reboot":false}
staged : stage=ready pct=100 cand=131
reboot : HTTP 200
after  : local_ver=131 state=connected ssid=Power boot=84
RESULT: PASS 远程升级成功，无需串口/USB
```

升级后槽位与账本（同一次上电内读回）：

```json
{"slot0":{"rc":0,"ver":"1.131.0","size":869476},
 "slot1":{"rc":0,"ver":"1.130.0","size":869476},
 "confirmed":true,"local_ver":131,"swap":1}

{"total":14,"conn":9,"disc":1,"fail":4,"abn_boot":0,
 "last_drop":{"t":97,"held_s":0,"dr":2,"drtxt":"User request","rc":0,"rctxt":"none","rssi":-30,"ssid":"Power"},
 "last_fail":{"t":9,"sc":3,"rssi":0,"ssid":"Power"}}
```

两点读法：

- `slot0=1.131.0` / `slot1=1.130.0`：新固件落在 slot0，**旧版还在 slot1**，
  这就是"回滚的物理前提"——回退只需要把启动槽指回去，不需要重新下载；
- 账本 `total` 继续累加、`last_drop` 仍是升级前那条：**升级不会清空诊断历史**，
  因为账本在 NVS，不在被擦写的 OTA 槽里。

## 六、P4 掉电回滚：真拔一次电（实测）

### 6.1 这里原本有个洞

命中窗口的条件写在 RAM 里：

```c
static bool g_win_started;
static uint32_t g_win_ticks;
```

于是"窗口内拔电"这件事的真实结局是：重启后 `g_win_started=false`，**窗口从头再走 60 s**，
链路正常 → `self-test OK` → 候选固件转正。也就是说这个设计里**掉电根本不会触发回退**，
只有"崩溃计数变大"和"窗口结束时链路仍断"两条会回退。

掉电又恰恰不会让 `crash` 涨（`poweron` 不算异常复位），所以两条判据都抓不到它。

### 6.2 补的判据

候选已 armed（说明上次是带着"待自证"重启的），但**本次启动上来就是 dirty**，
且复位原因是 `poweron` / `brownout` / `pwr_glitch` —— 说明上一轮没走任何正常退出路径：

```c
if (!ops_boot_last_clean()) {
	const char *rst = ops_boot_rst_reason();

	if (strcmp(rst, "poweron") == 0 || strcmp(rst, "brownout") == 0 ||
	    strcmp(rst, "pwr_glitch") == 0) {
		LOG_ERR("self-test: power cut in window (rst=%s) -> revert", rst);
		(void)ota_revert_to_secondary("power cut in window");
		return;
	}
}
```

软重启（`software`）不算：OTA 自己重启、回退重启都会 `ops_boot_mark_clean()`，
如果把它们也算进来，每次正常升级都会自我回退。

### 6.3 时间轴与实测

| 时刻 | 动作 | 观察（全部来自局域网） |
|---|---|---|
| T0 | 远程升级到 v134 | `ready 100%` → `HTTP 200` → `local_ver=134 boot=88` |
| T0+约 15 s | **人工拔电源**（窗口 60 s 内） | 板子离线 |
| T0+约 20 s | 插回电源 | 先起一会儿（等待窗口判据），HTTP 超时属预期 |
| T0+约 45 s | 回到可访问 | `local_ver=133`、`boot.n=90`、`rst=software`、`clean=true`、`crash=6` |

判据全绿：

```json
// GET /api/status
"ota":{"local_ver":133,"cand":0,"win":false}
"boot":{"n":90,"crash":6,"last_up":16,"clean":true,"rst":"software"}

// GET /api/ota/slots
{"slot0":{"rc":0,"ver":"1.133.0"},"slot1":{"rc":0,"ver":"1.134.0"},
 "confirmed":true,"local_ver":133,"swap":1}

// GET /api/wlog（第二条 kind=4 就是这次拔电）
{"t":6,"k":4,"dr":0,"rc":0,"sc":1,"rssi":0,"hold":16,"ssid":"poweron"}

// GET /api/drops
{"abn_boot":2,...}
```

怎么读这三组数：

- `slot0=1.133` / `slot1=1.134`：**跑的是旧版，新候选留在 slot1**，
  这才是"回退"而不是"重新下载了一个旧包"；
- `crash` 还是 6：回退路径自己调了 `ops_boot_mark_clean()`，
  **不把这次回退记成一次崩溃**，否则崩溃计数会被自己的救命动作污染；
- `hold=16`：那次候选固件只活了 16 秒就被拔电；
- `abn_boot=2`：账本里两条 `kind=4`（前一次是 5.5 之前的普通拔电，这一次是窗口内拔电）。

### 6.4 边界（不要吹成"防砖"）

- 这是**应用侧**回退：候选固件如果连启动都起不来、或者启动后在跑到窗口判据之前就 panic，
  bootloader 不会替你回退 —— 那种情况仍然只能 USB 重刷；
- `boot_request_upgrade()` 触发的槽搬移本身需要时间，**搬移过程中再掉电**是有风险窗口的，
  验收时不要在搬移阶段反复拔插；
- 本次测试的成功前提是旧版镜像在 slot1 完整可读（`SWAP_USING_MOVE` 布局），
  换成 OFFSET 布局这条路走不通（旧镜像落点不满足升级槽要求，会被判无效并擦掉）。

### 6.5 "OTA 过程中掉电"到底要不要重刷：按阶段分开看

一句话：**双分区保护的是"正在写"，不是"写完之后新固件能不能活"。** 两者是不同的失败：

| 掉电发生在 | 板上发生了什么 | 下次启动 | 要不要重刷 |
|---|---|---|---|
| 正在传 / 正在写 slot1 | 运行槽 slot0 一个字节没动；slot1 的镜像不完整，头/摘要都对不上 | bootloader 照旧从 slot0 起旧固件 | **不要**，重发一次 |
| 写完但还没切槽 | 切槽标记没打（或打了但没重启），启动槽仍是旧的 | 旧固件 | **不要** |
| 已重启、bootloader 正在搬移镜像 | 搬移写了一半，这一段没有事务保护 | 视搬移进度，可能两边都不完整 | 有小概率**要**（唯一风险窗口） |
| 已跑在新固件、窗口还没转正 | 我们补的判据：dirty + `poweron` → 判"窗口内拔电" | 回退到旧槽（本节实测） | **不要** |
| 新固件起不来 / 判据跑到之前就 panic | 应用层代码没机会跑，PERMANENT 语义下 bootloader 不做 trial 回滚 | 卡在新固件 | **要**，只能 USB |

所以"OTA 中掉电 ⇒ 必须重刷"是错的；真正只能 USB 的是最后一行。
反过来也成立：**别把"双分区"当成"新固件写崩了也能救"的承诺**，它救不了写崩的固件。

### 6.6 让"正在 OTA"看得见：紫色呼吸灯

问题很实际：升级时灯还是"联网绿"，现场分不清"卡住了"还是"正在写"。

做法是给 LED 线程加一个优先级最高的覆盖色，判断依据直接读 OTA 快照的 `stage`：

```c
ota_on = strstr(st, "\"stage\":\"recv\"")   ||   /* 正在收字节 */
         strstr(st, "\"stage\":\"verify\"") ||   /* 收完在回读校验 */
         strstr(st, "\"stage\":\"ready\"");      /* 已写好，等切槽重启 */

if (ota_on) {
	base[0] = 150;   /* R */
	base[2] = 175;   /* B */   /* → 紫色（R+B），无 G */
} else {
	switch (g_state) { /* 绿 / 蓝 / 红 照旧 */ }
}
```

三个要点：

- **只换基色，不动包络**：亮度仍走同一套 4 s 余弦呼吸（绝对 UTC 相位），
  所以紫灯和绿灯的节奏完全一致，不会因为"OTA 模式"打乱同步规范；
- **覆盖所有状态**：`recv`/`verify`/`ready` 三态都紫，因为"传完了还没切槽"同样是进行中；
- **失败不变紫**：`stage=fail` 不在列表里，灯回到链路色，避免"失败了还一直紫"。

实测：v136 → v137 远程升级期间灯为紫色呼吸，切槽重启后回到绿色（链路已连）。
