# 17.9 回滚方案评估：DIRECT_XIP 与自证窗口

> 目标只有一个：**新固件坏了，板子能不能自己回到旧固件。**
> 本篇先摆候选路线，再用手上真实证据逐条判可行性。
> 新增了一个只读接口 `/api/ota/slots`（读两个槽的镜像头），评估用的数据都出自它。

判据来自 `embedded-ota-pipeline` 的 `references\acceptance.md` 第三节（P4 掉电回滚）：
零点必须是**重启**，判据必须是"断电前槽 ≠ 上电后槽"，且日志里不能出现 `self-test OK`。

## 1. 现状（事实）

| 事实 | 证据 |
|---|---|
| 换槽模式 = SWAP_USING_OFFSET | `mcuboot\zephyr\.config`：`OFFSET=y / MOVE=n / SCRATCH=n` |
| 升完级直接永久转正 | `boot_request_upgrade(BOOT_UPGRADE_PERMANENT)` |
| 应用侧"确认"接口恒失败 | `boot_write_img_confirmed()` 返回 -5，`ota_confirm_if_healthy()` 因此是空实现 |
| 无 scratch、无 otadata | `zephyr.dts` 实测分区表（见 17.7） |
| 镜像 839 KB，两槽各 1344 KB | `fw_v117.signed.bin` = 859684 B |

`boot_write_img_confirmed()` 的实现（`zephyr\subsys\dfu\boot\mcuboot.c:461`）：

```c
if (boot_set_next(fa, true, true) != 0) {   /* fa = ACTIVE_SLOT，当前运行槽 */
    rc = -EIO;
}
```

要写的是**正在运行那个槽的 trailer**。这一步失败，才是"没有自动回滚"的根 —— 不是模式选错。

另一条同文件的逻辑（449-456 行）：trailer magic 为 `BOOT_MAGIC_UNSET`（从没写过）时，
`boot_is_img_confirmed()` **直接返回 true**。所以首烧的镜像天然"已确认"，也天然永远不进自证窗口。

## 2. 四条候选路线

### 2.1 DIRECT_XIP（不带 revert）

机制：mcuboot 从"版本更高"的槽直接启动，不做搬运。

**硬阻塞：ESP32 镜像按绝对地址链接。** mcuboot 的 espressif 端口读镜像头里的 `entry_addr` 直接跳：

```c
/* bootloader\mcuboot\boot\espressif\port\esp_loader.c:124 */
if (!esp_ptr_in_iram((void *)load_header.entry_addr)) {
    BOOT_LOG_ERR("Application entry point (0x%x) is not in IRAM. Aborting");
}
```

同一个二进制放进 slot1，`entry_addr` 仍然指向 slot0 —— 直接启动 slot1 等于执行 slot0 的内容。
所以必须配 per-slot 链接版本：sysbuild `SB_CONFIG_MCUBOOT_DIRECT_XIP_GENERATE_VARIANT`
（`share\sysbuild\images\bootloader\Kconfig:159`，**标 EXPERIMENTAL**），它用
`slot1-partition` snippet 额外产出 `<app>_slot1_variant`。

代价：

- 每次构建两份镜像，OTA 要推"目标槽对应的那一份"；我们 `:8080` 现在固定写 slot1；
- sysbuild 自动 `select NO_DOWNGRADE`，`force` 降级调试路径失效；
- **仍然没有回滚** —— 这是 DIRECT_XIP 的定义。

结论：不做。它省的是搬运，我们要的是回去。

### 2.2 DIRECT_XIP_WITH_REVERT

在 2.1 上加 revert：镜像以 test 启动，**必须运行时确认**，否则下次重启 bootloader
判定它坏了、擦掉、回旧镜像（`boot\zephyr\Kconfig:688` 原文要求"trailer magic 打进签名镜像"，
且"without the image being confirmed at runtime … considers the image faulty and erases it"）。

两个前置条件**都卡在我们这里**：运行时确认 = 写运行槽 trailer = 还是 -5；
以及 per-slot variant 的全部代价。换模式并不能绕过那个 -EIO。

### 2.3 换 SWAP 家族（MOVE / SCRATCH）

确认动作仍然写运行槽 trailer，不解决 -EIO；SCRATCH 还得多一个分区，4 MB 布局里没有。

### 2.4 RAM_LOAD

镜像要链接成"从 RAM 运行"，本板镜像 839 KB，ESP32-S3 内部 SRAM 只有 512 KB 量级，
还要给 bootloader 留专用 RAM —— 物理装不下，排除。

## 3. 实测：两个槽里到底是什么（实验 1，已完成）

接口：`GET /api/ota/slots?k=<口令>`。它做三件事：`boot_read_bank_header()` 读头、
再用 `flash_area_read()` 按 mcuboot v1 真实布局（+0 magic / +4 load_addr / +8 hdr_size /
+12 img_size / +16 flags / +20 ver）解一遍 **槽首 +0 与 +4096** 两个位置。

v117 实机返回（原文）：

```json
{"slot0":{"rc":0,"ver":"0.0.0","size":859316,
          "p0":"m=0x96f3b83d sz=859316 v=0.0.0","p4k":"m=0xba252011 …"},
 "slot1":{"rc":-5,
          "p0":"m=0x96f3b83d sz=859316 v=0.0.0","p4k":"m=0xba252011 …"},
 "confirmed":true,"local_ver":117,"swap":1}
```

四条读数各有含义：

1. **`swap=1` 是 `BOOT_SWAP_TYPE_NONE`，不是 TEST**（枚举定义在 `include\zephyr\dfu\mcuboot.h:43`，
   从 NONE 开始编号）。即稳态、无待换槽。
2. **`confirmed:true` 是"假确认"**：因为 trailer magic 从没写过，被当作已确认（第 1 节那段逻辑）。
3. **slot1 里确实有镜像，而且就在 +0**：`p0` 有 magic `0x96f3b83d`，`p4k` 没有。
   而 `rc:-5` 的原因是 app 侧 helper 在"非 REVERT 状态"下**按 +4096 读次要槽**
   （`mcuboot.c:273-289` 的分支），读到的是镜像正文而不是头，于是头校验失败。
   这就是"magic 在但读不出来"的真正原因，不是槽坏。
4. **两个槽的镜像大小、版本完全一样（859316 / 0.0.0）** —— 这是最要紧的一条：
   **我们签名时从来没给镜像头写过版本号**（imgtool 默认 0.0.0），版本门禁全靠 HTTP 层的
   `X-Version`。后果是：任何"按镜像头版本做决策"的机制（DIRECT_XIP 挑高版本、
   `NO_DOWNGRADE` 比较）在本工程里**全部失效**，而且**现在无法用镜像头区分新旧**。

## 4. 评估结论（按证据修正）

| 方案 | 成本 | 覆盖 | 风险 | 结论 |
|---|---|---|---|---|
| A. 应用侧自检回退（把 slot1 重新标成待启动） | 中 | 能跑但坏 | 中（见下） | **先补前置条件再做** |
| B. 确认状态外置到 `sys` 分区，由 mcuboot 读 | 大 | 起不来的也能回 | 高（动 bootloader） | 靠后 |
| C. DIRECT_XIP_WITH_REVERT | 大 | 起不来的也能回 | 高（实验性 + 仍要写运行槽） | 暂不做 |
| D. DIRECT_XIP / RAM_LOAD | —— | 不回 / 装不下 | —— | 排除 |

方案 A 原本看起来最划算：swap 后旧镜像留在 slot1，自检不健康就 `boot_request_upgrade()`
（写**非运行槽** trailer，正是 OTA 每天在做的成功操作），重启后搬回来。
但实测把它的两个前提各打了一个问号：

- 前提一"slot1 里有旧镜像"：**内容在 +0 处确实有**，但因为镜像头版本全是 0.0.0，
  **无法证明它是旧版**（也可能就是当前版本的副本）；
- 前提二"被打 pending 的 slot1 会被正确搬回"：mcuboot 的 OFFSET 模式对"升级槽镜像应在第二扇区"
  有明确假设（`flash_img.c` / `boot_get_image_start_offset` 都按 +4096 算），
  而实测 swap 之后的 slot1 镜像落在 **+0** —— 布局与"升级槽"不一致，
  **bootloader 会不会接受、会不会搬错，未验证**。

所以方案 A 不能直接开工，顺序要改成：

1. **先让镜像头带上真实版本**（签名时写 version），否则后面每次判断都是瞎猜；
2. 再做一个低风险小实验：对 slot1 打 pending → 重启 → 看 `swap` 与 `local_ver` 怎么变，
   最坏情况是 bootloader 拒绝（继续跑当前镜像），不会砖；
3. 通过后才实现"自检窗口 → 提交回退"。

## 5. 仍要做的关键实验（实验 2）：-5 究竟来自哪一层

这是"bootloader 级回滚"唯一的开关，三种可能结论完全不同：

| 可能 | 现象 | 结论 |
|---|---|---|
| esp32 flash 驱动拒绝写"正在执行的映射区" | DBG 里 `Flash write error: <ESP_ERR_…>`（`drivers\flash\flash_esp32.c:174`） | B/C 都难，只能外置状态 |
| 镜像没带 trailer magic | `boot_set_next` 内部读回失败 | 打包参数可解，成本骤降 |
| 分区属性/只读 | `flash_area_write` 直接 -EACCES | 改 DT 即可 |

做法：临时开 `CONFIG_MCUBOOT_LOG_LEVEL_DBG` + flash 驱动 DBG，或开 `CONFIG_MCUBOOT_SHELL=y`
用板上 `mcuboot confirm` 当场复现，抓那一行 `Flash write error:`。

## 6. 一句话结论

**DIRECT_XIP 不是这条板子的回滚答案**：ESP32 镜像按绝对地址链接，它要 per-slot variant（实验性），
revert 依赖的运行时确认又正是恒失败的那个写操作。
而"应用侧自检回退"这条现实路径，实测暴露出两个必须先补的漏洞：
**镜像头没有版本号**、**swap 后 slot1 的镜像落在 +0 而不是升级槽的 +4096**。
这两个不补齐，任何回滚方案都只能"看起来能跑，出事不敢用"。

## 7. 未验证部分（别当成结论）

- 方案 A 未实机验证；
- slot1 里那份镜像是旧版还是当前版，**无法用镜像头判定**（版本全 0.0.0）；
- slot1 打 pending 后 bootloader 的行为未测；
- `boot_write_img_confirmed()` 的 -5 底层 errno 未定位；
- P4 掉电回滚测试未做（`acceptance.md` 要求的反向对照也没做）。
