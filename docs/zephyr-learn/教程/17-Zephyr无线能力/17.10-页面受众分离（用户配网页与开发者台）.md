# 17.10 页面受众分离：用户配网页 vs 开发者调试台

> **这一章解决的是一个产品问题，不是技术问题。**
>
> 用户的原话：*"手机连上的 ESP32 内置网址只支持基础联网管理和 WiFi 连接管理；OTA、远程调试是联网后局域网内的另一个调试控制台。面向开发者才需要命令，面向用户要简单快捷连上就行。"*
>
> 现场证据是手机截图：手机连 `S3-Portal` 打开 `192.168.4.1` 后，页面上有「固件升级（局域网 OTA）」卡片和「远程命令」输入框——两个都该只在局域网侧出现。

关键词：**受众分离 / 按来源判身份 / 接口同源分离 / 生成式页面 / 真浏览器验收**

---

## 一、先明确"分离"分的是哪三层

很多实现停在第 1 层就以为做完了，结果手机换一台浏览器、或者手敲 API 还能进去：

| 层 | 做什么 | 少做的后果 |
|---|---|---|
| ① 页面层 | AP 侧回用户页，局域网侧回开发者台 | 用户看到 OTA / 命令入口（就是本次的现场） |
| ② 接口层 | 开发者接口在 AP 侧返回 **404** | 用户页干净了，但浏览器手敲 `/api/shell` 照样能跑命令 |
| ③ 传输层 | OTA 的 :8080 在 AP 侧 **拒绝连接** | 页面没入口，但 `curl` 直接往 :8080 塞固件仍能写槽 |

三层都要按同一个判据来判：**这个已 accept 的 socket，对端是谁**。

---

## 二、为什么不能"开两个 HTTP 服务"

`HTTP_SERVICE_DEFINE(_name, _host, ...)` 的 `_host` 确实允许绑定具体 IP。但本板的结构决定了它不可行：

1. **AP 地址可以编译期写死**（`192.168.4.1`）；
2. **STA 地址是 DHCP 拿的**（实测 `10.115.126.239`），编译期根本不知道；
3. 再起一个绑定 `0.0.0.0:80` 的服务，会和绑定 `192.168.4.1:80` 的那个**抢同一个端口**，Zephyr 的 HTTP server 也不支持两个 service 监听同一端口再分流。

所以采用：**单一 `:80` 服务 + accept 后按对端地址判来源**。

```c
/* main.c：判据只有一处，所有 handler 都调它 */
static bool client_side_ap(struct http_client_ctx *client)
{
	struct sockaddr_in peer;
	socklen_t plen = sizeof(peer);
	static struct in_addr ap_addr;      /* 首次调用时从 AP_IP 解析并缓存 */
	struct in_addr peer_host;

	if (zsock_getpeername(client->fd, (struct sockaddr *)&peer, &plen) < 0) {
		return true;                    /* 取不到就按 AP 侧从严 */
	}
	if (peer.sin_family != AF_INET) {
		return true;                    /* 非 IPv4 同样从严 */
	}
	...
	return (peer_host.s_addr & 0xFFFFFF00u) == (ap_addr.s_addr & 0xFFFFFF00u);
}
```

三个细节值得记：

- `client->fd` 在 `server.h` 的 `INTERNAL_HIDDEN` 段里，但**应用代码可以访问**，实测可用；
- 判据按 **`/24` 网段**比，而不是精确比 `192.168.4.1`——DHCP 池是 `192.168.4.10–25`，客户端地址永远不是 `.1`；
- 取不到对端地址、或不是 IPv4，**一律按 AP 侧处理**。这是"从严"：宁可让开发者少一个接口，也不把 shell 暴露给未知来源。

## 三、鉴权：AP 侧免密，局域网侧要 `k=`

`auth_pass` 的签名从"只看请求"改成"看请求 + 看连接"：

```c
static bool auth_pass(struct http_client_ctx *client,
                      const struct http_request_ctx *req,
                      struct http_response_ctx *resp)
{
	if (client_side_ap(client)) {
		return true;        /* 进热点本身就要 WPA2 密码，不该再叠一层口令 */
	}
	...  /* 局域网侧仍然比对 ?k=<口令>，401 回 JSON */
}
```

`AUTH_GUARD()` 宏改成调三参版本——`client` 在每个 handler 的形参里都有，所以 20 个调用点一行都不用改。

**为什么 AP 侧免密是对的**，而不是偷懒：

- 连 `S3-Portal` 已经要输 WPA2 密码 `<REDACTED-PSK>`，这是一道真实的门；
- 产品要求是"简单快捷连上就能管理 WiFi"，再加一层"请到路由器上查口令"直接违背需求；
- 口令是**给局域网侧**用的：那块网络里可能有别的设备，不能让同网段任意主机改你的 WiFi。

新增 `DEV_GUARD()`：AP 侧直接 `HTTP_404_NOT_FOUND` + JSON，而不是"重定向到用户页"（重定向会让 API 调用方拿到 200 的 HTML，反而更难排查）。

```c
#define DEV_GUARD()                                                     \
	do {                                                                \
		if (client_side_ap(client)) {                                   \
			resp 404 + {"ok":false,"err":"developer console is on the LAN side only"}; \
			return 0;                                                   \
		}                                                               \
	} while (0)
```

插在 9 个开发者 handler 的 `AUTH_GUARD();` 之后：`status`、`apclients`、`rssi_hist`、`wlog`、`boot`、`ota/slots`、`ota/revert`、`pw`、`shell`。

### 3.1 顺带修掉一个"真浏览器才暴露"的鉴权 bug

`auth_pass` 原来是这样找口令的：

```c
const char *p = strstr(buf, "k=");   /* ← 裸搜 */
```

而 `/api/connect` 的查询串是 `?ssid=...&psk=WrongPass&k=<REDACTED-PSK>`。**`psk=` 这个词的尾巴上正好就是 `k=`**，于是 `strstr` 先命中它，口令被判成"密码不对"，凡带 `psk` 的请求全 401。

- 为什么 curl 手打没发现：手打时习惯把 `k=` 写在最前面，`strstr` 先命中真的那个；
- 为什么真浏览器必现：页面统一拼 `?ssid=..&psk=..&k=..`，`k` 永远在最后。

修法是**只认参数边界上的 `k=`**：

```c
const char *q = buf;
while ((q = strstr(q, "k=")) != NULL) {
	if (q == buf || q[-1] == '?' || q[-1] == '&') { p = q; break; }
	q += 2;
}
```

注意 `q == buf` 这一支不能少：**GET 的 `req->data` 带前导 `?`**，只判 `&k=` 会把 `?k=...` （也就是最常见的那个写法）判成没给口令。这个坑和上一个叠在一起，修完第一个会立刻踩到第二个。

## 四、接口层：给用户页单独开一个"最小状态"接口

用户页只需要"现在连没连、连的谁、IP 是多少、信号多少"，而 `/api/status` 是给开发者看的（还带 boot 计数、复位原因、netcheck、OTA 槽位/版本）。

所以新增 `GET /api/wifi`，字段刻意只有 7 个：

```json
{"state":"connected","ssid":"Power","ip":"10.115.126.239",
 "msg":"connected","last_err":"","rssi":-32}
```

它在两侧都可用（AP 侧免密、局域网侧要 `k`），资源定义紧跟 `status_detail`：

```c
HTTP_RESOURCE_DEFINE(portal_wifi, portal_service, "/api/wifi", &wifi_detail);
```

这一步的意义不是省几个字节，而是**约定**：手机侧永远看不到"槽位/复位原因/崩溃计数"这类只有维护者才关心的字段。

## 五、页面层：`index_handler` 按侧分页 + 响应头自证

`/` 和 `/index.html` 共用一个 handler，三处分支：

| 条件 | 回什么 | 响应头 |
|---|---|---|
| AP 侧 | `user_html`（用户配网页） | `X-Portal-Scope: user` |
| 局域网侧 + 无 `k` | 要口令的小页面 `unlock_html` | — |
| 局域网侧 + 有 `k` | `index_html`（开发者台） | `X-Portal-Scope: dev` |

`X-Portal-Scope` 是**给机器看的**：`curl -I` 或机内自检一行就能判"这一侧拿到的是哪一页"，不用去猜 HTML 内容。

> 小坑：换成新 header 数组时，`header_count` 忘了从 `html_header` 换过来。C 里数组和计数是两个参数，编译器不会拦你。

## 六、用户页不再手写 C 字符串：真 HTML + 生成头文件

### 6.1 为什么必须改

第一版图省事，把整页 HTML 写成一个 C 字符串数组。三层引号叠在一起：

- HTML 属性用 `'` / `"`；
- JS 字符串再用 `"`；
- JS 里还要拼 HTML 字符串。

于是 C 层全靠 `\"`，一旦哪一处多数/少数一个反斜杠：

- **C 编译照样通过**（语法合法，只是内容错了）；
- 手机打开页面才炸：`SyntaxError: Unexpected token e in JSON at position 1`、`SyntaxError: Unexpected identifier 'status'`。

抽取出来用 `node --check` 校验才发现，`renderSaved` / `scan` 那几个拼接串在 `data-c='"+` 处被切断成半句——JS 字符串提前结束，后面变成裸标识符。

### 6.2 现在的结构

| 文件 | 角色 |
|---|---|
| `src/user_page.html` | **唯一事实来源**，真 HTML，正常缩进与换行 |
| `tools/gen_pages.py` | 把它变成 `src/l1/pages.h`（每行一个 C 字面量，转义全由机器做） |
| `src/l1/pages.h` | 生成物，**不要手改**（2026-11-16 分层后从 `src/pages.h` 挪到这里） |
| `tools/page_check.py` | 离线校验：JS 过 `node --check` + 页面里不许出现开发者字样/接口 |

`src/l1/page.c` 只留：

```c
#include "pages.h"
```

而原来那段字面量位置只留一句注释，说明"改页面去改 html，再重新生成"。

### 6.3 构建时强制

`tools/build_ota.ps1` 在 `west build` **之前**串了两步，任一失败直接 `exit 1`：

1. `python tools/gen_pages.py`（重新生成 `src/l1/pages.h`）；
2. `python tools/page_check.py --node <node.exe>`（页面内容边界 + JS 语法）。

"页面坏了就别编译"——这条比事后在手机上排 `SyntaxError` 便宜太多。

`page_check.py` 现在的判据：

- 白名单接口只允许 `/api/wifi`、`/api/scan`、`/api/scan/start`、`/api/connect`、`/api/saved`、`/api/forget`、`/api/disconnect`；
- 文本禁用：`固件升级`、`远程命令`、`OTA`、`槽位`、`复位原因`、`boot`；
- `<script>` 抽出来交给 `node --check`。

实测输出：

```
page bytes : 8003
api calls  : ['/api/connect','/api/disconnect','/api/forget','/api/saved','/api/scan','/api/scan/start','/api/wifi']
ok: JS 语法通过
RESULT: PASS
```

## 七、传输层：OTA 的 `:8080` 同一个判据

`ota.c` 的 accept 循环原来不取对端地址。现在接出来判一次，**落在 AP 网段就直接关连接**：

```c
struct sockaddr_in peer;
socklen_t plen = sizeof(peer);
int cli = zsock_accept(srv, (struct sockaddr *)&peer, &plen);
if (peer_side_ap_24(peer)) {
	LOG_WRN("ota: reject %s (AP side, developer only)", ...);
	zsock_close(cli);
	continue;                 /* 拒绝连接，不是拒绝请求 */
}
handle_one(cli);
```

两个设计点：

- **拒绝连接而不是拒绝请求**：拒绝请求意味着要把整个 body 收完再回 4xx，手机侧白传 850 KB；更糟的是半截固件可能已经进了备用槽；
- `OTA_AP_SIDE_IP "192.168.4.1"` 这个宏必须和 `main.c` 的 `AP_IP` 一致，注释里写死这条约束——两处常量各写各的是这类项目的常见腐化点。

## 八、Telnet：直接关掉（本轮决定）

页面分完之后，`CONFIG_SHELL_BACKEND_TELNET` 成了**唯一的漏口**：

- Zephyr 这一版 telnet backend 绑 `0.0.0.0`、**没有来源过滤、也没有认证钩子**；
- 手机连上热点就能拿到一个**无口令的交互式 shell**——比"页面上有个输入框"严重得多。

三个候选：

| 方案 | 代价 | 结论 |
|---|---|---|
| ① 关掉 Telnet，远程执行只走 `/api/shell` | 失去交互式手感 | **采用** |
| ② 给 telnet 加口令 | 要包一层或改 backend，改动面大 | 否 |
| ③ 自写 TCP shell 监听 + 同款来源判据 | 多一个监听线程要维护 | 否 |

`prj.conf` 里改成一个否定赋值加一段原因说明：

```conf
# CONFIG_SHELL_BACKEND_TELNET is not set
```

**注意**：改 `prj.conf` 是 Kconfig 输入变化，会触发**一次全量重编**（本轮实测 540 s）。这是唯一一次值得付的：之后改 `main.c` / `ota.c` 仍然是 20 s 左右（版本注入在构建后重签，见 17.5）。

关掉之后启动日志里 `shell_telnet: Telnet shell backend initialized` 这类行整体消失，正好当"真的关了"的证据。

## 九、机上自检：让"哪一侧拿到哪一页"变成可自动判定的断言

新增 `http_self_test_scope(const char *host, const char *expect)`：

- 连 `host:80` 发 `GET / HTTP/1.1`；
- 只读响应头里的 `X-Portal-Scope:`；
- 打印 `scope-test: %s -> scope=%.*s (expect %s) OK|MISMATCH`。

调用点两处：

1. 启动自检里，在 `http_self_test("/api/wifi")` 之后：

```c
http_self_test_scope(AP_IP, "user");          /* 手机侧拿到用户页 */
http_self_test("/api/shell?cmd=kernel%20uptime");   /* 期望 404：手机侧没有命令 */
http_self_test("/api/ota/slots");                   /* 期望 404：手机侧没有 OTA */
```

2. `ipv4_event_handler` 里 `STA got IP` 之后：

```c
http_self_test_scope(g_ip, "dev");            /* 局域网侧拿到开发者台 */
```

实测四条全绿（`logs\serial-v126-notelnet.log`）：

```
self-test: GET /api/wifi -> "HTTP/1.1 200"
scope-test: 192.168.4.1 -> scope=user (expect user) OK
self-test: GET /api/shell?cmd=kernel%20uptime -> "HTTP/1.1 404"
self-test: GET /api/ota/slots -> "HTTP/1.1 404"
...
scope-test: 10.115.126.239 -> scope=dev (expect dev) OK
```

**为什么这套自检比手机截图可靠**：板子自己连自己两个地址，两条路径都覆盖，而且判据是响应头 + 状态码，不依赖"页面上看不看得见"。

## 十、真浏览器验收第二次（页面 OTA）

上一版卡在"产品内置浏览器与局域网隔离"，只能用 Python 直连验证接口。这次换成**桌面 Chrome**（局域网可达），把整条页面 E2E 走了一遍：

| 步骤 | 现场 |
|---|---|
| 打开 `http://10.115.126.239/?k=<REDACTED-PSK>` | 开发者台，`已连接 Power / 10.115.126.239 / -20 dBm` |
| 选文件 | `fw_v127.signed.bin`（869140 B，`1.127.0.0`） |
| 点「上传」 | JS `prompt` 问版本，默认 `127` |
| 传输中 | `板端 126 · 待装 127`、`recv94% (821178/869140 B)` |
| 完成 | `slot1 已写入：期望摘要 + Flash 回读都通过（22.8 s，sha=54314c077bda…）`、`ready100%` |
| 切槽后 | `/api/status` → `local_ver=127`，重启日志 `Booting Zephyr OS` 正常，STA 自动回到 `Power` |

截图证据：`img-ota-page-lan-success.png`（同一目录）。

三个结论：

1. 页面自己的**纯 JS SHA-256** 与设备端流式 SHA 一致——"期望摘要由发起端算"这条真的成立；
2. 上传走 `:8080`、状态走 `:80`，两条链路互不挤占；
3. 点「取消」不重启时，`slot1` 已经写好并置了标记，下次复位就切过去——**上传与切槽是两个独立动作**，这一点在页面上表现为"确认框"。

## 十一、真实掉线 `reason_code` 样本（本轮首次拿到）

`/api/wlog` 的字段是 `{t, k(kind), dr(dreason), rc(reason_code), sc(status_code), rssi, ssid}`。本轮抓到两条：

### 11.1 运行期掉线（本地发起）

串口原文（`logs\serial-v126-drop.log`）：

```
<inf> ops: wlog: kind=2 reason=2 rc=0 sc=0 rssi=-21 ssid=Power
<inf> portal: STA disconnect requested by user
<err> net_http_server: HTTP request handling error (-115)
<inf> portal: disconnected "Power" reason=2(User request) rc=0(none) sc=0 rssi=-21
```

- `dreason=2` = "User request"，`reason_code=0` = 驱动没给 802.11 原因（本地断开不是 AP 发的帧）；
- `-115` 是 HTTP 请求在链路被拔掉时的正常错误，不是新 bug；
- **`/api/shell?cmd=portal drop` 一定会超时**：命令把正在服务这个请求的 STA 链路关掉了，响应发不回去。要断网就用串口或直接操作 AP 侧。

### 11.2 关联失败（错密码）

```
wlog: kind=3 dreason=0 rc=0 sc=1 rssi=-44 ssid=OpenWrt
```

- `kind=3` 是连接失败分支，`sc=1` 对应"路由器没响应（信号弱，或 2.4G 信道被占）"；
- 这一版驱动的 4-way 握手失败**没有填 `reason_code`**，只体现在 `CONNECT_RESULT.status`。

### 11.3 结论：不再靠"挂串口等掉线"

挂串口等样本这个做法本身是错的：掉线可能几小时才来一次，而板子重启/掉电后现场就没了。本轮把它改成**断连即落盘、上电可查询**的账本（下一节），串口只在"想看当场时序"时才用。

真正"AP 端踢人"的样本（`reason_code` 2/4/8/15/34）仍然需要一台**可控 AP**：连上后用后台把客户端踢掉。本轮没有这样的设备（不能动用户的 `Power` 路由器、也不能切 PC 的 WiFi）。代码路径、字段、翻译表都已就绪，缺的只是触发条件——写进未完成项，不假装有了。

## 十二、断连账本：自动落盘，上电后局域网可查（本轮新增）

> 需求原话：*"掉线样本不用长挂着等着采集。每次 WiFi 断连后把相关日志/状态自动写入 NVS，下次上电联网后 PC 局域网可查询。"*

### 12.1 先发现一个"写了但读不回来"的 bug

`ops.c` 里其实早就在写：

```c
settings_save_one("wlog/blk", &g_ev, sizeof(g_ev));
```

但**没有注册对应的 settings handler**。`settings_save_one` 只是往 NVS 里塞了一个 key，`settings_load()` 时没人认领这个子树，于是：

- NVS 里确实有数据；
- 上电后 `/api/wlog` 永远是空的。

这就是"只能靠串口看"的真因——不是没记，是记了没读。

修法是补一个静态 handler：

```c
static int wlog_set_cb(const char *name, size_t len, settings_read_cb read_cb, void *cb_arg)
{
	if (strcmp(name, "blk") != 0) {
		return -ENOENT;
	}
	if (len != sizeof(g_ev)) {            /* 结构体加过字段 → 旧 blob 丢弃 */
		memset(&g_ev, 0, sizeof(g_ev));
		g_ev.magic = EV_MAGIC;
		return 0;
	}
	struct ops_ev_store tmp;
	if (read_cb(cb_arg, &tmp, sizeof(tmp)) < 0) {
		return -EIO;
	}
	if (tmp.magic != EV_MAGIC || tmp.head >= OPS_EV_N || tmp.count > OPS_EV_N) {
		return 0;                      /* 坏 blob 不解释，直接忽略 */
	}
	g_ev = tmp;
	LOG_INF("wlog: restored %u event(s), head=%u", ...);
	return 0;
}

SETTINGS_STATIC_HANDLER_DEFINE(ops_wlog, "wlog", NULL, wlog_set_cb, NULL, NULL);
```

两个判据值得记：

- **长度不符就丢弃**：结构体后来加了 `conn_s`，旧 blob 反序列化会整体错位，读出来的"现场"是假的，比没有更糟；
- **magic + head/count 越界都要挡**：NVS 是掉电安全的，但版本错配和人为写坏都可能发生。

### 12.2 记录字段：加一个"这条链路活了多久"

```c
struct ops_ev_rec {
	uint32_t up_s;        /* 事件发生时的上电秒数 */
	uint32_t conn_s;      /* 掉线前这条链路活了多少秒 */
	uint8_t  kind;        /* 1=connect 2=disconnect 3=conn_fail */
	uint8_t  dreason;
	uint16_t reason_code; /* ★ 802.11 Deauth/Disassoc reason */
	uint16_t status_code;
	int8_t   rssi;
	char     ssid[OPS_SSID_MAX];
};
```

`conn_s` 是这一轮唯一真正要新增的语义：**"连上 3 秒就断"和"连了 40 分钟才断"是完全不同的故障**，只看 `reason_code` 分不开。

顺手修掉一个统计 bug：主动断开（`portal drop` / 页面「断开」）会先把 `g_connected_at` 清零，等 `DISCONNECT_RESULT` 事件到达时时间戳已经是 0，于是 `held` 永远记成 `0 s`。改法是在清零前先把时长算到一个 `g_link_held_s` 里，事件处理时优先用时间戳、没有就用它。

### 12.3 查询接口 `/api/drops`（开发者侧，AP 侧 404）

```json
{"total":8,"conn":4,"disc":1,"fail":3,
 "last_drop":{"t":97,"held_s":34,"dr":2,"drtxt":"User request",
              "rc":0,"rctxt":"none","sc":0,"rssi":-30,"ssid":"Power"},
 "last_fail":{"t":9,"sc":3,"rssi":0,"ssid":"Power"}}
```

设计要点：

- **`last_drop` 与 `last_fail` 分开**。合成一个 `last` 会让排障时读错：`kind=3` 是"从来没连上"，不是"网络掉过"；
- 带**人话翻译**（`drtxt` / `rctxt`），值班的人不用回查枚举表；
- `disc` / `fail` 计数给"这块网络到底稳不稳"一个粗判据。

启动时还会在串口打一行，串口没接也照样能在 `/api/drops` 里看到：

```
<inf> ops: wlog: restored 1 event(s), head=1
<inf> ops: last wifi event: kind=2 ssid=Power dr=2 rc=0(none) sc=0 rssi=-30 held=0s at up=97s
```

### 12.4 实机验证（跨越一次冷复位）

| 步骤 | 结果 |
|---|---|
| 烧 v128（新结构体） | 启动 `wlog: restored 1 event(s)`，旧格式 blob 被正确接管 |
| `portal drop` 断开 | 账本出现 `kind=2 dr=2 rc=0 sc=0 rssi=-30 ssid=Power` |
| `portal conn` 连回 | 新增 `kind=1`，`/api/drops` 的 `last_drop` 正确指向那条掉线 |
| `kernel reboot cold` | 重启后 `/api/wlog` 仍有上一轮的 `kind=2`（`t=97`）——**跨复位持久** |
| 重启后 `/api/drops` | `total=8 / conn=4 / disc=1 / fail=3`，`last_fail` 是本次启动的 `sc=3` |

这条链路就是"下次上电联网后 PC 局域网可查询"的实现方式：**不再需要串口在场**。

### 12.5 浏览器侧：为什么 CDP 这条路这次没走通

按"直接上 CDP 更方便"的思路写了 `tools/page_ota_cdp.py`：独立 profile 起 Chrome（`--remote-debugging-port`）、`DOM.setFileInputFiles` 直接塞文件（不弹原生对话框）、`Page.handleJavaScriptDialog` 答 `prompt`/`confirm`、`Page.captureScreenshot` 截图。

协议侧全部走通了：页面加载、版本 `prompt`（`必须大于板端 128` → 答 `129`）、点「上传」、进度读到 `上传中 849 KB`。但**上传请求被浏览器自己掐了**，`catch` 到的是 `TypeError: Failed to fetch`，而同一台机器上直连 `:8080` 用 Python 打一遍 `OPTIONS`，返回是 `200 + Access-Control-Allow-*` 齐全。

结论：这不是板子的问题，是**新 Chrome 实例的本地网络访问策略**——Chrome 130+ 对"页面（非安全上下文、私网地址）→ 本地网络端口的 POST"有额外拦截，首次要用户授权；用户平时那个 profile 早已点过"允许"，所以旧 profile 能过，全新 profile 不过。命令行的 `--disable-features=LocalNetworkAccessChecks` 在当前版本上也没绕过去。

因此本轮**页面 OTA 的证据仍用桌面 Chrome 真实点击那一组**（`img-ota-page-lan-success.png`，`slot1 已写入…22.8 s`、`ready100%`、`local_ver 126 → 127`）。CDP 工具留着，等确认可用的关闭开关或改用 `Browser.grantPermissions` 之后再跑一遍。
