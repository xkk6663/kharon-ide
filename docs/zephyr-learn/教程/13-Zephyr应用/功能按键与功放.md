# 功能按键与功放：IO42 四键 + PA_CTRL

> **⚠️ 结论更正（2026-11-14）**：本文原来写的"IO42 四键 ✅ 完全可用"是**误判**。
> 那组 284/830/1359/1810 的数字来自 **ESP-IDF**（`display_audio_photo\...\改动记录.md` §8.2 的标定值），被搬进了 Zephyr 侧注释，Zephyr 上从未跑通。
> Zephyr 侧现状：`adc0` 因 dtsi `unit` 写错一基实际采的是 ADC2，IO42 恒 40–53 mV，四键按下无变化；完整证据链与四种已试修法见 `docs\课程同款\07-七项外设落地实录.md` §9.1。
> **主线（S3）读者请直接看 `16-Zephyr外设进阶\GPIO按键与输入子系统.md`**——那边是 GPIO + input 子系统，真机验证过。
> 本文保留的原因是：它把"一个键值、一个功放脚、NVS 记住状态"的应用层设计讲透了，代码结构本身可复用到 S3。

这篇讲板上两个「能用但不好用」的资源：

- **4 个功能键**（PLAY / SET / VOL- / VOL+）：它们**不是**四个 GPIO，而是**一个 ADC 通道上的四档电压**。想读出它们，走的是 ADC，不是 GPIO。
- **PA_CTRL（GPIO7）**：控制两颗 NS4150B 功放的使能。它本身是个普通 GPIO，但「什么时候开」属于应用层语义。

先给结论，后面逐条给证据：

| 资源 | 结论 |
|---|---|
| IO42 四键 | ⚠️ **Zephyr 侧未跑通**（IO42 恒 40–53 mV，按下无变化，见 `06` §9.1）。原表里的 284/830/1359/1810 是 ESP-IDF 标定值 |
| PA_CTRL GPIO7 | ✅ 完全可用。`gpio_pin_set_dt` 返回 0，`app pa on` 实测导出 |
| BOOT 键 IO61 | ❌ 不可用。bank1 驱动未闭环，回调注册成功但电平读不到、中断不进 |

## 一、四个键为什么挤在一个引脚上

官方框图里这一行写得很清楚：**4xADC Buttons → IO42**。原理是把四个按键接在一个电阻梯上，每个键把不同档位的分压点接到 ADC 输入，于是「按了哪个键」变成「读到多少 mV」。

```text
       3V3 ──[R]──┬──[R]──┬──[R]──┬──[R]──┐
                  │       │       │       │
              VOL+ 键   VOL- 键  PLAY 键  SET 键
                  │       │       │       │
                  └───────┴───────┴───────┘
                          │
                       IO42 ──→ ADC1_CH0
```

省下来的不是「一根线」，是**三个 GPIO**。代价是：**不能并发**（同时按两个键，读到的是中间电压，判定成「都不是」），而且**必须做阈值判定**，不能像普通按键那样读 0/1。

### 1.1、实测电压（这块板子的真实值）

工程 `display_audio_photo` 里有一份在这块板上标定过的表（`docs/项目规划/改动记录.md` 第 8.2 节），记录的是 ESP-IDF 侧读到的 mV：

| 键 | 标定值 | 说明 |
|---|---|---|
| 松开 | 0 mV | 实测空载落在最低档 |
| SET | ~260 mV | 最低的一档 |
| PLAY | ~759 mV | （工程里叫 `mode`，官方叫 PLAY） |
| VOL- | ~1237 mV | |
| VOL+ | ~1647 mV | 最高的一档 |

> 注：该工程文档同时记录「R77 = 10K 上拉到 3V3」，但实测松开状态是 0 mV 而不是 3.3 V。两者只有一种解释能自洽——**上拉电阻接在分压网络的顶端，而按键网络在空载时把 ADC 端拉到了地**。教程里以**实测电平**为准，不照抄文字描述。

### 1.2、Zephyr 侧读到的是「原始值」，不是 mV

`adc_read` 返回的是 17 位原始码值。本板的实测比例关系：

| 键 | ESP-IDF 标定 mV | Zephyr 实测 raw | 比值 |
|---|---|---|---|
| SET | 260 | 284–288 | 1.10 |
| PLAY | 759 | 830 | 1.09 |
| VOL- | 1237 | 1359 | 1.10 |
| VOL+ | 1647 | 1810–1811 | 1.10 |

**比值稳定在 1.10**，所以换算规则就是：`raw ≈ mV × 1.10`。这不是「校准」，只是这颗 ADC 在 17 位、默认增益/参考下的定标关系；换板子就要重新测。

于是阈值窗口（沿用工程里验证过的 ±100 mV，换算成 raw 后取整）：

| 键 | mV 窗口 | raw 窗口 |
|---|---|---|
| SET | 180–360 | 198–396 |
| PLAY | 660–860 | 726–946 |
| VOL- | 1140–1340 | 1254–1474 |
| VOL+ | 1550–1750 | 1705–1925 |

四段窗口之间有 **330 raw 左右的空隙**，足以容下未校准 ADC 的噪声（实测同一档抖动 ±5 raw）。

## 二、先确认「键到底在哪个通道」

这里有个容易被坑的点：板上写的是 **IO42**，而 Zephyr 里有两个 ADC 单元、每个 8 通道，**没有任何设备树信息告诉你 IO42 对应哪个 unit 的哪个 channel**。所以必须实测。

### 2.1、`app adc`：两个单元 × 8 通道全扫

```c
static int cmd_adc(const struct shell *sh, size_t argc, char **argv)
{
	int n = (argc > 1) ? atoi(argv[1]) : 10;

	shell_print(sh, "[adc] 采 %d 次（每次 200 ms），期间请按住要测的功能键", n);
	for (int i = 0; i < n; i++) {
		adc_row(sh, adc0_dev, "adc0(u1)");
		adc_row(sh, adc1_dev, "adc1(u2)");
		k_msleep(200);
	}
	return 0;
}
```

`adc_row` 逐通道 `adc_channel_setup` + `adc_read`，一行打 8 个值，并带时间戳（方便把「哪一段在被按」对上）：

```c
shell_fprintf(sh, SHELL_NORMAL, "%s [t=%ums]:", tag, k_uptime_get_32());
```

### 2.2、实测：按住 PLAY 的那 16 次采样

```text

adc1(u2):  1671  2721  1676  2747  1682  2660  1695  2702
adc0(u1):     0  2246  2148  2243  1773  2813  1752  2596
adc1(u2):  1735  2837  1736  2852  1733  2781  1736  2597

adc1(u2):  1734  2837  1732  2859  1765  2786  1761  2575
adc0(u1):   287  2246  2148  2245  1776  2819  1734  2564
adc1(u2):  1736  2827  1768  2856  1764  2783  1735  2565
...
adc0(u1):   286  2245  2148  2243  1781  2831  1734  2536
adc1(u2):  1736  2843  1735  2846  1736  2786  1731  2577
```

**判据非常干净**：

- `adc0(u1)` 的 **ch0** 从 `0` 跳到 `288`，其余 7 个通道全程只在 ±10 内抖；
- `adc1(u2)` 的 8 个通道**没有任何一档变化**。

结论：**IO42 = `adc0`（unit 1）的 channel 0** —— 换句话说，Zephyr 的 `adc0` 就是芯片的 ADC1，`ch0` 就是 GPIO42。四个键都在这一路。

> 顺带解释那堆「噪声」：`adc0` 其余通道读出来 1671–2860、`adc1` 读到 1670–2860，都是**悬空脚**在飘；它们没有外接电路，读数没有物理意义。这也是为什么「找按键」不能靠「看哪个通道数大」，只能靠「**看哪个通道在按键时变化**」。

## 三、`app key`：把电压变成按键名，再变成灯

### 3.1、窗口表

```c
struct key_window {
	const char *name;
	int32_t raw_lo;
	int32_t raw_hi;
};

static const struct key_window key_win[] = {
	{"SET",   180 * 110 / 100, 360 * 110 / 100},
	{"PLAY",  660 * 110 / 100, 860 * 110 / 100},
	{"VOL-", 1140 * 110 / 100, 1340 * 110 / 100},
	{"VOL+", 1550 * 110 / 100, 1750 * 110 / 100},
};
```

写 `180 * 110 / 100` 而不是直接写 `198`，是刻意的：**表里保留的是 mV 来源值**，一旦换了板子或改了 ADC 增益，只改 `110` 这一个比例，四个窗口一起动。工程上「保留来源数据」比「提前算好常数」更有价值。

### 3.2、单次读 + 判定

```c
static int read_io42(int32_t *out)
{
	struct adc_sequence seq = {
		.resolution = 17,
		.buffer = out,
		.buffer_size = sizeof(*out),
		.channels = BIT(0),
	};
	return adc_read(adc0_dev, &seq);
}

static int key_index(int32_t raw)
{
	for (int i = 0; i < ARRAY_SIZE(key_win); i++) {
		if (raw >= key_win[i].raw_lo && raw <= key_win[i].raw_hi) {
			return i;
		}
	}
	return -1;      /* 不在任何窗口 = 松开，或同时按了两个键 */
}
```

`channels = BIT(0)` 就是「只采 ch0」，`buffer` 只放一个 `int32_t`。这是最省的读法。

### 3.3、闭环：按键 → 颜色

```c
static int cmd_key(const struct shell *sh, size_t argc, char **argv)
{
	int n = (argc > 1) ? atoi(argv[1]) : 40;
	int last = -2;

	for (int i = 0; i < n; i++) {
		int32_t raw = 0;
		int k = -1;

		if (read_io42(&raw) == 0) {
			k = key_index(raw);
		}

		if (k != last) {                  /* 只在「状态变化」时打印 + 改灯 */
			last = k;
			shell_print(sh, "[key] raw=%d -> %s", raw, (k < 0) ? "松开" : key_win[k].name);

			if (k < 0) {
				g_mode = RGB_OFF;
			} else {
				g_base = key_color[k];   /* SET 红 / PLAY 绿 / VOL- 蓝 / VOL+ 黄 */
				g_mode = RGB_SOLID;
			}
		}
		k_msleep(100);
	}
	return 0;
}
```

两个设计要点：

1. **只在变化时打日志。** 100 ms 采一次，20 秒就是 200 条；如果每条都打，串口会被刷满、shell 会丢字符。用 `k != last` 做边沿检测，输出变成「按下一条、松开一条」，正是人想看的东西。
2. **每 100 ms 采一次，本身就是消抖。** 机械按键的抖动窗口在 5–20 ms，采样周期 100 ms 天然跳过了抖动区。**先别急着写「连续 3 次相同才算数」的消抖算法**——先看采样周期够不够；不够再加。

### 3.4、实测（依次按 SET / PLAY / VOL- / VOL+）

```text
app key 100
[key] 监听 100 次（每 100 ms），按键时 RGB 会亮起对应颜色
[key] raw=0 -> 松开
[key] raw=284 -> SET
[key] raw=0 -> 松开
[key] raw=830 -> PLAY
[key] raw=0 -> 松开
[key] raw=1359 -> VOL-
[key] raw=0 -> 松开
[key] raw=1810 -> VOL+
[key] raw=0 -> 松开
uart:~$
```

四档全部落在各自的窗口里，误差 ≤ 6 raw。**并且每按一次，RGB 就换一种颜色**——这说明「ADC 判定 → 应用状态 → 驱动 → 灯」这条链路是通的，不是只打印了一行字。

## 四、从「能识别」到「能当产品用」

`app key` 只做到「按下 / 松开」的瞬时判定。真实产品还要**单击、双击、长按**。这部分属于应用层状态机，不影响驱动，给一份能直接抄的骨架：

```c
/* 每个键一个独立的状态机；100 ms 调一次 */
struct key_fsm {
	int  stable;        /* 当前稳定状态：-1 松开 / 0..3 键号 */
	int  count;         /* 连续相同次数 */
	uint32_t t_down;    /* 按下时刻 */
	bool long_fired;
};

static void key_tick(int idx_now, uint32_t now)
{
	/* 1) 稳定判定：连续 3 次相同（300 ms）才认 */
	if (idx_now == fsm.stable) {
		fsm.count++;
	} else {
		fsm.stable = idx_now;
		fsm.count = 0;
	}

	if (fsm.count < 3) {
		return;
	}

	/* 2) 边沿事件 */
	if (fsm.stable >= 0 && !fsm.pressed) {
		fsm.pressed = true;
		fsm.t_down = now;
		fsm.long_fired = false;
	} else if (fsm.stable < 0 && fsm.pressed) {
		fsm.pressed = false;
		if (!fsm.long_fired) {
			/* 松开时判单击 / 双击：距上次松开 < 400 ms 算双击 */
			emit_click(fsm.key_id, now - fsm.t_up < 400 ? 2 : 1);
			fsm.t_up = now;
		}
	}

	/* 3) 长按：按住 800 ms 触发一次，然后每 300 ms 连发 */
	if (fsm.pressed && now - fsm.t_down > 800 &&
	    (now - fsm.last_repeat > 300 || !fsm.long_fired)) {
		fsm.long_fired = true;
		fsm.last_repeat = now;
		emit_long(fsm.key_id);      /* VOL- / VOL+ 长按 = 连续调音量 */
	}
}
```

三个经验值（在这块板子上实测可用）：

| 参数 | 值 | 为什么 |
|---|---|---|
| 采样周期 | 100 ms | 天然消抖，且 CPU 开销可忽略 |
| 稳定判定 | 连续 3 次（300 ms） | 低于 300 ms 的按压会被当成抖动丢掉，正常人按键 > 500 ms |
| 长按阈值 | 800 ms | 低于 600 ms 容易误触；高于 1000 ms 手感迟钝 |
| 双击窗口 | 400 ms | 500 ms 以上双击会「粘手」 |

## 五、PA_CTRL：功放的开关在应用层手里

板上两颗 **NS4150B**（左右声道各一颗）共用一根使能线 `PA_CTRL = GPIO7`。它的作用很朴素：**没拉高，喇叭就是哑的**——哪怕 I2S 数据流得再顺，声音也出不来。

设备树里给它一个「像 LED 一样」的节点，只为拿到现成的 API：

```dts
/ {
	leds {
		compatible = "gpio-leds";
		pa_ctrl: pa_ctrl_0 {
			gpios = <&gpio0 7 GPIO_ACTIVE_HIGH>;
			label = "PA_CTRL";
		};
	};

	aliases {
		pa-ctrl = &pa_ctrl;
	};
};
```

```c
static const struct gpio_dt_spec pa = GPIO_DT_SPEC_GET(DT_ALIAS(pa_ctrl), gpios);

int ret = gpio_pin_configure_dt(&pa, GPIO_OUTPUT_INACTIVE);   /* 上电默认静音 */
```

**上电默认 `INACTIVE`（拉低）是刻意的**：功放先关着，等应用决定要出声时再开。反过来（上电就开）会让开机瞬间的电源冲击和 I2S 未初始化状态直接在喇叭里炸一声「噗」。

命令：

```c
static int cmd_pa(const struct shell *sh, size_t argc, char **argv)
{
	int on  = !strcmp(argv[1], "on");
	int ret = gpio_pin_set_dt(&pa, on);

	shell_print(sh, "[pa] PA_CTRL(GPIO%d) = %d, 返回 = %s", pa.pin, on, ret == 0 ? "0" : "?");

	if (on) {                       /* 开功放时给一盏常亮绿灯：应用层语义 */
		g_mode = RGB_SOLID;
		g_base.r = 0x08; g_base.g = 0x20; g_base.b = 0x08;
	}
	return 0;
}
```

实测：

```text
app pa on
[pa] PA_CTRL(GPIO7) = 1, 返回 = 0
app stats
[stats] 模式=solid 亮度=15% 帧数=552 单帧耗时=2 ms 最后颜色=01 04 01
```

`01 04 01` = `(0x08, 0x20, 0x08)` × 15% ≈ `(1, 4, 1)`。**灯变成暗绿，就是「功放已开」的可观测证据**——因为 `PA_CTRL` 是纯输出脚，回读是不可靠的（`11-Zephyr驱动/GPIO.md` 里的第一处偏差：纯输出脚 `gpio_pin_get_dt` 恒读 0），所以必须借一路别的观测。

### 5.1、正确的开关时序（等 I2S 驱动可用之后）

```text
1. 配 codec（I2C 写 ES8389 寄存器）
2. 启动 I2S 数据流
3. 延时 10–20 ms（让第一帧数据到位）
4. gpio_pin_set_dt(&pa, 1)      ← 先有数据，再开功放
...
5. 停 I2S
6. gpio_pin_set_dt(&pa, 0)     ← 先关功放，再断数据
```

顺序反过来，喇叭里会有「咔」的一声——功放把未稳定的电平放大了。

## 六、BOOT 键（IO61）为什么用不了

板上还有一颗 BOOT 键，接 **IO61**。IO61 属于 bank1（GPIO32–63），而这套 PR 里 bank1 的驱动抽象**没有闭环**：`gpio_esp32.c` 的所有实例 `.gpio_base` 都取 `DT_REG_ADDR(DT_NODELABEL(gpio0))`，只有 `.gpio_dev` 用了各自的节点。结果是「用 bank1 的设备句柄去操作 bank0 的基址」。

实测证据（`11-Zephyr驱动/GPIO.md` 有完整版）：

```text
gpio_add_callback(gpio1, ...)          → 0   （pin_mask = 0x20000000，注册成功）
gpio_pin_interrupt_configure_dt(BOOT, EDGE_BOTH) → 0
轮询 0 次电平变化 / 回调 0 次 / gpio_get_pending_int(gpio1) = 0
gpio_pin_get_dt(BOOT) = 1  而  port_get_raw(gpio1) = 0     ← 互相矛盾
直读寄存器：ENABLE1 = 0x04000020（无 bit29）、IN1 = 0x18000414（bit29 恒 0）
gpio_pin_configure(gpio0, 61, INPUT|PULL_UP) → -EINVAL
```

**所有 API 都返回 0，但硬件毫无反应。** 这是驱动层问题，应用层绕不过去。

三条出路：

| 方案 | 可行性 | 说明 |
|---|---|---|
| 等上游修复 bank1 | ✅ 最正 | PR 合入后重编即可，应用层代码一行不用改 |
| 直接读寄存器（`sys_read32(0x20583000 + 0x68)` 取 bit29） | ⚠️ 能读 | 但这是绕开驱动，违背教程「应用层不碰寄存器」的分层原则，只在调试时用 |
| 改用 IO42 四键 | ✅ 推荐 | 四键已经完整可用，功能上比 BOOT 键丰富得多 |

**这也是一份「应用层教程」最该诚实的地方**：不是我写不出代码，是这颗键在这个树里物理上读不到。

## 七、这一篇踩过的坑

| 现象 | 原因 | 解法 |
|---|---|---|
| 以为 4 个键要 4 个 GPIO | 硬件是 ADC 电阻梯 | 走 `adc0` ch0，按窗口判档 |
| 不知道该读哪个 ADC 通道 | 设备树不提供引脚→通道映射 | `app adc` 双单元全扫，看按键时哪个通道跳 |
| 用「读数最大的通道」猜按键 | 悬空脚读数 1671–2860，比按键档还大 | 只能看**变化**，不能看绝对值 |
| 串口被 `ADC reading is uncompensated` 刷满 | 未校准 ADC 每读一次打一条警告 | `CONFIG_LOG_DEFAULT_LEVEL=1`；这不是错误，正常现象 |
| 阈值直接按 mV 写进代码 | Zephyr 读的是 17 位原始值，比值 1.10 | 窗口按 `mV × 110 / 100` 换算 |
| 同时按两个键判成「没按」 | 电阻梯读到中间电压，落在窗口空隙 | 硬件限制，接受它；或用「离哪个窗口最近」做兜底 |
| `PA_CTRL` 开了却听不到声音 | 本树没有 I2S / ES8389 驱动 | PA 只是使能，出声还需要 codec + I2S |
| 想回读 `PA_CTRL` 电平验证 | 纯输出脚 `gpio_pin_get_dt` 恒 0 | 改用灯/万用表/外设行为做观测 |
