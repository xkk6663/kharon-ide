# 换芯片实战（三）：把 STM32F103C8T6（Blue Pill）接进这棵树

> **现状校准（2026-11-19）**：F103 已进入当前主线：应用 `applications/stm32f1/f103_breath`，
> 工程 `kharon-manifest/products/kharon/f103_breath.yaml`，日常入口 `kharon build/flash/debug -p f103_breath`。
> 本文命令是 2026-11-15/16 的现场记录，`build.ps1` / `env.ps1` / `.venv` 属于旧入口；
> 对照映射见本组 README §4.1。正文保留现场细节。

> 一句话结论：**同一厂商、同一系列（STM32F 系列）里换型号，`main.c` 和 `build.ps1` 的用法都不用改；但这棵树里的 F1 系列是"半张白纸"——厂商 HAL 包、pinctrl dtsi、`core_cm3.h`、LL 头 shim 四样要先补齐，才轮得到"写代码"。补齐有两条路：**能通网就按 §3.1 的清单一次性拉上游仓**，没网才走 §4~§7 的离线复原。**
>
> 本篇是第 15 组第三篇。前两篇各自解决一个问题：`换芯片实战.md`（RISC-V → Xtensa，换架构）、`换芯片实战-STM32F411.md`（ESP32 → STM32F411，换厂商 + 换探针）。这一篇解决第三个问题：**换了厂商之后，换同系列里"更小的一颗"，为什么反而更麻烦**——因为你踩的不再是板级差异，而是"这棵树压根没装过这个系列"。

## 1. 硬件：这轮少一根按键线

| 东西 | 实物 | 接到哪 |
|---|---|---|
| 开发板 | Blue Pill（STM32F103C8T6，LQFP48） | — |
| 烧录器 | DAP-Link（CMSIS-DAP） | SWDIO / SWCLK / GND / 3V3 四根 |
| 串口 | DAP-Link 的 CDC 虚拟串口 | 板子 **PA9(TX) → 探针 RX**、**PA10(RX) → 探针 TX**，共地 |
| 灯 | 板载 LED | **PC13，低电平点亮**（`GPIO_ACTIVE_LOW`） |
| 按键 | **无** | 板上只有 NRST / BOOT0 两个按钮，都不是 GPIO |

**这一格"按键：无"是本篇和第二篇的第一个实质差别。** 第二篇能按 PA0 验证去抖，是因为 Black Pill 板上真有一颗接在 PA0 的按键；Blue Pill 没有。所以：

- 本轮需求里也没有提按键，工程就只做"呼吸 + 串口统计"；
- **不能照抄 `DT_ALIAS(sw0)`**——`stm32f103_mini` 的板级 dts 里根本没有 `sw0` 别名，写了会直接编译报错（`undefined node label 'sw0'`）。

如果你以后要在这块板上做按键，得自己飞一根线到 PA0（或任意 GPIO），再在 overlay 里加一个 `gpio-keys` 节点并给出 `sw0` 别名——那是"给板子加外设"，不是"换芯片"。

## 2. 这块板在树里叫什么

| 问题 | 答案 |
|---|---|
| 板目标 | `stm32f103_mini`（`zephyr\boards\others\stm32f103_mini`） |
| 完整 target 名 | `stm32f103_mini/stm32f103xe`（qualifier 是 SoC 名） |
| 板级 dts 的 SoC include | `<st/f1/stm32f103Xc.dtsi>` → 一路展开到 `stm32f103Xb.dtsi` |
| 板级 dts 的引脚 include | `<st/f1/stm32f103r(c-d-e)tx-pinctrl.dtsi>` |
| LED / 控制台 | `gpioc 13 GPIO_ACTIVE_LOW`（`led0` 别名）、`usart1` + `usart1_tx_pa9`/`usart1_rx_pa10` |
| 时钟 | HSE 8 MHz → PLL ×9 → **72 MHz**，AHB 1 / APB1 2 / APB2 1 |

**注意这里有个"名不副实"：板子按 F103xE 建，实物是 C8T6。** `xe` 是 256 KB flash / 48 KB RAM 那一档，`C8T6` 是 **64 KB flash / 20 KB RAM**。两者引脚完全同构，只有容量差 4 倍。这件事对"能不能跑"没影响（这轮固件 17104 B，塞进 64 KB 绰绰有余），但对"报告准不准"影响很大——你会在 size 报告里看到 `26.10%` 还是 `6.68%` 的差别。

处理办法见第 7 节：**不新建板子，只在工程 overlay 里把 `flash0` / `sram0` 的 `reg` 改回实物值。**

顺带一句证据：OpenOCD 连上这颗芯片时自己打印了 `device id = 0x20036410` 和 `flash size = 64 KiB`（见第 10 节），说明"实物是 64 KB"这件事不是我推的，是探针读出来的。

## 3. F1 在你树里是"缺口"：三处空

换厂商那一轮（第二篇）我们只复原了 F4 需要的那一份，于是**接手时**这棵树的状态是：

| 位置 | 现状 | 后果 |
|---|---|---|
| `west\modules\hal\stm32\dts\st\` | 只有 `f4\`（1 个文件） | 板级 dts 的 `#include <st/f1/...pinctrl.dtsi>` 找不到 |
| `west\modules\hal\stm32\stm32cube\` | 只有 `stm32f4xx\`（+ `common_ll`） | `CONFIG_SOC_SERIES_STM32F1X` 找不到 `stm32f1xx` 子目录，CMake 直接失败 |
| `west\modules\hal\cmsis_6\CMSIS\Core\Include\` | 只有 `core_cm4.h` | F1 的 `stm32f103xe.h` 里写的是 `#include "core_cm3.h"` |

好消息是 **Zephyr 核心仓那边是齐的**：

- `zephyr\dts\arm\st\f1\` 有 15 个 SoC dtsi（`stm32f1.dtsi`、`stm32f103X6/X8/Xb/Xc/...`、`stm32f105/107`）；
- `zephyr\soc\st\stm32\stm32f1x\` 有完整 SoC 支撑代码；
- `stm32cube\series_list.cmake` 的 `supported_series` 里**已经写着 `stm32f1`**——也就是说"缺的只是那份厂商包"，不是"Zephyr 不支持 F1"。

所以这一篇的绝大部分工作量，是把四样东西搬回树上。下面按"照着做就能复现"的顺序写。

### 3.1 先选路线：拉齐上游仓（推荐，已完成）/ 离线复原（退路）

这四样东西**本来都在上游**，只差一次 `west update`。网络能通时，正确做法是让 git 把两个模块拉到 `west.yml` 钉住的 revision 上；网络不通时，才用第 4~7 节那种"按 URL 一个个取"的离线复原。

**本轮结果（2026-11-16 晚）：`hal_stm32` 与 `cmsis_6` 已换成真 git 仓，双板 `-Pristine` 复编通过、烧录与串口也补跑过；crypto 两个在 §3.2 同一轮补拉成功**：

| 项目 | 落点 | HEAD（= `west.yml` 钉住的 revision） | 取法 | 规模 |
|---|---|---|---|---|
| `hal_stm32` | `west\modules\hal\stm32` | `2fd0502dd5e02aa3e95a2f01278fdf27e42d7229` | 无 blob 克隆 + 稀疏检出（分 5 批补 blob） | 2682 文件 / 185.5 MB（含 `.git`） |
| `cmsis_6` | `west\modules\hal\cmsis_6` | `1c1840af7a7e757d6e2fec3ddb0e5ce0dfcc93c8` | 整仓浅克隆（第 3 次成功） | 796 文件 / 18.3 MB |

复编结果与离线复原版**完全一致**（同一套源码语义、同一个 bin 尺寸）：F103 `17104 B`（FLASH 26.10% / RAM 25.55%），F411 `19940 B`（3.80% / 4.25%）——这正好反证"离线复原那几份文件补得对"，也是"换来源必须重编、不能沿用旧数字"的一次实证。

> **烧录与串口也已在上游模块落地之后补跑**（插上 DAP-Link，`west flash` + `probe_serial.py COM10 32`）：`SWD DPIDR 0x1ba01477`、`Cortex-M3 r1p1`、`device id = 0x20036410`、`flash size = 64 KiB`、`wrote 17104 bytes`；串口横幅 `k_busy_wait(1000 us) = 72429 cycles = 1005 us (core 72 MHz)`、`breathing ON`，32 s 窗口 `duty 38~1000 µs`、`avg=1010 / min=1006 / max=1039 / late=0`、约 981 帧/s。**换源码来源之后烧录与运行表现与离线版一致**，第 11~12 节那三组数字不用改。

**待拉齐清单**（`revision` 都读自 `west\zephyr\west.yml`，不是抄来的）：

| 项目（west 名） | 落点 | revision | 上游包里本来有什么 | 离线复原只塞了什么 |
|---|---|---|---|---|
| `hal_stm32` | `west\modules\hal\stm32` | `2fd0502dd5e02aa3e95a2f01278fdf27e42d7229` | STM32Cube 的**全系列** HAL/LL（F0/F1/F2/F3/F4/F7/G0/G4/H5/H7/L0/L1/L4/L5/U5/WB/WL…）+ `dts\st\` 下每个系列的整套引脚库（`f1\` 就有 58 个文件）+ `stm32cube\common_ll\include\` 那 42 个统一入口（**每个文件里已经写好了所有系列的分支**） | 上一轮只塞了 `stm32f4xx\`；这一轮只加了 `stm32f1xx\`、`dts\st\f1\` 的**一个** pinctrl 文件，外加 42 个手写的 LL shim（只认 F4，这轮给其中 22 个补了 F1 分支） |
| `cmsis_6` | `west\modules\hal\cmsis_6` | `1c1840af7a7e757d6e2fec3ddb0e5ce0dfcc93c8` | CMSIS Core 的**全部**内核头（`core_cm0/0plus/1/3/4/7/23/33/35p/sc000/sc300.h`）+ `m-profile\` | 上一轮只有 `core_cm4.h`；这一轮补了 `core_cm3.h` 等 10 个 |

一句话：**离线复原出来的树，"能编 F4 和 F1"，但少的是整个系列库和上游维护的 LL 入口**。手工那 42 个 shim 是这轮最不该长期背的债——上游版本里每个系列分支都是现成的。

拉齐的姿势（`west update` 要求目标目录"不存在或已是本项目的 git 仓"，这两个目录是手工建的，直接 update 会因"目录非空且不是 git 仓"失败），所以顺序必须是**先挪走、再 clone、再 checkout 到 revision**。这三步已经封成脚本：

```powershell
# 1) 只看清单，不联网、不改文件
pwsh -File .\tools\pull-stm32-modules.ps1 -DryRun

# 2) 真拉（默认走本机 127.0.0.1:7890 代理 + 稀疏模式；直连加 -Direct，换端口用 -Proxy）
pwsh -File .\tools\pull-stm32-modules.ps1

# 网络特别好的时候可以一把拉全（跳过稀疏检出），代价是单包大、断了要重来
pwsh -File .\tools\pull-stm32-modules.ps1 -Full
```

脚本做五件事，且**失败不会把树弄坏**：

1. 从 `zephyr\west.yml` 现读两个 revision（清单改了它自动跟着改）；
2. 旧目录整体挪到 `west\_offline_bak_<时间戳>\`（**不删**，编译验证过再手动清）；
3. `hal_stm32` 默认走**无 blob 克隆 + 稀疏检出**：先 `git clone --depth 1 --filter=blob:none --no-checkout`（只有 commit/tree，几百 KB），再 `fetch --depth 1 origin <revision>` 取钉住的那个 commit，`sparse-checkout init --no-cone` 后**分批**补 blob（根文件/zephyr → `stm32cube` 的 CMake 与 `common_ll` → `stm32f1xx` → `stm32f4xx` → `dts`），每批几 MB；
4. 失败自动重试（默认 20 次 × 6 s），卡住 60 s 就自己断（`http.lowSpeedTime=60`）再重来；重试的是**整批**，不是续传；
5. 校验 `HEAD == revision` + 六个关键路径（F1 的 `stm32f1xx` / 启动文件 / pinctrl / LL 入口，`core_cm3.h` / `core_cm4.h`），任一缺失直接红字报出来。

稀疏检出留下的仓是"缺其它系列 blob、但 git 关系完整"的：`git status` 干净、`HEAD` 对得上 revision、`west` 认它是本项目，只是 F0/F7/H7 那些用不到的系列 blob 没下载（真要用时 git 会按需补）。想补齐全部内容：在模块目录里 `git sparse-checkout disable`（要联网）。

拉齐之后**必须重跑一遍实测**（因为编的源码换了来源，不是同一批文件了）：

```powershell
.\tools\build.ps1 -App .\applications\stm32f1\f103_breath -Board stm32f103_mini -Pristine
.\tools\build.ps1 -App .\applications\stm32f4\f411_breath -Board blackpill_f411ce -Pristine
```

两条都绿了再谈 `-Flash`。本轮两条都已跑通（`build=97.6s` / `107.9s`，bin `17104 B` / `19940 B`），随后也补跑了烧录与串口（见 §3.1 开头、§11、§12.2：`device id 0x20036410`、`wrote 17104 bytes`、`avg=1010 / late=0`），三组数字与离线复原版一致。另外确认 west 也认这些目录：

```powershell
west list | Select-String "hal_stm32|cmsis_6|mbedtls|tf-psa"
```

```
cmsis_6       modules/hal/cmsis_6           1c1840af7a7e757d6e2fec3ddb0e5ce0dfcc93c8
hal_stm32     modules/hal/stm32             2fd0502dd5e02aa3e95a2f01278fdf27e42d7229
mbedtls       modules/crypto/mbedtls        c43f34b93797e81fd0257c30004dcd0ae332ae51
tf-psa-crypto modules/crypto/tf-psa-crypto  765af96a20a2b408474dcd950372ba9af4d26b62
```

> **本机网络实况（2026-11-16 19:00 起，写在这里省你一次误判）**：代理恢复后 `curl.exe` 走 `127.0.0.1:7890` 连 `github.com` 4/4 成功（3.9~7.9 s），`git ls-remote` 2/2 成功，但**传输阶段仍然脆**：
> - `cmsis_6` 整仓 18.3 MB：第 1 次跑到 210 s 报 `early EOF / invalid index-pack output`，第 2 次 TLS 握手就失败，**第 3 次 93 s 拉完**；
> - `hal_stm32` 整仓浅克隆：第 1 次 6 分钟 `tmp_pack` 一直是 0 B（挂死），第 2 次跑到 13.5 MiB 时 `early EOF` 断掉（约 51%），第 3 次同样断在 `44 bytes of body are still expected`；
> - 换**无 blob 克隆**（220 KB，一次过）+ 稀疏分批补 blob（5 批，58 s 走完）才把 `hal_stm32` 拿下来。
>
> 结论：这支代理对大 pack 会截断，**能下来的是"小请求、多批次"**。所以脚本默认走稀疏模式，"整仓一次拉全"只在网络好时手动 `-Full`。

### 3.2 顺带把 crypto 两个也换成真仓（ESP32 那条线要用）

脚本其实不只管 STM32：清单里还有 `mbedtls` 与 `tf-psa-crypto`（ESP32 的 HTTPS / WPA 原语要吃）。2026-11-16 20:30 之后同一支代理恢复，补拉成功：

| 项目 | 落点 | HEAD（= pin） | 规模 | 与旧补文件目录对比 |
|---|---|---|---|---|
| `mbedtls` | `modules\crypto\mbedtls` | `c43f34b93797e81fd0257c30004dcd0ae332ae51` | 335 文件 | 旧目录多出的 19 个文件全是它自己的 `.git` 脚手架，**源码一份不缺** |
| `tf-psa-crypto` | `modules\crypto\tf-psa-crypto` | `765af96a20a2b408474dcd950372ba9af4d26b62` | 626 文件 / 24 MB | 逐文件比对 **626 vs 626，差集为空** |

**这一节真正的坑是 URL，不是网络**：`west.yml` 里 crypto 两条**没有写 `url`**，走文件头 `defaults: remote upstream`，而 `upstream` 的 `url-base` 是 `https://github.com/zephyrproject-rtos`——所以钉住的 revision 只存在于 **zephyrproject-rtos 的镜像仓**里。按直觉去拉原厂 `Mbed-TLS/mbedtls`，克隆会成功（默认分支 HEAD `33cc9de`），但再想取 pin 就报：

```
fatal: remote error: upload-pack: not our ref c43f34b93797e81fd0257c30004dcd0ae332ae51
```

这个报错长得像网络问题（`exit 128`），实测却连试 22 次一模一样——**换 URL 就一次过**。判据很简单，一条命令就能验：

```powershell
git ls-remote https://github.com/zephyrproject-rtos/mbedtls HEAD        # → c43f34b…（正好是 pin）
git ls-remote https://github.com/zephyrproject-rtos/tf-psa-crypto HEAD  # → 765af96…（正好是 pin）
```

两个镜像的 `HEAD` 都**正好等于 pin**，所以整仓 `clone --depth 1` 下来不用再补 fetch，脚本里"HEAD ≠ pin 才补 fetch"的分支在这两条上根本不会触发。

**另一个必须记住的取舍**：crypto 两个仓只有 20 MB 量级，**别用稀疏检出**。`tf-psa-crypto` 我先按大仓走了无 blob 克隆，结果卡在 `checkout`——稀疏检出之后 checkout 仍要按需下载几百个 blob，代理一抖就 `exit 128`；改成普通 `clone --depth 1`（第 4 次重试成功，15.6 s）就干净落地了。判据：**仓 < 30 MB 走整仓，> 100 MB 才上无 blob**。

crypto 换完之后，ESP32 那条线要重编一次（`zephyr` 里还留着 `modules/mbedtls/legacy_support.cmake` 的本地补丁，正好借这次复编确认它还成立）。

下面第 4~7 节是**离线复原（退路）**，只在你确实没网时用；已经拉齐的话可以整段跳过，直接看第 8 节。

## 4. 离线复原（退路）①：pinctrl dtsi（1 个文件）

> 只在没网时走这一节；能用 §3.1 的脚本拉齐就跳过 4~7。

上游位置：`hal_stm32` 的 `dts/st/f1/`，共 58 个 pinctrl 文件（`api.github.com` 列目录一次 200 成功，第二次就被 403 限流——60 次/小时，别连用）。

**只搬板子真正 include 的那一个**：`stm32f103r(c-d-e)tx-pinctrl.dtsi`，37738 B。

```powershell
# 注意两件事：① URL 里的括号要编码成 %28 %29；② 落盘文件名要保留括号（板级 dts 里就是这个名字）
curl.exe -L --retry 2 --connect-timeout 20 `
  -o "C:\Users\xiao1\Desktop\ELAB\kharon-ide\west\modules\hal\stm32\dts\st\f1\stm32f103r(c-d-e)tx-pinctrl.dtsi" `
  "https://raw.githubusercontent.com/zephyrproject-rtos/hal_stm32/2fd0502dd5e02aa3e95a2f01278fdf27e42d7229/dts/st/f1/stm32f103r%28c-d-e%29tx-pinctrl.dtsi"
```

`2fd0502dd5e02aa3e95a2f01278fdf27e42d7229` 是 `zephyr\west.yml` 里 `hal_stm32` 钉的 revision——**取上游文件一律按这个 SHA，别用 `main`**，否则你会在"版本漂移"上浪费一晚。

网络现实（本轮实测）：`Invoke-WebRequest` 对 raw 小文件经常 `基础连接已经关闭`；`curl.exe -L --retry 2` 三次都成。同一个 URL 换 `gh-proxy.com` / `ghfast.top` / `ghproxy.net` 三个镜像全断，`api.github.com` 用过一次就 403。结论：**curl 直连 raw，慢就慢，别折腾镜像。**

### 5.1 CMakeLists：5210 B，别拿 F4 的改

它是一份"按 Kconfig 开关逐条挂源文件"的清单，61 条 `zephyr_library_sources(_ifdef)`，路径写死是 `drivers/src/...`：

```cmake
zephyr_library_sources(soc/system_stm32f1xx.c)
zephyr_library_sources(drivers/src/stm32f1xx_hal.c)
zephyr_library_sources(drivers/src/stm32f1xx_hal_rcc.c)

## 6. 离线复原（退路）③：`stm32f1xx_hal_conf.h`（Cube 里没有）

Cube 包只提供 `stm32f1xx_hal_conf_template.h`，而 `stm32f1xx_hal.h` 第 29 行写的是：

```

缺它就会在**第一次编译任何 C 文件时报**：

```
fatal error: stm32f1xx_hal_conf.h: No such file or directory
```

正确做法：取 **上游 Zephyr 定制版**（16117 B），放到 `drivers\include\stm32f1xx_hal_conf.h`：

### 7.2 `common_ll` 的 shim 只有 F4 分支

`stm32cube\common_ll\include\stm32_ll_*.h` 是上一轮**手写**的单系列 shim（不是上游原样），长这样：

```c
/* Local shim generated from STM32CubeF4 (single-series tree). */
#if defined(CONFIG_SOC_SERIES_STM32F4X)
#include <stm32f4xx_ll_gpio.h>
#endif
```

F1 编译时它会安静地什么都不包含，然后在两个地方炸：

```
soc\st\stm32\common\gpioport_mgr.c:164: 'LL_GPIO_PULL_UP' undeclared
soc\st\stm32\common\stm32_backup_domain.c:24: implicit declaration of 'LL_PWR_EnableBkUpAccess'
```

修法是给每个"F1 也有对应头"的 shim 加一条 `#elif` 分支（共 22 个文件，`adc/bus/cortex/crc/dac/dma/exti/fsmc/gpio/i2c/iwdg/pwr/rcc/rtc/sdmmc/spi/system/tim/usart/usb/utils/wwdg`）：

```c
/* Local shim (offline tree: F1 + F4). */
#if defined(CONFIG_SOC_SERIES_STM32F4X)
#include <stm32f4xx_ll_gpio.h>
#elif defined(CONFIG_SOC_SERIES_STM32F1X)
#include <stm32f1xx_ll_gpio.h>
#endif
```

其余 20 个不用动，它们分两类（**现场数的，不是估的**）：15 个是"F4 也没有这个外设"的纯注释文件（`bdma/comp/crs/dbgmcu/dcache/dmamux/hsem/i3c/icache/ipcc/lpuart/opamp/pka/radio/ucpd`），5 个是只转发 F4 头的单行 include（`dma2d/fmc/fmpi2c/lptim/rng`——F1 确实没有这些外设）。**空 shim 不是 bug，是"这个系列没有这个外设"的诚实表达**；真正该做的是换成上游仓（§3.1），而不是继续在这 42 个文件上手工补分支。

> 一次性做法（本轮实际用的）：遍历 `common_ll\include`，对每个 `stm32_ll_X.h` 检查 `stm32f1xx\drivers\include\stm32f1xx_ll_X.h` 是否存在，存在就重写成上面那段"F4 + F1"两分支。这样以后加 F0/F7 只是再补一条 `#elif`。

## 9. overlay：把 256 KB 改回 64 KB

`applications\stm32f1\f103_breath\boards\stm32f103_mini.overlay`，两段：

```dts
/ {
	chosen {
		zephyr,console = &usart1;
		zephyr,shell-uart = &usart1;
	};
};

/* C8T6 的真实容量：64 KB flash / 20 KB SRAM（对照 dts\arm\st\f1\stm32f103X8.dtsi） */
&flash0 {
	reg = <0x08000000 DT_SIZE_K(64)>;
	ranges = <0 0x8000000 DT_SIZE_K(64)>;
};

&sram0 {
	reg = <0x20000000 DT_SIZE_K(20)>;
};
```

**这里有一个必须踩过才知道的坑**：一开始我是这么写的——

```dts
/ {
	soc {
		flash-controller@40022000 {
			flash0: flash@8000000 { reg = ...; };
		};
		sram0: memory@20000000 { reg = ...; };
	};
};
```

结果 DTS 直接报：

```
devicetree error: Label 'sram0' appears on /memory@20000000 and on /soc/memory@20000000
```

意思是"你居然又声明了一个同名节点"，而不是"你在覆盖原节点"。**结论：想改已有节点一律用标签 `&flash0` / `&sram0`，不要靠重写路径去合并。**（DTS 的合并规则对"同名 label"很敏感，路径写对了也可能因为 `#address-cells` 之类的上下文不同被当成新节点。）

后面那几条 `&usart2/&i2c1/&rtc/... status = "disabled"` 是"这轮不用的板载外设"，和第二篇同样的思路：关掉不等于板子坏了，只是少初始化几个设备。

**编完要回读一次 dts**，确认改写真的生效（而不是"看着改了"）——`build\stm32f1\f103_breath\default\zephyr\zephyr.dts` 里：

```dts
/* node '/soc/flash-controller@40022000/flash@8000000' */
flash0: flash@8000000 {
	reg    = < 0x8000000 0x10000 >;        /* in ..\applications\stm32f1\f103_breath\boards\stm32f103_mini.overlay:20 */
	ranges = < 0x0 0x8000000 0x10000 >;    /* in ..\applications\stm32f1\f103_breath\boards\stm32f103_mini.overlay:21 */
};

/* node '/memory@20000000' */
sram0: memory@20000000 {
	reg = < 0x20000000 0x5000 >;           /* in ..\applications\stm32f1\f103_breath\boards\stm32f103_mini.overlay:25 */
};
```

`0x10000` = 64 KB、`0x5000` = 20 KB，注释还直接标出"来自本工程 overlay"——这是 **dts 层的回读证据**，和下一节 OpenOCD 打印的 `flash size = 64 KiB` 互相印证：一个来自编译期，一个来自探针读芯片。

### 12.2 长窗口统计（`logs\f103-serial-run.txt`，50 s）

```
t=  32 s duty= 549 us frame avg=1010 min=1006 max=1037 us late=0 frames=31389
t=  34 s duty=  59 us frame avg=1010 min=1008 max=1037 us late=0 frames=33351
t=  36 s duty= 962 us frame avg=1010 min=1006 max=1039 us late=0 frames=35313
...
t=  50 s duty=  22 us frame avg=1010 min=1006 max=1037 us late=0 frames=49047
```

- `duty` 在 **22…998 µs** 之间游走 → 呼吸曲线（sin²）在 0→1000→0 之间走完了；
- `frames` 50 s 走了 49047 帧 → **≈981 帧/s**，接近 1 kHz 目标（每帧实际 1010 µs，所以是 990 Hz 左右）；

**为什么 PC13 又是软 PWM**：和第二篇同一个原因——F103 的 PC13 在复用表里只有 GPIO / RTC-TAMP / EXTI13，**没有任何 `TIMx_CHy`**，硬件 PWM 到不了这颗灯。这一条跟"芯片便宜"没关系，跟"这颗脚在封装里怎么复用"有关。

| 6 | `'LL_GPIO_PULL_UP' undeclared` | `common_ll` shim 只写了 F4 分支 | 给 22 个 shim 加 `#elif ... STM32F1X` |
| 7 | `implicit declaration of 'LL_PWR_EnableBkUpAccess'` | 同 6（`stm32_backup_domain.c`） | 同 6 |
| 8 | `Label 'sram0' appears on /memory@20000000 and on /soc/memory@20000000` | 用 `/ { soc { ... } }` 重写节点，被当成新节点 | 用标签 `&flash0` / `&sram0` 覆盖 |
| 9 | size 报告分母是 256 KB | 板目标 SoC 是 `xe`，实物是 `c8` | overlay 里改 `flash0`/`sram0` 的 `reg` |
| 10 | `undefined node label 'sw0'` | Blue Pill 没有用户按键，板 dts 也没 `sw0` | 本工程不做按键；要用就自己飞线 + overlay 加 `gpio-keys` |
| 11 | 产物落到 `build\stm32f4\...` | `build.ps1` 把 `stm32*` 全归 F4 | 加 `stm32f103|stm32f1` 分支，并让默认 OpenOCD cfg 按系列分流 |
| 12 | `check-layout.ps1` 报"层级不合规" | 白名单没 `stm32f1` | `$allowedTop` 增加 `stm32f1` |
| 13 | OpenOCD 认不出内核 | 默认 cfg 是 `target/stm32f4x.cfg` | F1 版 cfg 用 `target/stm32f1x.cfg` |
| 14 | `Failed to read memory at 0xe000ed04` | 没接 nRST，复位后读 DEMCR 失败 | 当噪音看；要确定性复位按 NRST / 重插 USB |
| 15 | 新 overlay 不生效 | 增量 configure 不重跑 dts | 第一次必须 `-Pristine` |
| 16 | 拉 crypto 报 `upload-pack: not our ref` | `west.yml` 没写 `url`，走 `defaults: remote upstream` → 仓在 `zephyrproject-rtos` 镜像，不在 `Mbed-TLS` 原厂 | 用 `git ls-remote https://github.com/zephyrproject-rtos/<repo> HEAD` 验一遍（HEAD 应等于 pin），再克隆 |
| 17 | 小仓上无 blob 克隆卡在 `checkout` | 稀疏检出后 checkout 仍按需下载 blob，代理一抖就 `exit 128` | 仓 < 30 MB 直接整仓 `clone --depth 1`；> 100 MB 才用无 blob + 稀疏 |

> 和第 15 组第二篇的 18 条坑表合起来看：**F4 那 18 条讲"换厂商要补哪三层"，这 17 条讲"补得不够全时会在哪炸"**。真正复用价值在第 3/4/5/6 条——它们是"离线复原一个 STM32 系列"的标准动作清单。

## 14. 和 F411 那篇的差异对照

| | STM32F411CEU6（第二篇） | STM32F103C8T6（本篇） |
|---|---|---|
| 板目标 | `blackpill_f411ce`（一段式） | `stm32f103_mini`（两段式 `stm32f103_mini/stm32f103xe`） |
| 树里模块现状 | 缺，需补 `stm32f4xx` + pinctrl + `core_cm4.h` | **再缺一次**：`stm32f1xx` + pinctrl + `core_cm3.h` + LL shim |
| 主频 | 96 MHz（HSE 25 MHz ×…） | 72 MHz（HSE 8 MHz，PLL ×9） |
| LED | PC13 低电平亮，无 TIM 通道 | 同（PC13 低电平亮，无 TIM 通道） |
| 按键 | PA0（`sw0` 别名，板载） | **无**（板载只有 NRST/BOOT0） |
| 软 PWM 帧周期实测 | 1005 µs | 1010 µs |
| 固件体积 | 19940 B / 3.80%（512 KB） | 17104 B / 26.10%（**64 KB**） |
| 探针 | DAP-Link，`stm32f4x.cfg` | 同一个 DAP-Link，`stm32f1x.cfg` |
| 容量与实物不符 | 无（板 dts 就是 512 KB） | **有**（板 dts 256 KB，实物 64 KB）→ overlay 改 |

## 15. 迁移检查表：下一块 F1 板照着走

1. **树里有没有这个系列**：`modules\hal\stm32\stm32cube\{series}xx\`、`dts\st\{family}\`、`cmsis_6` 里对应的 `core_cmX.h`。缺哪个补哪个（第 4~7 节）。
2. **板目标 name 与 qualifier**：`west boards | Select-String <关键词>`，确认 `-Board` 该写什么。
3. **板 dts 的 SoC 档位 vs 实物容量**：不一样就在 overlay 改 `&flash0` / `&sram0`，别让 size 报告骗你。
4. **LED / 控制台是否已是 `led0` / `usart1`**：是就别写引脚号；不是就在 overlay 里加别名。
5. **这颗灯有没有定时器通道**：查复用表 / `zephyr.dts` 里 `pwm` 节点有没有这颗脚的 pinctrl。没有就软 PWM（第二篇 7.1 的实现可以直接搬）。
6. **有没有用户按键**：没有就别写 `DT_ALIAS(sw0)`。
7. **探针**：DAP-Link 一律 `interface/cmsis-dap.cfg`，只改 `target/stm32fXx.cfg`；没接 nRST 就 `reset_config none`。
8. **仓库入口**：`build.ps1` 的 chip 推断、`check-layout.ps1` 的白名单、`-OpenocdConfig` 默认值，三处都要认识新系列。
9. **第一次编译一定 `-Pristine`**，否则新 overlay 不进 dts。
10. **抓横幅用 `west flash` 而不是 `build.ps1 -Flash`**（后者 configure 太慢，窗口会错过）。
