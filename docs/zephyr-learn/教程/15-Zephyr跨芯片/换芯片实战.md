# 15 · 无缝换芯片实战：同一份应用代码，从 Korvo-1(S31) 跑到 ESP32-S3

> **现状校准（2026-11-19）**：这是 S31→S3 的历史实战，保留现场命令与数字；
> 当前仓库操作主线已切到 **F411/F103 + Kharon**（见 `tutorials/10–14`），
> 旧 `env.ps1` / `.venv` / `build.ps1` 的对照映射见本组 README §4.1。

> **实测环境**：Win11 + pwsh 7 + Zephyr `4.5.99` / commit `34e025569cbb` + Zephyr SDK `1.0.1`
> **本回合手上有两块板**：
> - Korvo-1（ESP32-S31，RISC-V，`COM9`，CP210x）
> - ESP32-S3 最小开发板（Xtensa，`COM11`，**芯片内置 USB-Serial-JTAG**，VID_303A&PID_1001）
>
> 这一章里每一段串口原文都是从 `logs\serial-s3-*.txt` 里直接抄的，不是"理论上应该"。唯一没实机验证的环节是最后那一趟"Korvo 回归烧录"——那会儿 COM9 已经从设备管理器里消失了（板子被拔下来换成了 S3），所以只留了编译回归，正文里明确标了出来。

## 0. 这一章到底解决什么问题

你提出的需求是"把官方给的 S3 的 Zephyr 镜像拉下来，做无缝换芯片的教程"。拆开它，其实是三个问题：

| # | 问题 | 一句话答案 |
|---|---|---|
| Q1 | 有没有"官方 S3 镜像"可以直接刷？ | **没有**。Zephyr 只发"官方支持"（板级定义 + 工具链），不发预编译 `.bin`。你得自己编。 |
| Q2 | 那用什么编？ | **只能用官方 Zephyr SDK 1.0.1**。Espressif 那个 `xtensa-esp-elf` 编不了（第 2 节有原始报错）。 |
| Q3 | 我 Korvo 上的应用代码，能原样搬到 S3 吗？ | **能，但要先把"板子有什么"从代码里摘出去**。改完的结果是：**同一份 `applications\esp32s31\korvo_apps`，两行命令编出两块板的固件，各自都能跑**（第 6、8 节）。 |

顺带还发现了一个比"换芯片"更隐蔽的东西：**ADC 分辨率也是 SoC 属性**（S31 是 17 位，S3 只有 12 位），它会让你同一行 `adc_read` 在另一块板上直接报错。这一条在第 6.7 节。

## 1. "官方镜像"这四个字，得拆开看

### 1.1 Zephyr 不发预编译固件

这件事和 ESP-IDF 完全不同，先把预期修正过来：

| | ESP-IDF | Zephyr |
|---|---|---|
| 有没有官方 `.bin` | 官方 example 有时给，社区也发 | **不发**。官方发布物只有 SDK 和源码 |
| "支持某块板"意味着 | 有 `idf.py set-target` 的预设 | **源码树里有这块板的 `boards\<vendor>\<board>\` 目录** |
| 你拿到的产物 | 可能的现成固件 | **必须自己 `west build`**（想要别人编好的，只能找第三方） |

所以"去找 S3 的官方镜像"这个动作，正确的落地方式是：**确认这棵树里有没有 S3 的板级定义；有，就用官方工具链自己编一份**。这一步做完，你拿到的才是"官方支持"意义上的镜像。

### 1.2 "官方支持" = 三件套，缺一件都跑不起来

| 层 | S3 上的具体东西 | 缺了会怎样 |
|---|---|---|
| **SoC 层** | `dts\xtensa\espressif\esp32s3\esp32s3_common.dtsi`（内存映射、`adc0/adc1`、`rmt@60016000`、`usb_serial: uart@60038000`、`intc`…） | 没有寄存器基址，驱动无处落脚 |
| **板级层** | `boards\espressif\esp32s3_devkitc\`（`board.yml`、`esp32s3_devkitc_procpu.yaml`、`.dts`、`-pinctrl.dtsi`、`_defconfig`） | 不知道 LED 在哪个脚、控制台走哪个口、flash 多大 |
| **工具链** | Zephyr SDK 1.0.1 里的 `xtensa-espressif_esp32s3_zephyr-elf` | 编不出 Xtensa 机器码（第 2 节） |

> 同一个 SDK 里还有 `riscv64-zephyr-elf`，Korvo-1（S31）用的就是它——第 3 节讲怎么让一个 SDK 同时覆盖两块板。

前两层这棵树里**已经有了**——这就是本回合最省事的地方。第三层没有，得装。

### 1.3 树里现成的三块 S3 板

```
west\zephyr\boards\espressif\
├── esp32s3_devkitc\        ← 本回合用的（官方 DevKitC-1）
├── esp32s3_box3\           ← 带屏的 Box
└── esp32s3_eye\            ← 带摄像头的 Eye
```

`esp32s3_devkitc\` 里的关键文件：

| 文件 | 作用 | 本回合关心什么 |
|---|---|---|
| `board.yml` | 板子清单（给支持矩阵和 CI 用） | 只声明 `soc: esp32s3` |
| `esp32s3_devkitc_procpu.yaml` | **真正的板级身份** | `identifier: esp32s3_devkitc/esp32s3/procpu`、`arch: xtensa`、`toolchain: zephyr` |
| `esp32s3_devkitc_procpu.dts` | 板级 devicetree | flash 8 MB、`chosen zephyr,console = &uart0`（**第 5 节的祸根**） |
| `esp32s3_devkitc-pinctrl.dtsi` | 引脚复用预定义 | 里面有 `uart0_default`、`i2c0_default` 等 |
| `esp32s3_devkitc_procpu_defconfig` | 默认 Kconfig | 决定了默认开哪些驱动 |

看 `esp32s3_devkitc_procpu.yaml` 里那行 `toolchain: zephyr` 就明白了：**这块板官方就是用 Zephyr SDK 编的**，所以第 2 节那条路不是"退而求其次"，是"唯一正解"。

### 1.4 板目标为什么是三段：`esp32s3_devkitc/esp32s3/procpu`

| 段 | 值 | 含义 |
|---|---|---|
| 第 1 段 | `esp32s3_devkitc` | **板名**（目录名） |
| 第 2 段 | `esp32s3` | **SoC 名**（dtsi 里的芯片型号） |
| 第 3 段 | `procpu` | **CPU 集群**。S3 是双核（`procpu` / `appcpu`），S31 是 `hpcore` / `lpcore` |

对应到 Korvo-1 就是 `esp32s31_function_coreboard/esp32s31/hpcore`。**三段任何一段写错，`west build` 都会说找不到板子**；而且这三段是"板目录 + SoC + cluster"拼出来的，不是随便起的名字。

> 顺带回答一个常见误解："S3 是单核还是双核？"——硬件是双核，但 Zephyr 这边**一次只能跑一个 cluster**，`procpu` 就是主核那份 dts。想要 AMP 双核，得用 sysbuild 同时编 `appcpu`（本回合没做，标 📖）。

## 2. 工具链：S3 只有一条路，而且很窄

### 2.1 先撞的墙：Espressif 的 `xtensa-esp-elf`（**这条路已验证做不通，别再试**）

本机原来就有 ESP-IDF 的 Xtensa 工具链：`C:\Espressif\tools\xtensa-esp-elf\esp-15.2.0_20251204`。第一反应是"Korvo 用的就是 ESP-IDF 的 RISC-V 工具链，那 S3 用 ESP-IDF 的 Xtensa 工具链应该也行"。

设成 `ZEPHYR_TOOLCHAIN_VARIANT=cross-compile` 之后，CMake 是**能过**的（它能找到编译器），但一进编译就炸：

```
zephyr/toolchain.h:422: error: Kconfig/toolchain endianness mismatch
zephyr/toolchain.h:431: ... CONFIG_LITTLE_ENDIAN but __ORDER_BIG_ENDIAN__
```

根因很干脆——**那个工具链默认是大端核**：

```powershell
& "C:\Espressif\tools\xtensa-esp-elf\esp-15.2.0_20251204\xtensa-esp-elf\bin\xtensa-esp-elf-gcc.exe" -dM -E -x c NUL |
  Select-String "BYTE_ORDER|XTENSA_EB"
# #define __XTENSA_EB__ 1
# #define __BYTE_ORDER__ __ORDER_BIG_ENDIAN__
```

然后尝试"把它掰成小端"，全部失败：

| 尝试 | 结果 |
|---|---|
| `EXTRA_CFLAGS=-mlittle-endian` | `unrecognized command-line option` |
| `EXTRA_CFLAGS=--endian=little` | 同上 |
| `EXTRA_CFLAGS=-mno-big-endian` | 同上 |
| `-mdynconfig=xtensa_esp32s3.so` | `XTENSA_GNU_CONFIG could not be loaded` |
| `gcc --print-multi-lib` | 里面**确实**有 `esp32s3;@mdynconfig=xtensa_esp32s3.so`，但要 dynconfig 文件与路径，缺一不可 |
| `cmake/toolchain/xt-clang` 变体 | 那是 Cadence/Tensilica 商用工具链，不是 esp-clang，不适用 |

**结论**：Espressif 的 Xtensa 工具链是给 ESP-IDF 用的（IDF 自己传一堆 flag 去做小端/核配置），它不认 Zephyr 的调用方式。**S3 必须用官方 Zephyr SDK。**

### 2.2 为什么 Zephyr SDK 行：它带的是"小端核"变体

SDK 里的这个工具链名字很长，但关键就在 `zephyr-elf` 三个字：

```
xtensa-espressif_esp32s3_zephyr-elf-gcc.exe
```

验证一行就够：

```powershell
& "C:\Users\xiao1\zephyr-sdk-1.0.1\gnu\xtensa-espressif_esp32s3_zephyr-elf\bin\xtensa-espressif_esp32s3_zephyr-elf-gcc.exe" -dM -E -x c NUL |
  Select-String "BYTE_ORDER"
# #define __BYTE_ORDER__ __ORDER_LITTLE_ENDIAN__      ← 对了
```

### 2.3 版本必须对齐 `SDK_VERSION`

Zephyr 源码里有个文件 `zephyr\SDK_VERSION`，本树写的是：

```
1.0.1
```

所以下载的 SDK 必须是 `1.0.1`。版本不匹配时 CMake 会警告，严重时工具链参数对不上直接编不过。**先看 `SDK_VERSION`，再去下对应版本**，不要凭"最新版应该更好"。

### 2.4 下载：直连太慢，分段并行是唯一解

`west` 自身就有装 SDK 的子命令（`west sdk --help` 能看到 `List and Install Zephyr SDK`）：

```powershell
west sdk install -t xtensa-espressif_esp32s3_zephyr-elf -b C:\Users\xiao1
```

但实测**直连 GitHub 只有 ~11 KB/s**（104 MB 的包要 2.6 小时）。用 `gh-proxy.com` 镜像单流也就 ~98 KB/s。最后靠 **12 路 `curl -r` 分段并行**拉到 **~800 KB/s**，思路是：

```powershell
# 1) 先拿包大小（HEAD），切成 N 段
#    $size / $n 算出每段字节范围
# 2) 并发下载每一段到 $env:TEMP\sdkseg\<i>.bin
for ($i = 0; $i -lt $n; $i++) {
    $from = $i * $chunk
    $to   = [Math]::Min(($i + 1) * $chunk - 1, $size - 1)
    Start-Process curl.exe -ArgumentList @(
        "-L", "-s", "-r", "$from-$to",
        "-o", "$env:TEMP\sdkseg\$i.bin",
        "https://gh-proxy.com/https://github.com/zephyrproject-rtos/sdk-ng/releases/download/v1.0.1/<包名>.7z"
    ) -WindowStyle Hidden
}
# 3) 等全部落地后按顺序二进制拼接（不要用文本方式！）
```

拼接和解压都别走文本通道，直接用 .NET 的 `[IO.File]` 和 `py7zr`：

```powershell
$fs = [IO.File]::Create($arc)
for ($i = 0; $i -lt $n; $i++) {
    $b = [IO.File]::ReadAllBytes("$env:TEMP\sdkseg\$i.bin")
    $fs.Write($b, 0, $b.Length)
}
$fs.Dispose()

& "$root\.venv\Scripts\python.exe" -c "import py7zr; py7zr.SevenZipFile(r'$arc','r').extractall(path=r'C:\Users\xiao1\zephyr-sdk-1.0.1\gnu')"
```

本回合实际下了两个包：

| 包 | 大小 | 解到哪 |
|---|---|---|
| `zephyr-sdk-1.0.1_windows-x86_64_minimal.7z` | 104,319,274 B | `C:\Users\xiao1\zephyr-sdk-1.0.1\` |
| `toolchain_gnu_windows-x86_64_xtensa-espressif_esp32s3_zephyr-elf.7z` | 47,622,966 B | `C:\Users\xiao1\zephyr-sdk-1.0.1\gnu\` |

### 2.5 一个必须知道的坑：minimal 包里**没有工具链本体**

`minimal` 解出来只有这些：

```
C:\Users\xiao1\zephyr-sdk-1.0.1\
├── cmake\                  ← SDK 的 CMake 包（注册用）
├── hosttools\
├── sdk_gnu_toolchains      ← 只是一份清单文件，不是工具链
├── sdk_version             ← "1.0.1"
└── setup.cmd
```

第一次解完直接 `west build` 会报找不到编译器——因为真正的编译器要单独下（就是上表第二个包），**并且必须解到 `<sdk>\gnu\<工具链名>\`**。这是 `setup.cmd` 里写死的安装位置：

```bat
REM # Install GNU toolchains
if [%DO_GNU_TOOLCHAIN%] neq [] (
  if not exist gnu\ mkdir gnu
  pushd gnu
  ... 7z x -o. !TOOLCHAIN_FILENAME!
```

解完后目录是这样（`gnu\` 下多了一层工具链名）：

```
C:\Users\xiao1\zephyr-sdk-1.0.1\gnu\
└── xtensa-espressif_esp32s3_zephyr-elf\
    ├── bin\        ← xtensa-espressif_esp32s3_zephyr-elf-gcc.exe 就在这
    ├── lib\
    └── ...
```

### 2.6 注册 CMake 包（少了这步，`ZEPHYR_SDK_INSTALL_DIR` 也可能找不到）

`sdk\cmake\zephyr_sdk_export.cmake` 是个安装脚本，跑一次就把 SDK 路径写进**用户级 CMake 包注册表**：

```powershell
$cmake = "$root\.tools\cmake\cmake-3.30.2-windows-x86_64\bin\cmake.exe"
& $cmake -P "C:\Users\xiao1\zephyr-sdk-1.0.1\cmake\zephyr_sdk_export.cmake"
# → Zephyr-sdk (C:/Users/xiao1/zephyr-sdk-1.0.1/cmake) has been added to the user package registry in:
#   HKEY_CURRENT_USER\Software\Kitware\CMake\Packages\Zephyr-sdk
```

> 那行提示是写到 **stderr** 的，pwsh 里会显示成 `cmake.exe : ...` 的红字，但 `exit=0`，是正常的。

## 3. 统一工具链：一个 SDK、两个目标、一套变量

### 3.1 先纠一个常见误解

第 2 节讲过"S3 必须用官方 Zephyr SDK"，于是很容易顺势以为 **S31 也要用另一套工具链**——很多教程（包括本教程早先的版本）就是写成"Korvo 用 ESP-IDF 的 `riscv32-esp-elf`、S3 用 Zephyr SDK"。

**这不是设计，是历史原因**：Zephyr SDK 是一个**多目标**（multi-target）SDK，`gnu\` 下可以同时放任意多个交叉工具链；当初装 SDK 时为了省下载量，只勾了 `xtensa-espressif_esp32s3_zephyr-elf` 一个目标，`gnu\` 里没有 `riscv64-zephyr-elf`，Korvo 才"被迫"退回 ESP-IDF 的 `riscv32-esp-elf`，并用 `cross-compile` 变体。

判断依据就在构建缓存里：老 Korvo 构建目录的 `CMakeCache.txt` 写着

```
ZEPHYR_TOOLCHAIN_VARIANT:STRING=cross-compile
CMAKE_C_COMPILER:STRING=C:/Espressif/tools/riscv32-esp-elf/esp-15.2.0_20251204/riscv32-esp-elf/bin/riscv32-esp-elf-gcc.exe
```

### 3.2 补齐第二个目标

```powershell
$root = "C:\Users\xiao1\Desktop\ELAB\kharon-ide"
$env:PATH = "$root\.tools;$env:PATH"          # setup.cmd 需要 7z，见 3.5
Set-Location -LiteralPath "C:\Users\xiao1\zephyr-sdk-1.0.1"
.\setup.cmd /t riscv64-zephyr-elf             # 非交互安装（注意是 /t，不是 -t）
.\setup.cmd /c                                # 注册 CMake 包
```

装完 `gnu\` 下就是两个目标：

```
C:\Users\xiao1\zephyr-sdk-1.0.1\gnu\
├── riscv64-zephyr-elf                     ← Korvo-1 / S31（RISC-V）
│   └── bin\riscv64-zephyr-elf-gcc.exe     (Zephyr SDK 1.0.1) 14.3.0
└── xtensa-espressif_esp32s3_zephyr-elf    ← ESP32-S3（Xtensa）
    └── bin\xtensa-espressif_esp32s3_zephyr-elf-gcc.exe
```

> 一个 `riscv64-` 前缀的编译器编 32 位 RISC-V 是正常的：Zephyr 用 multilib 工具链，`-march/-mabi` 由 SoC 的 Kconfig 传下去，不需要另装 `riscv32-*`。

### 3.3 一套环境变量，两块板通用

```powershell
$root = "C:\Users\xiao1\Desktop\ELAB\kharon-ide"
$sdk  = "C:\Users\xiao1\zephyr-sdk-1.0.1"

$env:PATH = "$root\.venv\Scripts;$root\.tools\cmake\cmake-3.30.2-windows-x86_64\bin;$root\.tools\ninja;" +
            "$sdk\gnu\riscv64-zephyr-elf\bin;$sdk\gnu\xtensa-espressif_esp32s3_zephyr-elf\bin;$env:PATH"
$env:ZEPHYR_BASE = "$root\west\zephyr"
$env:ZEPHYR_TOOLCHAIN_VARIANT = "zephyr"
$env:ZEPHYR_SDK_INSTALL_DIR = $sdk
Remove-Item Env:\CROSS_COMPILE   -ErrorAction SilentlyContinue
Remove-Item Env:\TOOLCHAIN_HOME  -ErrorAction SilentlyContinue
```

`env.ps1` 已经按这套写好，直接 `. .\scripts\kharon-env.ps1` 即可。对比旧写法：

| | 旧：两套（互斥） | 新：统一（同一套） |
|---|---|---|
| `ZEPHYR_TOOLCHAIN_VARIANT` | `cross-compile`（S31）/ `zephyr`（S3） | **`zephyr`**，两块板都一样 |
| `ZEPHYR_SDK_INSTALL_DIR` | S31 不设、S3 设 | **统一个值** |
| `TOOLCHAIN_HOME` / `CROSS_COMPILE` | S31 必设、S3 必须清 | **都不用设，清掉即可** |
| PATH | 两套 PATH 轮流前置 | 两个 `gnu\...\bin` 一起进 PATH，互不冲突 |
| 换板时要做什么 | 回到"切换开关"改一堆变量 | **什么都不用改** |

CMake 选哪个编译器，是按 `BOARD` 的 `arch` 自动决定的，PATH 里多放一个无关的 `bin` 不影响结果——所以两块板可以共用一个终端。

### 3.4 实测：同一条命令构建两块板

同一个 app（`applications\esp32s31\korvo_sys`），只改 `-b`：

| | Korvo-1（S31 / RISC-V） | ESP32-S3 |
|---|---|---|
| 板目标 | `esp32s31_function_coreboard/esp32s31/hpcore` | `esp32s3_devkitc/esp32s3/procpu` |
| 构建目录 | `build\esp32s31\korvo_sys\s31-debug` | `build\esp32s3\korvo_sys\s3-debug` |
| 构建缓存里的编译器 | `...\gnu\riscv64-zephyr-elf\bin\riscv64-zephyr-elf-gcc.exe` | `...\gnu\xtensa-espressif_esp32s3_zephyr-elf\bin\xtensa-...-gcc.exe` |
| 镜像 | 148480 B | 147876 B |
| 编译结果 | `[319/319]` 全部成功 | 成功 |

```powershell
west build -b esp32s31_function_coreboard/esp32s31/hpcore ..\applications\esp32s31\korvo_sys -d build\esp32s31\korvo_sys\s31-debug
west build -b esp32s3_devkitc/esp32s3/procpu            ..\applications\esp32s31\korvo_sys -d build\esp32s3\korvo_sys\s3-debug
```

编译成功时那段输出里会带一行：

```
-- Found toolchain: zephyr 1.0.1 (C:/Users/xiao1/zephyr-sdk-1.0.1)
```

看到它，说明走的是 SDK；如果显示 `cross-compile` 或报 `unable to find the toolchain`，先回 3.3 检查环境变量。

### 3.5 这一段踩的两个坑（都很隐蔽）

**坑 1：`west sdk install` 在 Windows 上解包要 `7z`，没有就 FATAL**

```
Zephyr SDK setup requires '7z' to be installed and available in the PATH.
FATAL ERROR: command "C:\Users\xiao1\zephyr-sdk-1.0.1\setup.cmd /c" failed
```

Windows 版 SDK 把每个目标打成 `toolchain_gnu_windows-x86_64_<target>.7z`，`setup.cmd` 里固定调 `7z x`。不想装 7-Zip 软件的话，下官方独立版（588 KB，免安装）：

```powershell
Invoke-WebRequest -Uri "https://www.7-zip.org/a/7zr.exe" -OutFile "$root\.tools\7zr.exe"
Copy-Item "$root\.tools\7zr.exe" "$root\.tools\7z.exe"   # 脚本认的是 7z 这个名字
# 然后把这个目录放到 PATH 最前面
```

**坑 2：`west sdk install -t ...` 会挂死——它在等你按 y/n**

## 5. 控制台"哑巴"：本章最值钱的一个坑

### 5.1 现象

第一次烧完，`COM11` 打开成功、串口**一行字都没有**：

```
---- COM11 : 0 lines ----
```

而烧录本身是成功的（`Hash of data verified`）。板子明明在跑，但你看不到任何东西。

### 5.2 根因：板上有两路 USB，而 `chosen` 选了另一路

DevKitC-1 这类板子有**两个 USB-C 口**：

| 口 | 走谁 | 在 dts 里叫 | 电脑上看到 |
|---|---|---|---|
| **UART 口** | 板载 CP2102 桥 → `uart0` | `chosen zephyr,console = &uart0` | `COM` + Silicon Labs 驱动 |
| **USB 口** | **芯片内置 USB-Serial-JTAG** → `usb_serial` | `usb_serial: uart@60038000` | `USB 串行设备 (COMx)`，**VID_303A&PID_1001** |

板级 dts 默认把控制台给了 `uart0`（因为绝大多数人用 UART 口）。**你要是只插了 USB 口，日志就全部跑到那个没人接的 `uart0` 上去了**——串口工具这边当然是一片空白。

本回合的板子正好只接了 USB 口，所以复现了这个坑。

### 5.3 三步定位法（以后遇到"烧成功但没输出"照这个走）

**第一步：确认你连的是哪个口。**

```powershell
Get-CimInstance Win32_PnPEntity | Where-Object { $_.Name -match "\(COM\d+\)" } |
  ForEach-Object { "{0} | {1}" -f $_.Name, $_.DeviceID }
```

看到 `USB\VID_303A&PID_1001&MI_00` → 这是**芯片原生 USB**（USB-Serial-JTAG）；
看到 `VID_10C4` 之类（Silicon Labs）→ 这是**CP2102 那一路**。

**第二步：确认固件把日志发给了谁。** 编译产物里有展开后的完整 dts：

```powershell
Select-String -Path build\samples\esp32s3\hello_world\default\zephyr\zephyr.dts -Pattern "zephyr,console" -Context 0,2
# zephyr,console = &uart0;        ← 找到问题
```

**第三步：确认 Kconfig 侧的控制台后端也对上了。**

```powershell
Select-String -Path build\samples\esp32s3\hello_world\default\zephyr\.config -Pattern "CONSOLE|USB_SERIAL_JTAG"
# CONFIG_CONSOLE=y
# CONFIG_ESP_CONSOLE_USB_SERIAL_JTAG=y
# CONFIG_ESP_USB_SERIAL_JTAG_ENABLED=y
```

### 5.4 修法：overlay 里把 `chosen` 切到 `usb_serial`

```dts
&usb_serial {
	status = "okay";
};

/ {
	chosen {
		zephyr,console = &usb_serial;
		zephyr,shell-uart = &usb_serial;
	};
};
```

两个点都要改：`zephyr,console` 管 `printk`/日志输出，`zephyr,shell-uart` 管 shell 的输入输出。只改一个会出现"能看日志但敲命令没反应"（或者反过来）。

改完重新编译（**要 `-p always`**，dts 变了必须重跑配置），烧进去立刻有字：

```
*** Booting Zephyr OS build 34e025569cbb ***
Hello World! esp32s3_devkitc/esp32s3/procpu
```

### 5.5 这个修法什么时候该撤

- **只插 USB 口** → 保留（本节这样）
- **插 UART 口（CP2102）** → 把这几行删掉，回到默认 `uart0`，否则你会在 CP2102 那边看不到东西
- **两个口都插** → 只能选一个；USB-Serial-JTAG 和 UART 桥同时接电脑容易出枚举冲突，建议只插一个

> 一句话记住：**"烧成功 + 串口没输出" 九成是 `chosen` 选错了口，不是固件挂了。**

## 6. 同一份代码换板：能力探测（本章的核心手法）

### 6.1 两种思路，先选对方向

| 思路 | 做法 | 优点 | 代价 |
|---|---|---|---|
| A. 板级裁剪 | 应用里 `#ifdef CONFIG_BOARD_xxx` 判断板名 | 直观 | 每加一块板就要改应用，越加越脏 |
| B. **能力探测**（本回合用） | 应用只问"这台设备有没有这个能力"，由 dts 回答 | 加板不用改应用 | 要求板级 overlay 把"有什么/没什么"写清楚 |

结论：**用 B**。判断依据放在 devicetree 里，应用层只做 `DT_HAS_ALIAS(...)` 查询——这和"Zephyr 的一切都从 dts 来"是同一套世界观。

### 6.2 写法：把"有没有"变成编译期常量

```c
#define STRIP_NODE DT_ALIAS(led_strip)
#define PA_NODE    DT_ALIAS(pa_ctrl)

/* 板级 overlay 给了这个别名，就是 1；没给（或 /delete-property/ 删了）就是 0 */
#define HAS_STRIP DT_HAS_ALIAS(led_strip)
#define HAS_PA    DT_HAS_ALIAS(pa_ctrl)

#if HAS_STRIP
static const struct device *const strip = DEVICE_DT_GET(STRIP_NODE);
#endif

#if HAS_PA
static const struct gpio_dt_spec pa = GPIO_DT_SPEC_GET(PA_NODE, gpios);
#endif
```

`DT_HAS_ALIAS` 定义在 `zephyr\include\zephyr\devicetree.h:295` 附近，是个纯宏，编进 `.rodata` 的常量——**没有运行时代价**，也不会因为别名不存在而编译报错（`DEVICE_DT_GET` 才会）。

代码里真正要包起来的地方就三处：

| 位置 | 没能力时怎么办 |
|---|---|
| 动画线程 `rgb_thread` | 保留线程但空转（`k_msleep(period)`），这样 `app stats` 的帧节奏照样能看 |
| `cmd_pa` | 直接打印"本板 dts 里没有 pa_ctrl 别名…此命令不生效"，返回 `-ENOTSUP` |
| `main()` 里的初始化/日志 | `device_is_ready(strip)`、`gpio_pin_configure(pa)`、`LOG_INF` 全部按 `HAS_*` 条件编译 |

### 6.3 板级 overlay 的文件名规则（不写一行命令行就生效）

```
applications\esp32s31\korvo_apps\boards\
└── esp32s3_devkitc_esp32s3_procpu.overlay     ← 文件名 = 板目标把 "/" 换成 "_"
```

板目标是 `esp32s3_devkitc/esp32s3/procpu`，下划线化就是 `esp32s3_devkitc_esp32s3_procpu`。Zephyr 在 `west build -b <这个板>` 时**自动**把这个 overlay 叠加到板级 dts 上，**不需要 `-DDTC_OVERLAY_FILE=`**。

> ⚠️ **重要更正（第 16 组实测发现的坑，这里必须写死）**：`boards\<board>.overlay` 和 `app.overlay` 是**二选一**，不是叠加。
> 依据在 `zephyr\cmake\modules\configuration_files.cmake:75-89`：先找 `socs\<soc>.overlay`，再找 `boards\<board>.overlay`；**只要命中一个，`DTC_OVERLAY_FILE` 就被定下来，后面那段 `NAMES "app.overlay"` 的兜底根本不会执行**。
> 本工程的实测证据：`build\esp32s31\korvo_apps\s31-debug\CMakeCache.txt` 里是 `DTC_OVERLAY_FILE=…\applications\esp32s31\korvo_apps\app.overlay`，而 `build\esp32s3\korvo_apps\s3-debug\CMakeCache.txt` 里只有 `…\boards\esp32s3_devkitc_esp32s3_procpu.overlay`——**同一份 prj 的一份 app.overlay，在 S3 上完全没有被用**。
> 后果很实在：`korvo_sys` 的 `app.overlay` 里那句 `&coretemp { status = "okay"; }` 在 S3 上没生效，节点还是 `disabled`，于是 `DEVICE_DT_GET` 报 `__device_dts_ord_48 undeclared`（详见第 16 组）。
> **所以：一旦你给某个 app 加了 `boards\<board>.overlay`，就要把 `app.overlay` 里"这块板也必须成立"的内容整段搬进那个文件。** 想两者都要，只能显式写法：`west build -DDTC_OVERLAY_FILE="a.overlay;b.overlay"`（分号分隔，正斜杠路径）。

### 6.4 覆盖顺序：overlay 是"后置"的，所以能删别名

单个 overlay 内部的生效顺序是：**SoC dtsi → 板级 dts → overlay**。overlay 最后应用，所以能覆盖前面的、`/delete-property/` 因此有效：

```dts
/ {
	aliases {
		/delete-property/ pa-ctrl;   /* S3 没有功放使能脚 → 别名删掉，应用自动裁掉这段 */
		led-strip = &led_strip;      /* 但灯有，起个别名让应用认得 */
	};

	led_strip: ws2812 {
		compatible = "worldsemi,ws2812-pulse-io";
		pulse-ios = <&rmt 0>;
		chain-length = <1>;
		color-mapping = <LED_COLOR_ID_GREEN LED_COLOR_ID_RED LED_COLOR_ID_BLUE>;
		reset-delay = <300>;
	};
};

&pinctrl {
	rmt_s3: rmt_s3 {
		group1 {
			pinmux = <RMT_OUT0_GPIO48>;   /* DevKitC-1 板载 RGB 在 GPIO48 */
		};
	};
};

&rmt {
	pinctrl-0 = <&rmt_s3>;
	pinctrl-names = "default";
	status = "okay";
};

&adc0 { status = "okay"; };
&adc1 { status = "okay"; };
```

**两个细节**：

1. `RMT_OUT0_GPIO48` 这个宏来自 `zephyr\include\zephyr\dt-bindings\pinctrl\esp32s3-pinctrl.h`，**每块板、每个脚都有一个**，换脚就是换这一行。
2. `color-mapping` 必须是 `GRN/RED/BLU` 这个顺序——WS2812 的线序就是 GRB，写错了红蓝会互换（Korvo 那章的 RGB 页也踩过同样的事）。

### 6.5 横幅也用"板子自己报的名字"

应用启动横幅原本写死 `Korvo apps`。改成一个 Kconfig 字符串就自动跟着板走：

```c
printk("=== Korvo apps（同一份代码，%s）===\n", CONFIG_BOARD_TARGET);
```

实测两块板的输出分别是：

```
=== Korvo apps（同一份代码，esp32s31_function_coreboard/esp32s31/hpcore）===
=== Korvo apps（同一份代码，esp32s3_devkitc/esp32s3/procpu）===
```

**这一行是"同一份代码真的在两块板上跑"最直接的证据**——不用去看构建目录。

### 6.6 还有一层能力差异，dts 别名管不到：ADC 分辨率

以为"dts 层面搞定就完事"是不对的。本回合跑 `app adc` 的时候，S3 直接刷了一屏错误：

```
<err> adc_esp32: unsupported resolution (17)
adc0(u1) [t=4802ms]: err err err err err err err err
```

根因很直白：

| 芯片 | ADC 最大分辨率 |
|---|---|
| ESP32-S31 | **17 位**（Korvo 那章的按键标定全是按 17 位做的） |
| ESP32-S3 | **12 位** |

应用里写死 `.resolution = 17`，在 S3 上就是"驱动说你没这个能力"。**这不是 dts 的问题，是 SoC 属性**——所以要在运行时问驱动，而不是在编译期猜板名：

```c
static uint8_t g_adc_res;

static int adc_probe_read(const struct device *dev, uint8_t ch, int32_t *raw)
{
	static const uint8_t cand[] = {17, 16, 15, 14, 13, 12};
	struct adc_sequence seq = { .buffer = raw, .buffer_size = sizeof(*raw), .channels = BIT(ch) };

	if (g_adc_res != 0) {
		seq.resolution = g_adc_res;
		return adc_read(dev, &seq);
	}

	for (size_t i = 0; i < ARRAY_SIZE(cand); i++) {
		seq.resolution = cand[i];
		if (adc_read(dev, &seq) == 0) {   /* 第一个读成功的就记住 */
			g_adc_res = cand[i];
			return 0;
		}
	}
	return -ENOTSUP;
}
```

再把 Korvo 上标定好的按键窗口"折回 17 位尺度"，这样同一套窗口两块板都能用：

```c
static int32_t adc_raw_to_17bit(int32_t raw)
{
	return (g_adc_res == 0 || g_adc_res == 17) ? raw : (raw << (17 - g_adc_res));
}
```

改完在 S3 上实测：

```
[adc] 采 2 次（每次 200 ms），ADC 分辨率=12 位
adc0(u1) [t=1898ms]:  2602  2494  2326  2840  2721  2587  2486  2535
adc1(u2) [t=1899ms]:  2810  3182  3532  3532  3309  2870  2538  2471
[key] raw=2855（12 bit） -> 松开
```

**结论要记住的是方法论，不是这段代码**：换芯片时会遇到三类差异，处理方式各不相同——

| 差异类型 | 例子 | 处理方式 |
|---|---|---|
| **设备有没有** | WS2812、PA_CTRL | dts 别名 + `DT_HAS_ALIAS`（编译期裁掉） |
| **参数范围不同** | ADC 17 位 vs 12 位 | 运行时试探（驱动返回码），不要在应用里写死 |
| **物理接法不同** | 灯在 GPIO37 / GPIO48 | 板级 overlay 改 pinmux 一行 |

## 7. 分区表：S3 自带 `storage`，`store.c` 一个字都不用改

这是本回合的意外之喜。原来担心"S3 上跑 NVS 得自己补 overlay 写分区表"，实际查了默认分区表就放心了：

`zephyr\dts\vendor\espressif\partitions_0x0_amp.dtsi` → `partitions_0x0_amp_4M.dtsi` 里：

```dts
storage_partition: partition@3b0000 {
	compatible = "zephyr,mapped-partition";
	reg = <0x3b0000 0x30000>;     /* 0x30000 = 192 KB */
	label = "storage";
};
```

编出来的 `zephyr.dts` 也是同一个值，可以自己核：

```powershell
Select-String -Path build\esp32s3\korvo_apps\s3-debug\zephyr\zephyr.dts -Pattern "storage_partition" -Context 0,4
```

两板分区对照：

| 分区 | Korvo-1（S31） | ESP32-S3 DevKitC |
|---|---|---|
| `mcuboot` | `0x2000` / 56 KB | `0x0` / 64 KB |
| `sys` | `0x10000` / 64 KB | `0x10000` / 64 KB |
| `image-0` | `0x20000` / 7936 KB | `0x20000` / 1344 KB |
| `image-1` | `0x7e0000` | `0x170000` |
| `appcpu` / `lpcore` | `lpcore` 两个 32 KB | `appcpu` 两段 448 KB + `lpcore` 两段 32 KB |
| **`storage`** | `0xfb0000` / **192 KB** | `0x3b0000` / **192 KB** |
| `coredump` | `0xfff000` / 4 KB | `0x3ff000` / 4 KB |

**两块板都是 192 KB，`compatible` 也都是 `zephyr,mapped-partition`**，所以：

- `applications\esp32s31\korvo_apps\src\store.c` / `store.h` **不差分毫就能用**（它只查 `FIXED_PARTITION_ID(STORAGE_PARTITION)` 和 `flash_area`）；
- `prj.conf` 里那四行（`FLASH` / `FLASH_MAP` / `FLASH_PAGE_LAYOUT` / `NVS`）也不用动；
- 真正需要移植的只有第 6 节那些"板子差异"，**持久化本来就属于芯片无关层**。

> 但键空间还是要自己规划：`K_MODE=20 / K_RGB=21 / K_BRIGHT=22 / K_PA=23` 这套编号是为"同一块板跑过 `korvo_nvs`（它用 `id=10`）"留的余量。换板以后如果两块板都被刷过不同工程，也别用 0-9 这段——那是演示键的默认区。

### 8.3 S3 · 复位后配置恢复（`logs\serial-s3-apps-2.txt`）

```
[boot] 恢复配置：模式=solid 基色=14 00 00 亮度=15% 第 3 次开机（本板无 PA_CTRL）
[stats] 模式=solid 亮度=15% 帧数=47 单帧耗时=1 ms 最后颜色=03 00 00
```

`0x14` 按 15% 亮度算下来就是 `0x03`（20×0.15≈3），**第一帧就是恢复色**，说明 `cfg_load()` 仍然跑在 `k_thread_create` 之前（`14-Zephyr系统与进阶\NVS持久化.md` 第 8 节讲的那条顺序约束，换芯片后依然成立）。

### 8.4 S3 · 没有的能力：`app pa` 优雅拒绝

```
uart:~$ app pa on
[pa] 本板 dts 里没有 pa_ctrl 别名（S3 最小板没有功放使能脚），此命令不生效
```

不是崩、不是编译报错，而是**明确的 `-ENOTSUP` + 人话**。这就是第 6.1 节选 B 方案的收益：多用一块板，应用层一行不用改。

### 8.5 两板对比（同源码、同工程、不同架构）

| 指标 | Korvo-1（S31 / RISC-V） | ESP32-S3（Xtensa） |
|---|---|---|
| 板目标 | `esp32s31_function_coreboard/esp32s31/hpcore` | `esp32s3_devkitc/esp32s3/procpu` |
| 工具链 | 同一套 Zephyr SDK 1.0.1：`riscv64-zephyr-elf`（`VARIANT=zephyr`） | 同一套 Zephyr SDK 1.0.1：`xtensa-espressif_esp32s3_zephyr-elf` |
| 镜像偏移 | `0x2000` | `0x0000` |
| `korvo_apps` FLASH | 213504 B（1.27% / 16 MB 表） | 214708 B（2.56% / 8 MB 表） |
| 串口 | `COM9`（CP2102） | `COM11`（USB-Serial-JTAG） |
| 单帧耗时 | **2 ms** | **1 ms** |
| `storage` 分区 | `0xfb0000` / 192 KB | `0x3b0000` / 192 KB |
| PA_CTRL | GPIO7，有 | 无（自动裁掉） |
| ADC 分辨率 | 17 位 | 12 位（自动探测） |
| 四键 IO42 分压梯 | 有（SET/PLAY/VOL-/VOL+） | **无**（S3 最小板没这四个键，`app key` 读的是悬空脚） |

**这一轮没做到的一件事，如实写在这里**：回烧 Korvo 时 `COM9` 已经从设备管理器消失（板子被拔下来换成 S3 了），所以 Korvo 侧只做了**编译回归**（`BUILD_EXIT=0`、213504 B，二进制里能查到新增的 `ADC 分辨率` 字符串），**没有在这一轮重新实机跑**。上一轮的 Korvo 实机数据仍保留在 `logs\serial-apps-nvs-A~E.txt`。

## 9. 换芯片六步清单（照着走就行）

| 步 | 动作 | 检查点 |
|---|---|---|
| 1 | 查树里有没有这块板：`boards\<vendor>\<board>\`，看 `*.yaml` 的 `identifier` / `arch` / `toolchain` | `arch` 决定工具链路线 |
| 2 | 按 `zephyr\SDK_VERSION` 装**官方 SDK**（不是 ESP-IDF 的工具链），并补齐本板架构的 gnu 目标（S31 → `riscv64-zephyr-elf`，S3 → `xtensa-espressif_esp32s3_zephyr-elf`） | `gnu\` 下两个目标都在；`Found toolchain: zephyr x.y.z` |
| 3 | 环境变量只设一套：`VARIANT=zephyr` + `ZEPHYR_SDK_INSTALL_DIR`，清掉 `CROSS_COMPILE`/`TOOLCHAIN_HOME` | 两块板同一个终端都能编 |
| 4 | 先跑 `samples\hello_world`，打通"编—烧—看日志" | `Hello World! <板目标>` |
| 5 | 控制台口不响就查 `chosen`（两路 USB 的板必踩） | `zephyr.dts` 里 `zephyr,console` 指向你插的那个口 |
| 6 | 加 `boards\<board>_<soc>_<cluster>.overlay`：别名、pinmux、控制台；再按第 6.6 节补运行时能力探测 | 横幅里出现新板名 + 该没有的功能自动消失 |

## 10. 本轮踩到的坑（全表）

| # | 现象 | 原因 | 解法 |
|---|---|---|---|
| 1 | `toolchain.h` 报 endianness mismatch | Espressif `xtensa-esp-elf` 默认大端核 | 换 Zephyr SDK（不要再试 endian flag） |
| 2 | `-mdynconfig=xtensa_esp32s3.so` 报 `XTENSA_GNU_CONFIG could not be loaded` | 缺 dynconfig 文件与路径 | 同上，放弃这条路 |
| 3 | `west sdk install` 挂死、看着像下载卡住 | 脚本认 `/t`，`west` 传参不对 → 进交互模式等 `choice y/n`，一个字节都没下 | 直接跑 `.\setup.cmd /t <目标>`，别用 `west sdk install` |
| 4 | `Zephyr SDK setup requires '7z' ... FATAL ERROR` | Windows 版目标包是 `.7z`，`setup.cmd` 固定调 `7z x` | 下独立版 `7zr.exe` 复制成 `7z.exe` 放到 PATH（免安装） |
| 5 | 解完 minimal 包还是找不到编译器 | minimal **不含**工具链本体 | 另下 `toolchain_gnu_…7z`，解到 `<sdk>\gnu\` |
| 6 | `ZEPHYR_SDK_INSTALL_DIR` 设了还报找不到 | SDK 的 CMake 包没注册 | 跑 `setup.cmd /c`（或 `cmake -P cmake\zephyr_sdk_export.cmake`） |
| 7 | S3 编译跑到 `unable to find the toolchain` | 残留 `CROSS_COMPILE` / `TOOLCHAIN_HOME` | 切环境时显式 `Remove-Item Env:\...`（统一 SDK 后只剩这一条要注意） |
| 8 | `-DDTC_OVERLAY_FILE=C:\...` 报 `Error in cmake code` | 反斜杠被 CMake 当转义 | 路径一律**正斜杠**（或用 `boards\` 自动匹配，根本不传这个参数） |
| 9 | 烧录成功、串口 0 行 | `chosen zephyr,console = &uart0`，但只插了 USB 口 | overlay 切到 `usb_serial`（console + shell-uart 两个都要） |
| 10 | `App RGB 灯不亮`（数值对、看不到光） | pinmux 脚号不对（不同 S3 小板 RGB 脚不同） | 查原理图改 `RMT_OUT0_GPIOxx` 一行 |
| 11 | `adc_esp32: unsupported resolution (17)` | S3 ADC 只有 12 位 | 运行时从 17 往下降探测（第 6.6 节） |
| 11 | `read_serial.py` 报 `could not open port 'COM9'` | 脚本里**硬编码 COM9** | 用 `tools\zephyr\probe_serial.py COM11 8 --reset` |
| 12 | `serial_cmd.py COM11` 返回 `0 lines` | 它自带 RTS 复位，USB-Serial-JTAG 会重新枚举，端口瞬间消失 | 用不主动复位的 `tools\zephyr\usb_cmd.py` |
| 13 | `TaskOutput` 里看不到构建输出 | pwsh 偶发 stdout 空（exit 0） | 重定向到 `logs\*.txt` 再 `Read` |
| 14 | S3 启动就有 `SHA-256 comparison failed` | 未签名镜像 | 无视，`Attempting to boot anyway` |

串口工具对照（**这块最容易浪费时间**）：

| 场景 | 用哪个 |
|---|---|
| Korvo-1（COM9，CP2102） | `tools\zephyr\read_serial.py`、`tools\zephyr\serial_cmd.py COM9 "cmd@3"` |
| S3（COM11，原生 USB）纯抓日志 | `tools\zephyr\probe_serial.py COM11 8 --reset` |
| S3 发 shell 命令 | `tools\zephyr\usb_cmd.py COM11 "app stats@3" "app saved@4"` |
