## 1. 硬件：四根线，先认清每个脚

| 功能 | 芯片引脚 | 板上丝印 | 电气约定 | 谁在用 |
|---|---|---|---|---|
| LED | **PC13** | `LED` | **低电平点亮**（`GPIO_ACTIVE_LOW`） | 呼吸灯 |
| 按键 | **PA0** | `KEY`（也叫 WKUP） | **按下接 GND**，靠芯片内部上拉（`GPIO_ACTIVE_LOW \| GPIO_PULL_UP`） | 开关呼吸 |
| 串口 TX | **PA9** | `A9` | USART1_TX，115200 8N1 | 日志输出 |
| 串口 RX | **PA10** | `A10` | USART1_RX（本轮不用，留着收命令） | — |
| 调试 | **PA13 / PA14** | `SWDIO` / `SWCLK` | SWD，DAP-Link 的 2 根信号线 | 烧录/调试 |

接线（DAP-Link → 板子）：

```
DAP-Link 3V3  ->  板子 3V3      （给板子供电，也可以 USB 单独供电，别同时接两个 5V 源）
DAP-Link GND  ->  板子 GND
DAP-Link SWDIO->  PA13
DAP-Link SWCLK->  PA14
DAP-Link RX   ->  PA9   （探针收、芯片发 —— 交叉接）
DAP-Link TX   ->  PA10  （可选，本轮不需要）
```

> **别接 nRST**。Black Pill 的 R 脚接了复位按键，DAP-Link 的 RST 引到它会让 OpenOCD 多一个"复位方式"的选择题。本轮的 OpenOCD 配置故意不接硬件复位，用 **SYSRESETREQ（软复位）**，见第 10 节。

**这块板的关键数字**（板级 dts 写的，不是猜的）：

| 项 | 值 | 来源 |
|---|---|---|
| Flash | 512 KiB | `flash size = 512 KiB`（OpenOCD 实测输出） |
| SRAM | 128 KiB | `blackpill_f411ce.yaml` |
| 主频 | **96 MHz** | `&rcc { clock-frequency = <DT_FREQ_M(96)>; }` |
| 时钟源 | HSE **25 MHz** 晶振 → PLL（M=25, N=192, P=2 → 96 MHz） | `&clk_hse` / `&pll` |
| APB1 / APB2 | 48 MHz / 96 MHz | `apb1-prescaler = <2>` |

注意：F411CEU6 本身能跑 100 MHz，但板上是 **25 MHz** 晶振，25×192/2/25 = 96 MHz 是这块板能给的最整的频率。**不要照抄 CubeMX 工程的 100 MHz 配置**——那是给 8 MHz 晶振的板子写的。

## 2. "跨芯片"到底跨了几层：六步清单

本组第一篇的六步是"应用层视角"的六步；换成 STM32，同一套骨架里有两层是**全新**的，一层是**要重写**的。下面这张表是本轮真正动手的清单：

| # | 层 | 在 ESP32 上的样子 | 在 STM32F411 上的样子 | 本轮动作 | 状态 |
|---|---|---|---|---|---|
| 1 | **工具链目标** | `riscv64-zephyr-elf` / `xtensa-espressif_esp32s3_zephyr-elf` | **`arm-zephyr-eabi`** | 装 SDK 的第 3 个目标 | ✅ |
| 2 | **SoC 支持** | 主干自带 `esp32s3`（S31 靠未合并 PR） | 主干自带 `stm32f4x` + `stm32f411xe` | 什么都不用做 | ✅ 天生就有 |
| 3 | **厂商 HAL 模块** | `modules/hal/espressif` | **`modules/hal/stm32`**（外加 Cortex-M 必需的 `modules/hal/cmsis_6`） | `west update`（本机网络走不通 → 改**离线复原**，见第 4 节） | ✅ 已编过 |
| 4 | **板目标** | `esp32s3_devkitc/esp32s3/procpu`（三段） | **`blackpill_f411ce`**（一段） | 什么都不用做，主干里有 | ✅ 天生就有 |
| 5 | **控制台 chosen** | `usb_serial` / `uart0` | **`usart1`（PA9/PA10）** | overlay 显式钉死 | ✅ |
| 6 | **烧录探针** | esptool + `--esp-device COMx` | **OpenOCD + DAP-Link（CMSIS-DAP）** | 新写 `dap_link_openocd.cfg`，改 `build.ps1` 的 flash 分支 | ✅ |

**一句话记住差别**：ESP32 那套"板目标三段式 + esptool 烧 bin"，在 STM32 上变成"**板目标一段式 + OpenOCD 烧 hex**"，而"厂商 HAL"这一层从"Espressif 一家"变成"**ST 的 Cube + ARM 的 CMSIS 两层**"。

### 2.1 为什么 STM32 比 ESP32 多一层模块

ESP32 的 SoC 代码和 WiFi/BLE blob 都在 `hal_espressif` 里；STM32 不一样，它的外设驱动（GPIO/UART/时钟树）**不在 Zephyr 里**，而在 ST 官方的 **STM32Cube HAL** 里。Zephyr 的做法是：

```
zephyr/soc/st/stm32/stm32f4x/       ← Zephyr 自己的 SoC 胶水（soc.c / power.c），只 select HAS_STM32CUBE
modules/hal/stm32/stm32cube/stm32f4xx/
        ├── soc/          ← CMSIS device 头 + system_stm32f4xx.c
        └── drivers/      ← stm32f4xx_hal_*.c / stm32f4xx_ll_*.c
```

`zephyr/modules/Kconfig.stm32` 里那几百个 `CONFIG_USE_STM32_HAL_xxx` 就是"**要不要把这个 HAL 源文件编进来**"的开关，Zephyr 的驱动（`drivers/serial/uart_stm32.c` 之类）反过来 `select` 它们。所以：**没有这个模块，连 `soc.h` 都 include 不出来**，更别说点灯。

### 2.2 为什么还多一个 `cmsis_6`

Zephyr 4.2 起，Cortex-M 的 `core_cm4.h` 不再自带在树里，而是要求 `CMSIS_6` 模块（`modules/hal/cmsis_6`）。缺它的典型报错是 Kconfig 阶段就死：

```
warning: HAS_CMSIS_CORE_M ... has direct dependencies 0 ... but is currently being y-selected by CPU_CORTEX_M
error: Aborting due to Kconfig warnings
```

这条报错的迷惑点在于：它不说"你缺模块"，只说"某个符号的依赖是 0"。**看到 `HAS_CMSIS_CORE*` 的依赖为 0，先去查 `modules/hal/cmsis_6` 在不在。**

## 3. 第 1 步：给 SDK 补上 ARM 目标

### 3.1 一个 SDK，三个目标

Zephyr SDK 1.0.1 不是"一个编译器"，而是**一堆按架构分目录的 GNU 工具链**：

```
C:\Users\xiao1\zephyr-sdk-1.0.1\
├── gnu\
│   ├── riscv64-zephyr-elf\                    ← Korvo-1 / S31（RISC-V）
│   ├── xtensa-espressif_esp32s3_zephyr-elf\   ← ESP32-S3
│   └── arm-zephyr-eabi\                       ← 本轮新装（Cortex-M）
└── ...
```

`env.ps1` 的作用就是把这三个 `bin` 都塞进 PATH，并且**只认 `ZEPHYR_SDK_INSTALL_DIR` 这一处**：

```powershell
$sdk\gnu\riscv64-zephyr-elf\bin
$sdk\gnu\xtensa-espressif_esp32s3_zephyr-elf\bin
$sdk\gnu\arm-zephyr-eabi\bin
```

为什么不在工程里写死 `CROSS_COMPILE=arm-none-eabi-`？因为**项目规则是"一套变量编所有板"**：

- 写死系统 GCC 的路径 → 换台机器就崩，而且版本/库版本和 SDK 不一致时，同一份代码在两块板上表现不同；
- 用 SDK 的 `arm-zephyr-eabi` → `ZEPHYR_TOOLCHAIN_VARIANT=zephyr` 保持不变，`build.ps1`、`env.ps1`、`CMakePresets.json` 全都不用改一行；
- 出问题时**少一个变量**：链接脚本、newlib、`--sysroot` 都是 SDK 打包好的，跟 RISC-V/Xtensa 两个目标行为一致。

> 本轮为了在下载窗口里先把 `hal_stm32` 的缺件问题摸清楚，临时用系统 `arm-none-eabi-gcc 13.3.1` 做了一次"探路编译"（`build\stm32f4\f411_breath\xc-probe`，跑完就删）。**交付的构建目录只用 SDK 那一次**。教程里保留这段是因为它解释了"为什么两次编译的报错不一样"——探路编译能看到 C 代码层面的缺件，SDK 编译才是最终口径。

### 3.2 官方包与校验

SDK 的 ARM 目标在官方 release 里是单独的 7z：

```
https://github.com/zephyrproject-rtos/sdk-ng/releases/download/v1.0.1/
        toolchain_gnu_windows-x86_64_arm-zephyr-eabi.7z      79,217,349 B
        md5.sum                                               （同一目录）
```

校验值（`md5.sum` 原样）：

```

```

装法就三步（解包后的顶层目录必须是 `arm-zephyr-eabi`）：

```powershell

if ($md5 -ne "5292327efe175468b0552f0302e87935") { throw "md5 mismatch" }

# 2) 解到 SDK 的 gnu\ 下（7z 在这个仓库里就有：.tools\7z.exe）

# 3) 验证
C:\Users\xiao1\zephyr-sdk-1.0.1\gnu\arm-zephyr-eabi\bin\arm-zephyr-eabi-gcc.exe --version
```

看到 `arm-zephyr-eabi-gcc.exe (Zephyr SDK ...) 12.x` 这一行就成了。

### 3.3 国内网络的现实（本机实测）

这一段不是"运维八卦"，是**复现门槛**：79 MB 的单文件在 6 KB/s 的连接上要 3.5 小时。

| 通道 | 实测 | 能不能用 |
|---|---|---|
| `github.com` 直连（release 资产） | 000 / 超时 | ❌ |
| `codeload.github.com` | ≈26 KB/s，不支持 Range | ⚠️ 慢且不能分段 |
| `raw.githubusercontent.com` | 9–15 KB/s，可用 | ✅ 只适合小文件（胶水/头文件） |
| `gh-proxy.com` / `ghfast.top` / `ghproxy.net` | 7–80 KB/s 波动，**支持 Range（206）** | ✅ 本轮用的就是这三个 |
| `api.github.com` | 可用，但 60 次/小时未认证限额 | ⚠️ 递归列目录会直接撞墙 |
| `gitclone.com` / gitee 镜像 | 502 / 需要认证 | ❌ |

**分段下载的两个坑**（都踩了）：

1. 镜像"忽略 Range"时会返回 `200` + 整个文件，你按"段"去追加就写出一个坏文件。第一次拼出来的 79 MB 包 md5 不符就是这么来的。**每一段都要断言 `code==206` 且 `Content-Length` 等于段长**。
2. 后台任务（`run_in_background`）写在**沙箱 overlay**里，任务结束文件就消失。要么在前台命令里 `Start-Process -WindowStyle Hidden` 起独立进程，要么别指望文件留下。

## 4. 第 3 步：把厂商 HAL 拿进树

### 4.1 标准动作

```powershell
cd C:\Users\xiao1\Desktop\ELAB\kharon-ide\west   # west 工作区根
west update hal_stm32 cmsis_6
```

`west update` 会在 `modules/hal/stm32` 放 ST 的 Cube（本轮 west.yml 钉的 revision 是 `2fd0502dd5e02aa3e95a2f01278fdf27e42d7229`，仓库约 168 MB），在 `modules/hal/cmsis_6` 放 ARM 的 CMSIS Core 头。**这一步没网络就过不去**，而它恰好是本轮最耗时的一步。

### 4.2 这个模块里到底有什么（按目录看）

```
modules/hal/stm32/
├── CMakeLists.txt                  add_subdirectory_ifdef(CONFIG_HAS_STM32CUBE stm32cube)
├── stm32cube/
│   ├── CMakeLists.txt              ← 按 CONFIG_SOC 挑 series 目录、定义 USE_HAL_DRIVER 等宏
│   ├── series_list.cmake           ← 支持哪些系列（stm32f4 在列表里）
│   └── stm32f4xx/
│       ├── soc/                    ← stm32f4xx.h / stm32f411xe.h / system_stm32f4xx.c
│       ├── drivers/include/        ← stm32f4xx_hal_*.h、stm32f4xx_ll_*.h、stm32f4xx_hal_conf.h
│       └── drivers/src/            ← stm32f4xx_hal_*.c、stm32f4xx_ll_*.c
└── zephyr/module.yml               name: hal_stm32 / build: cmake: . / settings: dts_root: .
```

两个容易忽略的点：

- **`dts_root: .`**——`<st/f4/stm32f411c(c-e)ux-pinctrl.dtsi>` 这种"引脚复用描述"是**模块**提供的，不在 `zephyr/dts` 里。模块缺了它，dts 编译第一行就报 `No such file or directory`。
- **`Kconfig` 不在模块里**。`CONFIG_USE_STM32_HAL_*` 全在 `zephyr/modules/Kconfig.stm32`，模块只提供"源文件和头文件"。所以模块的 Kconfig 找不到**不是错**，别去补。

### 4.3 本轮的特殊处理（诚实记录）

本机 `github.com` 直连不可用，`west update` 拉不下来；浅克隆在 6–22 KB/s 也不现实。最终采用的办法是：

1. 用 `raw.githubusercontent.com` 把模块的**胶水文件**逐个取回（`CMakeLists.txt`、`stm32cube/CMakeLists.txt`、`stm32cube/stm32f4xx/CMakeLists.txt`、`series_list.cmake`、`zephyr/module.yml`）；
2. 用本机已有的 **STM32Cube_FW_F4_V1.28.2**（`C:\Users\xiao1\STM32Cube\Repository\...`）把 `soc/`、`drivers/include/`、`drivers/src/` 填进去；
3. `cmsis_6` 用同样办法取 Core 头（`core_cm4.h`、`cmsis_gcc.h`、`cmsis_compiler.h`、`m-profile/*.h`）。

**结果是能编、能烧、能跑**，但要说清代价：这个目录**不是 git 仓库**，以后 `west update` 会嫌它"非空"而拒绝覆盖，最好整个删掉重拉。也就是说——这是一次"离线复现"，不是仓库的标准状态。

这段还有一个收获：**缺件是一个一个暴露的**，按报错顺序能看出 HAL 的依赖链：

| 报错 | 缺什么 | 说明 |
|---|---|---|
| `st/f4/stm32f411c(c-e)ux-pinctrl.dtsi: No such file` | 模块 `dts/st/f4/*-pinctrl.dtsi` | `dts_root` 提供的引脚库 |
| `HAS_CMSIS_CORE_M ... dependencies 0` | `modules/hal/cmsis_6` | Cortex-M 的 `core_cm4.h` |
| `include could not find: series_list.cmake` | `stm32cube/series_list.cmake` | 模块自己列支持系列 |
| `m-profile/cmsis_gcc_m.h: No such file` | CMSIS6 的 `m-profile/` 子目录 | 新版 CMSIS 把头拆开了 |
| `Legacy/stm32_hal_legacy.h` | Cube 的 `Inc/Legacy/` | HAL 的兼容层 |
| `stm32_ll_bus.h` / `stm32_ll_pwr.h` / `stm32_ll_hsem.h` | `stm32cube/common_ll/include/` | **跨系列统一入口**，内部 `#if defined(CONFIG_SOC_SERIES_STM32F4X)` 转发到 `stm32f4xx_ll_*.h` |

最后一条是最值得记的：Zephyr 的 SoC 代码 include 的是 `<stm32_ll_bus.h>`（**不带系列前缀**），由模块里的"分发头"按 `CONFIG_SOC_SERIES_*` 转发。所以换系列时驱动代码不用改，转发头也不用改——这就是"一层抽象省掉 N 个 `#ifdef`"的样子。

## 5. 第 4 步：板目标为什么只有一段

### 5.1 板名的三种形状

| 形状 | 例子 | 什么时候用 |
|---|---|---|
| 一段 | **`blackpill_f411ce`** | 板上只有**一个** SoC、一个核，Zephyr 能自己从板级 dts 推出 SoC |
| 三段 | `esp32s3_devkitc/esp32s3/procpu` | 板上**多核/多 SoC**（ESP32 的 procpu + appcpu），必须点名 |
| 带限定 | `blackpill_f411ce/stm32f411xe` | 显式指定 SoC 限定（一般不用写） |

`west build -b blackpill_f411ce` 时，Zephyr 打印的是：

```
-- Board: blackpill_f411ce, qualifiers: stm32f411xe
```

`qualifiers` 就是从 `board.yml` / dts 的 `compatible` 里推出来的 SoC。

### 5.2 板级五个文件各管什么

```
zephyr/boards/weact/blackpill_f411ce/
├── board.yml                     identifier / name / vendor（给工具链和文档看）
├── blackpill_f411ce.yaml         arch: arm / toolchain: zephyr,gnuarmemb / supported: gpio?（← 见下）
├── blackpill_f411ce_defconfig    ARM_MPU / HW_STACK_PROTECTION / SERIAL / UART_CONSOLE / GPIO
├── blackpill_f411ce.dts          ★ 引脚、时钟树、chosen、flash 分区
├── board.cmake                   ★ 声明支持哪些 runner（openocd / jlink / dfu-util …）
├── Kconfig.blackpill_f411ce      板级自己的 Kconfig（本轮没用）
└── support/openocd.cfg           ← **ST-Link 专用**，本轮必须覆盖（见第 10 节）
```

`.yaml` 里的 `supported: [counter, spi, i2c, uart, pwm, adc]` 是"**板级声明的能力**"，不是"驱动一定会编"。真正编不编由 `prj.conf` 决定。

### 5.3 板上真正被用到的三处 dts

```dts
/* LED：PC13，低电平亮 */
leds { compatible = "gpio-leds";
       user_led: led { gpios = <&gpioc 13 GPIO_ACTIVE_LOW>; label = "User LED"; }; };
aliases { led0 = &user_led; };

/* 按键：PA0，按下拉低，内部上拉 */
gpio_keys { compatible = "gpio-keys";
            user_button: button { gpios = <&gpioa 0 (GPIO_ACTIVE_LOW | GPIO_PULL_UP)>;
                                  zephyr,code = <INPUT_KEY_0>; }; };
aliases { sw0 = &user_button; };

/* 控制台：USART1，PA9/PA10，115200 */
chosen { zephyr,console = &usart1; zephyr,shell-uart = &usart1; };
&usart1 { pinctrl-0 = <&usart1_tx_pa9 &usart1_rx_pa10>;
          pinctrl-names = "default"; current-speed = <115200>; status = "okay"; };
```

**`aliases` 里的 `led0` / `sw0` 是重点**：`main.c` 用 `DT_ALIAS(led0)`、`DT_ALIAS(sw0)` 取引脚，**源码里没有一个数字**。这是本组第一篇"把差异赶到 overlay"的落地方式——换一块也有 `led0/sw0` 的板，`main.c` 一行不改。

## 6. 第 5 步：控制台从哪个口出来

### 6.1 两个"看起来都是串口"的东西

ESP32 上我们习惯看 `usb_serial`（芯片自带的 USB-JTAG）；STM32F411 的 USB 是 `usbotg_fs`（PA11/PA12），且**没有内置 USB-UART 桥**。这块板上能出日志的只有两种：

1. **USART1（PA9/PA10）** → 接到 DAP-Link 的 CDC 串口 → 电脑上是一个普通 COM 口；
2. USB OTG（PA11/PA12）→ 需要自己写 USB CDC 类，本轮不做。

所以 `chosen zephyr,console` 必须是 `usart1`。板级 dts 已经这么写了，overlay 里再钉一次只是"**把隐式约定改成显式约定**"——万一以后有人改板级 dts，你的工程不会莫名静默。

### 6.2 认准是哪个 COM 口

DAP-Link 在设备管理器里会占**两个接口**：一个是调试器（不显示为 COM），一个是 CDC 串口。本机的枚举结果：

```
USB 串行设备 (COM10)   USB\VID_0D28&PID_0204&MI_01
```

- `VID_0D28` / `PID_0204` = **DAP-Link**（CMSIS-DAP 的通用 VID/PID）；
- `MI_01` = 复合设备的第 1 个接口（第 0 个是调试器）；
- 同一个 VID/PID 下的 `MI_00` 不是 COM。

对比：ESP32-S3 原生 USB 是 `VID_303A&PID_1001`（COM11）。**两块板同时在桌上时，别抓错口**——这是本轮最容易犯的低级错，抓错的表现是"串口一片安静"，然后你会去怀疑 `prj.conf`。

一条命令查清楚：

```powershell
Get-CimInstance Win32_PnPEntity | Where-Object { $_.DeviceID -match "0D28" } |
  ForEach-Object { "{0} | {1}" -f $_.Name, $_.DeviceID }
```

### 6.3 overlay 里钉死控制台

`applications\stm32f4\f411_breath\boards\blackpill_f411ce.overlay` 的关键几行：

```dts
/ {
	chosen {
		zephyr,console = &usart1;
		zephyr,shell-uart = &usart1;
	};
};

&usart1 {
	current-speed = <115200>;
	status = "okay";
};
```

顺手把本工程**用不到的外设全部 `status = "disabled"`**（`i2c1`、`spi1`、`rtc`、`usbotg_fs`、`adc1`、`timers4`）：

```dts
&i2c1     { status = "disabled"; };
&spi1     { status = "disabled"; };
&rtc      { status = "disabled"; };
&usbotg_fs { status = "disabled"; };
&adc1     { status = "disabled"; };
&timers4  { status = "disabled"; };
```

这不是洁癖。板级 dts 把 `timers4` 的 `pwm4`（PB6/PB7）默认开着了，而本工程用软件 PWM，**两个 PWM 实现同时在场**会让"到底谁在控制 PC13"变得含糊。第一批 `status = "okay"` 留给真正需要它的工程。

## 7. 第 6 步之前，先回答一个问题：PC13 能硬件 PWM 吗

**不能。** 这不是配置问题，是芯片能力问题：

| 引脚 | 定时器复用通道 | 还能干什么 |
|---|---|---|
| PC13 | **无任何 TIMx_CHy** | GPIO 输出/输入、RTC 的 TAMP 输入、EXTI13 |
| PB6 | TIM4_CH1 | 硬件 PWM（板级 dts 里的 `pwm4`） |
| PB7 | TIM4_CH2 | 硬件 PWM |

证据怎么来的（你自己也能复核）：

1. 查板级 dts 引用的 pinctrl 文件：`west\...\&timers4` 的 `pwm4` 用的是 `&tim4_ch1_pb6` / `&tim4_ch2_pb7`，**没有 pc13**；
2. 在模块的 pinctrl dtsi 里搜 `pc13`，只会看到 `adc1_in...`（F4 的 PC13 甚至连 ADC 都没有）之类的条目，**没有 `tim*_ch*_pc13`**；
3. 芯片手册的复用表（Alternate function mapping）里 PC13 一栏是空的。

所以"呼吸灯"在这颗灯上只有三条路：

| 方案 | 做法 | 代价 |
|---|---|---|
| **软件 PWM（本轮）** | 1 kHz 帧 + `k_busy_wait` 切占空比 | CPU 在亮灯期间被占满；帧周期有 µs 级抖动 |
| 硬件 PWM | 把灯挪到 PB6/PB7（外接 LED），或用 `pwm4` 驱动外接灯 | 要改接线；PC13 依然用不上 |
| 定时器 + GPIO 中断 | 用 TIM 中断翻转 PC13 | 中断频率高（1 kHz~10 kHz），开销和软件 PWM 同级 |

### 7.1 软件 PWM 的实现（`src\main.c`）

核心就四行：

```c
gpio_pin_set_dt(&led, 1);            /* ACTIVE_LOW：逻辑 1 = 拉低 = 亮 */
k_busy_wait(on_us);
gpio_pin_set_dt(&led, 0);
k_busy_wait(PWM_PERIOD_US - on_us);  /* 补足 1000 us 一帧 */
```

亮度表是 **sin² 的 65 档**（`duty_lut`，0→1000→0 µs），每档保持 47 帧：

- 1 帧 = 1 ms → 65 × 47 ≈ 3055 帧 ≈ **3.05 s 一次完整呼吸**；
- 分辨率 1 µs / 1000 µs = **0.1% 占空比**；
- 为什么是 sin² 而不是 sin：人眼对亮度的感知近似 gamma≈2，sin² 的曲线看起来才是"匀速呼吸"。

按键在同一个 1 kHz 帧里轮询，**连续 20 帧一致才算一次按下**（20 ms 去抖），切换 `breathe` 开关。

### 7.2 这份实现的真实代价（实测，不是理论）

用 `printk` 每 2 s 报一次帧周期统计，串口原文（本节数字来自本机实测）：

```
t=   6 s duty= 225 us frame avg=1005 min=1003 max=1021 us late=0 frames=5934
```

三个数字要读懂：

- **avg=1005 µs**：比 1000 多 5 µs，这是 `gpio_pin_set_dt`（走驱动层）+ 循环本身的固定开销。**呼吸周期因此变成约 3.07 s**，不是 3.05 s。
- **min=1003 / max=1021**：帧内抖动 ≤20 µs（约 1%~2%）。这是"只有 SysTick/UART 中断偶尔插进来"的情况。
- **`late=0`**：整整 22 秒、2 万多帧，没有一帧被拉长到 1050 µs 以上。

看起来太完美了？因为**统计口径本身排除了 `printk`**：代码是"测完 `dur` 再打印"，打印完才重新取 `frame_start`。也就是说打印耗掉的 5 ms 落在两帧之间，**不进任何一帧的统计**。但它在物理上仍然存在——那一帧的亮度被"冻住"5 ms，肉眼在暗处能看出一次微小的塌陷。这是同步 `printk` 的必然代价，不是 bug。

> 口径的坑：`late` 门限设在 1050 而不是 1000，是因为空载帧本来就 1005 µs——**门限贴着理论值会让计数器每帧都 +1，读数变成"帧数"**（本轮第一版就是这样，见第 12 节第 7 条）。
>
> 第二个口径的坑（按键验证时才暴露）：关灯态主循环是 `k_msleep(1)`，帧周期 **1094 µs**，如果照旧统计，`late` 会每帧 +1、`frames` 冻结在切换那一刻。所以最终版把统计块整体包进 `if (breathe)`：**只统计正在呼吸的软 PWM 帧**，关灯态改打一行 `breathing OFF (idle, CPU released, frames=…)`。这样 `late` 的含义才始终是"PWM 帧被拉长了"，而不是"有两种帧混在一起"。（见第 12 节第 13 条）

## 8. 工程结构：按仓库规则摆

### 8.1 为什么源码不放 `west`

仓库的硬规则（`docs\参考\构建入口与产物规则.md`）：

- `west\` **只放上游源码**（`.west` 工作区，`west update` 会往里灌东西）；
- 自己的工程一律 `applications\<芯片>\<工程>\`；
- 产物一律 `build\<芯片>\<工程>\<配置>\`；
- 环境变量只有一个来源：`env.ps1`。

所以本轮新增的是：

```
applications\stm32f4\
├── common\
│   └── dap_link_openocd.cfg          ← 多工程共用的探针配置
└── f411_breath\
    ├── CMakeLists.txt                project(f411_breath) + target_sources(app PRIVATE src/main.c)
    ├── prj.conf                      CONSOLE / SERIAL / UART_CONSOLE / GPIO / MAIN_STACK_SIZE
    ├── src\main.c                    ★ 全部应用逻辑（零引脚号）
    ├── boards\blackpill_f411ce.overlay  ★ 显式控制台 + 关掉用不到的外设
    └── CMakePresets.json             f411-debug / f411-release（可选的 IDE 入口）
```

构建产物落在：

```
build\stm32f4\f411_breath\default\
```

### 8.2 四份文件的分工（一张表说清）

| 文件 | 管什么 | **不该**放什么 |
|---|---|---|
| `CMakeLists.txt` | 工程名、源码列表 | 引脚、Kconfig |
| `prj.conf` | 要不要 CONSOLE/GPIO/SERIAL 这些**子系统** | 板级引脚、CPU 频率 |
| `boards\<board>.overlay` | **这块板的**引脚/外设/控制台 | 应用逻辑 |
| `src\main.c` | 应用逻辑，只通过 `DT_ALIAS(led0/sw0)` 取引脚 | 任何魔数引脚号、任何 `#ifdef CONFIG_xxx 板名` |

`CMakeLists.txt` 原文（就这么短）：

```cmake
cmake_minimum_required(VERSION 3.20.0)
find_package(Zephyr REQUIRED HINTS $ENV{ZEPHYR_BASE})
project(f411_breath)
target_sources(app PRIVATE src/main.c)
```

`prj.conf` 每一行都要能说理由（本轮只有 5 行）：

```conf
CONFIG_CONSOLE=y            # 打开控制台框架
CONFIG_SERIAL=y             # 控制台的后端是串口
CONFIG_UART_CONSOLE=y       # 串口控制台（而不是 semihosting / RAM console）
CONFIG_GPIO=y               # LED 和按键都走 GPIO 驱动
CONFIG_MAIN_STACK_SIZE=2048 # printk 同步写 UART，main 栈给足
```

> 注意：`CONFIG_GPIO=y` 在这块板上**板级 defconfig 已经开了**，这里再写一遍是"工程自证"——不依赖板级默认值，换板时行为可预期。

### 8.3 这份 `main.c` 为什么敢"零引脚号"

```c
static const struct gpio_dt_spec led = GPIO_DT_SPEC_GET(DT_ALIAS(led0), gpios);
static const struct gpio_dt_spec key = GPIO_DT_SPEC_GET(DT_ALIAS(sw0),  gpios);
```

`GPIO_DT_SPEC_GET` 在**编译期**就把 `<控制器, 引脚号, 有效电平, 上拉配置>` 打包成常量。所以：

- 换引脚 = 改 overlay / 板级 dts，**不用改 C**；
- 低电平点亮 = `GPIO_ACTIVE_LOW` 已经在 `gpio_dt_spec` 里，代码里统一 `gpio_pin_set_dt(&led, 1)` 表示"逻辑亮"；
- 按键上拉 = `GPIO_PULL_UP` 也在 spec 里，`gpio_pin_get_dt(&key)` 返回的是"逻辑按下 = 1"。

这三件事合起来就是本组第一篇那句"**把板子差异赶到 dts**"的具体做法。

## 9. 编译：走 Zephyr SDK，唯一入口

### 9.1 命令

```powershell
. .\scripts\kharon-env.ps1     # 或者在仓库根开一个已加载 env 的 pwsh
.\tools\build.ps1 -App .\applications\stm32f4\f411_breath -Board blackpill_f411ce
```

**不要**直接 `west build`。`build.ps1` 是这棵树唯一的构建入口，它替你做四件 `west build` 不做的事：

1. 调 `env.ps1`，保证 `ZEPHYR_BASE` / `ZEPHYR_TOOLCHAIN_VARIANT=zephyr` / `ZEPHYR_SDK_INSTALL_DIR` / `CCACHE_DIR` 只有一个来源；
2. 从 `-Board` 推断芯片目录（`stm32|blackpill` → `stm32f4`），产物强制落 `build\stm32f4\<工程>\<配置>`；
3. 统一 `-b`、`-d`、`-j`、ccache 环境；
4. 统计 configure/build 耗时，打印镜像尺寸。

### 9.2 为什么必须走 SDK，而不是系统里的 `arm-none-eabi-gcc`

本轮先用系统 GCC 探过路（`C:\DevEnv\GNU-tools-for-STM32`，13.3.1），能编过、能烧、能跑。但**项目口径是统一 SDK**，理由不是"系统 GCC 不行"，而是四条工程约束：

| 约束 | 系统 GCC | Zephyr SDK |
|---|---|---|
| 版本可复现 | 每台机器各装各的，13.3.1 / 12.x 混用 | 1.0.1 固定，`--version` 带 SDK 标识 |
| C 库配套 | 自带的 newlib，和 Zephyr 的 `picolibc` 选择可能打架 | SDK 内置 picolibc 头/库，与 Zephyr 版本对齐 |
| 链接脚本工具 | `ld` 版本各异，`--relax` 行为不同 | SDK 里 `ld.bfd 2.43.1` 固定 |
| 排查基准 | 报错先怀疑"是不是你这台机器的 GCC" | 报错就是代码/配置的问题 |

一句话：**跨芯片最容易出的不是编译错误，而是"这台机器能编、那台机器编出来不一样"**。三块板（RISC-V / Xtensa / ARM）共用同一个 SDK 根目录，才能保证 `env.ps1` 一套变量编三块板。

## 10. 第 6 步：DAP-Link 烧录（必须覆盖板级 cfg）

### 10.1 板级自带的 cfg 为什么用不了

`west\zephyr\boards\weact\blackpill_f411ce\support\openocd.cfg`：

```
source [find interface/stlink-dap.cfg]     ← 只认 ST-Link
transport select dapdirect_swd             ← ST-Link 的私有传输层
reset_config srst_only
```

`interface/stlink-dap.cfg` 说的是 ST-Link 的 DAP 协议；**CMSIS-DAP（DAP-Link）根本不走这条路**。本轮实测（拿这块 DAP-Link 直接跑板级那份 cfg，只 `init` 不烧）：

```
WARNING: interface/stlink-dap.cfg is deprecated, please switch to interface/stlink.cfg
Warn : DEPRECATED! use 'transport select swd', not 'transport select dapdirect_swd'
Error: open failed
exit=1
```

`Error: open failed` 就是"探针打不开"——不是线接错了（同一个探针换我们自己的 cfg 立刻 `DPIDR 0x2ba01477`）。板级 `board.cmake` 只声明"这块板支持 openocd runner"，**不承诺用哪个探针**——探针配置是使用者的责任。

### 10.2 本轮的 cfg（4 条）

`applications\stm32f4\common\dap_link_openocd.cfg`：

```
source [find interface/cmsis-dap.cfg]      # DAP-Link 走标准 CMSIS-DAP
transport select swd                       # 只用 SWD 两线（SWCLK/SWDIO）
source [find target/stm32f4x.cfg]          # 目标芯片族
reset_config none                          # 不依赖 SRST（板上只接了 SWD 4 线）
```

`reset_config none` 的理由要说清：DAP-Link 的 nRESET 只有在**接到板上 R 脚**时才有效。多数人只接 `3V3 / GND / SWDIO / SWCLK` 四根（本轮也是），所以不能假设 SRST 存在。代价见 10.4。

- **Cortex-M4 r0p1** = 核识别成功（不是"generic ARM"）；
- **device id `0x10006431`** = STM32F411，`flash size 512 KiB` 和芯片型号一致；
- **wrote 32768 bytes**：注意不是 19676。hex 按地址段写，`0x08000000` 起会被对齐到 32 KB 边界，多出来的部分填的是"未用区域"，不是固件变大；
- **1.52 s / 21 KiB/s**：CMSIS-DAP 在 2 MHz SWCLK 下的正常速度。

### 10.4 末尾那两条 `Error` 要不要管

```
Polling target stm32f4x.cpu failed, trying to reexamine
Info : SWD DPIDR 0x2ba01477
Error: Failed to read memory at 0xe000ed04
Examination failed, GDB will be halted. Polling again in 100ms
flashed OK
```

`0xe000ed04` 是 **SCB->ICSR**。现象是"写完了、复位了，然后想回头看一眼 CPU 状态，发现读不到"——因为 `reset_config none` 下没有硬复位线，OpenOCD 只能靠 SYSRESETREQ，复位后目标立刻跑起来、调试域短暂不可读。（"为什么读不到"这一句是推断；**能验证的部分**是：固件确实重启了——下一节的串口里出现了开机横幅。）**固件已经写完，`flashed OK` 和退出码 0 都说明成功**。

三种处理，按代价从低到高：

| 做法 | 效果 | 代价 |
|---|---|---|
| **不管它**（本轮采用） | 烧录成功，日志末尾多 4 行噪音 | 每次要解释一遍 |
| 把最后一步改成"写完就 shutdown" | 日志干净 | 需要自己拼 openocd 命令，绕开 west runner |
| 把 DAP-Link 的 nRESET 接到板子 R 脚，cfg 改 `reset_config srst_only srst_nogate` | 复位可控、能 halt | 要加一根线；本轮实测在没接线时反而报 `cannot read IDR` |

> 结论：**这不是错误，是"没有硬复位线"的必然现象**。要真正干净，得接第五根线。

## 11. 串口实测：开机横幅原文

### 11.1 抓开机的正确姿势

横幅（`*** Booting Zephyr OS build ... ***`）**只在复位后打印一次**。所以顺序必须是"**先开抓取，再触发复位**"：

```powershell
# 1) 先起抓取（14 s，后台）
python .\tools\zephyr\probe_serial.py COM10 14     # 注意：不要加 --reset，见 11.4

# 2) 再让 OpenOCD 复位并放开
openocd -f .\applications\stm32f4\common\dap_link_openocd.cfg `
        -c "init" -c "reset_config srst_only srst_nogate" `
        -c "reset halt" -c "reset run" -c "shutdown"
```

第二步会打印 `Error connecting DP: cannot read IDR` / `AP write error, reset will not halt`——**但复位确实发生了**（因为 `reset halt` 失败后 `reset run` 仍然下发了 SYSRESETREQ）。判据不是 OpenOCD 的嘴，而是串口里出现了横幅。

### 11.3 这段输出各自在证明什么

| 输出 | 证明了什么 |
|---|---|
| `Booting Zephyr OS build 34e025569cbb` | 跑的是**这棵树**编出来的固件（build 号和 `west` 仓库一致），不是别的板子残留的镜像 |
| `board: blackpill_f411ce/stm32f411xe` | 板目标 + SoC 限定都对了（这也是 `CONFIG_BOARD_TARGET` 的原样输出） |
| `led0: gpio@40020800 pin 13` | `0x40020800` 是 **GPIOC** 的基址，pin 13 → PC13 对上了 |
| `sw0: gpio@40020000 pin 0` | `0x40020000` 是 **GPIOA**，pin 0 → PA0 对上了 |
| `pwm: software, 1000 us frame` | 走的是软件 PWM，不是硬件 PWM |
| `k_busy_wait(1000 us) = 96322 cycles = 1003 us (core 96 MHz)` | 时钟树真的跑在 96 MHz（`96.322 MHz × 1 ms ≈ 96322`），且 `k_busy_wait` 误差 3 µs |
| `LED blink 3x done` | GPIO 通路通、**极性对**（低电平亮）；如果极性反了，这 3 下会变成"亮 120 ms / 灭 80 ms"，肉眼几乎看不出，但后面呼吸会变成反相 |
| `breathing ON (press KEY/PA0 to toggle)` | 进入主循环，按键去抖已就绪 |
| `t=2/4/6 ... frames=1976/3955/5934` | 每 2 s 涨约 1979 帧 → 帧率 ≈ 990 Hz，即 `1 kHz` 的软 PWM 真的在跑 |
| `avg=1005` | 每帧固定开销 5 µs（驱动层 + 循环），所以呼吸周期是 3.07 s 而不是 3.05 s |
| `late=0` | 2 万多帧没有一帧超过 1050 µs（口径见 7.2） |

### 11.4 一个被证伪的用法：`--reset` 对 STM32 无效

仓库里的 `tools\zephyr\probe_serial.py` 支持 `--reset`（拉 RTS 脉冲）。在 ESP32 原生 USB 上这招有效，**在 DAP-Link CDC 上无效**——DAP-Link 的 RTS 没有接到 STM32 的 NRST。实测：

```
t=   0 s duty= 500 us frame avg=1005 min=1003 max=1019 us late=0 frames=43535
```

`frames=43535` 说明它根本没重启，抓的是"跑到一半"的现场。所以 STM32 要复位只能靠 OpenOCD（11.1 的第二步）。

### 11.5 按键：真人按了 10 次，全对上（并顺手修掉两个统计缺陷）

`KEY pressed -> breathing ON/OFF` 这条日志要一根真手指按 PA0（机器替不了）。做法很简单：**先从另一侧打开串口抓取窗口，人再按**。

```
python .\tools\zephyr\probe_serial.py COM10 30     # 起窗口（被动读，10 s / 30 s 都行）
                                            # 然后按 K0（PA0，板边那个 K0/WKUP 键）
```

抓到的实录（完整原文见 `logs\f411-serial-key.txt`，这里是修完统计口径后的那一段）：

```

KEY pressed -> breathing OFF
t=  30 s breathing OFF (idle, CPU released, frames=73180)
t=  34 s breathing OFF (idle, CPU released, frames=73180)
KEY pressed -> breathing ON
t=  36 s duty= 941 us frame avg=1007 min=1003 max=3358 us late=1 frames=74495

```

一共抓到 **10 次切换**（跨两次窗口），没有一次误触发、没有一次漏触发。逐条读：

| 现象 | 说明 |
|---|---|
| `KEY pressed -> breathing OFF` 紧跟在按键之后 | 20 帧（20 ms）去抖在真机上成立：手抖、触点弹跳都没漏进 `breathe` |
| 关灯态两行 `frames` 相同（`73180` → `73180`） | 关灯后不再产帧，`k_msleep(1)` 真的把 CPU 交出去了 |
| 恢复呼吸的那一帧 `late=1 / max=3358 µs` | **真开销**：一条 `printk` 要 ~2.3 ms，正好压在这一帧里，肉眼看是一次亮度塌陷。这是软 PWM + 同步打印的固有代价，不是 bug |
| 稳定后立刻回到 `avg=1005 / late=0` | 切换没有污染后续统计 |

**这一轮还顺手改了两处代码**（都是按键验证逼出来的，不是猜的）：

1. **统计只在呼吸态累计**。旧版关灯态帧周期 1094 µs > 1050 门限，`late` 每帧 +1、`frames` 冻结（第 1 轮实录里 `late=1818 frames=861880` 就是这个假象）。现在关灯态打 `breathing OFF (idle, CPU released, frames=…)`。
2. **上报时间戳改用 `k_uptime_get()`**。旧版用 `cycles_to_us(k_cycle_get_32())` 当秒数，96 MHz 下 2³² 个 cycle 只有 **44.7 s**，于是 `t=41 s` 之后突然跳成 `t=0 s`。帧周期测量仍然用 cycle（两次采样相减，回绕也正确），只有"秒"这个量换成 64 位毫秒。

> 抓取侧的干扰：DAP-Link 的 CDC 在持续打印时**偶发丢行首几个字节**，实录里会有 `…e…pressed` 这类残行（约占 1/10）。原文件里同一行内容其实是完整的，重抓即得干净版本。**这不是固件问题**——同一份固件在 55 s 窗口里 28 行全部正常。

这样，硬件/去抖/翻转逻辑三项全部 ✅。仍然没做的是用示波器量 PA0 的抖动余量和 PWM 边沿。

## 13. 代价与替代：软件 PWM 值不值

### 13.1 本轮方案的真实成本（都是量出来的）

| 成本 | 实测值 | 说明 |
|---|---|---|
| CPU 占用 | 亮灯期间 **≈100%** 单核 | 主循环里 `k_busy_wait` 占满，没有别的线程能跑（本工程没有别的线程，所以不痛） |
| 帧周期 | **1005 µs**（目标 1000） | 5 µs 是 `gpio_pin_set_dt` + 循环的固定开销 |
| 抖动 | min 1003 / max 1021 µs | 只有中断插进来时才抖；≤2% |
| 亮度凹陷 | 每 2 s 一次（约 5 ms） | 同步 `printk` 卡住主循环；统计口径排除了它，但肉眼可能看得出 |
| 呼吸周期 | **≈3.07 s** | 65×47 帧 × 1005 µs |

### 13.2 四条替代路，按"改多少"排序

| 方案 | 怎么做 | 代价 | 何时选 |
|---|---|---|---|
| **A. 保持软 PWM，只降帧率** | `PWM_PERIOD_US` 改 2000（500 Hz），busy_wait 总量翻倍但 CPU 占用不变——**没用** | — | ✗ 不推荐，等同于没改 |
| **B. `k_timer` / 硬件定时器 + 回调** | 1 kHz 周期回调里 `gpio_pin_set`，帧周期由硬件保证 | 1 kHz 中断开销仍在；回调里不能阻塞；亮度凹陷消失 | 想在灯亮着的同时跑别的活 |
| **C. 换成有定时器通道的脚** | PB6/PB7（`tim4_ch1/ch2`，板级 `pwm4` 已声明），用 `pwm_set` | 要外接 LED；另有 TIM4 16 位 ARR 的坑（`-134`），见 13.3 | 真正的"硬件 PWM 呼吸灯"练习 → **已实测，见 13.3** |
| **D. 换芯片/换板** | 选 LED 挂在 TIM 通道上的板（如 Nucleo 系列很多如此） | 换硬件 | 下一个项目选型时 |

本轮刻意**没用 C** 做主方案：题目要求"LED 在 PC13"，而 PC13 的能力边界就是这个教程最值钱的一节。硬把灯挪到 PB6 是"绕开问题"，不是"解决问题"。

但它值得单独做一次对照实验——见 13.3（新增工程 `applications\stm32f4\f411_hwpwm`，已实机跑通）。

> 顺带说一句：如果以后要做"多台设备同步呼吸"（相位对齐），软 PWM 是**做不到**的——它靠循环计数推时间，每台设备的循环开销都不一样。那种场景必须走硬件定时器 + 绝对时间基准。

### 13.3 硬件 PWM 对照实验：TIM4 要先把时钟分下来

新工程 `applications\stm32f4\f411_hwpwm`（与 `f411_breath` 并列，互不影响）：

| 项 | 内容 |
|---|---|
| 通道 | `pwm4` CH1 = **PB6**（sin² 呼吸）、CH2 = **PB7**（反相，= period − duty） |
| 曲线 | 复用 `f411_breath` 那张 sin² 65 档表，亮度曲线可以直接对比 |
| 主循环 | 每 1 ms 一拍（`k_msleep(1)`），**每 47 ms 才写两次寄存器** |
| 板载灯 PC13 | 只在开机闪三下（证明跑的是这块板） |
| 按键 PA0 | 按一下停/继续呼吸（与 `f411_breath` 同样的 20 帧去抖） |
| `prj.conf` | 相对 `f411_breath` 只多一行 `CONFIG_PWM=y` |

**第一个坑：板级 dts 已经把 `pwm4` 声明好了，但 1 kHz 直接 `pwm_set()` 会返回 `-ENOTSUP`（-134）。**

```
pwm_set failed: -134
pwm_set failed: -134      ← 每 47 ms 一条，串口被刷满
...
```

根因是 **TIM4 是 16 位计数器，ARR 最大 65535**，而 F411 上 TIM4 挂在 APB1、时基是 `APB1 × 2 = 96 MHz`：

```
96 MHz / 1 kHz = 96000 个计数  >  65535   → 装不下 → 驱动回 -ENOTSUP
```

板级 dts 的 `pwm4` 没写 `st,prescaler`（默认 0 = 不分频），所以必须自己加 overlay。**注意属性挂在 `timers4` 上，不是 `pwm4` 子节点**——`pwm_stm32.c` 里 `PWM(index)` 展开成 `DT_INST_PARENT(index)`，读的是父节点的 `st,prescaler`：

```dts
/* applications\stm32f4\f411_hwpwm\boards\blackpill_f411ce.overlay */
&timers4 {
	st,prescaler = <1>;   /* 实际分频 = prescaler + 1 = 2 → 时基 48 MHz */
};
```

改完 1 kHz = **48000 个计数**，装得下；分辨率 `1/48000 ≈ 20.8 ns`（比软 PWM 的 1 µs 细 50 倍）。

**第二个坑：新增的 `boards\<board>.overlay` 在增量 configure 里不生效。**

第一次加完 overlay 直接 `build.ps1`，生成的 `zephyr.dts` 里 `st,prescaler` 还是 `<0x0>`，`-134` 照旧。因为 overlay 列表是在 configure 阶段算的，新增文件不在依赖图里，`west build --cmake-only` 没重新算。改成 `-Pristine` 后立刻出现：

```
st,prescaler = < 0x1 >;   /* in ..\applications\stm32f4\f411_hwpwm\boards\blackpill_f411ce.overlay:14 */
```

**证据：不靠示波器，用寄存器回读证明"参数真的进了 TIM4"。** 统计行里直接打 PSC/ARR/CCR（`TIM_TypeDef` 偏移：PSC `0x28`、ARR `0x2C`、CCR1 `0x34`、CCR2 `0x38`）：

```
t=   6 s duty= 355 us frames=5455 psc=1 arr=47999 ccr1=17040 ccr2=30960
t=   8 s duty= 854 us frames=7273 psc=1 arr=47999 ccr1=40992 ccr2=7008
t=  10 s duty=   2 us frames=9091 psc=1 arr=47999 ccr1=96    ccr2=47904
t=  12 s duty= 941 us frames=10909 psc=1 arr=47999 ccr1=45168 ccr2=2832
```

对得上的三件事：

1. **`psc=1, arr=47999`** → `96 MHz / (1+1) / (47999+1) = 1000 Hz`，帧率就是 1 kHz；
2. **`ccr1 = duty × 48`**（355×48 = 17040、941×48 = 45168），**`ccr2 = (1000−duty) × 48`**（30960、2832），两路严格互补；
3. `frames` 每 2 s 涨约 1818，说明主循环只是"每 ms 空转一圈"，**没有 `busy_wait` 占 CPU**——这是与软 PWM 最本质的差别。

构建与体积：`configure=37.8s build=9.5s total=47.3s`，`FLASH 21824 B / 4.16%`、`RAM 5632 B / 4.30%`（日志 `logs\f411-hwpwm-build.log`，串口原文 `logs\f411-hwpwm-serial.txt`）。

**接线**（任选其一；**千万别把 PB6 和 PB7 短接在一起**——两个推挽输出对短，一高一低就是互相灌电流）：

| 方式 | 做法 | 能看到什么 |
|---|---|---|
| 外接 LED | `PB6 → 220~1kΩ → LED 长脚`，`LED 短脚 → GND` | 与 PC13 同相位的呼吸；接第二只到 PB7 则是跷跷板 |
| 万用表 | 红笔 PB6、黑笔 GND，DC 电压档 | 0→≈0 V，50%→≈1.6 V，100%→≈3.3 V，跟着呼吸上下摆 |
| 示波器 | 探头 PB6 对 GND | 1 kHz 方波，占空比 0~100% 缓变，边沿干净 |

**这条实验证明了什么、没证明什么**：寄存器与串口证明 TIM4 的时基、周期、两路占空比全部正确配置，且主循环不再占 CPU；**波形本身（上升沿抖动、实际频率误差）没有上示波器量**，外接 LED 的亮度对比属于肉眼判断，不写进"实测"。

## 15. 自检答案（本组第二篇的 6 道）

**1. `-b blackpill_f411ce` 为什么不是三段式？**
因为板上只有**一个** SoC、**一个**核。`board.yml` 里 `identifier: blackpill_f411ce`，Zephyr 从板级 dts 的 `compatible = "st,stm32f411..."` 自推出 SoC（日志里的 `qualifiers: stm32f411xe`）。带 `/<soc>/<cluster>` 的是"一块板上多个 SoC 或多个核簇"的情况，最典型就是 ESP32-S3（`procpu` / `appcpu`）。

**2. 树里有板级目录，为什么还编不出 ARM 固件？缺哪两样？**
缺 **①ARM 工具链目标**（`zephyr-sdk-1.0.1\gnu\arm-zephyr-eabi`）和 **②厂商 HAL 模块**（`modules\hal\stm32`，外加 4.2 起必需的 `modules\hal\cmsis_6`）。板级目录只描述"这块板长什么样"，编译 ARM 代码还需要编译器、CMSIS 内核头、STM32Cube HAL/LL 源码与 `series_list.cmake`。少任何一样，报错都不是"板子不支持"，而是"找不到 `core_cm4.h` / `stm32f4xx_hal.h`"。

**3. `chosen zephyr,console` 指 `usart1` 之后，PA9/PA10 复用是谁配的？overlay 为什么不写 `pinctrl-0`？**
板级 `.dts` 里 `&usart1 { pinctrl-0 = <&usart1_tx_pa9 &usart1_rx_pa10>; }` 已经写好，`pinctrl` 子系统在设备初始化时把这些引脚切成 AF7（USART1）。overlay 只需要改**值**（波特率、`status`），不需要重复声明复用——重复写反而会在"板级改了引脚"时产生两份真相。

**4. 为什么不能直接 `pwm_pin_set_usec()`？**
因为 PC13 在 STM32F411 的复用表里**没有任何 TIMx_CHy**（只有 GPIO / RTC-TAMP / EXTI13）。`pwm_pin_set_usec` 要求"这个引脚已经通过 dts 绑定到一个 PWM 控制器通道"，而 PC13 绑不上——编译期就会因为找不到 `pwm` 设备而失败，或者运行期返回 `-ENOTSUP`。能硬件 PWM 的是 PB6/PB7（TIM4_CH1/CH2）。

**5. `west flash` 选 esptool 还是 OpenOCD，是它自己猜的吗？**
不是猜，是**板级 `board.cmake` 声明 + 命令行 `--runner` 决定**：`board.cmake` 里 `board_runner_args(openocd ...)`、`include(${ZEPHYR_BASE}/boards/common/openocd.board.cmake)` 之类把可用 runner 注册进来；`west flash` 在这些 runner 里挑（或按 `--runner` 指定）。ESP32 的板级只注册 esptool，STM32 的注册 openocd/jlink/dfu-util 等——**"用哪个探针"最终还是人给的 `--config`**。

**6. 换 STM32F103（Blue Pill）要动哪几处？**
四处：①板目标换成 `bluepill` 之类（树里若没有，先加板级目录）；②LED/按键引脚与极性（F103 的 Blue Pill 是 PC13 LED + PA0 键，恰好同构，overlay 基本不用改）；③flash/RAM 大小由板级 dts 决定（F103C8 = 64 KB / 20 KB，`prj.conf` 可能要减栈）；④探针配置不变（还是 SWD + CMSIS-DAP），但 `target/stm32f1x.cfg` 要换。此外 F103 无 FPU、主频 72 MHz，`k_busy_wait` 的循环常数会变——**这也是为什么 `self-test` 那行要打印实测周期数**。
