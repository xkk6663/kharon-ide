## 1. 七项各自属于哪一层（先把边界说清）

| 项目 | 应用层要做的 | 驱动层 | 板级/SoC 层 |
|---|---|---|---|
| ADC 四键 | 读通道、判电压窗、映射键名 | `drivers/adc/adc_esp32.c`（现成） | SoC 有 `adc0/adc1`；板级只要 `status=okay` |
| WS2812 | 组 `led_rgb` 结构、调 `led_strip_update_rgb` | `drivers/led_strip/ws2812_rmt_esp32.c`（现成） | 板级给 `led-strip` 节点 + `RMT_OUT0_GPIO37` |
| PWM | 算 period/pulse、调 `pwm_set_cycles` | `drivers/pwm/pwm_led_esp32.c`（现成） | 板级要 `channel0@0 {reg;timer;}` + `LEDC_CH0_GPIOxx` |
| SPI 屏 | SPI 写寄存器 + `mipi_dbi` 封装 | `display_xxx`（取决于屏 IC） | 板级 spi 节点 + 屏节点 |
| I2C 传感器 | `i2c_write_read` / 传感器驱动 | `drivers/i2c/i2c_esp32.c`（现成） | 板级 I2C 引脚 + 上拉 |
| CAN 环回 | `can_set_mode` + `can_send` + 等 msgq | `drivers/can/can_esp32_twaifd.c`（**问题所在**） | SoC 有 `twai0`，板级给 TX/RX 引脚 |
| LVGL | `lv_*` 业务界面 | 无（LVGL 是模块不是驱动） | 需 display 驱动先通 |

> 判据：**只要你不碰 `zephyr\drivers\`、`zephyr\dts\bindings\`、`zephyr\soc\`、`hal\`，你就在应用层。**
> 本工程 `applications/esp32s31/korvo_periph` 全程没动上面四个目录，唯一的"越界"是**板级 overlay**（那是你自己的板，本来就归你）。

### 2.3 两个"踩过才知道"的实现细节

**① ADC 位宽靠探测，不写死**

```c
static const uint8_t cand[] = {17, 16, 15, 14, 13, 12};
for (...) { seq.resolution = cand[i]; if (adc_read(dev, &seq) == 0) { g_adc_res = cand[i]; return 0; } }
```
S31 的 SAR ADC 是 **17 bit**（`SOC_ADC_DIGI_MIN_BITWIDTH == MAX == 17`）。写死 12 bit 也能跑，但分辨率白白丢 5 位。

**② 四键电压梯是"松开 = 0 mV"，不是常见的"松开 = 满量程"**

| 状态 | 实测 mV |
|---|---|
| 松开 | 0 |
| SET | 260 |
| PLAY | 759 |
| VOL- | 1237 |
| VOL+ | 1647 |

判定窗：`KEY_RELEASE_MV=150`、`KEY_TOL_MV=180`、`ADC_FSR_MV=3300`。
**为什么不用 dts 的 `adc-keys`**：它内部调 `adc_raw_to_millivolts_dt()`，依赖 channel 子节点上的 `zephyr,resolution`/`zephyr,vref-mv`；S31 的 `adc0/adc1` 在 SoC dtsi 里**没有 channel 子节点**，且 `SOC_ADC_ATTEN_NUM == 1`（只有 0 dB 一档），换算尺度对不上，阈值没法定。所以自己在应用层按"最近匹配"判，反而稳。

### 3.3 `korvo adc 1` —— 8 通道读数

修正 `unit` 之前（SoC dtsi 原样，`unit = <1>`）：

```
[adc] t=9970ms:      0   2245   2195   2244   1546   2630   1487   2627
```

修正 `unit` 之后（板级 overlay 里 `&adc0 { unit = <0>; }`）：

```
[adc] t=13918ms:   1857   2658   1600   2658    err    err   1526   2628
```

两处差别说明得很清楚：改之前 `ch0` 是死 0（`adc0` 实际在采 ADC2 的通道，IO42 根本没进采样）；改之后 IO42 有了 40–53 mV 的真实偏置。**但 ch4/ch5 会打 `Selected IO pin is not valid` / `Error disconnecting io (2002874975)`——io 号是垃圾值，说明 `adc_channel_io_map[unit][ch]` 在读越界。**

### 3.4 `korvo keys 10` —— 按下四键仍然无反应（真实结论）

```
[keys] res=17 bit，监听 100 次（每 100 ms），按下/松开才打印
[keys] raw=1856 -> 46 mV -> 松开
```

10 秒窗口内四键轮流按过，**只有这一行、raw 一点没动**。同一份固件两次启动之间，`ch0` 还会从 1856 漂到 2077。结论见 §9.1：**这条通路在 Zephyr 侧目前不成立，不是应用层判窗写错了。**

### 3.5 `korvo led` / `korvo pwm`

```
uart:~$ korvo led 20 0 0
[led] r=20 g=0 b=0            ← 应看到 WS2812 亮暗红（IO37）

uart:~$ korvo pwm 40
[pwm]  40%  period=40000 pulse=16000 (1 kHz @ IO44)
```
`period=40000` 就是 `cycles/1000`：LEDC 源 40 MHz → 1 kHz 周期 40000 个计数，占空 40% = 16000。**这不是估算值，是驱动回填的真工期。**

### 3.6 `korvo i2c` —— 扫到板载 codec

```
[i2c] 扫 I2C0（IO0=SDA / IO1=SCL）0x08..0x77 ...
[i2c]   0x10 ACK
[i2c]   0x14 ACK
[i2c] 共 2 个器件（板载 ES8389 在 0x10 / 0x14）
```
这两个地址是 **ES8389 codec**（板上唯一的 I2C 器件）。你要接外接传感器时，这条命令会自动多出一个地址——这就是"第 5 项现在能验、将来也能验"的用法。

### 3.7 `korvo can` —— 唯一没通的一项

```
uart:~$ korvo can
[can] set_bitrate(500k) = 0
[can] mode=LOOPBACK bitrate=500k
[can] state=0 err_cnt(tx=0 rx=0)（0=ERROR_ACTIVE 正常）
[can] send 返回 -5（-5=EIO，驱动的 TX 完成状态位报错），继续等回环帧...
[can] 没收到回环帧（500 ms 超时）
[can] 收尾 state=0 err_cnt(tx=0 rx=0)
```

**怎么读这四行：**

| 证据 | 说明 |
|---|---|
| `set_bitrate(500k) = 0` | 位时序算出来了（如果 dts 没 `bus-speed` 导致 timing=0，这里会非 0） |
| `state=0 / err_cnt = 0,0` | 控制器在 ERROR_ACTIVE，**总线上没发生位错误、ACK 错误、填充错误** |
| `send 返回 -5` | 来源 `can_esp32_twaifd.c:590`：`tx_status == TXT_TOK ? 0 : -EIO`，即 TX 缓冲区状态读成了"发送失败" |
| 收不到环回帧 | 说明帧确实没发出去（loopback 是控制器内部自环，不需要收发器） |

**结论：不是"缺 CAN 收发器"，也不是应用层写错，而是 Zephyr 这颗新 IP（`espressif,esp32-twaifd`）的驱动在 LOOPBACK 下"TX 启动/完成"这一段没走通。**
驱动的 loopback 支持是现成的（`can_esp32_twaifd.c:92` 能力位包含 `CAN_MODE_LOOPBACK`，`:142-152` 同时开 `loopback + self_test`，注释写明"让控制器 ACK 自己的帧"），但实测就是不生效。

**下一步你能做的三件事（按代价从小到大）：**

1. **放着**：CAN 在本板没有 PHYS 收发器，本来就只能做内部自测，不影响你学第三、四课。
2. **换验证方式**：用 ESP-IDF 的 `twai` 例程在同一块板上跑 loopback，确认是"IP/板子"还是"Zephyr 驱动"的问题（这一步只需编译一个 IDF 例程，不动本工程）。
3. **报到上游**：给 Zephyr 提 issue，附上面这段串口原文 + `set_bitrate=0` + `err_cnt=0`。这种"状态位报错但计数器全 0"的组合对驱动作者是最有用的线索。

## 4. 三项缺东西的，缺在哪层

### 4.1 SPI 屏点亮（第 4 项）—— 缺硬件

板载屏是 **4.3″ RGB 并口（DB0~DB15 + PCLK/HS/VS/DE + SPI 初始化脚）**，不是 SPI 屏。走它属于"第 7 项（板载屏）"的范畴，成本见 §4.3。
你要跑"SPI 屏"这条，最省事的是**买一块 ST7789 / GC9A01 模块**（20 元级），按 `04` 的七步接 SPI2 + DC/RST/BL 三个 GPIO，应用层用 `mipi_dbi` 那套。

### 4.2 I2C 外接传感器（第 5 项）—— 驱动链路已验，只缺器件

`i2c_write/i2c_read` 通路已用 ES8389 验证（ACK 都回来了）。接 BME280 / MPU6050 这类器件时，只要在 `prj.conf` 开对应驱动（如 `CONFIG_BME280`），dts 加一个子节点，应用层 `sensor_sample_fetch` + `sensor_channel_get` 就能读。

### 4.3 板载 4.3″ RGB 屏 + LVGL（第 7 项）—— 缺三层东西

| 层 | 现状 | 证据 |
|---|---|---|
| SoC 节点 | ❌ 无 `lcd_cam` | `dts\riscv\espressif\esp32s31\esp32s31_common.dtsi` 里 grep `lcd`/`cam` 零命中 |
| pinmux 宏 | ❌ 无 `LCD_*` / `CAM_*` | `esp32s31-pinctrl.h` 零命中 |
| display 驱动 | ❌ 无并口/RGB 驱动 | `drivers/display` 里 ESP32 只有 `display_esp32_dsi.c`（P4 的 DSI） |
| LVGL 模块 | ❌ 本机没拉 | `modules\lib\gui\lvgl` 不存在；`west.yml` 钉了 commit 但没 fetch（本机 GitHub 443 不通） |

结论没变：**板载 RGB 屏是"造轮子级"**（SoC 节点 + pinmux + display 驱动三缺），不是应用层能补的。想现在看到屏，走 SPI 小屏这条路。

## 5. 编译时间的真相（为什么有时 9 秒、有时 10 分钟）

| 你改了什么 | CMake 是否重跑 configure | 耗时（实测） |
|---|---|---|
| 只改 `src\main.c` | 否 | **8.8 s / 9.2 s** |
| 改 `prj.conf` 或 `boards\*.overlay` | **是**（Kconfig 全量解析 + 重生成 `autoconf.h` + `devicetree_generated.h`） | 307 目标 / **638 s** |
| 首次 build（空目录） | 是 | 同上量级 |

也就是说：**"增量编译"对 .c 文件是生效的（9 秒）；但你只要动 conf 或 overlay，Zephyr 就把整个图形重新生成一遍，几乎所有 .obj 都要重编。** 这不是 ccache 没命中，而是"配置变了 → 编译命令变了（`-DCONFIG_xxx` 变了）→ 缓存全失效"。

省时间的做法：
- 调业务逻辑时只改 `.c`，别顺手改 `prj.conf`；
- 一次把 `prj.conf`/overlay 想全再改，别来回改；
- 后台跑编译（本工程用 `build\esp32s31\korvo_lab\s31-debug.ps1` + `Start-Process pwsh`，日志落 `logs\`），别让工具调用卡住把进程杀掉。

## 8. 把应用层真正用起来：`korvo demo`

前面九条命令是"手动挡"，`korvo demo` 是**自动挡**——它把输入、线程通信、动作串成第四课那条主线：

```
demo_scan 线程（prio 8，50 ms 轮询 ADC1_CH0）
        │  key_pick() 判电压窗，只在"按下沿"投递
        ▼
   k_msgq（demo_q，深度 8）
        ▼
demo_worker 线程（prio 7）→ demo_act()：改 WS2812 颜色 + 改 PWM 占空比
```

一条命令开关：

```
uart:~$ korvo demo
[demo] 开始（每 50 ms 扫一次四键）：
       SET   -> 红灯 + PWM 100%
       PLAY  -> 绿灯 + PWM 50%
       VOL+  -> 蓝灯 + PWM +10%
       VOL-  -> 橙灯 + PWM -10%
       再敲一次 korvo demo 停止

uart:~$ korvo demo
[demo] 已停止（灯灭、PWM 0%）
```

按下键后串口会多出一行（这条**需要你手指按一下**）：

```
[demo] SET  -> 红 + PWM 100% (pulse=40000)
[demo] VOL- -> 橙 + PWM 40% (pulse=16000)
```

### 8.1 为什么"扫描线程 + 消息队列 + 工作线程"，而不是一个 while 循环搞定

| 写法 | 问题 |
|---|---|
| 一个线程里轮询 ADC 再直接改灯/PWM | 扫描周期被动作拖慢；PWM 写入失败时整条扫描停摆 |
| 扫描线程只投递、工作线程执行 | 扫描周期稳定（50 ms）；动作慢也不影响识别按键；以后换成 `input` 子系统只在投递端换实现，worker 一行不改 |

对应第四课的知识点：**input 回调 → 消息队列 → 处理线程**。这里是"ADC 轮询 → 消息队列 → 处理线程"，骨架完全一致，只是采集端从"驱动回调"换成了"应用轮询"（因为 S31 的 ADC 没有阈值中断，四键本来就是电压窗判定）。

### 8.2 实测：启动、切走、停止都正常

```
=== [injected] korvo demo @ 6s ===
[demo] 开始（每 50 ms 扫一次四键）： ...
=== [injected] korvo info @ 10s ===       ← demo 运行中，shell 仍然可用
  led_strip ws2812 ready / adc0 ready / ledc0 ready / i2c0 ready / twai0 ready
=== [injected] korvo demo @ 14.1s ===
[demo] 已停止（灯灭、PWM 0%）
```

日志：`logs\s31-periph-demo.txt`；镜像 `Wrote 257152 bytes` + `Hash of data verified`。

## 9. 遗留问题（没解决的，如实记）

### 9.1 ADC 四键在 Zephyr 侧不成立（2026-11-14 定论）

**先纠正一个前提**："之前跑通过一次"的那次，跑的是 **ESP-IDF**，不是 Zephyr。

- 证据：`display_audio_photo\docs\项目规划\改动记录.md` §8.2 —— `R77=10K 上拉到 3V3`、四键共 ADC1_CH0=GPIO42、实测 SET 260 / mode 759 / VOL- 1237 / VOL+ 1647 mV；
- 实现：`display_audio_photo\main\middleware\system\button_service.c:151-158`，`iot_button_new_adc_device`，`.unit_id = ADC_UNIT_1`、`.adc_channel = ADC_CHANNEL_0`。
- Zephyr 侧唯一"看起来跑通"的记录是 `applications\esp32s31\korvo_apps\src\main.c:396-401` 的注释，它自己写着"实测电压（ESP-IDF 侧标定值）"——那是搬过来的数字，没在 Zephyr 上验过。

**三条硬证据（都不是应用层能改的）**：

| # | 现象 | 证据 |
|---|---|---|
| 1 | `adc0` 采的不是 IO42 | `zephyr\dts\riscv\espressif\esp32s31\esp32s31_common.dtsi:456` 写 `unit = <1>`；HAL `adc_types.h:22` 的 `ADC_UNIT_1` 是 **0**；驱动 `adc_esp32.c:334` 直接拿 `unit` 当 `adc_channel_io_map` 行下标 → 实际落到 ADC2（IO50..57） |
| 2 | ch4/ch5 越界 | `korvo adc 1` 打 `Selected IO pin is not valid` + `Error disconnecting io (2002874975)`，**io 号是垃圾值**，说明那张表被读到了行外 |
| 3 | 读数自己漂 | 同一份固件两次启动：`ch0 = 1856` ↔ `2077`；且 `ch0` 永远在 40–53 mV，四键按下零变化 |

**已做过的尝试（全部失败，记下来免得重走）**：

| 尝试 | 结果 |
|---|---|
| 应用层对 ch0 自己调 `gpio_pin_configure(GPIO_DISCONNECTED)` 配 IO42 pad | `raw` 仍为 0，四键无反应 |
| 板级 overlay 改 `&adc0 { unit = <0>; }` `&adc1 { unit = <1>; }` | IO42 从死 0 变成 40–53 mV，**按键仍无反应**；ch4/ch5 越界报错 |
| `korvo pad`（数字输入读电平，三种 pull） | IO42/IO43/IO61 全读 0，而 **IO5（gpio0）能正确读到 上拉=1/下拉=0** → gpio1 的输入寄存器在这份驱动上读不出真实电平 |
| 应用层绕开驱动直调 HAL（候选方案 A） | 用户决定不走，未实施 |

**结论**：这是 Zephyr 在 S31 上的 ADC/GPIO 通路问题（dtsi 编号一基错位 + `io_map` 越界 + gpio1 读数异常），不属于"应用层写法"。如果想在 Zephyr 上真跑四键，只有两条路：等上游修，或在应用层绕开驱动直调 HAL（会破坏"只用公开驱动 API"的课程口径）。

1. **CAN LOOPBACK 在 `espressif,esp32-twaifd` 上不通**：mode/bitrate/state/err_cnt 全正常，TX 完成状态位报 ERR，收不到帧。应用层已排除嫌疑，下一步需 IDF 对照或上游 issue。
2. **`applications\esp32s31\korvo_lab` 那份镜像烧进去后启动静默**（停在 `I (spi_flash): flash io: dio` 之后，无 banner），原因未查。七项统一切到 `korvo_periph`，`korvo_lab` 暂不再用。
3. **板载 4.3″ RGB 屏 + LVGL**：SoC 节点 / pinmux / display 驱动 / LVGL 模块四缺，需要"造轮子"，不在应用层范围。**注意：这块屏在主干 Zephyr 上是能走通的——S3 的 SoC dtsi 有 `lcd_cam` + `mipi-dbi` 子节点，也有现成驱动，见 `08`。**
4. **WS2812 与 PWM 的"肉眼/波形"验收**：软件侧返回值都为 0，最终确认需要你按 §7 看一眼灯、或接表。
5. **`korvo keys N` 的 N 是次数不是秒**（每次 100 ms）：`keys 8` 只有 0.8 s，容易误以为"一按就结束"。已在 §7 里改了说明。
