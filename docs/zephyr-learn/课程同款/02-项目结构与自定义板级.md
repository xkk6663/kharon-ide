## 一、Zephyr 项目结构

### 1.1 前言：为什么先学结构

Up 主把这一节的重要性用 `IMPORTANT` 标了出来：**后面所有自定义配置，都建立在"知道每个文件归谁管"上。**

他用的是一块自制 STM32H743 板（核心板 + 底板，底板带 CH340N 串口和 WS2812B），并且如实写了两个自己板子的硬件 bug：CH340 与 USART2 接反、WS2812B 驱动不了。**这一点值得学**——把"我的板子哪里不对"写清楚，读者才不会在"照抄却跑不通"上浪费时间。

我们的板子是 ESP32-S3 模组 + Korvo 底板，同样要说清自己的硬件事实：**板上没有"一根 GPIO 就能点亮"的 LED，只有一颗接在 IO48 的 WS2812**；按键是接在 **IO45** 的用户键（按下接地）。

这两条会改变第三课的两处写法：

| 他的写法 | 我们的写法 | 原因 |
|---|---|---|
| `leds { compatible = "gpio-leds"; ... }` | `rgb_led { compatible = "worldsemi,ws2812-pulse-io"; pulse-ios = <&rmt 0>; ... }` | WS2812 是单线时序器件，GPIO 拉高不会亮，必须由 RMT 产生 800 kHz 波形 |
| `main.c` 里 `gpio_pin_toggle_dt(&led)` | `main.c` 里 `led_strip_update_rgb(strip, &px, 1)` | 换成 `led_strip` 驱动后 API 也跟着换，但"代码不写引脚号"这一点没变 |

这一改并不违背他"点灯实验不改 main.c"的核心结论——**"改 dts 就能换硬件"依然成立**，只是我们的"灯"需要换一套驱动接口，所以 `main.c` 的写法跟着变了一次；从第四课的按键开始，就又是"`main.c` 完全不碰引脚"的形态了。

### 1.2 Devicetree：把"硬件长什么样"从代码里摘出去

他讲的核心是解耦。同一件"点灯"，两条路线对比：

| 步骤 | STM32 HAL（CubeMX 路线） | Zephyr（DT 路线） |
|---|---|---|
| 选引脚 | 在 CubeMX 图形界面里点 | 在 `.dts` 里写 `rgb_led { pulse-ios = <&rmt 0>; }` + `rmt_default { pinmux = <RMT_OUT0_GPIO48>; }` |
| 电气特性 | CubeMX 里配推挽/上拉/速度 | `-pinctrl.dtsi` 里写 `output-high` / `bias-pull-up` |
| 开关外设 | `HAL_GPIO_Init()` | `CONFIG_LED_STRIP=y` + `CONFIG_WS2812_STRIP_PULSE_IO=y`（Kconfig） |
| 业务代码 | `HAL_GPIO_TogglePin(GPIOx, PIN)` | `led_strip_update_rgb(strip, &px, 1)` |
| 换板 | 重开 CubeMX、重新生成工程 | 只改 dts/overlay，`main.c` 不动 |

代价是要学 DT；收益是**换芯片只改 dts**。这也正是我们把这套教程主线放在 S3 上的理由：换板成本被压到 dts/overlay 这一层。

### 1.3 Kconfig：三层合并，`menuconfig` 不持久

他给的那张流程图，这里按同样顺序复述：

```
内核默认 Kconfig ┐
板级 _defconfig  ├──► Kconfig 合并引擎 ──► .config ──► autoconf.h ──► 内核/驱动的 #ifdef
应用 prj.conf    ┘              ↑
                     menuconfig / guiconfig（只改 .config，不持久）
```

三条结论（照他的原话）：

1. **应用级 `prj.conf` 覆盖板级 config**；
2. 大部分情况不用管内核默认值，只需管板级 + 应用级；
3. **不要靠 `menuconfig` 改配置**——它改的是生成出来的 `.config`，重跑 CMake 就刷掉。正确姿势：查 [Kconfig Search](https://docs.zephyrproject.org/latest/kconfig.html) + 手写 `prj.conf` 或 `_defconfig`；`menuconfig` 只用来"探索有哪些符号"。

生成物位置：

| 他的（Linux） | 我们的（Windows） |
|---|---|
| `cmake-build-release-zephyr/zephyr/.config` | `build\esp32s3\blinky-s3\s3-debug\zephyr\.config` |
| `.../zephyr/include/generated/zephyr/autoconf.h` | 同目录下 `zephyr\include\generated\zephyr\autoconf.h` |

## 二、CMakePresets.json：第三课做法，今天已删除

第三课用 `CMakePresets.json` 把 `BOARD`、编译器、`ZEPHYR_BASE`、构建目录固化进项目。
这套做法在今天的仓库已经**整体退场**，原因有两个：

1. 绝对路径 (`ZEPHYR_BASE`) 换机器就失效，且经常指向不存在的目录；
2. 构建参数已由产品 yaml、provider、host 三段事实解析，`--preset` 会形成第二份真相。

今天的等价入口：

```powershell

.\kharon.cmd run -p blinky_s3 --steps build --dry-run   # 看 argv
.\kharon.cmd run -p blinky_s3 --steps build,flash,monitor
```

如果你在旧文/旧截图里看到 `cmake --preset s3-debug`，那只是历史证据，不再可执行。
下一节从“板级文件逐个写”开始，讲的是 dts/Kconfig 原理；**落点按本篇顶部校准和 15 篇**。
## 三、CMakeLists.txt：不再写 `BOARD_ROOT`

第三课有两种做法：在 `CMakeLists.txt` 里 `set(BOARD_ROOT ...)`，或把 `BOARD_ROOT` 放进
`CMakePresets.json`。今天两种都不在 APP 里出现——**板级由 Zephyr module 提供**：

```text
kharon-boards/zephyr/module.yml
  → west 把 kharon-boards/boards 加进 BOARD_ROOT
  → kharon.cmd 构建时设置 EXTRA_ZEPHYR_MODULES
  → west boards 看见 korvo1 / esp32s3_korvo / esp32s31_function_coreboard
```

Zephyr 找板的优先级仍然有效（课程原理没变）：

| 优先级 | 来源 |
|---|---|
| 1 | 用户显式 `BOARD_ROOT`（`set()` 或 `-DBOARD_ROOT=...`） |
| 2 | `ZEPHYR_BASE`（内核自带官方板） |
| 3 | `ZEPHYR_EXTRA_MODULES` 里模块带的板 |

我们走第 3 条，所以 APP 的 `CMakeLists.txt` 只保留最小三行：

```cmake
cmake_minimum_required(VERSION 3.20)
find_package(Zephyr REQUIRED HINTS $ENV{ZEPHYR_BASE})
project(blinky_s3)
target_sources(app PRIVATE src/main.c)
```

> 需要临时验证一块外来板时，才用 `-DBOARD_ROOT=...`；产品和日常构建不要写，
> 否则板级又会出现第二份真相。`kharon deps --check` 可验证 module 是否真的被 west 看见。

## 四、板级目录：结构硬性，但位置在 `kharon-boards`

两件事先说清：

1. **Zephyr 源码里也有 `boards/`**（`zephyr-workspace/zephyr/boards/espressif/`），那是原厂板级；
   **我们的板级在 `zephyr-workspace/kharon-boards/boards/espressif/`**，由 module 暴露给 west。
2. 中间那层是 `arch`（他写 `arm`，我们写 `xtensa`）；自研板目录名必须与 `BOARD` 值一致。

上游 S3 板级有 17 个文件，“标准长什么样”参照它：

```
zephyr-workspace\zephyr\boards\espressif\esp32s3_devkitc\
├── board.yml  board.cmake  Kconfig  Kconfig.esp32s3_devkitc  Kconfig.sysbuild
├── esp32s3_devkitc-pinctrl.dtsi
├── esp32s3_devkitc_procpu.dts / _defconfig / .yaml
├── esp32s3_devkitc_appcpu.dts / _defconfig / .yaml
├── esp32s3_devkitc_procpu_qemu.dts / _defconfig / .yaml
└── support\openocd.cfg      sysbuild.cmake      doc\index.rst
```

我们自己的 7 个文件（第三课要求的最小集，实际落点）：

```
zephyr-workspace\kharon-boards\boards\espressif\esp32s3_korvo\
```

| 文件 | 作用 | 必须 |
|---|---|---|
| `esp32s3_korvo_procpu.dts` | 主设备树 | ✅ |
| `esp32s3_korvo-pinctrl.dtsi` | 引脚复用（S3 有 pinmux 矩阵，配串口必须有） | ✅ |
| `esp32s3_korvo_procpu_defconfig` | 板级默认 Kconfig | ✅ |
| `Kconfig.esp32s3_korvo` | 声明 `BOARD_ESP32S3_KORVO` | ✅ |
| `Kconfig.defconfig` | 条件默认值，可为空 | ✅ |
| `board.cmake` | 烧录 / 调试（runner） | ✅ |
| `board.yml` | 板子元数据（`west boards` 用） | ✅ |
| `support/openocd.cfg` | 只有用 OpenOCD 才需要 | ⏭ 第三课没建 |

## 五、七个文件逐个写（现在放 `kharon-boards`）

### 5.1 `board.yml`

他的解释：`name` 必须等于目录名（等于 `BOARD` 值）；`vendor` 查 `zephyr/soc` 厂商目录；`soc` 名查 `zephyr/soc`。我们的：

```yaml
board:
  name: esp32s3_korvo
  full_name: ESP32-S3 Korvo Custom Board
  vendor: espressif
  socs:
  - name: esp32s3
```

他的 STM32 版 soc 名是 `stm32h743xx`（`zephyr/soc/st/stm32/` 下能查到）；我们在 `zephyr-workspace\zephyr\soc\espressif\esp32s3\` 查到的名字就是 `esp32s3`。

### 5.2 `Kconfig.<board>`

作用：让 Kconfig 系统"知道世界上有这块板"，并绑定 SoC。他的模板：

```
config BOARD_xxx
	bool "ST H743 Custom Board"
	select SOC_STM32H743XX
	help
	 My custom STM32H743 board ...
```

我们的 `Kconfig.esp32s3_korvo`：

```
config BOARD_ESP32S3_KORVO
	select SOC_ESP32S3
	select SOC_ESP32S3_PROCPU if BOARD_ESP32S3_KORVO_ESP32S3_PROCPU
	help
	  Custom ESP32-S3 board (Korvo carrier + S3 module).
```

三点：

- `BOARD_ESP32S3_KORVO` = 板名大写（`esp32s3_korvo` → `BOARD_ESP32S3_KORVO`），规则一致；
- S3 是双核（两个 CPU 簇），所以多一句 `select SOC_ESP32S3_PROCPU`——只在 `procpu` 变体成立时生效。STM32 没有这一层；
- `help` **建议写英文**：我们第一次写成中文，CMake 日志把中文打成了乱码（`Korvo 鎼存洘婢?`），不影响编译但排查时很难读。

### 5.3 `Kconfig.defconfig`

按"选了哪块板"给默认值。他是先留空：

```
if BOARD_ST_H743_BOARD
# 先留空
endif # BOARD_ST_H743_BOARD
```

我们的：

```
if BOARD_ESP32S3_KORVO

# Nothing to default here yet. Peripheral switches belong in the
# application's prj.conf, not in the board defconfig.

endif # BOARD_ESP32S3_KORVO
```

> **真实踩过的坑**：`BOARD_ESP32S3_KORVO` 这个符号**只能在 `Kconfig.<board>` 里定义一次**。我第一次在 `Kconfig.defconfig` 里又写了一行 `config BOARD_ESP32S3_KORVO`，配置阶段直接报：
>
> ```
> ...depends again on BOARD_ESP32S3_KORVO (defined at
>   .../Kconfig.defconfig:6, boards/Kconfig.v2:8, .../Kconfig.esp32s3_korvo:3)
> CMake Error at .../cmake/modules/kconfig.cmake:488 (message):
>   command failed with return code: 1
> ```
>
> 记住：`defconfig` 里**使用**它（`if BOARD_xxx`），不要**定义**它。

### 5.4 `<board>_defconfig`（板级默认配置）

他的原则：**只放这块板一定有的基础功能**（时钟、串口、GPIO、调试），外设默认 `n`，由应用 `prj.conf` 打开。他的内容：

```
CONFIG_BOARD_ST_H743_BOARD=y

CONFIG_GPIO=y
CONFIG_CLOCK_CONTROL=y
CONFIG_CLOCK_CONTROL_STM32_CUBE=y
CONFIG_STM32_ENABLE_DEBUG_SLEEP_STOP=y
```

我们的 `esp32s3_korvo_procpu_defconfig`（直接参照上游 S3 板）：

```
CONFIG_CONSOLE=y
CONFIG_SERIAL=y
CONFIG_UART_CONSOLE=y
CONFIG_GPIO=y
CONFIG_CLOCK_CONTROL=y

# ESP32 的中断分配器（intc_esp32.c）用 k_malloc，所以要给内核堆
CONFIG_HEAP_MEM_POOL_SIZE=4096
```

最后那一行是我们**编译失败后才补上的**（详见 §7.5），上游 S3 板的 `_defconfig` 里没有它——因为上游 CI 编的是带 sysbuild / 带其它配置的组合，把这个问题盖住了。

差异点，教程里值得明说：

| 他的 STM32 | 我们的 S3 | 原因 |
|---|---|---|
| 手写 `CONFIG_BOARD_...=y` | 上游 S3 板没写这行，我们也不写 | Zephyr 由板名自动生成 `CONFIG_BOARD_xxx=y` |
| `CONFIG_CLOCK_CONTROL_STM32_CUBE=y` | 没有 | ESP32 时钟走自己的 `clock_control_esp32`，不用 Cube 中间件 |
| `CONFIG_STM32_ENABLE_DEBUG_SLEEP_STOP=y` | 没有 | STM32 专属（H7 的 WFI 会关调试域） |
| 没有堆配置 | **`CONFIG_HEAP_MEM_POOL_SIZE=4096`** | ESP32 的中断控制器要用 `k_malloc` |

### 5.5 `board.cmake`（烧录配置）

他的解释：Zephyr 把烧录集成进 CMake，`flash` 目标靠这个文件知道"用哪个工具、怎么连"。核心两句：

```cmake
board_runner_args(openocd "--cmd-pre-load=targets/stm32h7x.cfg")
include(${ZEPHYR_BASE}/boards/common/openocd.board.cmake)
```

我们的（照上游 S3 板抄，因为 ESP32 用的是另一套 runner 模板）：

```cmake
if(NOT "${OPENOCD}" MATCHES "^${ESPRESSIF_TOOLCHAIN_PATH}/.*")
  set(OPENOCD OPENOCD-NOTFOUND)
endif()
find_program(OPENOCD openocd PATHS ${ESPRESSIF_TOOLCHAIN_PATH}/openocd-esp32/bin NO_DEFAULT_PATH)

include(${ZEPHYR_BASE}/boards/common/esp32.board.cmake)
include(${ZEPHYR_BASE}/boards/common/openocd.board.cmake)
```

他给的 runner 表里，和我们相关的三行：

| Runner | 适用 | 我们 |
|---|---|---|
| `esp32` | esptool 串口烧录 | **默认**，`west flash --esp-device COM11` |
| `openocd` | ST-Link / DAP-Link / FT2232 | S3 可走 USB-JTAG，本教程未用 |
| `pyocd` | CMSIS-DAP | 有 DAPLink 时用 |

### 5.6 主设备树 `esp32s3_korvo_procpu.dts`

全文（这就是"点灯所需的全部 dts"）：

```dts
/dts-v1/;

#include <espressif/esp32s3/esp32s3.dtsi>
#include <espressif/partitions_0x0_amp.dtsi>
#include <zephyr/dt-bindings/led/led.h>
#include <zephyr/dt-bindings/input/input-event-codes.h>
#include "esp32s3_korvo-pinctrl.dtsi"

/ {
	compatible = "espressif,esp32s3";
	model = "ESP32-S3 Korvo Custom Board";

	aliases {
		sw0 = &button0;
		watchdog0 = &wdt0;
	};

	chosen {
		zephyr,sram = &sram1;
		zephyr,console = &uart0;
		zephyr,shell-uart = &uart0;
		zephyr,flash = &flash0;
		zephyr,code-partition = &slot0_partition;
		zephyr,led-strip = &rgb_led;
	};

	/* 板载 WS2812 一颗：RMT 通道 0，物理顺序 GRB */
	rgb_led: ws2812 {
		compatible = "worldsemi,ws2812-pulse-io";
		pulse-ios = <&rmt 0>;
		chain-length = <1>;
		color-mapping = <LED_COLOR_ID_GREEN
				 LED_COLOR_ID_RED
				 LED_COLOR_ID_BLUE>;
		reset-delay = <300>;
	};

	/* 用户按键 KEY：IO45，按下接地 */
	buttons {
		compatible = "gpio-keys";

		button0: button_0 {

### 5.7 `esp32s3_korvo-pinctrl.dtsi`

```dts
#include <zephyr/dt-bindings/pinctrl/esp32s3-pinctrl.h>

&pinctrl {
	uart0_default: uart0_default {
		group1 {
			pinmux = <UART0_TX_GPIO43>;
			output-high;
		};

		group2 {
			pinmux = <UART0_RX_GPIO44>;
			bias-pull-up;
		};
	};

	rmt_default: rmt_default {
		group1 {
			pinmux = <RMT_OUT0_GPIO48>;
		};
	};
};
```

和他讲的"pinctrl 兼顾复用与电气特性"完全对得上：`pinmux` 是复用，`output-high` / `bias-pull-up` 是电气特性。

注意 `rmt_default` 这一组：`RMT_OUT0_GPIO48` 是**"把 RMT 外设的输出通道 0 接到 IO48"**，不是"把 GPIO48 配成输出"。WS2812 的时序由 RMT 硬件产生，所以数据脚必须挂在外设复用上，不能让 GPIO 驱动去翻转（§6.12 解释为什么 `gpio-leds` 在这里不可用）。

### 5.8 应用侧 `prj.conf` 与 `main.c`

按他"外设开关放应用层"的原则（§5.4），WS2812 的驱动开关不进 `_defconfig`，而是写在 `applications\esp32s3\blinky_s3\prj.conf`：

```conf
CONFIG_LED_STRIP=y
CONFIG_WS2812_STRIP_PULSE_IO=y
CONFIG_GPIO=y
```

`CONFIG_WS2812_STRIP_PULSE_IO` 依赖 `DT_HAS_WORLDSEMI_WS2812_PULSE_IO_ENABLED`（dts 里有那个 `compatible` 才会出现），并自动 `select PULSE_IO` → `PULSE_IO_ESP32_RMT` → `PULSE_IO_ESP32_RMT_DMA`。这一串在配置阶段已实测为 `y`（见 §7.4 补充行）。

`src\main.c` 全文：

```c
#include <zephyr/kernel.h>
#include <zephyr/drivers/led_strip.h>

#define STRIP_NODE DT_CHOSEN(zephyr_led_strip)
static const struct device *strip = DEVICE_DT_GET(STRIP_NODE);

static const struct led_rgb colors[] = {
	{ .r = 0x20, .g = 0x00, .b = 0x00 }, /* 红 */
	{ .r = 0x00, .g = 0x20, .b = 0x00 }, /* 绿 */
	{ .r = 0x00, .g = 0x00, .b = 0x20 }, /* 蓝 */
	{ .r = 0x00, .g = 0x00, .b = 0x00 }, /* 关 */
};

int main(void)
{
	unsigned int i = 0;

	if (!device_is_ready(strip)) {
		return -1;
	}

	while (1) {
		struct led_rgb px = colors[i % ARRAY_SIZE(colors)];

		led_strip_update_rgb(strip, &px, 1);
		i++;
		k_msleep(1000);
	}

	return 0;
}
```

两点值得记：`DT_CHOSEN(zephyr_led_strip)` 说明"板上唯一的灯"是从 `chosen` 取的，不是从硬编码的 `DT_ALIAS(led0)`；`led_strip_update_rgb` 的第 3 个参数是**像素个数**，必须等于 dts 的 `chain-length`（我们为 1），传错会写越界。<RichMediaReference>["https://halo.misakiotoha.top/archives/lesson-3-of-getting-started-with-zephyr-complete-the-project-configuration-of-a-custom-z1uj38h"]</RichMediaReference>

## 六、设备树语法（按他原文 1–14 的顺序）

### 1. 注释

`//` 单行、`/* */` 多行。他建议用 `/* */`（`//` 不是标准 dts 语法，Zephyr 能用）。我们的文件里两种都有，多行说明一律 `/* */`。

### 2. `/dts-v1/;`

每个 `xxx.dts` 必须以此开头，否则 dtc 直接报错。我们的 dts 第 5 行就是它。

### 3. 语句结束用 `;`

和 C 一样。

### 4. 根节点 `/`

所有硬件挂在 `/` 下。他的例子：

```
/ {
	// 根节点内容
};
```

我们的 `/` 下有四个容器：`aliases`、`chosen`、`leds`、`buttons`。

### 5. 节点：硬件对象 vs 容器

| 角色 | 作用 | 我们的例子 |
|---|---|---|
| 硬件对象节点 | 对应真实硬件，有 reg / 中断 / 时钟 | `rgb_led: ws2812`（板载 WS2812）、`button0: button_0`（按键） |
| 容器节点 | 不对应硬件，只归类 | `buttons`、`aliases`、`chosen` |

### 6. 节点标签

`标签: 节点名`。我们的 `rgb_led: ws2812 { ... }`，别处写 `&rgb_led`（`chosen` 里就是这么引用的）。

### 7. 节点属性

属性值类型表（他的原文），全部会遇到：

| 类型 | 写法 | 用途 |
|---|---|---|
| string | `"ESP32-S3 Korvo Custom Board"` | 名称、model |
| int | `<115200>` | 波特率、频率 |
| int array | `<0x0 DT_SIZE_M(8)>` | 地址 + 长度 |
| uint8-array | `[de ad be ef]` | MAC、初始化序列 |
| string-array | `"tx", "rx"` | 多字符串 |
| boolean | `hw-flow-control;` | 存在即 true |
| phandle | `<&uart0>` | 指向另一节点 |
| phandles | `<&tx &rx>` | 多个引用 |
| phandle-array | `<&gpio0 47 GPIO_ACTIVE_HIGH>` | 控制器 + 参数 |
| path | `&flash0` / `"/soc/flash@..."` | 按路径指定 |

规定属性（他给的清单）：`compatible`、`reg`、`status`、`interrupts`、`#address-cells`、`clocks`、`pinctrl-0`、`model`。

**`compatible` 才是驱动匹配的关键**，他讲得最细，这里换成我们的例子：

1. 我们写 `compatible = "worldsemi,ws2812-pulse-io"`；
2. 编译时 `gen_defines.py`（`zephyr/scripts/dts/gen_defines.py`）去找绑定文件 `zephyr/dts/bindings/led_strip/worldsemi,ws2812-pulse-io.yaml`；
3. 按 yaml 校验 dts，并把 `drivers/led_strip/ws2812_pulse_io.c`（里面是 `#define DT_DRV_COMPAT worldsemi_ws2812_pulse_io`）编进来；
4. 这个 yaml 里 `pulse-ios` 是必需的，所以我们的节点必须有 `pulse-ios = <&rmt 0>;`，否则报：

```
'pulse-ios' is marked as required in 'worldsemi,ws2812-pulse-io.yaml', but does not appear
```

（顺带一个对照：他原文用的是 `gpio-leds`，对应 `zephyr/dts/bindings/led/gpio-leds.yaml` 与 `drivers/led/led_gpio.c`，那条链路在我们这块板上不成立——原因见 §6.12。这就是"`compatible` 一改，驱动全换"的最直观例子。）

### 8. `#include`

DT 用 C 预处理器，所以宏都能用。我们的 dts 引了四个：

| include | 给的是什么 |
|---|---|
| `<espressif/esp32s3/esp32s3.dtsi>` | 片上外设：`gpio0`、`uart0`、`flash0`、`sram1`… |
| `<espressif/partitions_0x0_amp.dtsi>` | flash 分区表：`slot0_partition` 等 |
| `<zephyr/dt-bindings/input/input-event-codes.h>` | `INPUT_KEY_0` 这类键码 |
| `"esp32s3_korvo-pinctrl.dtsi"` | 本板 pinctrl |

`GPIO_ACTIVE_HIGH` / `GPIO_PULL_UP` 来自 `zephyr/dt-bindings/gpio/gpio.h`（被 SoC dtsi 间接带进来）。

### 9. 引用（`&`）——两类

**① 属性值里的引用**（当数据用）：

```
gpios = <&gpio0 47 GPIO_ACTIVE_HIGH>;
/*        ↑     ↑   ↑
 *      phandle cell0 cell1
 *      控制器   引脚号 标志位
 */
```

`#gpio-cells = <2>` 决定"引用 `gpio0` 要传几个参数"。`esp32s3_common.dtsi` 里 `gpio0: gpio@60004000 { #gpio-cells = <2>; }`——和 STM32 的 `gpioh` 完全同一个机制。

**② 节点级引用**（当操作对象用），写在根节点外面：

```
&uart0 {
	current-speed = <115200>;
	status = "okay";
};
```

SoC dtsi 里 `uart0` 可能是 `disabled`，这样"打开它并改波特率"。**建议用标签引用，不要写 `serial@60000000` 这种真实节点名**——他原文也这么说：标签稳定，路径会变。

### 10. `aliases`

给节点起别名，避免代码里写长路径：

```
aliases {
	sw0 = &button0;
	watchdog0 = &wdt0;
};
```

我们**没有** `led0`——因为这个别名背后是"普通 LED"，而我们的灯不是。板载 RGB 走的是 `chosen` 里的 `zephyr,led-strip`（见下一节），代码用 `DT_CHOSEN(zephyr_led_strip)` 取设备。

`sw0` 对应代码里的 `DT_ALIAS(sw0)`，`watchdog0` 是给 `wdt` 子系统认的。**"改 dts 不改 main.c"的秘密就在这里**：`main.c` 只认别名，不认引脚。

### 11. `chosen`

系统级"哪个设备干这个活"。我们实际用到的：

| 属性 | 指向 | 作用 |
|---|---|---|
| `zephyr,sram` | `&sram1` | 主 RAM，链接脚本用 |
| `zephyr,console` | `&uart0` | printk / 日志输出 |
| `zephyr,shell-uart` | `&uart0` | shell 用的串口 |
| `zephyr,flash` | `&flash0` | 默认 flash 设备（NVS / settings 用） |
| `zephyr,code-partition` | `&slot0_partition` | 当前运行的代码分区 |
| `zephyr,led-strip` | `&rgb_led` | `led_strip` 子系统认的"那颗灯"，代码用 `DT_CHOSEN(zephyr_led_strip)` |

他清单里还有 `zephyr,dtcm` / `zephyr,itcm`（H7 特有）、`zephyr,entropy`、`zephyr,can-primary` 等，S3 这块板一个都没用到。

### 12. pinctrl（以及"我们这块板没有独立 LED"）

他的原则：不是所有芯片都需要 pinctrl，最快的判断是看 `zephyr/boards` 里同型号官方板有没有 `xxx-pinctrl.dtsi`。S3 有（我们这份就是照 `esp32s3_devkitc-pinctrl.dtsi` 裁的）。

**硬件事实必须写清楚**：ESP32-S3-DevKitC 和 Korvo 底板上都**没有"给电平就亮"的 LED**。板载 RGB 是 WS2812，走单线时序协议（Zephyr 里用 `led_strip` + `pulse_io` + RMT，见 `docs\教程\11-Zephyr驱动\WS2812.md`），给高电平不会亮。

所以要点的就是这颗 WS2812，位置与写法：

| 项 | 值 | 说明 |
|---|---|---|
| 数据脚 | **IO48** | `RMT_OUT0_GPIO48`（`esp32s3-pinctrl.h:6122`） |
| 控制器 | `&rmt` 通道 0 | `pulse-ios = <&rmt 0>` |
| 驱动 | `worldsemi,ws2812-pulse-io` | 不能是 `ws2812-gpio`：那个用 ARM 内联汇编，只支持 nRF |
| Kconfig | `CONFIG_LED_STRIP=y` + `CONFIG_WS2812_STRIP_PULSE_IO=y` | 会自动 `select PULSE_IO`，进而选中 `PULSE_IO_ESP32_RMT` |
| `color-mapping` | G / R / B | WS2812 物理顺序是 GRB，驱动按此重排字节 |

`&rmt` 默认为 `disabled` 且没有引脚，两处都要补：

```dts
&pinctrl {
	rmt_default: rmt_default {
		group1 {
			pinmux = <RMT_OUT0_GPIO48>;
		};
	};
};

&rmt {
	pinctrl-0 = <&rmt_default>;
	pinctrl-names = "default";
	status = "okay";
};
```

**为什么不能像他那样写 `gpio-leds`**：`gpio-leds` 只做"拉高/拉低"，WS2812 靠 0.35 µs / 0.9 µs 的高电平宽度区分 0 和 1，软件翻转 GPIO 在 Xtensa 上锁不住时序。这是**器件协议差异**，不是 Zephyr 写法差异：只要你的板子是普通 LED，他的 `gpio-leds` 一字不改照样能用。

安装时把那颗灯当"设备"看，用 `led_strip` 的接口：

```c
#define STRIP_NODE DT_CHOSEN(zephyr_led_strip)
static const struct device *strip = DEVICE_DT_GET(STRIP_NODE);

struct led_rgb px = { .r = 0x20, .g = 0x00, .b = 0x00 };
led_strip_update_rgb(strip, &px, 1);   /* chain-length = 1，所以只传 1 颗 */
```

### 13. 时钟（这里和 STM32 不一样）

他的 H743 要手写 `&rcc`（选 HSI、配 6 个分频器），因为 H7 时钟树复杂、Zephyr 不给默认值。

**ESP32-S3 没有可手改的 `&rcc` 节点。** 在 `esp32s3_common.dtsi` 里查不到 `clock-controller` 节点；时钟由 `drivers/clock_control/clock_control_esp32.c` 按 SoC 配置自动设定（CPU 240 MHz、APB 分频固定），`CONFIG_CLOCK_CONTROL=y` 只是把这一层打开。

所以第三课"第 13 节"在我们的板子上**没有对应代码**，只需记住一句判断法：**去 SoC dtsi 里搜 `clock`，有节点就可能要手配，没有就是驱动代劳。** STM32 H7 属于前者，ESP32 属于后者。

### 14. 电源

他的 H743 要写 `&pwr { power-supply = "ldo"; }`（内部 LDO / SMPS / 外部供电三选一）。

ESP32-S3 也没有这个节点。相关的是 `power-states`（`light_sleep` / `deep_sleep` / `soft-off`），定义在 `esp32s3_common.dtsi` 第 43–57 行，供 `pm` 子系统用；关机走 `sys_poweroff()`。**同样：不是教程缺一节，是芯片没有这个选择项。**

> 补一条：`main.c` 的**单个目标文件**已经编过——`ninja -C <build> -j 1 CMakeFiles/app.dir/src/main.c.obj` → `[14/14] Building C object CMakeFiles/app.dir/src/main.c.obj`、`exit=0`（两个工程都是）。也就是说 `led_strip_update_rgb` 这套 API 的用法在编译层是对的，差的只是把 250 多个 HAL 源文件全编完所需的机器内存。

### 7.5 搭建这块自定义板时踩的四个坑（全部真实发生）

这一节是第三课最值钱的部分：**他讲的是"应该怎么写"，这里补上"写错了会怎样"。**

| # | 现象 | 根因 | 解法 |
|---|---|---|---|
| 1 | `west build` 报 `source directory "." does not contain a CMakeLists.txt` | 应用路径写在了 `--` 后面，被当成 CMake 参数 | 应用路径放在 `--` **之前** |
| 2 | 配置阶段报 `...depends again on BOARD_ESP32S3_KORVO` + `kconfig.cmake:488` | `Kconfig.defconfig` 里重复 `config BOARD_xxx` | 一个符号只在 `Kconfig.<board>` 定义一次 |
| 3 | 链接期报 `undefined reference to k_malloc`（来自 `intc_esp32.c`） | `CONFIG_HEAP_MEM_POOL_SIZE` 默认 0，中断分配器没有堆可用 | 板级 `_defconfig` 加 `CONFIG_HEAP_MEM_POOL_SIZE=4096` |
| 4 | 编译中途 `cc1.exe: out of memory allocating 1052671 bytes` | 本机可用提交内存被其它进程吃光（16 GB 物理内存只剩 ~2.7 GB，提交上限 62.6 GB 已用 62.5 GB） | 降低并行度 `-- -j 1`；关掉无关程序；实测把残留 `cc1` 全部结束后单个目标文件能编过 |

> 第 4 条的最新实测（2026-11-14，`logs\full-blinky-j1.log`）：即使 `-j 1` 单路串行，也在第 **73/254** 个目标 `modules/hal/espressif/zephyr/common/console_init.c` 处失败，报 `cc1.exe: out of memory allocating 65536 bytes`。同一套代码的 `main.c` 单目标能编过（`exit=0`），所以结论不变：**是这台机器的内存，不是代码**。真要在这台机上编完，需要关到只剩终端（约 8 GB 可用）或换 32 GB 内存的机器。

第 3 条尤其值得记住，它的**报错位置和根因完全不在一个地方**：

```
zephyr/drivers/interrupt_controller/intc_esp32.c:128: undefined reference to `k_malloc`
```

看到 `k_malloc` 找不到，第一反应不应该是"驱动 bug"，而应该是"**内核堆没开**"。ESP32 的中断控制器用 `k_malloc` 动态分配中断描述符，所以这块板必须给它一个堆；STM32 没有这个需求，这就是"他的第三课里没有这一行"的原因。

第 4 条属于环境问题：Zephyr 的 HAL 有 250 多个源文件，Zephyr 默认按 8 路并行编，单台 16 GB 笔记本在跑着 IDE / 浏览器 / 杀毒时会触发 `cc1` 内存不足。降 `-j`、清掉残留的 `cc1` 进程就能过，**不用改任何代码**。判断它属于环境问题而不是代码问题的方法：单独重编那一个 `.obj`（`ninja -C <build> -j 1 <目标文件>`）——能过就是环境，不能过才是代码。

## 十、逐行注释版：七文件 + main.c（当前落点 `kharon-boards`）

> 这一章是**代码级**的：每个文件贴出真实内容，并在每一行（或每一组）后面写清"这行在干什么、删了会怎样"。Up 主第三课偏"怎么建"，这一章偏"每一行为什么存在"。

### 10.1 `board.yml`

```yaml
board:
  name: esp32s3_korvo                  # ① 板名：BOARD=<这个名字>/<soc>/<核>
  full_name: ESP32-S3 Korvo Custom Board  # ② 人读的名字，只在文档/日志里出现
  vendor: espressif                    # ③ 厂商，gen_defines 会写成 CONFIG_BOARD_..._VENDOR
  socs:                                # ④ 挂哪颗 SoC（必须和 zephyr/soc 里的目录名一致）
  - name: esp32s3
```

| # | 关键点 | 写错会怎样 |
|---|---|---|
| ① | `name` 必须等于目录名 `esp32s3_korvo`，且和后面 `Kconfig.<board>`、`<board>_procpu_defconfig`、`<board>_procpu.dts` 的前缀完全一致 | 配置阶段报找不到板级，或干脆落到别的板上 |
| ④ | `socs.name` 是 `esp32s3`，Zephyr 会据此去 `soc/espressif/esp32s3` 找 `Kconfig.defconfig`、`soc.yml` | 拼错 = `SOC_ESP32S3` 选不上，后面 `select SOC_ESP32S3_PROCPU` 全废 |

（上游 `esp32s3_devkitc/board.yml` 里 `socs` 下面只给 `qemu` 写了 `variants: - name: qemu / cpucluster: procpu`，普通的 `procpu` / `appcpu` 并不写在 `board.yml` 里——它们来自 SoC 自己的核定义，所以我们的 `board.yml` 只有 `socs: - name: esp32s3` 也能用 `BOARD=esp32s3_korvo/esp32s3/procpu`。）

### 10.2 `Kconfig.esp32s3_korvo`

```kconfig
config BOARD_ESP32S3_KORVO                       # ① 板级符号：一个板一个
	select SOC_ESP32S3                           # ② 选中 SoC 家族
	select SOC_ESP32S3_PROCPU if BOARD_ESP32S3_KORVO_ESP32S3_PROCPU  # ③ 按变体选核
	help
	  Custom ESP32-S3 board (Korvo carrier + S3 module).             # ④ help 文本
```

| # | 关键点 | 说明 |
|---|---|---|
| ① | 符号名 = `BOARD_` + 板名大写 | `_defconfig` 里不要重复定义它（第三课"四个坑"第 2 条） |
| ② | `select SOC_ESP32S3` | 让 `soc/espressif/esp32s3/Kconfig` 里的 SoC 配置生效，进而带出 `ESP32S3_*` 一堆符号 |
| ③ | `if BOARD_..._PROCPU` | `BOARD=esp32s3_korvo/esp32s3/procpu` 时，构建系统会自动把变体符号置 y；选 `appcpu` 就换另一条 |

**变体符号是自动生成的吗？** 是——`board.yml` 里 `socs: - name: esp32s3`（没有 `variants`）时，Zephyr 会按 SoC 的核自动给出 `procpu` / `appcpu` 两个变体，并把 `BOARD_ESP32S3_KORVO_ESP32S3_PROCPU` 这类符号喂给 Kconfig。

### 10.3 `Kconfig.defconfig`

```kconfig
if BOARD_ESP32S3_KORVO

# Nothing to default here yet. Peripheral switches belong in the
# application's prj.conf, not in the board defconfig.

endif # BOARD_ESP32S3_KORVO
```

三句话讲透：

1. 这个文件的**语法位置**很特殊：它只接受 `config X` + `default ...`，且整体包在 `if BOARD_xxx` 里；
2. 里面**不能**再写 `config BOARD_ESP32S3_KORVO`——那是 `Kconfig.<board>` 的活，重复定义会得到 `depends again on BOARD_ESP32S3_KORVO`（我们真踩过，见 §7.5 第 2 条）；
3. 我们这里**故意留空**：本板"一定要有"的东西已经写在 `_defconfig`，外设开关按第三课原则交给应用。

> 对照他的文件：他在这里写的是 `config BOARD_ST_H743_BOARD / default y` 之类"板级默认值"，因为他的板有必须默认打开的项（如 `CLOCK_CONTROL_STM32_CUBE`）；我们把这些放进了 `_defconfig`，两种写法都合法，区别只是"默认值写在 Kconfig 还是写在 defconfig"。

### 10.4 `esp32s3_korvo_procpu_defconfig`

```conf
CONFIG_CONSOLE=y            # ① 打印子系统总开关
CONFIG_SERIAL=y             # ② 串口驱动框架
CONFIG_UART_CONSOLE=y       # ③ 让 console 走 UART（否则 printk 无处可去）
CONFIG_GPIO=y               # ④ GPIO 驱动（按键要用）
CONFIG_CLOCK_CONTROL=y      # ⑤ ESP32 的时钟子系统（SoC 侧依赖它）

# ESP32 的中断分配器 intc_esp32.c 用 k_malloc -> 内核堆是必须的
CONFIG_HEAP_MEM_POOL_SIZE=4096  # ⑥ 不给就链接失败：undefined reference to k_malloc
```

| # | 为什么在**板级**而不是应用级 | 依据 |
|---|---|---|
| ①–③ | 任何一块能"看见输出"的板都要串口控制台，属于板的基础能力 | Up 主的原则：`_defconfig` 只放"这块板一定有的" |
| ④ | 这块板有按键（IO45），GPIO 是板级事实 | 同上 |
| ⑤ | ESP32 SoC 层驱动依赖，属 SoC 事实 | `clock_control_esp32.c` 在 `PRE_KERNEL_1` 初始化 |
| ⑥ | **不是业务配置，是运行前提**：`intc_esp32.c` 每次分配中断描述符都 `k_malloc` | 实测链接报错，见 §7.5 第 3 条 |

最后一行是"教程里最值钱的一行"：它不在他的 STM32 板里，因为 ARM 的 NVIC 不需要动态分配。

### 10.5 `board.cmake`

```cmake
# ① 如果 OPENOCD 不是来自 Espressif 工具链，就当成没找到（防止系统里别的 openocd 混进来）
if(NOT "${OPENOCD}" MATCHES "^${ESPRESSIF_TOOLCHAIN_PATH}/.*")
  set(OPENOCD OPENOCD-NOTFOUND)
endif()

# ② 去 Espressif 工具链里精确找 openocd

| # | 关键点 | 缺了会怎样 |
|---|---|---|
| ① | `set(OPENOCD OPENOCD-NOTFOUND)` 是"主动失效" | 不去掉的话，用户 PATH 里任意一个 openocd 会被误用，报一堆芯片不匹配 |

### 10.6 主设备树 `esp32s3_korvo_procpu.dts`（逐行）

```dts
/dts-v1/;                                            /* ① 文件格式声明，缺了 dtc 直接拒绝 */

#include <espressif/esp32s3/esp32s3.dtsi>              /* ② SoC 全部片上外设 */
#include <espressif/partitions_0x0_amp.dtsi>           /* ③ flash 分区表（含 slot0_partition） */

		watchdog0 = &wdt0;                           /*    看门狗别名，wdt 子系统靠它找设备 */

几个最容易写错的地方，逐条点名：

1. **⑮ `pulse-ios = <&rmt 0>`**：不是 `gpios`。绑错属性名 = 绑定校验直接失败（`'pulse-ios' is marked as required`）。
2. **⑰ `color-mapping`**：写成 RGB 顺序会让红绿互换。WS2812 物理顺序是 GRB，这是器件手册事实。
3. **㉒ 标志位**：`GPIO_PULL_UP | GPIO_ACTIVE_LOW` 意味着"内部上拉 + 低电平=按下"。少了 `GPIO_ACTIVE_LOW`，按下会被读成"松开"，事件方向整体反过来。
4. **㉙ ㉛ `status = "okay"`**：SoC dtsi 里 `uart0`、`rmt` 默认可能是 `disabled`；只写 `pinctrl-0` 不写 `status`，节点仍然不参与构建。

### 10.7 `esp32s3_korvo-pinctrl.dtsi`（逐行）

```dts
#include <zephyr/dt-bindings/pinctrl/esp32s3-pinctrl.h>  /* ① 提供 UART0_TX_GPIO43 这类 pinmux 宏 */

&pinctrl {                                               /* ② 往 SoC 的 pinctrl 节点里加组 */
	uart0_default: uart0_default {                       /* ③ 组名：被 pinctrl-0 用标签引用 */
		group1 {                                         /* ④ 一个 group = 一组同电气属性的引脚 */
			pinmux = <UART0_TX_GPIO43>;                  /* ⑤ "IO43 复用为 UART0 TX" */
			output-high;                                 /* ⑥ 空闲时输出高（UART 空闲电平） */
		};

		group2 {
			pinmux = <UART0_RX_GPIO44>;                  /* ⑦ "IO44 复用为 UART0 RX" */
			bias-pull-up;                                /* ⑧ 上拉，防止悬空误触发 */
		};
	};

	rmt_default: rmt_default {
		group1 {
			pinmux = <RMT_OUT0_GPIO48>;                  /* ⑨ "IO48 复用为 RMT 输出通道 0" */
		};
	};
};
```

| # | 容易误解的点 |
|---|---|
| ⑤⑦⑨ | 这些宏不是"引脚号"，而是 `ESP32_PINMUX(pin, func_in, func_out)` 编码后的 32 位数。`UART0_TX_GPIO43` 和 `GPIO43` 完全不是一回事 |
| ④ | group 的划分依据是**电气属性**，不是"一个引脚一组"。同组共用一个属性集 |
| ⑥⑧ | 电气属性只能写在 group 上；写到 `pinmux` 同一行会报语法错误 |

### 10.8 `src\main.c`（逐行）

```c
#include <zephyr/kernel.h>                  /* ① k_msleep / ARRAY_SIZE 的来源 */
#include <zephyr/drivers/led_strip.h>         /* ② led_strip_update_rgb / struct led_rgb */

#define STRIP_NODE DT_CHOSEN(zephyr_led_strip)  /* ③ 从 chosen 取节点，不硬编码引脚 */
static const struct device *strip = DEVICE_DT_GET(STRIP_NODE); /* ④ 编译期绑定设备对象 */

static const struct led_rgb colors[] = {    /* ⑤ 四帧颜色，rgb 三个字节 */
	{ .r = 0x20, .g = 0x00, .b = 0x00 },
	{ .r = 0x00, .g = 0x20, .b = 0x00 },
	{ .r = 0x00, .g = 0x00, .b = 0x20 },
	{ .r = 0x00, .g = 0x00, .b = 0x00 },
};

int main(void)
{
	unsigned int i = 0;

	if (!device_is_ready(strip)) {          /* ⑥ 驱动初始化失败（比如 RMT 没开）就退出 */
		return -1;
	}

	while (1) {
		struct led_rgb px = colors[i % ARRAY_SIZE(colors)];  /* ⑦ 取当前帧 */

		led_strip_update_rgb(strip, &px, 1);  /* ⑧ 第 3 参 = 像素数，必须 ≤ chain-length */
		i++;
		k_msleep(1000);                       /* ⑨ 1 s 一帧，肉眼可见 */
	}

	return 0;
}
```

| # | 为什么这么写 | 换成别的写法会怎样 |
|---|---|---|
| ③ | `DT_CHOSEN` 让"灯在哪"完全由 dts 决定 | 用 `DT_NODELABEL(rgb_led)` 也编译得过，但那是"绑死标签"，换个板就得改代码 |
| ④ | `DEVICE_DT_GET` 是编译期常量，无运行期查找开销 | 用 `device_get_binding("ws2812")` 是运行期按名字找，容易找错到别的设备 |
| ⑥ | `ws2812_pulse_io` 的 `init` 会去申请 RMT 通道，失败时 `device_is_ready` 为假 | 跳过检查，后面 `update_rgb` 会返回 `-ENODEV`，但现象是"灯不亮、也不报错" |
| ⑧ | 驱动内部会检查 `num_pixels > length` 并返回 `-EINVAL` | 传 2 而 `chain-length = 1`，静默不亮 |

## 十一、从 `compatible` 到 `DT_DRV_COMPAT`：驱动到底怎么被"拉进来"

这一段是第三课最容易被跳过、但最该讲清的机制。**dts 里那个字符串，是如何变成一段被编进固件的 C 代码的？**

**第一步：字符串 → 符号**

```
"worldsemi,ws2812-pulse-io"
        ↓ 逗号变下划线、横线变下划线、全大写
DT_HAS_WORLDSEMI_WS2812_PULSE_IO_ENABLED
```

这个符号会出现在生成的 `.config` 里（我们实测到了）：

```
CONFIG_DT_HAS_WORLDSEMI_WS2812_PULSE_IO_ENABLED=y
```

**第二步：Kconfig 用它当"开关条件"**

`drivers/led_strip/Kconfig.ws2812:158` 写的是：

```kconfig
config WS2812_STRIP_PULSE_IO
	bool "WS2812 LED strip pulse_io driver"
	default y
	depends on DT_HAS_WORLDSEMI_WS2812_PULSE_IO_ENABLED   /* ← 就是这个依赖 */
	select PULSE_IO
```

所以"dts 里有节点"⇒"`.config` 有 `DT_HAS_..._ENABLED=y`"⇒"驱动符号默认为 y"⇒"`ws2812_pulse_io.c` 被加进编译列表"。**一行 dts 决定一个 `.c` 编不编**，这就是 DT 驱动模型的核心。

**第三步：驱动文件里反向声明自己是谁**

`drivers/led_strip/ws2812_pulse_io.c:7`：

```c
#define DT_DRV_COMPAT worldsemi_ws2812_pulse_io
```

这个宏让文件里所有 `DT_INST_*` 宏都按 `worldsemi,ws2812-pulse-io` 去取属性——`DT_INST_PROP(i, chain_length)` 就是在读 dts 的 `chain-length`。

**第四步：用 `DEVICE_DT_INST_DEFINE` 把实例注册进设备表（`ws2812_pulse_io.c:148-173`，原文节选）**

```c
static DEVICE_API(led_strip, ws2812_pio_api) = {
	.update_rgb = ws2812_pio_update_rgb,   /* ← 你在 main.c 调的就是它 */
	.length = ws2812_pio_length,
};

#define WS2812_PIO_DEVICE(idx)                                                    \
	static const uint8_t ws2812_pio_##idx##_color_mapping[] =                     \
		DT_INST_PROP(idx, color_mapping);                                     \
	static struct pulse_cell ws2812_pio_##idx##_cells[                            \
		DT_INST_PROP(idx, chain_length) *                                     \
		DT_INST_PROP_LEN(idx, color_mapping) * 8];   /* ← 缓冲区大小在编译期算好 */ \
	static const struct ws2812_pio_config ws2812_pio_##idx##_config = {           \
		.pio_dev = DEVICE_DT_GET(DT_INST_PHANDLE_BY_IDX(idx, pulse_ios, 0)),  \
		.channel = DT_INST_PHA_BY_IDX(idx, pulse_ios, 0, channel),            \
		.num_colors = DT_INST_PROP_LEN(idx, color_mapping),                   \
		.length = DT_INST_PROP(idx, chain_length),                            \
		.reset_delay = DT_INST_PROP(idx, reset_delay),                        \
		.cells = ws2812_pio_##idx##_cells,                                    \
	};                                                                            \
	static struct ws2812_pio_data ws2812_pio_##idx##_data;                        \
	DEVICE_DT_INST_DEFINE(idx, ws2812_pio_init, NULL, &ws2812_pio_##idx##_data,   \
			      &ws2812_pio_##idx##_config, POST_KERNEL,                \
			      CONFIG_LED_STRIP_INIT_PRIORITY, &ws2812_pio_api);

DT_INST_FOREACH_STATUS_OKAY(WS2812_PIO_DEVICE)
```

`DT_INST_FOREACH_STATUS_OKAY` 的意思是：**dts 里有几个 `status = "okay"` 的这种节点，就展开几份设备定义**。我们只有一个，所以只展开一次。

顺便能看出三件实事：

- `cells` 数组长度 = `chain-length × color-mapping 长度 × 8` = 1×3×8 = **24 个 cell**，编译期就定死，**没有堆分配**；
- `pulse-ios = <&rmt 0>` 的两个部分在这里被分别取走：`DT_INST_PHANDLE_BY_IDX(...,0)` 拿到 `&rmt` 设备，`DT_INST_PHA_BY_IDX(...,0,channel)` 拿到通道号 `0`；
- `.reset_delay = DT_INST_PROP(idx, reset_delay)` 就是 dts 里的 `reset-delay = <300>`。

**第五步：C 代码取设备**

```c
DEVICE_DT_GET(DT_CHOSEN(zephyr_led_strip))
```

展开成 `&__device_dts_ord_N`——一个编译期就确定的指针。名字对不上（比如 `chosen` 写错标签）会在编译期报错，而不是运行期找不到设备。**这就是 Zephyr 比 `device_get_binding()` 安全的地方。**

一条链总结：

```
dts: compatible="worldsemi,ws2812-pulse-io"
  → .config: CONFIG_DT_HAS_WORLDSEMI_WS2812_PULSE_IO_ENABLED=y
  → Kconfig: WS2812_STRIP_PULSE_IO=y（并 select PULSE_IO）
  → 编译: drivers/led_strip/ws2812_pulse_io.c 进列表
  → 链接: DT_INST_FOREACH_STATUS_OKAY 展开一个 struct device
  → 运行: main.c 的 DEVICE_DT_GET 直接拿到它
```

## 十二、`led_strip_update_rgb` 到底做了什么（真实代码路径）

很多人卡在"我调了一个函数，灯怎么就亮了"。拆成四层：

**第 1 层：你调的 API（`include/zephyr/drivers/led_strip.h:127`）**

```c
static inline int led_strip_update_rgb(const struct device *dev,
				       struct led_rgb *pixels, size_t num_pixels)
{
	const struct led_strip_driver_api *api = (const struct led_strip_driver_api *)dev->api;

	return api->update_rgb(dev, pixels, num_pixels);
}
```

就是一个函数指针转发，没有魔法。

**第 2 层：驱动把 RGB 编成"脉宽单元"（`drivers/led_strip/ws2812_pulse_io.c:38-94`）**

```c
#define WS2812_RESOLUTION_HZ 10000000   /* 一个 cell = 100 ns */
#define WS2812_CELL_PERIOD   13         /* 1.25 µs 一位 */
#define WS2812_DUTY_ZERO     4          /* 0 码：高电平 4 cell = 400 ns */
#define WS2812_DUTY_ONE      8          /* 1 码：高电平 8 cell = 800 ns */

static void ws2812_encode_byte(struct pulse_cell *cells, uint8_t byte)
{
	for (int i = 0; i < 8; i++) {
		cells[i] = (struct pulse_cell){
			.duty = (byte & BIT(7 - i)) ? WS2812_DUTY_ONE : WS2812_DUTY_ZERO,
		};
	}
}
```

- 一个字节 8 位 → 8 个 cell；
- 每个 cell 的 `duty` 决定高电平多宽；
- 我们的灯是 3 个颜色通道 × 8 位 = 24 cell/颗，`chain-length=1` 就是 24 个 cell。

`update_rgb` 里核心循环（`:60-79`）：

```c
for (size_t i = 0; i < num_pixels; i++) {
	for (uint8_t j = 0; j < cfg->num_colors; j++) {
		switch (cfg->color_mapping[j]) {
		case LED_COLOR_ID_RED:   component = pixels[i].r; break;
		case LED_COLOR_ID_GREEN: component = pixels[i].g; break;
		case LED_COLOR_ID_BLUE:  component = pixels[i].b; break;
		}
		ws2812_encode_byte(&cells[(i * cfg->num_colors + j) * 8], component);
	}
}
```

**`color-mapping` 在这里生效**：`j=0` 取 `LED_COLOR_ID_GREEN` ⇒ 先发 G 字节——这就是"我们写 RGB、硬件是 GRB"的解耦点。

**第 3 层：交给 `pulse_io` 发（`:81-88`）**

```c
req = (struct pulse_io_tx_req){ .cells = cells, .count = num_pixels * num_colors * 8 };
ret = pulse_io_transmit_sync(cfg->pio_dev, data->chan, &req, K_MSEC(100));
```

`pulse_io` 是"脉宽抽象层"：你给它"每个 cell 的占空比"，它负责用某个硬件外设把波形打出去。ESP32 上这个硬件就是 **RMT**（`pulse_io_esp32_rmt.c`）。

**第 4 层：锁存（`:91`）**

```c
k_usleep(cfg->reset_delay);   /* reset-delay = 300 µs，低电平保持 */
```

WS2812 是"没有时钟线"的协议，靠**超过 50 µs 的低电平**判定一帧结束并锁存。所以这行不是"随便 sleep 一下"，是协议要求。

**为什么不用 GPIO 翻转**：`ws2812_gpio.c:51-52` 里 `SET_HIGH` 是 `str %[p], [%[r], #0]`——ARM 的 OUTSET 寄存器内联汇编，且 `:82-98` 强依赖 nRF 的 HFCLK 申请。Xsensa 上既编不过也跑不了。

**串起来**：

```
main.c: led_strip_update_rgb(&px, 1)
  → led_strip.h 转发 api->update_rgb
  → ws2812_pulse_io.c: color_mapping 重排 + 每位编成 cell
  → pulse_io_transmit_sync（CELL 模式）
  → pulse_io_esp32_rmt.c: 配置 RMT 通道 0，cell→RMT 的 item
  → RMT 硬件从 IO48 输出 800 kHz 波形
  → k_usleep(300) 锁存
```

第三课只会告诉你"写 dts 就能点灯"。这一节告诉你**"点灯"在这棵树上到底是哪四段代码**——以后接 SPI 屏、接 WS2812 灯带（`chain-length` 调大）、换成 `ws2812-spi` 驱动，你都知道该改哪一层。
