# 04 · 给自己底板加外设（屏幕为例）：属于哪一层、要改什么

> **现行口径（2026-11-20）**：本篇写于主线还在 S31 时，示例多用 `boards\<板目标>.overlay`。
> 现在板级真相统一在 `zephyr-workspace\kharon-boards\boards\<vendor>\<board>\`；APP 侧仍可留
> `<board>.overlay` 做“这个应用额外要的外设”。方法论（五层职责、判定口诀、七步实操）不变，
> 落点按 [15 · 双根与 Board / APP / Product](../../tutorials/15-Zephyr工作区双根与板级APP产品.md) 为准。

> 问题：我要给自己的板子适配一块屏幕，是不是等于"去干上游的活"？属于哪个层面？要跑起来得改哪些东西？
> 一句话答案：**不是上游的活**。屏幕是"你这块底板独有的外挂"，落在**应用层**（`boards\<板目标>.overlay` + `prj.conf`），改 2 个文件就够；只有当 Zephyr **没有**这颗屏的驱动时，你才需要往下探一层（自己写驱动 + binding），那也不是"上游的活"，是"你自己的 module"。

---

## 1. 先分清五层：谁写什么、改哪算改谁的活

| 层 | 位置 | 写什么 | 改这层 = 干谁的活 |
|---|---|---|---|
| **① SoC** | `zephyr\dts\riscv\espressif\esp32s31\esp32s31_common.dtsi`、`zephyr\soc\espressif\esp32s31\` | 芯片里有哪些控制器、寄存器地址、引脚复用宏 | 乐鑫/Zephyr SoC 维护者。**你不改** |
| **② 板级** | `zephyr\boards\espressif\esp32s31_function_coreboard\`（15 文件） | 官方 coreboard 引出了哪些控制器、接哪几个脚、板载什么器件 | 板子作者（乐鑫）。**你不改** |
| **③ 应用层（你的板级差量）** | `applications\<app>\boards\<板目标>.overlay`（+ `elab-app-common\*.dtsi`） | "我这个应用要用什么" + "上游板级和我底板的接线差异" | **你的活，就改这里** |
| **④ binding（契约）** | `zephyr\dts\bindings\<类>\<vendor>,<chip>.yaml` | 这个 `compatible` 允许/必须有哪些属性 | 驱动作者。你不改；**你按它填** |
| **⑤ 驱动** | `zephyr\drivers\<类>\`（如 `display\display_st7789v.c`） | 真正操作寄存器的代码 | Zephyr 维护者。**Zephyr 没有时你才写** |

**三条判定问句**（以后任何外设都套这三句，就不会搞错层）：

1. **"所有用这颗芯片的板子都该有它吗？"** → 是 → ①SoC（例如"这颗 SoC 有 SPI2 控制器"）
2. **"这是乐鑫官方那块 coreboard 的接线吗？"** → 是 → ②板级（例如"BOOT 键在 G29""WS2812 在 G60"）
3. **"这是我这块底板独有的外挂吗？"** → 是 → ③应用层（**你的屏幕、你的传感器、你的功放使能脚**）
4. 补充：**"Zephyr 里有这颗芯片的驱动吗？"** → 没有 → ⑤驱动 + ④binding（自己写，放你的 module，不必上游）

你加屏幕 = 命中第 3 条，**一次都没碰到上游**。

---

## 2. 屏幕适配：三种形态，只有第一种是"改两个文件"

| 形态 | 例子 | Zephyr 里有没有驱动 | 你要动的地方 |
|---|---|---|---|
| **A. SPI / I2C 小屏（最常见）** | ST7789V 240×320、ST7735R、ILI9341、SSD1306 OLED | **有**（`dts\bindings\display\` 里能搜到 `sitronix,st7789v` / `solomon,ssd1306-*` 等） | ③应用层：overlay 加 pinctrl 组 + 打开总线 + `mipi_dbi` + 屏幕节点；`prj.conf` 开 2 个 Kconfig |
| **B. 屏挂在"板级没开"的总线上** | 同上，但 S31 板级只开了 `uart0/i2c0/rmt/twai0`，**没开 `spi2/spi3`** | 有 | 同 A，**多一步**：overlay 里 `&spi2 { status = "okay"; pinctrl-0 = <&…>; }` |
| **C. Zephyr 没有这颗屏的驱动** | 某国产屏 IC、并口 8080 屏 | 没有 | ⑤写驱动 + ④写 binding yaml + 自己的 module 结构 |

**A/B 是 90% 的场景，也是你的场景**（你手上那块屏只要 `compatible` 能在 `zephyr\dts\bindings\display\` 里搜到，就是 A/B）。

---

## 3. 以 ST7789V（SPI）为例：7 步，全都落在应用层

> **本节的节点结构不是猜的**：直接抄了一块真实存在的 Zephyr 板级——
> `zephyr\boards\waveshare\esp32s3_touch_lcd_1_28\esp32s3_touch_lcd_1_28_esp32s3_procpu.dts`（第 58-79 行的 `mipi_dbi` 块）。
> 你完全可以把这个文件当模板读，它和 S31 只是宏前缀不同。

### 第 1 步：确认 SoC 有控制器（不用改，只确认）
S31 的 SoC dtsi 里确实有：
```
spi2: spi@2038f000   spi3: spi@20390000
i2c0: i2c@20385000   i2c1: i2c@20386000
ledc0: ledc@20392000 adc0/adc1 …
```
→ 控制器存在，只是**板级没打开**（板级只 `status = "okay"` 了 uart0/i2c0/rmt/twai0/wdt0/trng0/gpio0/gpio1/ldo）。这就是"B 形态"。

### 第 2 步：读 binding，把它要求的东西抄全（这一步最省事）

`zephyr\dts\bindings\display\sitronix,st7789v.yaml`：
```
compatible: "sitronix,st7789v"
include: [mipi-dbi-spi-device.yaml, lcd-controller.yaml]
properties:
  x-offset: {required: true}    # 显存相对玻璃的列偏移
  y-offset: {required: true}
  mdac:     {required: true}    # Memory Data Access Control（扫描方向/镜像）
  mipi-mode:{required: true}
  vcom / gctrl / vrhs / vdvs / porch-param / pvgam-param / nvgam-param …
  ready-time-ms: {default: 40}
```
它 `include` 的两个文件又带来 **3 个 required**（这是很多人漏的地方）：

| 来源 | 必填属性 |
|---|---|
| `display-controller.yaml` | **`width`**、**`height`**（像素） |
| `lcd-controller.yaml` | **`pixel-format`**（`zephyr/dt-bindings/display/panel.h` 里的宏，RGB565 屏写 `PANEL_PIXEL_FORMAT_RGB_565`） |
| `sitronix,st7789v.yaml` | `x-offset`、`y-offset`、`mdac`、`mipi-mode` |

漏一个，dtc 立刻报 `'xxx' is marked as required in '…yaml', but does not appear`——**和他课里 `gpios` required 报错是同一个机制**。

### 第 3 步：确认 pinctrl 宏名（别猜，先 grep）
ESP32 的 pinmux 宏是 `信号_GPIOxx`，但 SPI2 的前缀是 **`SPIM2`**（不是 `SPI2`）：
```powershell
Select-String -LiteralPath west\zephyr\include\zephyr\dt-bindings\pinctrl\esp32s31-pinctrl.h `
  -Pattern '#define SPIM2_(MOSI|MISO|CLK|CSEL)_GPIO' | Select-Object -First 8
```
→ 实际会看到 `SPIM2_CSEL_GPIO0…`、`SPIM2_MOSI_GPIOxx`、`SPIM2_MISO_GPIOxx`、`SPIM2_CLK_GPIOxx`。**脚号按你原理图改**。

### 第 4 步：overlay 里写 pinctrl 组 + 打开 `&spi2`

```dts
/* applications\<app>\boards\esp32s31_function_coreboard_esp32s31_hpcore.overlay 追加 */
&pinctrl {
	spim2_korvo: spim2_korvo {
		group1 {
			pinmux = <SPIM2_MOSI_GPIO12>, <SPIM2_MISO_GPIO13>, <SPIM2_CLK_GPIO14>;
			output-high;
		};
	};
};

&spi2 {
	#address-cells = <1>;
	#size-cells = <0>;
	pinctrl-0 = <&spim2_korvo>;
	pinctrl-names = "default";
	cs-gpios = <&gpio0 17 GPIO_ACTIVE_LOW>;   /* CS 若是普通 GPIO 就写这里 */
	status = "okay";
};
```
> 脚号 12/13/14/17 只是示例，按你板子的实际接线改。

### 第 5 步：挂 `mipi_dbi` + 屏幕节点（**注意层级：不是直接挂在 `&spi2` 下**）

Zephyr 的 MIPI-DBI 是"一个虚拟控制器 + 一个面板"两层，`st7789v` 必须挂在 `mipi_dbi` 节点里（真实板级就是这么写的）：

```dts
#include <zephyr/dt-bindings/display/panel.h>

/ {
	mipi_dbi {
		compatible = "zephyr,mipi-dbi-spi";
		spi-dev = <&spi2>;                              /* 指向总线 */
		dc-gpios = <&gpio0 15 GPIO_ACTIVE_HIGH>;        /* D/C 脚：命令=0 数据=1 */
		reset-gpios = <&gpio0 16 GPIO_ACTIVE_LOW>;      /* 屏 RESET */
		write-only;                                     /* 屏只写，省 RAM */
		#address-cells = <1>;
		#size-cells = <0>;

		lcd: st7789v@0 {
			compatible = "sitronix,st7789v";
			reg = <0>;
			mipi-max-frequency = <4000000>;
			pixel-format = <PANEL_PIXEL_FORMAT_RGB_565>;

			width = <240>;
			height = <320>;
			x-offset = <0>;
			y-offset = <0>;
			mdac = <0x08>;                              /* 扫描方向，按屏手册/sample 改 */
			mipi-mode = "MIPI_DBI_MODE_SPI_4WIRE";
			status = "okay";
		};
	};
};
```

**为什么必须这样分层**（一句话解释）：`mipi_dbi` 节点负责"用 SPI + DC 脚模拟出 MIPI-DBI 的写命令/写数据时序"，`st7789v` 驱动只认"父节点是个 mipi-dbi 控制器"（源码里是 `DEVICE_DT_GET(DT_INST_PARENT(inst))`）。直接挂在 `&spi2` 下面，编译能过、运行起来拿不到控制器。

### 第 6 步：`prj.conf` 开两个符号（**第四课那个坑的翻版**）

```conf
CONFIG_DISPLAY=y       # display 子系统（menuconfig DISPLAY，相当于"框架"）
CONFIG_ST7789V=y       # 具体驱动
```
证据（`zephyr\drivers\display\Kconfig.st7789v`）：
```
config ST7789V
	depends on DT_HAS_SITRONIX_ST7789V_ENABLED
	select MIPI_DBI
```
→ **`depends on DT_HAS_..._ENABLED` 和 `CONFIG_INPUT` 是同一个陷阱**：dts 里节点 `status = "okay"` 只让 `DT_HAS_SITRONIX_ST7789V_ENABLED` 变真，**不会**自动打开 `CONFIG_ST7789V`。节点在、驱动没编 → 链接期 `undefined reference to __device_dts_ord_NN`，一字不差。

### 第 7 步：验证三件套（不要"编过了"就当成功）

```powershell
$b = "build\esp32s31\korvo_apps\s31-debug"
# ① 节点进树了吗（dtc 会在行尾标注来源文件，正好验证 overlay 生效）
Select-String -LiteralPath "$b\zephyr\zephyr.dts" -Pattern 'mipi_dbi|st7789v@|dc-gpios|spim2_korvo'
# ② 驱动符号开了吗
Select-String -LiteralPath "$b\zephyr\.config" -Pattern 'CONFIG_DISPLAY=|CONFIG_ST7789V|CONFIG_MIPI_DBI'
# ③ 设备 ready 吗（串口打印）
```
代码侧：
```c
#define LCD_NODE DT_NODELABEL(lcd)
const struct device *disp = DEVICE_DT_GET(LCD_NODE);
if (!device_is_ready(disp)) { printk("lcd not ready\n"); return -1; }
```

## 4. 如果 Zephyr 真没有这颗屏的驱动（C 形态）

那才需要"往下探一层"，但**依然不是上游的活**——你把它做成自己的 module：

```
applications\<app>\
├── drivers\display\
│   ├── CMakeLists.txt
│   ├── Kconfig
│   └── display_xxx.c          ← 照 drivers\display\display_st7789v.c 抄结构（display_driver_api + mipi_dbi 封装）
├── dts\bindings\display\
│   └── vendor,xxx.yaml        ← 照 sitronix,st7789v.yaml 写 required 属性
└── CMakeLists.txt             ← zephyr_library() / target_sources(app …)
```
两个关键点：
- binding 要能被 dtc 找到 → 通过 `DTS_ROOT` 或 module 的 `zephyr/module.yml`（`dts_root: dts`）暴露出去；
- 驱动 API 照现有驱动抄（`display_driver_api`、`mipi_dbi_*`），**别自己发明接口**——这是"能被上层复用"和"只能自己用"的分界线。

**什么时候这算"上游的活"**：你把这份驱动 + binding 提 PR 回 Zephyr 或乐鑫的仓库，才叫干上游的活。自己项目里写、自己用，不算。

## 5. 常见坑（按踩中概率排序）

| # | 坑 | 症状 | 处理 |
|---|---|---|---|
| 1 | **只写 dts，忘开 `CONFIG_<驱动>=y`** | 链接 `__device_dts_ord_NN` | `prj.conf` 显式开（`CONFIG_INPUT` 那一课的翻版） |
| 2 | **`st7789v` 直接挂在 `&spi2` 下，没套 `mipi_dbi`** | 编译过、运行 `device_is_ready` 失败或父设备拿不到 | 照 §3 第 5 步两层结构写 |
| 3 | **总线没开**（S31 板级 spi2/spi3 默认 disabled） | 设备不 ready；`zephyr.dts` 里 spi2 `status = "disabled"` | overlay 里 `&spi2 { status="okay"; pinctrl-0=…; }` |
| 4 | **pinctrl 宏名猜错**（写 `SPI2_MOSI_GPIOxx`，实际是 `SPIM2_*`） | 编译期 `undeclared` | 先 grep 头文件再写 |
| 5 | **required 属性漏填**（`width/height/pixel-format/x-offset/y-offset/mdac/mipi-mode`） | dtc 报 `marked as required … but not appear` | 对着三个 yaml 抄清单 |
| 6 | **DC/CS 搞混**：DC 在 `mipi_dbi` 的 `dc-gpios`，CS 在 `&spi2` 的 `cs-gpios` | 屏花屏/不响应 | 按 §3 位置放 |
| 7 | **SPI 频率过高 / 背光没开** | 黑屏但设备 ready | 先降到 4 MHz；背光脚当普通 GPIO 输出 |
| 8 | **改了 overlay 没重配** | 代码里还是旧设备 | `west build -p always`（第四课缓存坑） |

---

## 6. 一句话总结（三种问法的答案）

- **"是不是去干上游的活？"** → 不是。上游只管"乐鑫官方 coreboard 的接线"；你的屏幕只有你的底板有，属于应用层差量。
- **"属于哪个层面？"** → ③应用层（overlay + prj.conf）。若驱动缺失，才下探到 ⑤驱动 + ④binding，且仍是你自己的 module。
- **"要改些啥？"** → A/B 形态：`overlay` 里 ①pinctrl 组 ②`&spi2` 开总线 + CS ③`mipi_dbi`（dc/reset/spi-dev）④面板节点（含全部 required）；`prj.conf` 里 ⑤`CONFIG_DISPLAY=y` ⑥`CONFIG_<驱动>=y`。C 形态再加 driver + binding 两个目录。

> 判层口诀：**"芯片有"→SoC；"官方板有"→板级；"我这块板有"→overlay；"Zephyr 没驱动"→自己写 module。**
