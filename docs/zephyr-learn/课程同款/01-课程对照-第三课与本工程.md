## 0. 结论（先看这三段，不够再往下）

1. **教程和你不是"同一个东西的不同做法"，而是 Zephyr 的两类合法布局。** 他是"一个目录 = 一个应用 + 自己写板级"（`boards/arm/st_h743_board/`）；你是"一个 west 工作区 + 5 个应用 + 用别人（PR）的板级 + 用 `overlay` 打补丁"。两种都能编、都能烧，但文件放的位置、构建的入口、板级归谁维护，三件事全不一样。你拿他的文件名去你项目里搜，当然搜不到。

2. **你"看不懂依赖"的直接原因不是依赖乱，是根目录没有入口。** `zephyr-learn\` 下没有 `CMakeLists.txt`、没有 `prj.conf`、没有 `CMakePresets.json`、没有 `.vscode`。IDE 打开这个根目录，只能把它当"一个装着很多东西的文件夹"（他教程里 CLion 一打开就能展开一整棵 CMake 树，是因为他的根目录**就是**一个 CMake 工程）。所以第一件该做的事不是改结构，是**换打开方式**（第 4、6.1 节）。

3. **结构上真该改的只有两处，都是"重复"而不是"布局"**：`store.c` 两份完全相同；`pa_ctrl`/`rmt`/`adc0` 片段在 4 份 overlay 里重复。至于"要不要把板级搬成 `boards/riscv/korvo1`"——按你自己的判据，**现在不做**（第六节给理由和成本）。

## 1. 四个"不同"，不是四个"错误"

### 1.1 布局不同（这是根因）

Zephyr 里同时存在三种合法布局，长得完全不一样：

| | A · 树内 sample | **B · 教程第三课** | **C · 本工程** |
|---|---|---|---|
| 例子 | `zephyr\samples\basic\blinky` | `blinky-learn`（他从 sample 抄出来后改造） | `zephyr-learn\` |
| 板级在哪 | 上游 `zephyr\boards\` | **应用自己仓库的 `boards\arm\<board>\`** | 上游 PR 的 `zephyr\boards\espressif\esp32s31_function_coreboard\` |
| 谁是"项目根" | sample 目录 | 应用目录 | **west 工作区 `west\`**（应用在它外面） |
| 一个根里有几个应用 | 1 | 1 | **5**（`applications/esp32s31/korvo_*`） |
| 板子差异怎么表达 | 不需要 | 直接写 `.dts` | `*.overlay` 叠加 |
| 构建入口 | `west build` | `cmake --preset` / IDE | `west build` + `kharon env` |

你落在 C，教程讲的是 B。**B 和 C 的差别不在"哪个更标准"，在"板级定义归谁维护"**：他把板级从 Zephyr 树里摘出来放自己仓库（因为那块 STM32H743 是他画的，上游不可能收）；你这块板用的是 PR #119851 里的 `esp32s31_function_coreboard`（同芯片、不同板），所以选择"不摘、只补 overlay"。

> 这一条你的 `docs\参考\工程结构与可迁移性.md` 第一节已经写过 A/B/C。这里只补一句解释"为什么第三课会让人误以为 B 是唯一标准"：因为他整节课的任务就是"从零写一块板"，那个场景下 B 是唯一解。

### 1.2 硬件不同（这条决定了你不能 1:1 复刻）

| | 教程 | 你 |
|---|---|---|
| 芯片 | STM32H743IIT6（Cortex-M7，ARM） | ESP32-S31（RISC-V，双核 + LP core） |
| 编译器 | Zephyr SDK 的 `arm-zephyr-eabi-gcc` | 乐鑫 `riscv32-esp-elf-gcc 15.2.0`（`cross-compile` 模式） |
| 时钟 | 复杂时钟树，**必须手写 `&rcc`** 分频 | SoC dtsi 自带，靠 `&ldo`/regulator 管电源，**不写 `rcc`** |
| 烧录 | `stm32cubeprogrammer` / openocd（SWD） | `esp32` runner（esptool，串口 COM9，镜像偏移 `0x2000`） |
| 引脚复用 | `-pinctrl.dtsi` 写 PAxx/PBxx | 也是 `-pinctrl.dtsi`，但写 `I2C0_SDA_GPIO0` 这种**信号名 → GPIO 号**的宏 |

所以第三课里"时钟/电源"那一大段（他的 `&rcc` 六行分频 + `&pwr`），**在你这里整段跳过**——不是你没学会，是这块芯片不需要你写。

### 1.3 构建入口不同

| 教程的入口 | 你的等价物 |
|---|---|
| `CMakePresets.json` 里写死 `BOARD`、`ZEPHYR_BASE`、`Python3_EXECUTABLE`、`CMAKE_C_COMPILER` | `kharon env` + 命令行参数（`-b` 传板名，编译器靠 `CROSS_COMPILE`） |
| `cmake --preset zephyr-debug` | `west build -p -b <board> <app绝对路径> -d <build目录>` |
| `ninja -C cmake-build-debug-zephyr flash` | `west flash -d <build目录> --esp-device COM9` |
| CLion 打开项目 → 自动识别 preset | 打开 `applications\<某个app>` 或用 `compile_commands.json`（见 4.3） |

他为什么用 CMakePresets：因为他在 IDE 里点按钮。你为什么用 `west build`：因为你要同时管 5 个 app、2 套工具链（RISC-V 与 Xtensa），presets 会把两套硬编码在一份 JSON 里，反而更乱。**这是取舍，不是谁更先进。**

### 1.4 "项目"的粒度不同

教程里 `main.c` 一份，改完点灯就完事。你这边是 5 个独立应用，各有一套 `CMakeLists.txt` + `prj.conf` + `src\`：

| 应用 | 构建目录 | `main.c` 行数 |
|---|---|---|
| `applications\esp32s31\korvo_shell` | `build\esp32s31\korvo_shell\s31-debug` | 68 |
| `applications\esp32s31\korvo_nvs` | `build\esp32s31\korvo_nvs\s31-debug` | 276 |
| `applications\esp32s31\korvo_lab` | `build\esp32s31\korvo_lab\s31-debug` | 451 |
| `applications\esp32s31\korvo_sys` | `build\esp32s31\korvo_sys\s31-debug` | 478 |
| `applications\esp32s31\korvo_apps` | `build\esp32s31\korvo_apps\s31-debug`（S31）/ `build\esp32s3\korvo_apps\s3-debug`（S3） | 828 |

再叠上 `west\zephyr` 这一整棵源码树（几千个文件），你自然觉得"东西太多、串不起来"。**不是散了，是没有索引。**

3c | `cmake --preset` 编译 | `west build` | ❌ | 见 1.3

## 4. 你的依赖地图（这一节是"看不懂散落"的解药）

### 4.1 从一条命令到一个 elf，六层

```
[0] 环境层   kharon env
      PATH += .deps\venv\Scripts / .deps\tools\cmake-3.30.2 / .deps\tools\ninja
      ZEPHYR_BASE = <root>\west\zephyr        ← 不是根目录！
      ZEPHYR_TOOLCHAIN_VARIANT = cross-compile
      TOOLCHAIN_HOME / CROSS_COMPILE = C:/Espressif/tools/riscv32-esp-elf/...
      Set-Location <root>\west                ← west 认的是"有 .west 的那一层"

[1] 工作区层 west\.west\config
      manifest = zephyr\west.yml → west update 拉 modules\hal\espressif 等

[2] 板级层   west build -b esp32s31_function_coreboard/esp32s31/hpcore
      BOARD_DIR = zephyr\boards\espressif\esp32s31_function_coreboard
      读：<board>_hpcore.dts + -pinctrl.dtsi + _hpcore_defconfig
          + Kconfig.esp32s31_function_coreboard + board.yml + board.cmake

[3] 叠加层   DTC_OVERLAY_FILE（**只有一个**）
      本次 = <root>\applications\esp32s31\korvo_apps\app.overlay
      → 与 [2] 的 dts 合并成 build\esp32s31\korvo_apps\s31-debug\zephyr\zephyr.dts

[4] 配置层   CONF_FILE = <app>\prj.conf
      + 板级 _defconfig + Kconfig 树（zephyr\Kconfig → drivers\*\Kconfig.* …）
      → build\esp32s31\korvo_apps\s31-debug\zephyr\.config → include\generated\zephyr\autoconf.h

[5] 设备树编译
      zephyr.dts → edt.pickle → include\generated\zephyr\devicetree_generated.h
      代码里的 DT_ALIAS / DT_NODELABEL / DEVICE_DT_GET / GPIO_DT_SPEC_GET 全部来自这里

[6] 编译链接  CMakeLists.txt 的 target_sources(app PRIVATE ...) + 由 [4] 选中的驱动源码
      → zephyr\zephyr.elf → west flash（esp32 runner + esptool）
```

**谁写了什么、谁读它**（这张表就是"依赖关系"本身）：

| 文件 | 谁写 | 谁读 | 改错了会怎样 |
|---|---|---|---|
| `kharon env` | 你 | west / CMake | `west` 找不到工作区、编译器找不到 |
| `west\.west\config` | `west init` | west | `west build` 报 not in a workspace |
| `zephyr\boards\...\<board>.dts` | 乐鑫（PR） | `gen_defines.py` + dtc | 板子节点全没了 |
| `applications\<app>\app.overlay` | **你** | 同上（合并进 `zephyr.dts`） | 引脚/别名不对，编译期就报 `undeclared` 或运行期外设不通 |
| `applications\<app>\prj.conf` | **你** | Kconfig 合并引擎 | 驱动不进镜像 → `__device_dts_ord_NN undeclared` |
| `zephyr\boards\...\<board>_defconfig` | 乐鑫 | 同上（板级默认，被 `prj.conf` 覆盖） | 一般不动 |
| `applications\<app>\CMakeLists.txt` | **你** | CMake | 源码没编进去 / 不是 Zephyr 应用 |

### 4.2 三条命令，随时自查（在 `west` 目录下，先 `. .\scripts\kharon-kharon env`）

```powershell
. C:\Users\xiao1\Desktop\ELAB\kharon-ide\scripts\kharon-kharon env

# ① 这次构建到底用了哪块板、哪个 overlay、哪个 ZEPHYR_BASE（真值，不是我猜的）
Select-String -LiteralPath build\esp32s31\korvo_apps\s31-debug\CMakeCache.txt -Pattern '^(BOARD:|BOARD_DIR:|DTC_OVERLAY_FILE:|CONF_FILE:|ZEPHYR_BASE:|CROSS_COMPILE:)'

# ② Kconfig 最终合成了什么（想确认某个功能到底开没开，看这里，不看 prj.conf）
Select-String -LiteralPath build\esp32s31\korvo_apps\s31-debug\zephyr\.config -Pattern '^CONFIG_(NVS|FLASH_MAP|WATCHDOG|LED_STRIP|ADC)=' 

# ③ 设备树最终长什么样（overlay 有没有生效，这里一目了然）
Select-String -LiteralPath build\esp32s31\korvo_apps\s31-debug\zephyr\zephyr.dts -Pattern 'pa_ctrl|led-strip|wdt0|coretemp'
```

> ② 的读法：**打印出来的是开了的，没打印的就是没开**（`=n` 的项也常常不写进 `.config`）。上面这条在你机器上实测输出 `CONFIG_ADC=y / CONFIG_LED_STRIP=y / CONFIG_NVS=y / CONFIG_FLASH_MAP=y`，`WATCHDOG` 没打印——因为 `korvo_apps` 的 `prj.conf` 本来就没开它（那是 `korvo_sys` 的事）。
> ③ 的读法：命中条数就是"overlay + 板级 dts 合并后真实存在的节点数"，`pa_ctrl` 出现说明 `app.overlay` 确实生效了。

`build\esp32s31\korvo_apps\s31-debug\CMakeCache.txt` 里你现在能读到的事实（2026-11-13 的快照）：

```
BOARD:STRING=esp32s31_function_coreboard/esp32s31/hpcore
BOARD_DIR:PATH=...\west\zephyr\boards\espressif\esp32s31_function_coreboard
DTC_OVERLAY_FILE:STRING=...\applications\esp32s31\korvo_apps\app.overlay
CONF_FILE:STRING=...\applications\esp32s31\korvo_apps\prj.conf
ZEPHYR_BASE:PATH=...\west\zephyr
APPLICATION_SOURCE_DIR:PATH=...\applications\esp32s31\korvo_apps
```

**三条经验（比记住文件名有用）**：

1. **`__device_dts_ord_46 undeclared` 这类链接错误，方向永远是"驱动没进镜像"**，去查 `prj.conf`/`.config`，不要去改设备树。
2. **`app.overlay` 只在一个文件里生效**。`boards\<board>.overlay` 一旦存在，`app.overlay` 整段不生效（你这套的实测记录在 `docs\参考\工程结构与可迁移性.md` 第四节末）。判据就是上面 ① 那条：`DTC_OVERLAY_FILE` 只会给你一个文件。
3. **`ZEPHYR_BASE` 指向 `west\zephyr`，不是 `zephyr-learn\`**。这一点直接解释了他教程里"`ZEPHYR_BASE` 指向哪里"和你的不一样。

### 4.3 IDE 里怎么看（这就是"散落感"的真正来源）

| 你打开的是 | IDE 看到什么 | 结果 |
|---|---|---|
| `zephyr-learn\`（根） | 没有 `CMakeLists.txt`、没有 `prj.conf`、没有 `.vscode`/`.clangd` | 只能当文件夹浏览，跳转/补全全废 → "依赖看不懂" |
| `applications\esp32s31\korvo_apps\` | 3 行 `CMakeLists.txt`，但没有 `CMakePresets.json` | CMake 能加载，但要手工喂 `BOARD`/`ZEPHYR_BASE`/编译器 |
| 用 `compile_commands.json` | 存在：`build\esp32s31\korvo_apps\s31-debug\compile_commands.json` | **最省事**：clangd / VS Code C++ 插件直接读它，`DT_*` 宏、`device` 指针都能跳转 |

推荐做法：装 clangd 或 C/C++ 扩展，把 `--compile-commands-dir` 指到 `west\build-<你要看的app>`。这样你看到的"依赖"就是**这次构建真实用到的头文件与源文件**，而不是几千个 Zephyr 源文件。

## 5. "代码散落"的账

### 5.1 五个 app 的职责边界（先有这张表，才谈得上"散"）

| app | 练什么 | 关键 dts 引用 | 构建目录 |
|---|---|---|---|
| `korvo_shell` | shell 子系统 + device model | `pa-ctrl` | `build\esp32s31\korvo_shell\s31-debug` |
| `korvo_lab` | 四个驱动 API 逐个过 | `pa-ctrl`、`i2c0`、`adc0`、`rmt` | `build\esp32s31\korvo_lab\s31-debug` |
| `korvo_apps` | 业务层：状态机/线程/帧率/NVS | `led-strip`、`pa-ctrl`、`adc0/1`、`gpio_keys` | `build\esp32s31\korvo_apps\s31-debug`、`build\esp32s3\korvo_apps\s3-debug` |
| `korvo_sys` | 系统层：复位原因/温度/RNG/WDT/加密 | `coretemp`、`wdt0`、`trng0`、aes/sha | `build\esp32s31\korvo_sys\s31-debug`、`build\esp32s3\korvo_sys\s3-debug` |
| `korvo_nvs` | 持久化实验台 | 无（纯 NVS） | `build\esp32s31\korvo_nvs\s31-debug` |

五个 app 是**并列的实验台**，不是"一个项目的五层"。所以它们之间**本来就不该有代码依赖**——这正是它们看起来"各写一遍"的原因，不是架构失控。

### 5.2 真重复 vs 假重复

| 重复项 | 数量 | 判定 |
|---|---|---|
| `src\store.c`（`korvo_apps` 与 `korvo_nvs`） | 2 份，**SHA256 完全相同** | **真重复，值得抽** |
| overlay 里的 `pa_ctrl`（GPIO7 功放使能） | 4 份（lab / shell / apps / 各自一份；sys 没有） | 真重复，但每份上下文不同 |
| overlay 里的 `rmt`（WS2812 @ GPIO37） | 3 份（lab / shell / apps） | 真重复 |
| overlay 里的 `&adc0 { status = "okay"; }` | 3 份（lab / shell / apps），apps 还多一个 `adc1` | 真重复 |
| `prj.conf` 开头 6 行（console/serial/shell） | 5 份 | **假重复**：每份是"这个 app 要什么"的独立声明，抽公共 conf 反而更难读 |
| `main.c` 里的 `static int cmd_xxx(...)` shell 命令骨架 | 5 份 | **假重复**：这是 shell API 的正常写法，不是可抽象的业务 |

**判据一句话**：只有"改一处必须改多处、且改漏会出错"的重复才抽。`store.c` 是（改一处漏另一处，两块板行为不一致）；`prj.conf` 不是（各 app 本来就该独立声明）。

### 5.3 一个具体的"跟不了"案例（说明为什么要点灯得改写法）

第三课的点灯代码是：

```c
#define LED0_NODE DT_ALIAS(led0)
static const struct gpio_dt_spec led = GPIO_DT_SPEC_GET(LED0_NODE, gpios);
```

这块板的板级定义里**没有 `led0`**，只有：

```dts
aliases {
    sw0 = &boot_button;      /* BOOT 键，GPIO1 29 */
    led-strip = &led_strip;  /* WS2812，走 RMT OUT0，不是 GPIO */
    watchdog0 = &wdt0;
};
```

所以在你的工程上原样抄，第一行就编译失败。要"点灯"只有两条路：

- **走 WS2812**：`led_strip_update_rgb()`（`applications\esp32s31\korvo_apps` 就是这么做的，还叠了 25 fps 动画引擎）；
- **自己在 `app.overlay` 里造一个 `led0`**：`gpios = <&gpio0 N GPIO_ACTIVE_HIGH>`，但 GPIO7 是功放使能脚，点了喇叭会响/复位，别拿它点灯。

**这条正好把第三课的教学目标和你的现实接上了**：他"改 `.dts` 加 `led0`"，你"写 `overlay` 加别名"——动作同构，位置不同。

### 6.1 路线 0（成本 0，**推荐先做这个**）：不改目录，只换读法和入口

### 6.2 路线 1（半天，低风险）：把真重复抽掉

**a. `store.c` 抽成公共模块**（两份完全相同，风险最低）

```
applications\common\
├── include\store.h
├── src\store.c
└── CMakeLists.txt        ← 或在各 app 的 CMakeLists 里直接引
```

各 app 的 `CMakeLists.txt` 改成（`korvo_apps` / `korvo_nvs` 各一次）：

```cmake
target_sources(app PRIVATE ${CMAKE_CURRENT_SOURCE_DIR}/../common/src/store.c)
target_include_directories(app PRIVATE ${CMAKE_CURRENT_SOURCE_DIR}/../common/include)
```

验证：两个 app 各 `west build -p always` 一遍，`ls build-*\zephyr\zephyr.elf` 大小与原来接近（±1 KB 内，因为路径字符串会变）。

**b. overlay 抽公共 dtsi**（中等风险，先做一份试试）

```
applications\common\korvo_board.dtsi     ← pa_ctrl + rmt_korvo + &rmt + &adc0
```

各 overlay 首行加：

```c
#include "../common/korvo_board.dtsi"
```

- `korvo_lab` / `korvo_shell` 各自保留 `i2c0_korvo`（这两个才有 I2C）；
- `korvo_apps` 保留 `&adc1`；
- `korvo_sys` **不**引入（它没有这三样）。

验证方式（别只看"能编过"）：

```powershell
west build -p always -b esp32s31_function_coreboard/esp32s31/hpcore <app> -d <build目录>
# 抽之前先存一份对照：
Copy-Item build\esp32s31\korvo_shell\s31-debug\zephyr\zephyr.dts .\zephyr.dts.before
# 抽之后比对节点是否一致
Select-String -LiteralPath build\esp32s31\korvo_shell\s31-debug\zephyr\zephyr.dts -Pattern 'pa_ctrl|rmt_korvo|adc0'
```

**只在 `zephyr.dts` 里节点属性确实一致时才算成功**——"编过了"不等于"overlay 生效了"。

### 6.3 路线 2（半天～一天，中风险）：把板级搬成 `boards\riscv\korvo1`

这条就是"把第三课那套真做一遍"。**但你这个芯片不是 7 个文件，是 15 个**（其中与编译直接相关的 12 个），而且有几样教程里没有的：

| 需要 | 教程有 | 你需要额外处理 |
|---|---|---|
| `board.yml`（`name`/`vendor`/`socs`） | ✅ | 这块板的 `board.yml` 只有 4 个字段，**没有 `variants`** |
| `<board>_<variant>.yaml` | ❌ | **变体（hpcore/lpcore）靠这个文件声明**：`identifier: esp32s31_function_coreboard/esp32s31/hpcore`，还有 `arch: riscv`、`toolchain: zephyr`、`supported:` 能力清单 |
| `Kconfig.<board>` | ✅ | 多核：`select SOC_ESP32S31_HPCORE if ..._HPCORE`，照抄上游那 3 行 |
| 板目录 `Kconfig` | ❌ | 设 `HEAP_MEM_POOL_ADD_SIZE_BOARD`（HP 4096 / LP 256） |
| `<board>_<variant>_defconfig` | ✅（单核版叫 `<board>_defconfig`） | 变体后缀 `_hpcore` 是命名规则的一部分 |
| `<board>.dts` / `-pinctrl.dtsi` | ✅ | 直接抄上游，改 `model`/`compatible` |
| `board.cmake` | ✅ | 保留 `include esp32.board.cmake`（esptool runner），否则 `west flash` 挂 |
| `Kconfig.sysbuild` | ❌ | `choice BOOTLOADER → default BOOTLOADER_MCUBOOT`；sysbuild 路径会读它 |
| `_lpcore.dts` / `_lpcore.yaml` / `_lpcore_defconfig` / 分区 dtsi | ❌ | 多核板与 espressif 特有（分区来自 `espressif/partitions_0x2000_default_16M.dtsi`），抄漏一个就编不过 |
| `BOARD_ROOT` | 写在 CMakeLists | 你 5 个 app 都要各自写，或每次命令行传 `--board-root` |

做法（不动现有 5 个 app，先在一个临时 app 上验证）：

```powershell

New-Item -ItemType Directory -Force C:\Users\xiao1\Desktop\ELAB\kharon-ide\boards\riscv\korvo1
Copy-Item C:\Users\xiao1\Desktop\ELAB\kharon-ide\west\zephyr\boards\espressif\esp32s31_function_coreboard\* `
          C:\Users\xiao1\Desktop\ELAB\kharon-ide\boards\riscv\korvo1\ -Recurse
# 2. 改名 korvo1 / korvo1_hpcore，改 board.yml 的 name 与 full_name
# 3. 把三份 overlay 的公共片段并进 korvo1_hpcore.dts（overlay 只留本工程特有的）
# 4. 编译时指定板级根
west build -p -b korvo1/esp32s31/hpcore --board-root C:\Users\xiao1\Desktop\ELAB\kharon-ide `
           C:\Users\xiao1\Desktop\ELAB\kharon-ide\applications\esp32s31\korvo_sys -d C:\.build\esp32s31\korvo_sys\s31-debug
```

**判据（满足任意两条才值得做）**：

1. 你希望 `west boards` 里能看到 `korvo1`，别人/半年后的你一条 `-b korvo1/esp32s31/hpcore` 就编；
2. 应用数 ≥ 3 且 overlay 重复片段已经开始"改漏"；
3. 你要把这块板当长期实验台，或要把这套东西交给别人。

### 6.4 明确不建议做的三件事

| 不建议 | 为什么 |
|---|---|
| 把 5 个 app 合成 1 个（加 `app` 子命令） | 5 个是"并列实验台"，合并后一次编译要带全部驱动，镜像变大、日志变吵，且失去"同一份代码换了板才暴露差异"的对照价值 |
| 给每个 app 建 `boards\` 目录 | 每个 app 各存一份板级 = 5 份双份真相，比现在更散 |
| 把 `west` 挪出去 / 换工作区 | 所有已验证的 `build-*`、日志里的绝对路径都指向它，挪了等于重跑全部实测 |
| 把早期环境手记（`SETUP.md`，Zephyr SDK 路线，已于 2026-11-15 删除）当真照着做 | 实际落地走的是 Espressif 工具链，`README` §3 已注明 |

## 7. 五分钟自测

1. 你的项目里，哪一层是"west 工作区"？判断依据是哪个文件？
2. `ZEPHYR_BASE` 指向哪里？它和 `BOARD_ROOT` 分别解决什么问题？
3. 你这块板的板级定义在哪个目录？目录名为什么带 `hpcore`？
4. `app.overlay` 和 `boards\<board>.overlay` 能不能同时生效？用哪条命令一眼确认？
5. `korvo_apps` 的 `prj.conf` 里删掉 `CONFIG_NVS=y`，会在编译期还是运行期报错？报什么？
6. 第三课的点灯代码为什么不能直接抄到你这块板？
7. `store.c` 该不该抽成公共模块？`prj.conf` 开头那 6 行为什么不该抽？

<details>
<summary>答案</summary>

1. `west\`（依据：`.west\config`）。`applications\` 在它外面，所以每次 `west build` 都要写应用的绝对路径。
2. `ZEPHYR_BASE = <root>\west\zephyr`；`BOARD_ROOT` 只在"板级放自己仓库"时用，你现在不用。
3. `west\zephyr\boards\espressif\esp32s31_function_coreboard\`；`hpcore` 是多核 SoC 的 variant（HP core 跑 Zephyr，LP core 另有定义）。
4. 不能。`DTC_OVERLAY_FILE` 只有一个值，用 `Select-String -LiteralPath build\esp32s31\korvo_sys\noccache\CMakeCache.txt -Pattern '^DTC_OVERLAY_FILE'` 确认。
5. 编译/链接期：`nvs` 子系统没编进镜像，`store.c` 调用的符号找不到（或 `device_is_ready` 相关 `__device_dts_ord_NN undeclared`）。
6. 板级里没有 `led0` 别名；唯一的灯是 WS2812，走 `led_strip` API。
7. `store.c` 该抽（两份 SHA256 相同，改一处必漏另一处）；`prj.conf` 不该抽（每个 app 独立声明自己的依赖才可读）。
</details>
