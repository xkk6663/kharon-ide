## 一、项目迁移与新建

### 1.1 他为什么说“迁移非常快”

他的做法是把 `boards/` 和 `CMakePresets.json` 跟源码一起搬走：板级信息集中，所以同一块板换项目很快。
今天这个“集中”更进一步——**板级只存一份，不在 APP 里**：

| 要搬的东西 | 他那里 | 今天 |
|---|---|---|
| 板级 7 个文件 | 复制到新工程 `boards/` | 不复制；`zephyr-workspace/kharon-boards/` 共用 |
| 构建参数 | 复制 `CMakePresets.json` | 不复制；产品 yaml + provider + host 解析 |
| 应用代码 | 复制 `CMakeLists.txt` / `prj.conf` / `src/` | 从 `applications/_template` 复制 |

他的命令（Linux）：

```bash

cp blinky/CMakePresets.json input_rcc
```

今天的等价（PowerShell 7，根是 `zephyr-workspace`）：

### 1.2 `BOARD_ROOT` 不再搬来搬去

第四课的设计决定是“把 `BOARD_ROOT` 从 `CMakeLists.txt` 挪进 `CMakePresets.json`”。今天这一步不需要：

- `CMakeLists.txt` 不写 `set(BOARD_ROOT ...)`；
- `CMakePresets.json` 已删除；
- 板级由 `kharon-boards/zephyr/module.yml` 暴露，`kharon.cmd` 构建时注入 `EXTRA_ZEPHYR_MODULES`。

最终 `CMakeLists.txt` 就是最小四行：

```cmake

find_package(Zephyr REQUIRED HINTS $ENV{ZEPHYR_BASE})
project(input_btn)
target_sources(app PRIVATE src/main.c)
```

好处仍然是他说的那句：入口文件只管“编什么”，“怎么编”交给外面的事实层。
只是“外面”从 preset 变成了产品 yaml + provider。

### 1.4 迁移之后，`_defconfig` 就不动了

他的原话：**后续不再动板子默认配置文件，板级相关的 Kconfig 都写进应用级 `prj.conf`。** 他的 `_defconfig` 停在：

```
# Board
CONFIG_BOARD_ST_H743_BOARD=y

# GPIO
CONFIG_GPIO=y

# Clock
CONFIG_CLOCK_CONTROL=y
CONFIG_CLOCK_CONTROL_STM32_CUBE=y

# 允许调试器在 Sleep/Stop 下保持连接（H7 WFI 会关调试域）
CONFIG_STM32_ENABLE_DEBUG_SLEEP_STOP=y
```

我们的停在（第三课写好的那份，含后来补的堆配置）：

```
CONFIG_CONSOLE=y
CONFIG_SERIAL=y
CONFIG_UART_CONSOLE=y
CONFIG_GPIO=y
CONFIG_CLOCK_CONTROL=y

# ESP32 的中断分配器（intc_esp32.c）用 k_malloc，所以要给内核堆
CONFIG_HEAP_MEM_POOL_SIZE=4096
```

**为什么这条规矩重要**：`_defconfig` 是"板子的出厂设置"，写进去的东西会跟着这块板出现在**所有工程**里；某个项目特有的需求（比如这个项目要按键）写进 `prj.conf`，才不会污染别的项目。

### 1.5 [!IMPORTANT] CMake 缓存坑（他的重点提示）

他原文用 `[!IMPORTANT]` 标注：

> 如果你写完设备树、到源码里却找不到那个设备，而且设备树本身没问题——**说明 CMake 缓存是旧的**。最好的办法是直接删掉构建目录，重新加载 CMake。这大概率是你会经常遇到的问题。

为什么会有这个坑，机制是这样的：

```
.dts 改了
   ↓
CMake 只在"配置阶段"重新生成 zephyr.dts / devicetree_generated.h
   ↓
如果只是 ninja/cmake --build，不再跑配置阶段
   ↓
devicetree_generated.h 还是旧的 → DT_NODELABEL(xxx) 不存在 → 编译报 undeclared
```

今天的处理（PowerShell 7，根是 `kharon-ide`）：

```powershell
cd C:\Users\xiao1\Desktop\ELAB\kharon\kharon-ide
# 只删这个产品/target 的构建目录，不要删整个 build
Remove-Item -Recurse -Force ..\zephyr-workspace\build\esp32s3\input_btn\default
.\kharon.cmd run -p input_btn --steps build
```

`kharon` 在构建目录缺失时会重新走配置阶段，效果等价于他的“删掉构建目录重载 CMake”。
产品名和 work_dir 以 `.\kharon.cmd run -p input_btn --steps build --dry-run` 输出为准。

判断"是不是缓存问题"的三条经验（我们踩过的坑，按严重程度排）：

| 现象 | 大概率原因 |
|---|---|
| `DT_NODELABEL(xxx)` 报未定义 | dts 改了没重配（本节这个坑） |
| 设备树看起来对，但运行时 `device_is_ready()` 返回 false | `status` 没设 `okay`，或驱动 Kconfig 没开 |
| 链接期报 `undefined reference to __device_dts_ord_N` | dts 有节点但对应驱动没编进来（Kconfig 缺了） |

三种都很像"dts 写错了"，但只有第一种要删构建目录。

## 二、按键输入

### 2.1 先说清 Zephyr 的 `Input` 系统在解决什么

他把按键消抖的演进史讲成了一条线，这里压缩成表（原始故事建议回原文读，写得很生动）：

| 阶段 | 做法 | 遗留问题 |
|---|---|---|
| 1. 裸机轮询 | 读电平 + `HAL_Delay(20)` 再读一次 | CPU 干等 20 ms |
| 2. 外部中断 | 电平变化触发 EXTI | 没有消抖 |
| 3. 定时器轮询 | 20 ms 定时器查状态存变量 | 定时器被业务吃光 |
| 4. 硬件电容 | 按键并联电容到地 | 容值难选、BOM 成本 |
| 5. 中断 + 时间差 | 中断只置标志位，主循环比对 Systick 差值 ≥ 20 ms | 逻辑分散，按键一多全局变量满天飞 |
| 6. FreeRTOS | 单开一个任务轮询 | 同上，且占一个任务栈 |
| 7. **Zephyr Input** | 中断 + 驱动内消抖 + 事件上报 + 键码 | 学习成本（要懂 dts + 回调） |

Zephyr 这套有四个要点（他原文清单）：

1. **默认用中断**，不用你在主循环里轮询；
2. 支持"延迟 20 ms 后再回调"的消抖条件；
3. **回调运行在系统工作队列（system workqueue）线程里，不是中断上下文**——所以回调里可以放心 `k_msleep`、可以调 GPIO；
4. 引入了**键码**（`INPUT_KEY_x`），把"哪个引脚"和"哪个按键语义"解耦：代码里只认键码，不认 GPIO。

### 2.2 配置部分

#### （1）Kconfig：两条就够

| 配置 | 作用 |
|---|---|
| `CONFIG_INPUT=y` | 打开 **input 子系统核心**：事件结构、分发机制、`INPUT_CALLBACK_DEFINE` 注册。**不含任何硬件驱动** |
| `CONFIG_INPUT_GPIO_KEYS=y` | 打开 **gpio-keys 驱动**：解析 dts 节点，把 GPIO 中断 + 消抖包装成 input 事件 |

写进 `applications\esp32s3\input_btn\prj.conf`：

```
CONFIG_GPIO=y
CONFIG_INPUT=y
CONFIG_INPUT_GPIO_KEYS=y
```

想确认还有哪些相关符号，就 `grep` 一下：

```powershell
Select-String -Path C:\Users\xiao1\Desktop\ELAB\kharon\zephyr-workspace\zephyr\drivers\input\Kconfig* -Pattern 'INPUT'
```

#### （2）dts：`gpio-keys` 容器 + 每键一个子节点

他的写法（H743 + 2 个板载键 + 9 个外接键）：

```dts
#include <zephyr/dt-bindings/input/input-event-codes.h>   /* 键码宏必须引这个头 */

/ {
	gpio_keys: gpio_keys {
		compatible = "gpio-keys";
		debounce-interval-ms = <20>;

		user_bt1: user1 {
			gpios = <&gpioh 11 GPIO_ACTIVE_LOW>;
			zephyr,code = <INPUT_KEY_A>;
		};
		/* … user_bt2 用 &gpioh 10 / INPUT_KEY_B … */

		extend_bt1: e_bt1 {
			gpios = <&gpiof 7 GPIO_ACTIVE_LOW>;
			zephyr,code = <INPUT_KEY_1>;
		};
		/* … extend_bt2..bt9 用 &gpiof 5/4/3/2/1/0、&gpioi 11/10，键码 INPUT_KEY_2..9 … */
	};
};
```

我们的第三课板级里**已经有**这段（`buttons` 容器 + `button0`，挂 `&gpio0 45`，键码 `INPUT_KEY_0`，用户 KEY 按下接地）：

```dts
buttons {
	compatible = "gpio-keys";
	debounce-interval-ms = <20>;

	button0: button_0 {
		gpios = <&gpio0 45 (GPIO_PULL_UP | GPIO_ACTIVE_LOW)>;
		label = "User Key";
		zephyr,code = <INPUT_KEY_0>;
	};
};
```

（`debounce-interval-ms` 是第四课才加的，第三课版 `blinky_s3` 里没有；`input_btn` 的差异写在自己的
`boards/esp32s3_korvo.overlay`，不再靠复制整块板级。）

**第四课要做的事**是给它补一行消抖（他的 `debounce-interval-ms = <20>` 写在容器上，对全部子键生效）：

```dts
buttons {
	compatible = "gpio-keys";
	debounce-interval-ms = <20>;      /* ← 新增：全部按键统一 20ms 消抖 */

	button0: button_0 {
		gpios = <&gpio0 45 (GPIO_PULL_UP | GPIO_ACTIVE_LOW)>;
		label = "User Key";
		zephyr,code = <INPUT_KEY_0>;
	};
};
```

几个必须讲清的点（他原文的顺序）：

1. `gpio_keys` 是**容器**，`compatible = "gpio-keys"` 让 gpio-keys 驱动接管里面所有子节点；
2. `debounce-interval-ms` 写在容器上 → 所有键共用；也可以写在子节点上单独覆盖；
3. 子节点只写 `gpios`（引脚 + 有效电平）和 `zephyr,code`（键码）；
4. **不需要写"输入模式 / 中断类型"**——gpio-keys 会自动把引脚配成输入，并根据有效电平决定用上升沿还是下降沿；
5. 外接键想加就加，只是键码要换（`INPUT_KEY_1` … `INPUT_KEY_9`）。**注意物理接线要在自己板子上真有那根线**，否则按了没反应不是代码问题。

### 2.3 C 代码部分

#### （1）三个头文件

```c
#include <zephyr/kernel.h>          /* 内核 API：k_sleep / k_msleep / k_usleep */
#include <zephyr/drivers/gpio.h>    /* GPIO API */
#include <zephyr/input/input.h>     /* Input 子系统 API */
```

他的补充：`kernel.h` 里还有线程、同步原语、定时器、队列，"我们会放在专门的一课"（对应本教程 `12-Zephyr内核`）。

#### （2）GPIO 的常用 API（他的清单 + 用途）

```c
/* 下面这组是他原文的形态，用来记 API；我们这块板没有 led0（灯是 WS2812），按键用的是 gpio-keys */
static const struct gpio_dt_spec led = GPIO_DT_SPEC_GET(DT_NODELABEL(led0), gpios);

gpio_pin_configure_dt(&led, GPIO_OUTPUT_ACTIVE);   /* 配输出 */
gpio_pin_configure_dt(&led, GPIO_INPUT);           /* 配输入 */
gpio_pin_set_dt(&led, 1);                          /* 输出高 */
gpio_pin_set_dt(&led, 0);                          /* 输出低 */
gpio_pin_toggle_dt(&led);                          /* 翻转 */
gpio_pin_get_dt(&led);                             /* 读电平 */

/* 手动中断（用 gpio-keys 时不需要） */
gpio_pin_interrupt_configure_dt(&led, GPIO_INT_EDGE_FALLING);
gpio_init_callback(&cb, handler, BIT(led.pin));
gpio_add_callback(led.port, &cb);
```

`struct gpio_dt_spec` 是"设备树里的 GPIO 描述"在 C 里的化身：`port`（哪个控制器）+ `pin`（第几号）+ `dt_flags`（有效电平/上拉等）。

`GPIO_DT_SPEC_GET(LED0_NODE, gpios)` 里第二个参数 `gpios` **必须和 dts 里的属性名一致**——他特意提醒：

```dts
leds {
	compatible = "gpio-leds";
	led0: led_0 { gpios = <&gpioh 9 GPIO_ACTIVE_LOW>; };   /* ← 这个名字就是 C 里的 'gpios' */
};
```

改了属性名，驱动侧的取值代码也得改，所以**约定俗成的名字不要动**。

#### （3）最推荐的输入写法：`INPUT_CALLBACK_DEFINE`

他的示例（我换成我们的"KEY(IO45) → 板载 RGB(IO48)"）：

```c
#include <zephyr/kernel.h>
#include <zephyr/drivers/led_strip.h>
#include <zephyr/input/input.h>

#define STRIP_NODE DT_CHOSEN(zephyr_led_strip)
static const struct device *strip = DEVICE_DT_GET(STRIP_NODE);

static bool led_on;

static void apply_led(void)
{
	struct led_rgb px = led_on ? (struct led_rgb){ .r = 0x20, .g = 0x20, .b = 0x20 }
				   : (struct led_rgb){ .r = 0x00, .g = 0x00, .b = 0x00 };

	led_strip_update_rgb(strip, &px, 1);
}

static void input_call_back(struct input_event *event, void *user_data)
{
	ARG_UNUSED(user_data);

	if (event->type != INPUT_EV_KEY) {   /* 只处理按键类事件 */
		return;
	}

	if ((event->code == INPUT_KEY_0) && (event->value == 1)) {  /* KEY 按下 */
		led_on = !led_on;               /* 翻转灯的状态 */
		apply_led();
	}
}

INPUT_CALLBACK_DEFINE(NULL, input_call_back, NULL);

int main(void)
{
	if (!device_is_ready(strip)) {
		return -1;
	}

	apply_led();

	while (1) {
		k_msleep(1000);
	}
}
```

注意这里没有 `GPIO_DT_SPEC_GET` 了：灯不是普通 LED，`led_strip_update_rgb` 直接吃"像素数组"。**GPIO API 那一节照样要学**，因为你以后接的按键、继电器、传感器大多是"拉高/拉低"型的；只是我们这块板的灯恰好是时序器件。

宏展开后（他给的原样，只换函数名）：

```c
static const struct input_callback _input_callback__input_call_back
	__attribute__((section(".zephyr_" "_input_callback" "."
		"static" "." "_input_callback__input_call_back_")))
	__attribute__((__used__)) = {
	.dev = ((void *)0), .callback = input_call_back, .user_data = ((void *)0),
};
```

#### （4）`struct input_event`：只关心三个字段

```c
struct input_event {
	const struct device *dev;   /* 哪个设备报的，NULL = 未知 */
	uint8_t sync;               /* 同步标志，按键场景忽略 */
	uint8_t type;               /* 事件类型：INPUT_EV_KEY / INPUT_EV_REL … */
	uint16_t code;              /* 键码：INPUT_KEY_0 / INPUT_KEY_A … */
	int32_t value;              /* 值：按键 1=按下 0=松开；轴是位移量 */
};
```

- `type` / `code` 的宏都在 `<zephyr/dt-bindings/input/input-event-codes.h>`；
- `value` 的语义随设备类型变。

**为什么代码里要判 `value == 1`**：他没设中断触发方式时，Zephyr 默认**双边沿**，按下、松开各回调一次。我们只想要"按下"，所以判 `1`。

**能不能改成单边沿？** 他的回答很明确：

> 当然可以，`gpio_pin_interrupt_configure_dt(&btn, GPIO_INT_EDGE_FALLING)`。但是**完全不建议**——双边沿能让 Input 知道按键什么时候按下、什么时候释放；改单边沿会丢掉"释放"信息。

### 2.4 往下挖一层：`__attribute__`、段、`INPUT_CALLBACK_DEFINE`

这部分是他原文最有价值的一段，本教程照讲。

#### （1）`__attribute__` 常用属性表

| 属性 | 作用 | 什么时候用 |
|---|---|---|
| `section("name")` | 把变量/函数放进指定 ELF 段 | 需要"注册表"式收集时 |
| `used` | 即使没人引用也不许优化掉 | 配合 `section` 防止被 LTO 删 |
| `packed` | 取消结构体填充 | 网络协议头、Flash 存储结构 |
| `aligned(n)` | 按 n 字节对齐 | DMA 缓冲区（4/32 字节） |
| `weak` | 弱符号，可被强定义覆盖 | 默认处理函数、可替换的板级代码（写 HAL 时见过） |
| `noreturn` | 函数不返回 | 死循环函数 |

#### （2）`Section`（ELF）和 `Segment`（MMU）不是一回事

- 编译器/链接器嘴里的"段"是 **Section**，用于 ELF 格式，决定"这段东西放在哪个地址区间、什么属性（代码/只读/可写）"；
- 操作系统/MMU 嘴里的"段"是 **Segment**，是内存管理单位；
- 两个中文都翻成"段"，但**不是同一个概念**。他建议没听过的人去查，这里照办即可。

#### （3）为什么用"链接器段收集"而不是别的注册方式

他的对照表（原文）：

| | 函数手动注册 | `__weak` | Linker Section 收集 |
|---|---|---|---|
| 代码耦合 | 高（要改 main.c） | 中（要改同名函数） | **零耦合**（模块自治） |
| 支持数量 | 任意 | **只能一个** | 任意 |
| 运行时开销 | malloc / 链表插入 | 函数调用 | **零**（编译期排好） |
| 遗漏风险 | 高（忘了注册） | 中（忘了覆盖） | **零**（宏自动收集） |
| 内存占用 | 链表节点 + 指针 | 无 | **只读 Flash，不耗 RAM** |
| 初始化顺序 | 手动、易错 | 编译期 | **由 `SYS_INIT` 优先级控制** |

一句话：`INPUT_CALLBACK_DEFINE` 的本质是**把回调结构体塞进一个专用段**，启动时内核遍历该段逐个登记，所以既不用手写注册代码，也没有运行时开销。

#### （4）宏的三个参数

```c
#define INPUT_CALLBACK_DEFINE(_dev, _callback, _user_data) \
	INPUT_CALLBACK_DEFINE_NAMED(_dev, _callback, _user_data, _callback)
```

| 参数 | 类型 | 含义 |
|---|---|---|
| `_dev` | `const struct device *` | 只监听某个 input 设备；`NULL` = 监听全部 |
| `_callback` | 函数指针 | 你的回调 |
| `_user_data` | `void *` | 用户数据指针，回调时**原样传回** |

对应结构体：

```c
struct input_callback {
	const struct device *dev;
	void (*callback)(struct input_event *evt, void *user_data);
	void *user_data;
};
```

`_user_data` 的两个典型用途（他的例子）：

```c
/* ① 回调不硬编码全局变量名 */
void cb(struct input_event *evt, void *user_data)
{
	int *count = user_data;
	(*count)++;          /* 不关心 count 是全局还是局部 */
}

/* ② 同一个回调服务多个上下文 */
static int count_a = 0, count_b = 0;
INPUT_CALLBACK_DEFINE(dev_a, my_callback, &count_a);
INPUT_CALLBACK_DEFINE(dev_b, my_callback, &count_b);
```

`_dev` 的类型 `const struct device *` 就是 Zephyr 的统一设备抽象：GPIO / UART / I2C / SPI / ADC / 自己写的驱动，最终都是 `struct device *`，用同一套 API 操作。这一段会在第 11 章展开。

## 三、时钟配置（他第三个任务）

他第四课结尾预告了**时钟配置（RCC）**，原文尾部（时间偏移 5999 token 之后）未完整抓取，这里按他在第三课已经给出的 `&rcc` 写法补全"等价动作"，并明确标注哪些是原文、哪些是我们补的。

### 3.1 他的做法（STM32 H7）

```dts
&rcc {
	clocks = <&clk_hsi>;
	clock-frequency = <64000000>;
	d1cpre = <1>;
	hpre   = <1>;
	d1ppre = <1>;
	d2ppre1 = <1>;
	d2ppre2 = <1>;
	d3ppre = <1>;
};
```

要点：**先选时钟源**（HSI/HSE/PLL）、**再配总线分频**，因为 H7 的外设挂在不同的 D 域/APB 上，分频配错会导致串口波特率全错。

### 3.2 我们的做法（ESP32-S3）

**没有 `&rcc` 可写**（原因见 02 §6.13）。ESP32 的时钟树由 `clock_control_esp32.c` 在启动时按 SoC 配置设好：CPU 240 MHz、APB 分频固定、外设时钟按需 gate。

那"时钟配置"这一节在 S3 上还剩什么可做？——**验证**，也就是"我怎么知道时钟是对的"。这是可以动手的部分：

```c
#include <zephyr/kernel.h>

printk("hw cycles per sec = %u\n", (unsigned int)sys_clock_hw_cycles_per_sec());
printk("uptime ticks      = %lld\n", k_uptime_get());
```

`sys_clock_hw_cycles_per_sec()` 返回的就是**系统定时器的输入频率**（来自 SoC 时钟配置，不是你自己设的）。配合 `k_uptime_get()` 就能验证"1 秒是不是真 1 秒"：

```c
int64_t t0 = k_uptime_get();
k_msleep(1000);
printk("slept %lld ms\n", k_uptime_get() - t0);   /* 应该 ≈ 1000 */
```

这一步的价值：**时钟配错，最直观的症状就是"延时不准、串口波特率不对"**。在 STM32 上你要先会配 `&rcc` 才能验证；在 ESP32 上跳过配置、直接验证，反而更快定位问题。

### 3.3 想真的改频率怎么办

那是 SoC 层的事（改 `soc/espressif/esp32s3/` 的时钟初始化或 Kconfig），本教程遵守"只做应用层"的约定，不动内核目录。要改就开一个新的 SoC 变体或给上游提 patch，属于附录 A 那类"往 Zephyr 里加东西"的活。

### 4.1 一个必须知道的 S3 细节：IO45 是 strapping 引脚

`IO45` 在 ESP32-S3 上属于**上电采样引脚**（与 `IO0`、`IO3`、`IO46` 同组），它在上电瞬间的电平会影响 **VDD_SPI 电压选择**。所以：

- 运行时当普通按键用**没问题**（gpio-keys 已经按低电平有效处理）；
- **上电/复位的那一瞬间别按住它**——否则芯片可能按 1.8 V SPI 模式启动，表现为"程序不跑 / flash 读不到"，很容易被误判成烧录坏了；
- 烧录时同理：`west flash` 会自动拉 `IO0` 进下载模式，你手上别同时压着 IO45。

想把这类引脚挪开，只需要改 dts 里的 `gpios = <&gpio0 45 ...>` 这一个数字——这正是第三课"硬件描述集中在 dts"的价值。

（对照 Up 主的板子：他的是 STM32H743，也有 BOOT0，但只在复位时刻采样、且只影响启动来源；S3 的 strapping 引脚更多、更"敏感"，属于 S3 特有的坑。）

## 七、逐行注释：`input_btn` 的两处 APP 文件 + 板级 dts

> 这一章是**代码级**：把真正落盘的文件一行一行拆开，说清每行作用、写错的表现。Up 主第四课讲"是什么、为什么"，这一章补"每一行错在哪"。

### 7.1 `kharon-boards\boards\espressif\esp32s3_korvo\esp32s3_korvo_procpu.dts`（按键相关部分）

```dts
#include <zephyr/dt-bindings/input/input-event-codes.h>   /* ① INPUT_KEY_0 的宏定义在这里 */

/ {
	aliases {
		sw0 = &button0;                                  /* ② 给代码一个稳定别名 */
	};

	buttons {                                            /* ③ 容器：compatible 决定"谁来接管" */
		compatible = "gpio-keys";
		debounce-interval-ms = <20>;                     /* ④ 20 ms 消抖，写在容器=对所有子键生效 */

		button0: button_0 {                              /* ⑤ 子节点名随便，但只能靠 gpios 定位 */
			gpios = <&gpio0 45 (GPIO_PULL_UP | GPIO_ACTIVE_LOW)>; /* ⑥ 引脚 + 电气 + 有效电平 */
			label = "User Key";                          /* ⑦ 仅显示用 */
			zephyr,code = <INPUT_KEY_0>;                 /* ⑧ 上报的键码，代码里比它 */
		};
	};
};
```

| # | 这行的作用 | 删掉/写错会怎样 |
|---|---|---|
| ① | 提供 `INPUT_KEY_0`（值是 11，对应 Linux `KEY_0`） | 不 include 就报 `INPUT_KEY_0` 未定义；填字面量 `11` 能编过但没人看得懂 |
| ② | `sw0` 是"标准别名"，很多例程/子系统按它找按键 | 只影响用 `DT_ALIAS(sw0)` 的代码；我们代码用 `INPUT_CALLBACK_DEFINE(NULL, ...)`，不看别名 |
| ③ | `compatible = "gpio-keys"` 决定驱动是 `input_gpio_keys.c` | 写成 `gpio-keys` 之外的名字 = 找不到绑定，配置阶段报错 |
| ④ | 消抖时长；**这个属性在 gpio-keys.yaml 里定义，单位 ms** | 不写就没有消抖：机械键会一次按下报好几次 |
| ⑥ | `GPIO_ACTIVE_LOW` 把"低电平"翻译成"按下=1" | 少了它：按下被读成 0，`event->value == 1` 永远不成立，按键"没反应" |
| ⑧ | 键码是给**应用**看的，不是给驱动看的 | 两处不一致（dts 写 `INPUT_KEY_0`、代码比 `INPUT_KEY_1`）= 编译过、按键无反应 |

### 7.2 `prj.conf`

```conf
CONFIG_GPIO=y               # ① GPIO 驱动：gpio-keys 依赖它（板级 defconfig 已有，重复写无害）
CONFIG_INPUT=y              # ② Input 子系统核心：input_report / 回调分发 / input_event
CONFIG_INPUT_GPIO_KEYS=y    # ③ gpio-keys 驱动本体

CONFIG_LED_STRIP=y          # ④ 灯：led_strip 框架
```

| # | 只开一半会怎样 |
|---|---|
| ② 缺 | 驱动能编进去但 `input_report_key` 无实现 → 链接期 `undefined reference to input_report` |
| ③ 缺 | dts 里 `gpio-keys` 节点没有驱动接管 → `device_is_ready` 失败、无事件 |
| ⑤ 缺 | `led_strip` 框架在，但没有"具体怎么发波形"的后端 → 链接期找不到 `update_rgb` 实现 |

### 7.3 `src\main.c`（逐行）

```c
#include <zephyr/kernel.h>              /* ① k_msleep / bool */
#include <zephyr/drivers/led_strip.h>   /* ② led_strip_update_rgb / struct led_rgb */
#include <zephyr/input/input.h>         /* ③ INPUT_CALLBACK_DEFINE / struct input_event */

#define STRIP_NODE DT_CHOSEN(zephyr_led_strip)          /* ④ 从 chosen 取灯，不写引脚 */
static const struct device *strip = DEVICE_DT_GET(STRIP_NODE);  /* ⑤ 编译期绑定 */

static bool led_on;                                     /* ⑥ 应用自己的状态 */

static void apply_led(void)                             /* ⑦ 把状态翻译成一次硬件写 */
{
	struct led_rgb px = led_on ? (struct led_rgb){ .r = 0x20, .g = 0x20, .b = 0x20 }
				   : (struct led_rgb){ .r = 0x00, .g = 0x00, .b = 0x00 };

	led_strip_update_rgb(strip, &px, 1);                /* ⑧ 1 = 像素数（chain-length） */
}

static void input_call_back(struct input_event *event, void *user_data)  /* ⑨ 回调签名固定 */
{
	ARG_UNUSED(user_data);                              /* ⑩ 没用就显式标记，避免 -Wunused */

	if (event->type != INPUT_EV_KEY) {                   /* ⑪ 过滤：还有 ABS/REL/SYN 等类型 */
		return;
	}

	if ((event->code == INPUT_KEY_0) && (event->value == 1)) {  /* ⑫ 只认"这个键按下" */
		led_on = !led_on;                               /* ⑬ 状态翻转 */
		apply_led();                                    /* ⑭ 立刻写硬件 */
	}
}

INPUT_CALLBACK_DEFINE(NULL, input_call_back, NULL);     /* ⑮ 静态注册：编进专属链接段 */

int main(void)
{
	if (!device_is_ready(strip)) {                      /* ⑯ 驱动没起来就直接返回 */
		return -1;
	}

	apply_led();                                        /* ⑰ 上电先"灭"一次，状态确定 */

	while (1) {
		k_msleep(1000);                                 /* ⑱ 主线程只睡觉，活都在回调/work 里干 */
	}

	return 0;
}
```

| # | 值得记住的点 |
|---|---|
| ⑨ | 回调**不能返回 int、不能改签名**——`INPUT_CALLBACK_DEFINE` 要求 `void (*)(struct input_event *, void *)` |
| ⑪ | 不判 `type` 的话，触摸/编码器的事件也会进你的分支 |
| ⑫ | `value` 只会有 0/1（`input_report_key` 内部做了 `!!value`），但**按下和松开各来一次** |
| ⑮ | `_dev` 传 `NULL` = 收所有设备的 input 事件；传 `DEVICE_DT_GET(...)` 只收那一个 |
| ⑱ | 回调在**系统工作队列线程**里跑，不是中断上下文，所以这里能 `led_strip_update_rgb`（内部有 `k_usleep`） |

**为什么不能在回调里做重活**：`ws2812_pulse_io.c:91` 的 `k_usleep(reset_delay)` 会阻塞 300 µs；`pulse_io_transmit_sync` 还会等 RMT 发完。这些都在系统工作队列线程上，会推迟同一线程里的其它工作项（包括别的输入事件）。按键场景够用，但别在这儿加 `k_sleep(1000)`。

## 八、`gpio-keys` 驱动内部：从中断到 `input_report_key`

Up 主说"gpio-keys 会自动配输入、按有效电平定边沿、20 ms 后回调"。这四句话在代码里分别是四段：

**① 初始化：配输入 + 装中断（`drivers/input/input_gpio_keys.c:183-211`）**

```c
for (int i = 0; i < cfg->num_keys; i++) {
	const struct gpio_dt_spec *gpio = &cfg->pin_cfg[i].spec;

	if (!gpio_is_ready_dt(gpio)) {
		LOG_ERR_DEVICE_NOT_READY(gpio->port);
		return -ENODEV;
    }

	ret = gpio_pin_configure_dt(gpio, GPIO_INPUT);      /* ← "自动配输入"就是这行 */
	...
	pin_data[i].dev = dev;
	k_work_init_delayable(&pin_data[i].work, cfg->handler);  /* ← 每个键一个延迟工作项 */

	if (cfg->polling_mode) {
		continue;
	}

	ret = gpio_keys_interrupt_configure(&cfg->pin_cfg[i].spec, &pin_data[i].cb_data,
					    cfg->pin_cfg[i].zephyr_code);
```

**② 中断回调：只重排工作项（`:136-149`）**

```c
static void gpio_keys_interrupt(const struct device *dev, struct gpio_callback *cbdata, uint32_t pins)
{
	...
	k_work_reschedule(&pin_data->work, K_MSEC(cfg->debounce_interval_ms));  /* ← 20 ms 后再说 */
}
```

**这行就是"消抖"的全部秘密**：中断来了不立刻上报，而是把工作项推迟 20 ms；20 ms 内抖动会不断 `reschedule`，只在最后一次之后 20 ms 才真正执行。

**③ 工作项到期：真正读引脚并上报（`:116-134` + `:67-92`）**

```c

{
	...
	gpio_keys_poll_pin(dev, key_index);
}

static void gpio_keys_poll_pin(const struct device *dev, int key_index)
{
	...
	ret = gpio_pin_get_dt(&pin_cfg->spec);            /* ← 这里才读电平 */
	...
	new_pressed = ret;
	if (new_pressed != pin_data->cb_data.pin_state) { /* ← 状态变了才上报 */
		pin_data->cb_data.pin_state = new_pressed;

	}

```

**④ 边沿类型：`GPIO_INT_EDGE_BOTH`（`:168`）**

```c
ret = gpio_pin_interrupt_configure_dt(gpio_spec, GPIO_INT_EDGE_BOTH);
```

这解释了 Up 主那句"默认双边沿、不建议改单边沿"：双边沿才能同时拿到"按下"和"松开"；只开下降沿会**永远收不到松开事件**，于是"长按/双击"这类逻辑全废。

**为什么 `GPIO_ACTIVE_LOW` 真的起作用**：`gpio_pin_get_dt()` 读的是**逻辑值**——底层 `gpio_pin_get_raw()` 拿物理电平，再按 `dt_flags` 里的 `GPIO_ACTIVE_LOW` 取反。所以 dts 里那个 flag 不是"注释"，是运行期行为。

一条链总结：

```
IO45 电平变化
  → GPIO 控制器中断
  → gpio_keys_interrupt：k_work_reschedule(work, 20 ms)     ← 消抖
  → 20 ms 后 gpio_keys_change_deferred → gpio_keys_poll_pin  ← 读逻辑电平
  → 状态真的变了 → input_report_key(dev, INPUT_KEY_0, 1/0)
  → Input 子系统分发 → 我们的 input_call_back
```

## 九、`INPUT_CALLBACK_DEFINE` 注册的回调，是怎么被调到的

Up 主在第四课讲了"链接器段收集"，这里把**真实的三段代码**贴出来对上。

**① 宏的本体（`include/zephyr/input/input.h:150-156`）**

```c
#define INPUT_CALLBACK_DEFINE_NAMED(_dev, _callback, _user_data, name)         \
	static const STRUCT_SECTION_ITERABLE(input_callback,                   \
					     _input_callback__##name) = {      \
		.dev = _dev,                                                   \
		.callback = _callback,                                         \
		.user_data = _user_data,                                       \
	}

#define INPUT_CALLBACK_DEFINE(_dev, _callback, _user_data)                     \
	INPUT_CALLBACK_DEFINE_NAMED(_dev, _callback, _user_data, _callback)
```

`STRUCT_SECTION_ITERABLE(input_callback, ...)` 展开后是一个放在 `input_callback` 专属段里的常量结构体，且带 `__used`（防止 `-ffunction-sections` 把它当"没人引用"删掉）。

**② 分发端遍历这个段（`subsys/input/input.c:20-27`，原文）**

```c
static void input_process(struct input_event *evt)
{
	STRUCT_SECTION_FOREACH(input_callback, callback) {
		if (callback->dev == NULL || callback->dev == evt->dev) {
			callback->callback(evt, callback->user_data);
		}
	}
}
```

**这解释了 Up 主那句"`_dev` 传 NULL 收全部"**——判断条件就写在分发循环第 3 行。

**③ 你的回调落在哪个线程（`input.c:39-105`）**

- 默认（没开 `CONFIG_INPUT_MODE_THREAD`）：`input_report()` 组完 `struct input_event` 直接调 `input_process()`，**在调用者上下文分发**——对 gpio-keys 来说就是**系统工作队列线程**；
- 开了 `CONFIG_INPUT_MODE_THREAD`：先 `k_msgq_put` 进 `input_msgq`，由 `input` 专属线程取出再分发。

（`input.c:54-58` 还有一句很值得看：如果当前线程就是系统工作队列、调用方又要阻塞超时，它会主动把超时降成 `K_NO_WAIT`，并打日志 `Timeout discarded. No blocking in syswq.`——这正是"回调里别阻塞"的官方防线。）

所以我们 `main.c` 里那句 `k_msleep(1000)` 的主线程**不参与**按键处理；按键处理发生在系统工作队列里。这就是"回调里阻塞会拖累别的输入设备"的原因。

**三条链对照 Up 主第四课的三张表**：

| 他的说法 | 代码里对应 |
|---|---|
| 默认双边沿 | `input_gpio_keys.c:168` `GPIO_INT_EDGE_BOTH` |
| 可 20 ms 延迟回调，回调在系统工作队列线程 | `:148` `k_work_reschedule(..., K_MSEC(debounce_interval_ms))` + `:116` 延迟工作项处理函数 |
| 键码解耦（代码不认引脚） | `:90` `input_report_key(dev, pin_cfg->zephyr_code, ...)`，键码来自 dts 的 `zephyr,code` |
