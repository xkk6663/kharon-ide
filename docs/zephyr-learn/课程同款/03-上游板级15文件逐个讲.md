> **定位（2026-11-14 更新）**：本篇讲的是**附录 A（S31 Korvo-1）**那套上游 PR 板级 `esp32s31_function_coreboard` 的 15 个文件。主线读者若要对照"标准板级长什么样"，请改看 `west\zephyr\boards\espressif\esp32s3_devkitc\`（17 个文件），或直接看 `02` §4–§5（我们自己写的 7 个文件）。

## 1. 逐文件讲

### 1.1 `board.yml` —— 和他课里那 4 行**一字不差**

```
board:
  name: esp32s31_function_coreboard
  full_name: ESP32-S31-Function-CoreBoard-1
  vendor: espressif
  socs:
  - name: esp32s31
```

他课里的版本是 `name: st_h743_board / full_name / vendor: st / socs: - name: stm32h743xx`。
**同一个字段、同一个含义**：`name` 必须等于目录名（也就是你 `-b` 里斜杠前那一段），`socs` 必须等于 `zephyr\soc\espressif\` 下真实存在的 SoC 名。

你什么时候会用到它：
```powershell
west boards | Select-String esp32s31          # 枚举靠的就是这一层
```
以及排查"`-b` 写错了"：报 `Board "xxx" not found` 时，先去 `zephyr\boards\*\*/board.yml` 里搜那个名字，而不是改代码。

S3 的 `board.yml` 多了一个他课里没有的 **变体**字段：
```yaml
  socs:
  - name: esp32s3
    variants:
    - name: qemu
      cpucluster: procpu
```
→ 意思是"这块板除了真实硬件，还有个 qemu 变体（跑仿真）"。你 `-b esp32s3_devkitc/esp32s3/procpu` 里的 `procpu` 是 **CPU 簇**，不是变体；`-b esp32s3_devkitc/esp32s3/procpu/qemu` 才是变体。

### 1.2 `Kconfig.esp32s31_function_coreboard` —— 他课里 `Kconfig.xxx` 的完全对应物

```
config BOARD_ESP32S31_FUNCTION_COREBOARD
	select SOC_ESP32S31_HPCORE if BOARD_ESP32S31_FUNCTION_COREBOARD_ESP32S31_HPCORE
	select SOC_ESP32S31_LPCORE if BOARD_ESP32S31_FUNCTION_COREBOARD_ESP32S31_LPCORE
	select SOC_ESP32S31_REV_0_0
```

他课里的写法：
```
config BOARD_ST_H743_BOARD
	bool "ST H743 Custom Board"
	select SOC_STM32H743XX
```
**同一件事**：定义板子符号 → select 对应 SoC 符号（这就是"板子和 SoC 绑定"的地方）。

差别只有一个：**这块板有两个核**（HP 核 + LP 核），所以不能无脑 `select SOC_ESP32S31`，要用 `if BOARD_..._HPCORE` 条件选择；再加一条 `select SOC_ESP32S31_REV_0_0`（芯片 revision，`zephyr\soc\espressif\esp32s31\` 下按 revision 分目录）。

**这条 Kconfig 就是你在 `.config` 里看到的那两行符号的来源**：
```powershell
Select-String -LiteralPath build\esp32s31\korvo_apps\s3-debug\zephyr\.config -Pattern 'CONFIG_BOARD_|CONFIG_SOC_ESP32S3'
```
（S3 那次会看到 `CONFIG_BOARD_ESP32S3_DEVKITC=y`、`CONFIG_SOC_ESP32S3=y`，同理 S31 是 `CONFIG_BOARD_ESP32S31_FUNCTION_COREBOARD=y`。）

### 1.3 `Kconfig`（板目录下的这个文件）—— 他课里 `Kconfig.defconfig` 改了名

```
config HEAP_MEM_POOL_ADD_SIZE_BOARD
	int
	default 4096 if BOARD_ESP32S31_FUNCTION_COREBOARD_ESP32S31_HPCORE
	default 256 if BOARD_ESP32S31_FUNCTION_COREBOARD_ESP32S31_LPCORE
```

他课里 `Kconfig.defconfig` 的模板是：
```
if BOARD_ST_H743_BOARD
# 先留空
endif # BOARD_ST_H743_BOARD
```
**同一个角色**：给"选了这块板"时补默认值。你现在看到的实例是"HP 核额外多给 4 KB 堆、LP 核只给 256 B"——因为 LP 核内存本来就小。这条 Kconfig 会直接进 `.config` 的 `CONFIG_HEAP_MEM_POOL_ADD_SIZE_BOARD=4096`。

> 为什么改名？Zephyr 4.x 换成了新的板级 schema（`hw model v2`）：板目录下可以有 4 个 Kconfig 片段——`Kconfig`（默认值补充）、`Kconfig.<板名>`（板符号+select）、`Kconfig.defconfig`（老写法，仍兼容）、`Kconfig.sysbuild`。你在 `zephyr\cmake\modules\hwm_v2.cmake:104-107` 能看到这四行生成逻辑。**他课里那套写法依然合法**，只是这块板用了新名字。

这也解释了 00 号文档里为什么把 `Kconfig.defconfig` 标成 🔄：**概念 100% 同，文件名变了**。

### 1.4 `esp32s31_function_coreboard_hpcore_defconfig` —— 只有 5 行，原则和他讲的一模一样

```
CONFIG_CONSOLE=y
CONFIG_SERIAL=y
CONFIG_UART_CONSOLE=y
CONFIG_GPIO=y
CONFIG_REGULATOR=y
```

他的 defconfig（6 行）：
```
CONFIG_BOARD_ST_H743_BOARD=y
CONFIG_GPIO=y
CONFIG_CLOCK_CONTROL=y
CONFIG_CLOCK_CONTROL_STM32_CUBE=y
CONFIG_STM32_ENABLE_DEBUG_SLEEP_STOP=y
```

对照读法（这就是他"只放板子一定有的基础功能，外设交给 `prj.conf`"原则的实证）：

| 项 | 他 | 你 | 为什么 |
|---|---|---|---|
| 板子身份 | `CONFIG_BOARD_ST_H743_BOARD=y` | **没有这一行** | 新 schema 由 `Kconfig.<板名>` 的 `config BOARD_xxx` 自动带出，不用手写 |
| GPIO | `CONFIG_GPIO=y` | `CONFIG_GPIO=y` | 两块板都有 GPIO，必开 |
| 串口/控制台 | —（他的 defconfig 里没有） | `CONSOLE` / `SERIAL` / `UART_CONSOLE` | ESP32 的 console 是 UART0 焊死的，板级直接开；他没开是因为 H7 板子的串口要靠 `prj.conf`/`&usart` 自己配 |
| 时钟 | `CLOCK_CONTROL` + `STM32_CUBE` | **没有** | ESP32 时钟在 SoC 层内置，不存在"ST 的 cube 时钟驱动"开关 |
| 电源 | — | `CONFIG_REGULATOR=y` | 板上有 `&ldo` 节点（给 PSRAM 1.8V），要有 regulator 子系统才生效 |
| 调试 | `STM32_ENABLE_DEBUG_SLEEP_STOP` | 无（对应的是 `CONFIG_ESP32_DEBUG_*`/JTAG 相关） | 每颗芯片的"调试别断线"开关不同，属芯片层配置 |

**你能写的等价物**：`boards\<板目标>.conf`（你对 S3 写过一份 `CONFIG_INPUT=y`）。它是"应用级、但按板区分"的 Kconfig 片段，编译时随 `-b` 自动选中，和 defconfig 同一层级地参与合并。

### 1.5 `board.cmake` —— runner 机制，和他讲的一模一样，只是 runner 换了

```
if(NOT "${OPENOCD}" MATCHES "^${ESPRESSIF_TOOLCHAIN_PATH}/.*")
  set(OPENOCD OPENOCD-NOTFOUND)
endif()
find_program(OPENOCD openocd PATHS ${ESPRESSIF_TOOLCHAIN_PATH}/openocd-esp32/bin NO_DEFAULT_PATH)

include(${ZEPHYR_BASE}/boards/common/esp32.board.cmake)
include(${ZEPHYR_BASE}/boards/common/openocd.board.cmake)
```

他课里的写法：
```
board_runner_args(stm32cubeprogrammer "--port=swd" "--reset-mode=hw")
include(${ZEPHYR_BASE}/boards/common/stm32cubeprogrammer.board.cmake)
```
**结构完全同**：`include ${ZEPHYR_BASE}/boards/common/<runner>.board.cmake` 就是在注册 runner。差别只在 runner 家族：

| 他的 runner | 你的 runner（S31） | 说明 |
|---|---|---|
| `stm32cubeprogrammer` / `openocd-stm32` | `esp32`（esptool 家族） | 你运行时看到的就是它：`west flash --esp-device COM11` → `Wrote ... bytes`、`Hash of data verified` |
| — | `openocd` + `esp32s31-builtin.cfg` | 调试用，走芯片内置 USB-JTAG |

**所以"为什么烧录不用我写 board.cmake"**：上游已经 include 好了，`west flash` 直接可用；`--esp-device COM11` 是 esp32 runner 自己的参数（等于他 `--port=swd` 的位置）。

### 1.6 `esp32s31_function_coreboard_hpcore.yaml` —— 他课里没有的"旧式板描述"

```yaml
identifier: esp32s31_function_coreboard/esp32s31/hpcore
name: ESP32-S31-Function-CoreBoard-1 HP Core
vendor: espressif
type: mcu
arch: riscv
toolchain:
  - zephyr
supported:
  - adc
  - counter
  - crypto
  - dma
  - entropy
  - gpio
  ...
```

作用：老 schema 的板描述文件（`identifier` 就等价于 `-b` 那整串），`supported:` 是"这块板支持哪些子系统"的清单，`west boards` 与 twister 用它。

**你读它的唯一理由**：想知道"这块板到底支持哪些外设"时，`supported:` 列表比翻 dts 快。比如它列了 `pulse_io`、`led_strip`、`retained_mem`——这三个就是你 RGB、NVS 实验的底层支撑。

### 1.7 `Kconfig.sysbuild` —— 他第四课还没讲到，但迟早会撞上

```
choice BOOTLOADER
	default BOOTLOADER_MCUBOOT
endchoice
```

含义：用 sysbuild 构建时，bootloader 默认选 MCUboot。他课程到第四课为止都是"单镜像直接烧"，所以你暂时不用管；等你做 OTA / 双镜像时，这一行就是"为什么我的构建里多了一个 `mcuboot` 子镜像"的答案。

### 1.8 `support/openocd.cfg` —— 他课里"可选文件"的对应物

```
# ESP32S31 has a built-in JTAG interface over the USB Serial/JTAG controller.
set ESP_RTOS Zephyr
set ESP_ONLYCPU 1
source [find board/esp32s31-builtin.cfg]
```
他的 `support/openocd.cfg` 是 `targets/stm32h7x.cfg` 那种"芯片型号 + 调试接口"。你这里是"内置 USB-JTAG + 只跑 CPU0"。

**注意这条和你的调试体验直接相关**：S31 的 JTAG 走 USB-Serial/JTAG 控制器（同一根 USB 线既出串口又出调试），所以 `west debug` 不需要外接调试器。

### 1.9 LP 核三件套 —— 为什么"一块板两份 dts"

`_lpcore.dts` 很短，是另一颗核的世界：
```
#include <espressif/esp32s31/esp32s31_lpcore.dtsi>
chosen { zephyr,sram = &ulp_ram; zephyr,console = &lp_uart; zephyr,code-partition = &slot0_lpcore_partition; ... }
```
ESP32-S31 是**双核**：HP 核（RISC-V，跑 Zephyr 主系统）+ LP 核（ULP，低功耗协处理器）。`-b esp32s31_function_coreboard/esp32s31/lpcore` 编出来的是给 LP 核的固件。

他课里"一块板一个 `xxx.dts`"的模型在这里失效了——**同一块板、同一目录、两份 dts**，靠 `-b` 的位宽变体（`hpcore`/`lpcore`）选。这也顺带回答了他第四课"迁移只要复制 `boards` 目录"为什么在你这里变复杂：一块板要复制的是**两份** dts + 两套 defconfig。

### 1.10 `doc/index.rst` + `doc/img/*.webp` —— 纯文档

板子照片和官网文档源。`west boards` 的 `--format json` 里 `doc` 字段指向它。你基本不用看，但知道它在"为什么板目录里有一张图片"就够。

## 2. 主设备树 `_hpcore.dts` 逐段拆（116 行，全文件最重要的一份）

这份文件 = 他课里"你自己写的 `xxx.dts`"。**结构完全同构**，我按他的讲课顺序给你标号。

**① 头 5 行：版本声明 + include（他课 §3.3 第 2、8 条）**
```dts
/dts-v1/;
#include <espressif/esp32s31/esp32s31.dtsi>          ← 对应他的 <st/h7/stm32h743Xi.dtsi>
#include "esp32s31_function_coreboard_hpcore-pinctrl.dtsi"  ← 对应他的 xxx-pinctrl.dtsi
#include <zephyr/dt-bindings/input/input-event-codes.h>      ← 键码宏（第四课要用）
#include <zephyr/dt-bindings/led/led.h>                       ← 颜色 ID 宏（WS2812 要用）
#include <espressif/partitions_0x2000_default_16M.dtsi>       ← 分区表（对应他 H7 的 flash 分区约定）
```
**读法**：`esp32s31.dtsi` 里定义了 `&gpio0/&gpio1/&uart0/&i2c0/&rmt/&adc0/&ldo/&flash0/&psram0` 这些标签；**你 overlay 里能 `&` 到的东西，全部来自这几个 include**。

**② 根节点 `/`：compatible + model（他课 §3.3 第 4、7 条）**
```dts
/ {
	compatible = "espressif,esp32s31";
	model = "Espressif ESP32-S31-Function-CoreBoard-1 HP Core";
```
`model` 就是他在 `properties` 表里标"值自定义"的那一项；`compatible` 决定 SoC 层怎么认识这颗芯片。

**③ `chosen`（他课 §3.3 第 11 条）**
```dts
chosen {
	zephyr,sram = &sramhp;                 ← 主 RAM
	zephyr,console = &uart0;               ← 控制台（S3 板默认也是 uart0，所以你的 S3 overlay 才必须改它）
	zephyr,shell-uart = &uart0;
	zephyr,flash = &flash0;
	zephyr,code-partition = &slot0_partition;
	zephyr,canbus = &twai0;                ← 他清单里没有的一项（CAN 主控制器）
};
```
**这是"板级定默认、overlay 改选择"的典例**：S3 那份板级 dts 的 `chosen` 也是 `uart0`，但 DevKitC 只接了 USB 口 → 你的 `boards\esp32s3_devkitc_esp32s3_procpu.overlay` 里就得把 console 改成 `&usb_serial`（第 94-99 行）。**他课里 `chosen` 那一节，就是给这种场景做准备的。**

**④ `aliases`（他课 §3.3 第 10 条）**
```dts
aliases {
	sw0 = &boot_button;      ← 按键短名（你 05 文档里 DT_ALIAS(sw0)）
	led-strip = &led_strip;  ← 他课里是 led0 = &led0，同一种"别名"
	watchdog0 = &wdt0;
};
```

**⑤ 板载外设节点：`led_strip`（他课里 `leds` 的同位物）**
```dts
led_strip: ws2812 {
	compatible = "worldsemi,ws2812-pulse-io";   ← binding 名，决定哪个驱动接管
	pulse-ios = <&rmt 0>;                        ← phandle-array：引用 rmt 控制器 + 第 0 通道
	chain-length = <1>;
	color-mapping = <LED_COLOR_ID_GREEN LED_COLOR_ID_RED LED_COLOR_ID_BLUE>;
	reset-delay = <300>;
};
```
**对照他的 `leds { compatible = "gpio-leds"; led0: led_0 { gpios = <&gpioh 9 GPIO_ACTIVE_LOW>; }; }`**：容器节点 + `compatible` + 子节点里的"引用控制器+参数"三元组，**语法一模一样**，只是控制器从 `gpioh` 换成了 `rmt`、参数从"引脚+标志"换成"通道号"。
`#gpio-cells = 2` 那种"几个 cell"的机制在这里体现为 `pulse-ios` 的 2 个 cell（控制器 + 通道）。

**⑥ `gpio_keys`（第四课的主角，这里已经给你写好了）**
```dts
gpio_keys {
	compatible = "gpio-keys";
	boot_button: button {
		label = "Boot Button";
		gpios = <&gpio1 29 (GPIO_PULL_UP | GPIO_ACTIVE_LOW)>;
		zephyr,code = <INPUT_KEY_0>;
	};
};
```
他第四课让你**自己写**这一整块（11 个键）；你这边**上游已经写好 1 个键**：
- 容器名是 `gpio_keys`（S3 板是 `buttons`，所以 S3 覆盖 debounce 得写 `&{/buttons}`）
- 子节点 `button`（S3 是 `button0`）
- `gpios` 的第三个 cell 是**标志组合**（`PULL_UP | ACTIVE_LOW`），他课里只讲了 `GPIO_ACTIVE_LOW` 一个
- `zephyr,code` 用 `INPUT_KEY_0`（dtc 处理后是 `0xb` = 11），和他在 dts 里写 `INPUT_KEY_A/1/2…` 是同一套码表
- **没有 `debounce-interval-ms`** → 用驱动默认（30 ms）。你 S3 覆盖成 20 ms 时才需要加父节点属性

**⑦ 一堆 `&xxx { status = "okay"; pinctrl-0 = <&xxx_default>; }`（他课 §3.3 第 9 条"节点级引用"）**
```dts
&uart0  { current-speed = <115200>; pinctrl-0 = <&uart0_default>; status = "okay"; };
&i2c0   { clock-frequency = <I2C_BITRATE_FAST>; pinctrl-0 = <&i2c0_default>; status = "okay"; };
&gpio0 / &gpio1 { status = "okay"; };
&rmt    { pinctrl-0 = <&rmt_default>; status = "okay"; };
&twai0 / &wdt0 / &trng0 { status = "okay"; };
```
**这一整段就是"板级把能开的都开好"**。你在 overlay 里写 `&adc0 { status = "okay"; }`、`&adc1 { … }`、`&rmt { pinctrl-0 = <&rmt_korvo>; }` 全部是同一种语法（他的"节点级引用，写在根节点外"）——**唯一的区别是优先级：overlay 后合并，会覆盖这一层的值**。

**⑧ `&ldo`：他课"电源 `&pwr`"的你版本**
```dts
&ldo {
	status = "okay";
	ldo1@1 {
		regulator-init-microvolt = <1800000>;
		regulator-boot-on;
		regulator-always-on;
	};
};
```
他对 STM32H7 写的是 `&pwr { power-supply = "ldo"; }`（选供电方案）；你这边是"哪一路 LDO、给多少伏、是否常开"。**同样是"电源配置"，表达的层次不同**：H7 选方案，ESP32 配 regulator。

## 3. `_pinctrl.dtsi` 逐段（对应他课 §3.3 第 12 条）

```
&pinctrl {
	uart0_default: uart0_default {
		group1 { pinmux = <UART0_TX_GPIO58>; output-high; };
		group2 { pinmux = <UART0_RX_GPIO59>; bias-pull-up; };
	};
	i2c0_default: i2c0_default {
		group1 {
			pinmux = <I2C0_SDA_GPIO51>, <I2C0_SCL_GPIO50>;
			bias-pull-up;
			drive-open-drain;
			output-high;
		};
	};
	twai0_default: ... ; rmt_default: { group1 { pinmux = <RMT_OUT0_GPIO60>; }; };
};
```

**这就是他说的"pinctrl = 引脚复用 + 电气特性"两件事的实物**：
- 复用：`pinmux = <UART0_TX_GPIO58>` —— 把 GPIO58 切成 UART0_TX（ESP32 用**预定义宏**，他 STM32 那边是 `<&gpioa 9 …>` 那种"控制器+引脚+AF 号"）
- 电气：`bias-pull-up`（上拉）、`drive-open-drain`（开漏）、`output-high`（初始高电平）

**你必须知道的两个"边界"**：
1. 板级只给了 `rmt_default = RMT_OUT0_GPIO60`（上游板的 WS2812 在 GPIO60）。**Korvo-1 的 WS2812 在 GPIO37** → 所以 `applications\common\korvo_board.dtsi` 里必须新增 `rmt_korvo` 这个 pinctrl 节点，再用 `&rmt { pinctrl-0 = <&rmt_korvo>; }` 覆盖。这就是"板级写死的默认，你得用 overlay 换掉"的最典型例子。
2. `pinctrl-0` 只能有**一个**"default"组：覆盖时不是追加，是替换。所以你 overlay 里写 `pinctrl-0 = <&rmt_korvo>` 之后，板级的 `rmt_default` 就**不再生效**（这跟 overlay 覆盖 `status` 是同一种合并规则）。

## 4. S3 那份板级为什么不一样（17 个文件）

| 差异点 | S31 板级 | S3 板级 | 对你的影响 |
|---|---|---|---|
| 文件数 | 15 | 17（多 `appcpu`/`qemu` 两套 dts+yaml+defconfig、`sysbuild.cmake`） | 都是只读，不用管 |
| 按键节点名 | `/gpio_keys`（子节点 `button`） | **`/buttons`**（子节点 `button0`） | 覆盖 debounce 要写 `&{/buttons} { … }` |
| 按键引脚 | `&gpio1 29`（GPIO29） | `&gpio0 0`（BOOT） | DevKitC 的 KEY 在 IO45，你 overlay 里改成 `&gpio1 13` |
| console | `zephyr,console = &uart0` | **也是 `&uart0`**，且 `&usb_serial` 默认 `status = "disabled"` | 只插 USB 口时串口空白 → overlay 必须切 `chosen` + 打开 `&usb_serial` |
| flash | 16 MB | 8 MB | 你的 `FLASH 215716 B (2.57%)` 就是按 8 MB 算的 |
| `CONFIG_CLOCK_CONTROL` | 板级 defconfig 里**没有** | **有** | S3 的时钟驱动要显式开；S31 由 SoC 层处理 |
| 触点传感器 | 无 | `&touch { debounce-interval-ms = <30>; ... }` | 顺带说明：`debounce-interval-ms` 是 gpio-keys**父节点**属性，别往子节点里写 |

**一条经验**：换板第一件事不是改代码，是 `Select-String zephyr.dts -Pattern 'gpio_keys|buttons|sw0|console'`——先看这板级的"名字"，再决定 overlay 怎么写。这条比背文档有用。

## 6. "交界线"：哪些只能 overlay 改，哪些板级独占

| 你想动的东西 | 能不能在 overlay 里做到 | 怎么做 / 为什么不能 |
|---|---|---|
| `status`（开/关某个外设） | ✅ | `&adc0 { status = "okay"; }` |
| 引脚复用 / 电气特性 | ✅ | 新增 `&pinctrl { xxx: xxx { group1 { pinmux = …; }; }; }` 再 `pinctrl-0 = <&xxx>` |
| `chosen`（console/flash/sram…） | ✅ | 在 overlay 里再写一次 `/ { chosen { … }; }`，后合并覆盖 |
| `aliases` | ✅ | `/ { aliases { … }; }`；删别名用 `/delete-property/`（你 S3 那份删 `pa-ctrl` 就是这么干的） |
| 给已有外设加/改属性（频率、极性、去抖） | ✅ | 直接 `&节点 { 属性 = …; }` |
| 新增一个完整外设节点（WS2812、自造 `gpio-leds`） | ✅ | 根节点下加容器+子节点 |
| `board.yml` / `Kconfig.<板名>` / `board.cmake` / defconfig | ❌ | **不改**。要"每块板不同"，用 `boards\<板目标>.conf`；要"改烧录参数"，用命令行 `west flash --esp-device` |
| 主 dts 里被写死且不可覆盖的东西（如 `compatible`/`model`） | ⚠️ 覆盖意义不大 | 板级是"这块物理板"的身份，改它等于 fork 板级（→ 那才需要 `BOARD_ROOT`，也就是他第三课讲的那套） |

**一句话记住交界线**：**"覆盖已有节点的属性/状态" 永远在 overlay；"定义板子是谁、怎么烧" 永远在板级。** 他第三课整章讲的是后者，你只写前者——所以你只需要"读懂"他那一章，不需要"照做"。

## 8. 三个概念问题（问得准，答案也更值得写下来）

### 8.1 "这些文件是不是用来配置驱动的？"

**不是配驱动，是"声明硬件 + 声明板子身份"。** 驱动代码一行都不在板级目录里。完整的链条是三层：

| 层 | 在哪 | 回答什么问题 | 谁的活 |
|---|---|---|---|
| **SoC 层** | `zephyr\dts\riscv\espressif\esp32s31.dtsi`、`zephyr\soc\espressif\esp32s31\` | 这颗芯片里有 `uart0/rmt/adc0/ldo` 这些控制器吗？寄存器在哪？引脚复用宏叫什么？ | 芯片/SoC 维护者（乐鑫 + Zephyr） |
| **板级层** | 你正在读的这 15 个文件 | 这块板把哪几个控制器引出来了？接在哪几个脚？外挂什么器件（WS2812 / 按键 / PSRAM）？默认开哪些？叫什么名字、怎么烧？ | 板子作者（这里是乐鑫，不是你） |
| **应用层** | `applications\<app>\prj.conf` + `boards\<板目标>.overlay` | 我这个应用要用哪些功能？上游板级哪些接线跟我的底板不一样（差量补丁）？ | **你** |

而"驱动本身"在第四层：`zephyr\drivers\`（`gpio`、`input`、`uart`、`esp32\rmt`…），它靠 **binding yaml**（`zephyr\dts\bindings\**\*.yaml`）跟 dts 里的 `compatible` 对上号。板级里唯一"像配置驱动"的东西是 `xxx_defconfig` 里的 `CONFIG_GPIO=y` 这种开关——但它只是"默认把驱动编进去"，不是"配置驱动行为"。**驱动行为的配置，全在 dts 属性里**（`clock-frequency`、`current-speed`、`debounce-interval-ms`…），这也是他课一直强调 dts 的原因。

### 8.2 "dts 才是设备树的关键"——对，但只是一半

他这句话的意思是"板子的硬件事实写在 dts 里，改板就是改 dts"。在你这里要补成三件套，缺一件就出故障，而**三种故障你都踩过**：

| 你改了什么 | 还缺什么 | 症状（都发生在你这套工程里） |
|---|---|---|
| dts 有 `gpio_keys` + 代码有回调 | **Kconfig 没开 `CONFIG_INPUT`** | 链接期 `undefined reference to __device_dts_ord_19` / `input_report` |
| overlay 写对了内容，但放错位置（旧 `app.overlay`，板级 overlay 存在时整段不生效） | 文件**没被采用** | `__device_dts_ord_48 undeclared`（`korvo_sys` 在 S3 上） |
| 属性名写对位置了吗（`debounce-interval-ms` 写在子节点 `button0` 里） | **binding 校验** | dtc 直接报 `not declared in properties` |

所以准确的表述是：**dts 决定"硬件是什么"，binding 决定"谁来接管"，Kconfig 决定"驱动编不编"**。他课第三章讲 dts 篇幅最大，是因为"从零写一块板"时 dts 的工作量最大；你的场景里板级已经存在，你的工作量在 **overlay + Kconfig** 上（这也是为什么 `CONFIG_INPUT` 那行会成为一个整节课级别的坑）。

### 8.3 "上游板子也不是我们的硬件板，为什么不用自己配？"

**这句话的前半句完全正确，后半句的答案藏在"差多少"里。**

**上游板级是谁**：`esp32s31_function_coreboard` = 乐鑫的 `ESP32-S31-Function-CoreBoard-1`，一份"官方模组底板定义"：S31 双核（HP+LP）、16 MB flash、16 MB PSRAM、UART0（G58/G59，板上 USB 转串口）、I2C0（G51/G50）、RMT（G60）、BOOT 键（IO61 = `&gpio1 29`，gpio1 编号 0 对应 IO32）、LDO 1.8 V 给 PSRAM、`partitions_0x2000_default_16M` 分区表。

**Korvo-1 是另一块板**，但它是"同一颗 S31 模组 + 自己的底板"。真实差异只有 **4 处接线**（这也是你 `applications\common\` 里那两个 dtsi 的全部内容）：

| # | 项 | 上游 coreboard 默认 | Korvo-1 实际 | 你的补丁 |
|---|---|---|---|---|
| 1 | WS2812 数据脚 | `rmt_default` → **G60** | **G37** | `korvo_board.dtsi`：新增 `rmt_korvo`（`RMT_OUT0_GPIO37`）+ `&rmt { pinctrl-0 = <&rmt_korvo>; }` |
| 2 | 功放使能 PA_CTRL | **没有这个节点** | **G7**（高电平开） | `korvo_board.dtsi`：`pa_ctrl` 节点 + `pa-ctrl` 别名 |
| 3 | I2C0 | `i2c0_default` → **G51(SDA)/G50(SCL)** | **G0(SDA)/G1(SCL)** | `korvo_i2c.dtsi`：`i2c0_korvo` + 覆盖 `pinctrl-0`（只 `korvo_lab`/`korvo_shell` 用） |
| 4 | 四个功能键 | 只有 `boot_button`（IO61）；无 ADC 键 | **IO42 电阻梯**（一路 ADC 分四档） | `&adc0 { status = "okay"; }`（`korvo_apps` 再加 `&adc1`） |

**其余全部相同**：console UART、flash/PSRAM 容量、分区表、LDO、GPIO 控制器、`chosen` 的 `zephyr,flash`/`sram` —— 这些如果也自己写一遍，就是把乐鑫验证过的 90% 抄一遍，还抄错的风险自负。

**所以"不需要自己配"不是"偷懒"，而是三个机制在替你兜底**：

1. **板级的粒度本来就是"模组/底板"，不是"最终产品"**。`-b` 选的是"模组底板组合"，剩下 10% 的接线差异，官方留了 overlay 这个口子（`boards\<板目标>.overlay` 按 `-b` 自动挑，优先于 `app.overlay`）。
2. **SoC 层是芯片绑定的，抄不走**：`esp32s31.dtsi` 里有几百个节点/引脚宏，换板也不会变，它跟"你的底板长什么样"无关。
3. **overlay 是"差量"而不是"重写"**：你写 4 处补丁，合并后 `zephyr.dts` 与"从零写一块板"**完全等价**——这也是为什么迁移前后 `zephyr.dts` 能比到 `equal=True`。

**那什么时候必须自己整块写板级？**（判断标准就 4 条，命中任意一条才需要 fork）

| 命中条件 | 例子 | 你现在的状态 |
|---|---|---|
| 芯片在 `zephyr\soc\` 里没有 | 全新的 SoC | ❌ 不命中（S31/S3 都有） |
| 模组/flash/PSRAM/CPU 核/分区表 与上游不同，`-b` 表达不了 | 换 32 MB flash、只保留 LP 核 | ❌ 不命中（Korvo-1 沿用 16 MB/双核） |
| 要改"板子身份类"文件：`board.yml`、`Kconfig.<板名>`、`board.cmake`、`defconfig` | 换烧录 runner、改默认 bootloader、进 `west boards` 列表 | ❌ 不命中（你只想改接线） |
| 板级里写死且 overlay 覆盖不了的字段（`compatible`、`model`） | 需要"另一个板名"出现在构建系统 | ❌ 不命中 |

**如果哪天命中了**，他第三、四课讲的那套就立刻变成你的主线：`cp -r` 上游板目录 → 改 4~5 个文件 → `set(BOARD_ROOT ${CMAKE_CURRENT_SOURCE_DIR})`（或写进 presets 的 `cacheVariables`）→ `-b <板名>`。**他课里那些你现在标 ❌ 的条目（`BOARD_ROOT`、`Kconfig.xxx`、`board.yml`）全部会在那一天"活过来"。**先读懂、不必现在写，这就是 00 号文档把它们标成"看懂即可"的原因。
