## 3. 怎么用这张表学（四步法，每节课都能套）

1. **先看他的目录树**，把每个文件在你工程里"指认"出来——指认不出来的，就是 ❌ 或 🔄 那几条（对照 §0 的三个来源即可，不用逐个猜）。
2. **只看 ✅ 的条目动手**：dts 语法、Kconfig 符号、Input 回调、缓存、编译烧录——这些你照他的命令跑，把 `BOARD`/路径换成你的。
3. **🔁 的条目只换"名字"**：他 `xxx.dts` → 你 `boards\<板目标>.overlay`；他 `arm-zephyr-eabi` → 你 SDK 自选；他 `&pinctrl { … }` 的 `<&gpioh 9 …>` → 你 `pinmux = <RMT_OUT0_GPIO37>`。
4. **🔄 / ❌ 的条目只求"读懂"**：board.yml / Kconfig.xxx / BOARD_ROOT / `&rcc` 这些，你的答案是"上游已写、我不用写"，但必须能说出"它解决什么问题"——面试和排查现场都问这个。

## 4. 三个差异来源的"多看一层"（为什么它们不影响你学课）

**A. 板级归谁**——他的 8 文件里，真正**决定行为**的只有 `xxx.dts`（硬件描述）和 `xxx_defconfig`（默认功能）。这两个你都有等价物：前者 = 上游 `esp32s31_function_coreboard.dts` + 你的 overlay；后者 = 上游 `_defconfig` + S3 的 `boards\*.conf` + `prj.conf`。其余 6 个（`board.yml`/`Kconfig.xxx`/`Kconfig.defconfig`/`board.cmake`/`support/openocd.cfg`/`-pinctrl.dtsi`）是"让构建系统认识这块板"的样板件，上游已经替你写完了。

**B. 架构 + 工具链**——他的 presets 写死 `arm-zephyr-eabi-gcc`，因为一块板一个架构。你手上是**四块板、三种架构**（RISC-V / Xtensa / ARM），写死就错；Zephyr SDK 的 `zephyr` toolchain variant 会按 `CONFIG_*_ARCH` 自动挑编译器，所以你的 presets 里**故意不写** `CMAKE_C_COMPILER`，只写 `ZEPHYR_TOOLCHAIN_VARIANT=zephyr` + `ZEPHYR_SDK_INSTALL_DIR`（`env.ps1` 里已统一）。这也是"同一个 SDK 目录装多架构"和"his 一个 SDK 只装 arm"的差别，不是对错问题 —— 2026-11-16 补上 SDK 的第三个目标 `arm-zephyr-eabi` 之后，这条在 STM32F411/F103 上已经实机验证。

**C. 芯片外设树**——STM32 的 `&rcc`/`&pwr` 是"芯片太复杂、Zephyr 不敢给默认值"的产物；ESP32 的时钟/电源在 SoC 层锁死（`&ldo` 只暴露电压），应用层没有可调旋钮。**结论：他的时钟/电源两节，你只需要知道"为什么他没有默认值、我没有这个节点"，别去 `esp32s31.dtsi` 里硬找 `rcc`。**

## 6. 一句话回答"差得大吗"

**不大，但"大不大"取决于你拿什么比。**
拿**文件名**比：差得很大（他 8 个板级文件、你 1 个 overlay）。
拿**知识点**比：第三课 30 条里 **21 条**（✅14 + 🔁7）能原样照做或只换个名字，第四课 15 条里 **12 条**（✅10 + 🔁2）能原样照做；真正"你这里没有"的只有 **`&rcc`、`&pwr` 的 H7 专有写法、`BOARD_ROOT`/board.yml/Kconfig.xxx 这套自建板级样板、`CMakeUserPresets.json`**——它们恰好都**不需要你动手**。
你唯一必须补的补丁是"**板级在上游时，overlay 怎么写**"这一条，而这条 `02` 讲完了、`05` 的真机串口也验完了。
