# ADR-001：事实源与边界（板卡 / pack / provider）

- 状态：已采纳（2026-11-19）
- 背景：架构优化与目录重构（P0–P5）。三处历史表述互相矛盾，导致换机器或换芯片时
  出现「到底以哪份为准」的歧义。本 ADR 固定三条边界，后续文档若与此冲突，以本文件为准。

## D1：自研板卡是 west module，不是树内副本

**决策**：`esp32s31_function_coreboard` 等自研板的唯一事实源是
`kharon-boards`（一个 west module）。`zephyr-workspace/zephyr/boards` 下的同名目录
只是构建缓存/链接，**不是**可编辑的事实源。

**为什么**：

- Zephyr 的板级发现依赖 module 声明的 `boards/` 路径；把板子放回 `zephyr-workspace/zephyr/boards`
  会让 `west update` 与本地修改互相覆盖。
- 旧仓 classic / 本仓 kharon 共享同一份 manifest 时，module 版本可以随
  `manifests/zephyr.west.yml` 锁定；树内副本无法锁定。
- 「拷贝回树内」的副本一旦存在，就会出现两份同名板级定义，构建结果不可复现。

**后果**：

- 换机器由 `python -m kharon.bootstrap --check` 校验 module 是否存在，缺失时给出
  单条修复命令（`west update`），而不是让人手工拷贝。默认 `learning` 通道跟随上游
  全量；需要复现时用 `--pinned` 只校验 `zephyr.pinned_modules` 的 6 个模块。
- 任何提交里新增的板级文件都必须落在 `kharon-boards/boards/`。

## D2：pack 不写芯片的 memory / core

**决策**：芯片适配包（`packs/official/**`）只提供板级事实、工具链命令与调试参数；
`memory`、`core`、链接脚本归属由**项目**（`projects/*.yaml`）与芯片 pack 的只读
模板共同决定，pack 的安装/更新过程不得改写项目的 `memory`/`core`。

**为什么**：

- 同一颗芯片在不同板子上可能有不同的 Flash/RAM 几何与 bootloader 偏移；把 memory
  钉死在 pack 里会造成跨板污染。
- pack 是**数据**，应可被市场替换/升级；写入项目配置会让升级变成隐式的项目迁移。
- 项目配置才是「这块板子怎么跑」的最终裁决点，便于审计与回滚。

**后果**：

- `elab pkg install/update` 对 `projects/` 只做只读校验，差异以 doctor 警告呈现。
- 冲突时必须由人显式修改项目配置，不能靠升级 pack 悄悄改变行为。

## D3：provider 是 L1.5 适配层，不是插件

**决策**：provider（`services/elab/platform/provider.py` 及 `providers/**`）位于
L1 chip pack 与 L2 项目之间，用于把宿主机工具链（GNU/Keil/IAR/Zephyr SDK/ESP-IDF）
映射成统一命令；它**不**通过 DSH 插件市场分发，也不作为插件加载。

**为什么**：

- provider 需要读取宿主机路径、`host.local.yaml` 与 `config/host.<profile>.profile.yaml`；
  插件运行在受限沙箱里，拿不到这些事实。
- provider 的选择是**环境属性**（本仓只有 `kharon`），不是用户可安装的能力；
  把它做成插件会导致「装了插件但工具链不存在」的假成功。
- 保持 L1.5 独立，`doctor` 才能在编译前给出「工具链缺失 + 一条修复命令」。

**后果**：

- 新增工具链只改 `providers/**` 与 host profile，不改插件注册面。
- 插件只依赖稳定的 CLI/HTTP/事件契约，不感知 provider 实现。
