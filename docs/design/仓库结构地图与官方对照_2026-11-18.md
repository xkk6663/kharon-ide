# 仓库结构地图与官方术语对照（2026-11-18）

> 目的：把这套仓库的目录、命名、以及与 Zephyr 官方"独立应用工作区"的对应关系写成一张
> 能照着走的图。**以本文为准**；`CHANGELOG.md` 与 `docs/**/变更记录*` 里的旧写法是历史，
> 不再回改。

---

## 1. 三句话结论

1. 本仓是**独立应用（freestanding application）**形态：应用住在 `applications/`，工作区住在
   `west/`，应用**不在**工作区里 —— 官方对这三种形态都明确合法。
2. 官方**不规定**应用的父目录名（freestanding 应用放哪都合法）。官方示例里工作区应用用
   `applications/`、独立示例仓用 `app/`。本仓原先叫 `apps/`，已统一为 **`applications/`**，
   目的是与官方词汇对得上，而不是因为"官方要求这样"。
3. 真正与官方同构的是**每个应用内部**：`CMakeLists.txt` + `prj.conf` + `src/` +（可选）`boards/`。
   本仓 14 个应用全部合规（`korvo_nvs` 没有 `boards/` 也合法 —— boards 是可选的板级覆盖）。

---

## 2. 官方的三种应用形态 ↔ 本仓

| 官方形态 | app 在哪 | 与工作区的关系 | 本仓 |
|---|---|---|---|
| **仓库应用**（repository application） | 内核树内，如 `zephyr/samples/*` | 就在工作区里 | 不用 |
| **工作区应用**（workspace application） | `<workspace>/applications/<app>` | 在工作区里，官方默认假设 | 不用 |
| **独立应用**（freestanding application） | 任意路径，设 `ZEPHYR_BASE` 即可 | 在工作区**外** | **本仓用这个**：`applications/<family>/<app>` |

> 官方对三者没有"推崇"，只有默认假设（示例仓走工作区应用）+ 明确宽容。
> 所以本仓不是"偏离官方"，而是选了官方承认的一条路。

## 4. 命名规范（从本次改动起）

1. **应用目录 = snake_case，且与 `projects/*.yaml` 的 `name:` 逐字相同**。
   例：`applications/stm32f4/f411_breath` ↔ `projects/kharon/f411_breath.yaml`。
   （旧 `blinky-s3` 已改成 `blinky_s3`，因为它的工程名一直是 `blinky_s3`。）
2. **应用路径只给人看**。任何命令/配置都只用**工程名**（`-p f411_breath`）与**板名**
   （`${chip.target}`）；没有一处命令拼 `applications/...` 路径。
   例外：`project.yaml: root` 必须写路径，这是唯一显式依赖。
3. **`<family>` 层（`stm32f1` / `stm32f4` / `esp32s3` / `esp32s31`）是自加的**，官方没有；
   它不参与任何命令，只用于人眼浏览与批量脚本。
4. 芯片 id = 板名（board-as-chip 红线：芯片包**不写** memory/core/compiler_defines）。

## 5. Zephyr 自己的调试链，与本仓怎么接

官方那条链（这才是"Zephyr 自带的调试工具"）：

```
board.cmake ──configure──> build/<...>/zephyr/runners.yaml
                              │ runners: dfu-util / openocd / jlink / …
                              │ flash-runner / debug-runner
                              │ config.gdb / config.openocd / config.openocd_search
                              ▼
                     west flash / west debug / west debugserver
                              ▼
                     openocd + arm-zephyr-eabi-gdb（都在 Zephyr SDK 里）
```

实测（本机 f411_breath）：

- `runners.yaml` 的 `config.gdb` = `zephyr-sdk-1.0.1/gnu/arm-zephyr-eabi/bin/arm-zephyr-eabi-gdb-py.exe`
- `config.openocd` = `zephyr-sdk-1.0.1/hosttools/openocd/bin/openocd.exe`
  → **Zephyr SDK 1.0.1 自带 openocd**（此前"SDK 不含 openocd"的判断是错的）
- 这块板的官方 runner 齐全（dfu-util / stm32cubeprogrammer / openocd / jlink / blackmagicprobe），
  **默认 `flash-runner` 是 dfu-util**（板子带 DFU）。

本仓的选择，以及为什么不能照搬 `west flash`：

| 官方行为 | 本仓行为 | 原因 |
|---|---|---|
| `west flash` 默认走 `runners.yaml` 的 **dfu-util** | 不跑 `west flash` | 板子上插的是 **DAP-Link**，不是 DFU；要先进入 bootloader 才能 DFU，日常调试不现实 |
| openocd 的 interface 由板级 `openocd.cfg` 决定（默认 ST-Link） | 芯片包给**整份 cfg**（`debug.openocd_config`，DAP-Link 版） | interface 属于探针，不属于芯片；换探针不该改板级文件 |
| `west debug` 是**前台阻塞**的交互 | 内核自己做 gdb-mi 客户端 + openocd 会话 | 面板需要断点/变量/调用栈的结构化事件，不能只喂一个 TUI |

**关键点：工具本身用官方的，只是驱动方式不同。**
`plan.debug_profile()` 与 `flash.py` 现在都优先读 `runners.yaml` 的
`config.gdb` / `config.openocd` / `openocd_search`（`gdb_source=openocd_source=runners.yaml`），
芯片包的 `openocd_key` 退化成"没有构建产物时的兜底键"。这样：

- gdb = SDK 的 `arm-zephyr-eabi-gdb`（能读 Zephyr 的符号/RTOS 感知）
- openocd = SDK 自带那份（与 `west debug` 同一版本），scripts 也指向 SDK
- 只有 **interface/target 那份 cfg** 由我们覆盖（DAP-Link）
