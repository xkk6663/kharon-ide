# elab-flow 架构优化与目录重构方案（2026-11-19）

- 状态：提案，待评审后分阶段执行
- 范围：仓库根 `dsh-elab-flow`，包括主机内核、驾驶舱、DSH 插件、Zephyr 应用与工程数据
- 方法：对照 Zephyr 官方 Application Development / Modules / West 文档，结合本机源码、AST 度量、导入关系和 CI 配置取证
- 硬约束：**先补门禁，再移动文件；先保持行为，再优化目录；旧路径至少一个发布周期内保持兼容**
- 本文只定义方案，不要求一次性大重构；每个阶段都必须可独立验收、可回滚

---

## 0. 一句话结论

本项目的**芯片事实层、工具链事实层和 Zephyr 板级模块设计已经接近 Zephyr 的分层哲学**，真正的架构债务在四个位置：

1. 主机配置存在两套事实源和隐式 fallback；
2. 内核模块按文件平铺，几个文件已经超过千行；
3. HTTP 层把路由、会话、业务编排和权限检查放在一个超大 handler；
4. 前端契约需要人工两处同步，仓库还保留大量历史工程树。

因此正确路线不是“把仓库改得像 Zephyr”，而是：

- 保留 `packs / providers / projects / zephyr_modules` 的声明式边界；
- 给宿主工具链补上 manifest、profile 和稳定 API 治理；
- 按 bounded context 重组 `services/elab` 与 `cockpit`；
- 用代码生成消除 ICD 双镜像；
- 把历史 `examples/` 从日常认知负担中移出。

### 1.2 已存在的正确设计

这些设计应保留，不能因“目录重组”破坏：

| 设计 | 证据 | 价值 |
|---|---|---|
| 流程词汇从 HTTP 载体中移出 | `services/elab/flow.py:1-16` | 步骤标签和三档定义不再挂在某个前端上 |
| 芯片包不重复 Zephyr 硬件事实 | `packs/official/zephyr/framework/pack.yaml:5-11` | 防止“体检说一套、构建用另一套” |
| 自研板作为 Zephyr module | `zephyr_modules/elab-boards/zephyr/module.yml:19-22` | 避免 `west update` 冲掉板级文件 |
| `west build` 三形态适配 | `providers/official/zephyr/west/provider.yaml:61-78,94-134` | 工程只表达绑定，内核生成 argv |
| 三层 CMake 物理防火墙 | `applications/esp32s3/s3_wifi_portal/CMakeLists.txt:29-58` | 用 include 路径阻止反向依赖，且避免 STATIC 库丢弃注册段 |
| CLI 与驾驶舱共用运行路径 | `services/elab/run.py:1-16`，`cockpit/server.py:10-13` | 事件、dry-run 和真实执行同源 |
| 插件边界测试 | `packages/dsh-elab-cockpit/test/boundary.test.mjs:1-192` | 工具层与业务层之间的唯一缝隙是 HTTP ICD |
| 构建产物门禁 | `.github/workflows/elab.yml:208-245`，`plugin.yml:53-63` | 防止源码和入库产物漂移 |

### 1.3 Zephyr 官方文档对照

以下页面是本方案采用的官方口径：

- Application Development：<https://docs.zephyrproject.org/latest/develop/application/index.html>
  - 应用以 `CMakeLists.txt + prj.conf + src/` 为核心；
  - `prj.conf` 设置配置值，`Kconfig` 定义配置选项；
  - `boards/`、overlay、module 分别承载板级修改和可复用代码；
  - freestanding application 合法，不必强行搬入 west workspace。
- Modules：<https://docs.zephyrproject.org/latest/develop/modules.html>
  - module 通过 `zephyr/module.yml` 提供 CMake/Kconfig/board_root/dts_root 等集成信息；
  - west project 与 module 是两个概念；
  - 有独立上游生命周期的成熟代码适合做 module。
- West manifest：<https://docs.zephyrproject.org/latest/develop/west/manifest.html>
  - manifest 决定 workspace 中有哪些仓库及各自 revision；
  - 可复现构建依赖锁版本，而不是依赖本机现有目录。
- Devicetree：<https://docs.zephyrproject.org/latest/build/dts/index.html>
- Kconfig：<https://docs.zephyrproject.org/latest/kconfig.html>

映射到本项目：

| Zephyr 概念 | 本项目对应 | 当前状态 |
|---|---|---|
| DTS/板级事实 | `zephyr_modules/elab-boards/**` | 已正确独立 |
| Kconfig 配置值 | `applications/**/prj.conf` | 已按应用独立 |
| manifest 锁版本 | `manifests/zephyr.west.yml` | **缺失** |
| module | `packs/**`、`providers/**` 是宿主工具的数据包；不是 Zephyr module | 概念独立，但不应混称 |
| 稳定 API + 弃用周期 | `GET /api/capabilities`、`elab_*` 工具契约 | 有自描述，缺正式版本与弃用策略 |

## 2. 问题清单

### A1（P0）主机配置双事实源

证据：

- `services/elab/config.py:81-100`：`host_fallback` 主动读取 `kharon.host.yaml`，注释明确承认“两份主机事实源”。
- `services/elab/run.py:301-315`：`_host_value()` 在主 host 文件缺键时再查 fallback。
- `kharon.host.yaml:1-6`：文件自称“唯一主机事实源”，同时又说要用 `ELAB_HOST=` 选择。
- `kharon.host.yaml:32,43,48-67`：SDK、gdb、addr2line 等写死本机绝对路径。
- `docs/archive/design/执行计划_Zephyr工作区三形态适配_2026-11-18.md:413-472`：P5 分发与重建尚未开工；仓库根不存在 `manifest/`。

后果：

- `ELAB_HOST` 忘设时会静默走不同配置源；
- 两份文件都可能声称自己是唯一事实；
- clone 后无法保证同版本 workspace 与 SDK；
- CI 和本机 argv 一致只能靠人工维持。

目标：

- 入库配置只写 profile 与相对路径；
- 本机绝对路径放忽略文件；
- 显式选择 profile，禁止隐式 fallback；
- `elab doctor --strict-host` 能列出每个值的来源。

### A2（P0）HTTP 层超大人机交互 handler

证据：`cockpit/server.py` 4,302 行，`CockpitHandler` 约 1,967 行，`do_POST` 约 892 行；同时承载 run、debug 写操作、包操作、串口组件、帧协议、Modbus、SSE 等。

后果：

- 端点之间没有明确 owner；
- 权限检查、payload 解析、业务调用和响应格式相互纠缠；
- 单元测试只能从 HTTP handler 入口做集成测试，成本高；
- 新功能自然继续向同一文件堆积。

目标：

- `server.py` 只负责启动、组装和调度；
- 端点按资源拆为独立模块；
- handler 只做路由分发；
- 响应 schema 用快照测试锁定。

### A3（P1）流程定义双源

证据：

- `services/elab/flow.py:23-44` 定义 `STEP_META` / `KERNEL_PLANS`；
- `services/elab/run.py:43-50` 另定义 `ALL_STEPS` / `DEFAULT_STEPS`；
- `tests/test_flow_manifest.py` 负责检查两者一致。

虽然已有测试，但同一业务事实仍由两处声明。目标是由 `flow.py` 单一推导 `run.py` 的执行集合，测试只验证推导结果而不是验证“两份是否碰巧一致”。

### A4（P1）前端 ICD 双镜像

证据：`packages/dsh-elab-cockpit/test/boundary.test.mjs:46-50` 明确说明，因为 host 侧 TypeScript `rootDir` 限制，`domain/icd.ts` 与 `@elab/cockpit-ui-core/src/icd.ts` 必须“逐字同形”、改两处同步。两个文件分别约 1,374 行和 2,069 行。

后果：

- 类型修改依赖人工纪律；
- 网关/事件字段新增时可能出现一侧通过类型检查、另一侧运行期错位；
- DSH 插件和独立 Web UI 的行为一致性靠约定而非生成。

目标：单一 schema 生成两侧类型文件；生成物入库并由 CI 检查漂移。

### A5（P1）内核按文件平铺

证据：`services/elab` 47 个 Python 文件，约 2.7 万行；10 个文件超过 1,000 行。导入关系统计显示 `serialport` 入度 9、`_yaml` 8、`provider` 6、`pkg` 5，天然形成了若干中心。

后果：

- 串口、调试、编排、平台适配共处一个命名空间；
- 新维护者无法从目录判断依赖方向；
- 私有函数和跨模块 monkeypatch 难以治理；
- `from . import xxx` 使边界重构风险集中于全局包对象。

目标：按核心、流程、串口、调试、平台、API 六个 bounded context 建子包，旧路径用兼容层转发。

### A6（P1）文档与现行配置矛盾

证据：

- `packs/official/zephyr/framework/pack.yaml:73-74` 仍写“自研板真相在 `west/zephyr/boards`，仓库 `boards/` 只是归档副本”。
- `zephyr_modules/elab-boards/zephyr/module.yml:3-18` 已明确板子 module 化，并禁止树内副本。

后果：新的维护者会按过期说明把板子拷回 west 树，`west update` 后丢失。

目标：现行事实与历史记录分开；现行文档只保留一个有效口径。

### A7（P2）历史工程树占比过高

证据：`examples/` 入库 1,460 个文件，约 84 万行；现役 `applications/` 84 个文件、约 1.7 万行。

后果：代码搜索、依赖审计、clone、统计和文档导航都被厂商 HAL/CMSIS 干扰。

目标：现役应用留在 `applications/`；历史工程迁至独立仓或 `examples-archive/`，仓库只留索引与适配证据链接。

### A8（P2）Zephyr 事实源治理没有版本闭环

现状：板级 module 化正确，但 manifest、SDK 版本、模块 allowlist 和 bootstrap 尚未入库。现有计划中的 `kharon deps` 已接近完成使命。

目标：新增 manifest 与 bootstrap；`kharon deps` 从“拷贝还原”退休为只读校验。

### 3.2 事实源矩阵

| 事实 | 当前宿主 | 目标唯一宿主 | 禁止写入 |
|---|---|---|---|
| 芯片参数、厂商指纹、OTA 布局 | `packs/**` | 不变 | `services/elab`、`cockpit` |
| 工具链命令模板、产物路径 | `providers/**` | 不变 | 芯片包、项目 YAML |
| 工程绑定、串口判据、步骤覆盖 | `projects/**` | 不变 | 内核代码 |
| 本机工具绝对路径 | 两份 host YAML | `config/host.local.yaml`，忽略入库 | 项目 YAML、pack、provider |
| zephyr 版本与模块集合 | 本机磁盘 | `manifests/zephyr.west.yml` | 口头说明或历史文档 |
| 步骤标签与三档定义 | `flow.py` + `run.py` | `workflow/manifest.py` | 插件默认值、前端常量 |
| 事件与工具 schema | `docs/*.md` + 多份 TS | `contracts/*.schema.json` | 手工修改生成物 |
| 板级 DTS/Kconfig | `zephyr_modules/elab-boards/**` | 不变 | `packs/**` |

### 3.3 允许的依赖方向

```text
config/manifests/projects/packs/providers
                ↓（只读解析）
        services/elab/core + platform
                ↓
          services/elab/workflow
                ↓
      services/elab/api（CLI / HTTP 适配）
                ↓ HTTP ICD 或进程边界
      cockpit/web、packages/dsh-elab-cockpit
```

硬规则：

1. `services/elab/api` 不直接 import `serial/*` 或 `debug/*` 的具体实现，只调用 context 的公开 facade。
2. `cockpit/api/**` 可以 import `elab` 公开 facade，不得 import `elab` 私有子模块。
3. `packages/dsh-elab-cockpit/**` 不得静态 import 业务层，仍只走 loopback HTTP。
4. `domain/**` 保持纯 TypeScript；所有 I/O 留在 adapters。
5. `packs/**` 与 `providers/**` 不得互相 import；跨包共享只通过内核协议。
6. `applications/**/boards/*.overlay` 与应用源码分离；板级公共事实留在 module。

## 4. 分阶段执行方案

### P0：建立不可回退的安全网

目标：在移动任何文件之前，锁定行为与边界。

操作：

1. 新增 `tests/architecture/test_import_boundaries.py`
   - 用 `ast` 扫描 `services/elab/**/*.py`；
   - 禁止 `api` 反向依赖 `serial/debug` 的内部模块；
   - 禁止 `cockpit/api/**` 引用 `elab` 私有实现；
   - 禁止业务层 import `packages/**`。
2. 新增 `tests/contract/test_api_snapshots.py`
   - 对 `GET /api/capabilities`、`/api/projects`、`/api/plan` 做 JSON golden snapshot；
   - 删除字段或修改字段名必须显式更新快照。
3. 固化当前 baseline：
   - `elab list --json`
   - `elab doctor -p f411_breath --json`
   - `elab run -p f411_breath --dry-run`
   - `elab ws --json`
4. 保留现有测试入口，不先改 runner：
   - `PYTHONPATH=services python -m unittest discover -s tests -p "test_*.py"`
   - `./elab ci --job host-gate --json`

验收：

- 全部现有测试通过；
- 新增边界测试对当前源码通过；
- baseline 文件入库并标注生成命令；
- 本阶段不移动任何生产文件。

回滚：删除新增测试即可，无生产代码改动。

### P1：统一 host 配置与 Zephyr workspace 分发

目标：消除隐式 fallback，使 clone 后可复现。

操作：

1. 新增 `config/host.classic.profile.yaml` 与 `config/host.kharon.profile.yaml`
   - 只写 profile 名、键名、`${ELAB_ROOT}` 相对路径和版本约束；
   - 不包含 `C:/Users/...`。
2. 新增 `config/host.local.yaml.example` 与 `.gitignore` 规则
   - 本机 SDK、gdb、OpenOCD、venv 路径写入未入库的 `host.local.yaml`；
   - 合并优先级固定为：环境变量 > local > profile。
3. 修改 `Config`
   - `Config.host_path` 仍作为兼容入口，但内部调用新的 profile resolver；
   - `host_fallback` 保留一个发布周期：使用时打印 deprecation warning；
   - 新增 `host_value(key, source=True)`，doctor 可显示每个值的来源。
4. 修改 `run._host_value`
   - 删除“主文件没有就查 kharon 文件”的隐藏逻辑；
   - 缺键时报出 profile、key 和修复命令。
5. 新增 `manifests/zephyr.west.yml`
   - 锁 zephyr 仓库与 commit；
   - 按当前 `west list` 基线导出实际使用的 module allowlist；
   - 国内镜像只作为 remote 覆写，不能改变 revision。
6. 新增 `services/kharon/bootstrap.py`
   - `bootstrap --check`：只读检查 SDK、workspace、module、profile；
   - `bootstrap`：幂等创建 venv、初始化 workspace、按 manifest 拉取固定 revision；
   - `bootstrap --offline`：只利用本机已有目录，不联网；
   - 失败只输出一条可执行的修复命令。
7. `kharon deps` 改为只读校验：module.yml 有效、树内板副本不存在、`west boards` 能看到本仓板。

验收：

- 仓库中 `git grep -n "C:/Users/" -- '*.yaml'` 对入库 host 文件为零；
- 不设 `ELAB_HOST` 时，`elab doctor` 明确指出未选择 profile，而不是猜；
- 两台机器使用不同 local 路径，`elab run --dry-run` 的 argv 除路径前缀外语义一致；
- 临时干净目录执行 `kharon bootstrap --check` 能列出所有缺失项；
- 现有 `elab ws --json`、`elab doctor --workspace` 输出字段保持兼容。

回滚：保留旧 host 文件一个发布周期；resolver 可由环境变量切回 legacy 模式。

### P2：统一流程事实源并拆分 HTTP 路由

目标：让 `server.py` 成为组装层。

操作：

1. 将 `flow.py` 逻辑迁到 `workflow/manifest.py`
   - `STEP_META`、`KERNEL_PLANS` 保持原名；
   - `run.ALL_STEPS` 改为 `tuple(step_ids())`；
   - `DEFAULT_STEPS`、`ONHW_STEPS` 从 manifest 推导或显式标注为执行策略；
   - 旧 `elab.flow` 路径保留薄转发。
2. 在 `cockpit/api/routes/` 按资源拆文件
   - 第一批：`capabilities.py`、`projects.py`、`runs.py`；
   - 第二批：`serial_routes.py`、`debug_routes.py`、`pkg_routes.py`；
   - 每个 route 函数签名统一为 `handle(ctx, body/query) -> (payload, status)`。
3. `CockpitHandler.do_GET/do_POST` 改为查路由表
   - 不再在 handler 中出现具体业务分支；
   - body 解析、错误映射、JSON 响应仍由 handler 统一负责；
   - 写操作的 confirm/rev 检查移到对应 route 或共享 decorator。
4. 保持 `/api/west` 别名，新增 `/api/workspace`，避免前端一次性迁移。
5. 新增 route snapshot 测试
   - 对旧实现输出保存 JSON；
   - 拆分后逐条比对，状态码和字段名必须一致。

验收：

- `cockpit/server.py` 降至 500 行以内，`do_POST` 降至 120 行以内；
- 所有 API snapshot 与 P0 baseline 一致；
- `tests/test_flow_manifest.py` 改为验证“单一来源推导”，不再比对两份常量；
- CLI 与 HTTP 的 `build/flash/run` dry-run 输出一致。

回滚：路由表可切回旧 handler；本阶段保留原文件副本直到快照全绿。

### P3：重组 `services/elab`

目标：按 bounded context 建包，不改业务行为。

建议迁移分组：

| 目标子包 | 迁入模块 |
|---|---|
| `core/` | `_yaml.py`、`config.py`、`kernel/events.py`、错误类型 |
| `workflow/` | `flow.py`、`run.py`、`plan.py`、`builder.py`、`flash.py`、`monitor.py`、`doctor.py`、`ci.py`、`setup.py` |
| `serial/` | `serialport.py`、`serialmon.py`、`serialterm.py`、`serialcodec.py`、`serialframes.py`、`serialconsole.py`、`serialcontrol.py`、`serialtransport.py`、`serialwidgets.py`、`framelearn.py`、`logdecode.py`、`modbus.py`、`modbusmaster.py`、`netio.py` |
| `debug/` | `debugsession.py`、`debugstore.py`、`debugdata.py`、`debugsource.py`、`gdbmi.py`、`svd.py`、`rtos.py` |
| `platform/` | `pkg.py`、`provider.py`、`market.py`、`lock.py`、`adapt.py`、`skillgen.py`、`project_admin.py`、`wszephyr.py`、`westws.py`、`zephyr_meta.py`、`ota_layout.py` |
| `api/` | 从 `__main__.py` 拆出的 CLI parser 与命令实现、HTTP facade |

执行细节：

1. 每个子包一次只迁 2–3 个模块，使用 `git mv`。
2. 原路径保留兼容模块：
   - 公共符号使用 `from .<newpath> import *`；
   - 对测试使用的私有符号增加 `__getattr__` 转发；
   - 不保留第二份实现。
3. 禁止在迁移提交中修 bug、改输出或重命名函数。
4. 每批迁移后运行：
   - Python 单测；
   - `elab --help`；
   - `elab ci --job host-gate --json`；
   - 插件 npm test（确认 HTTP ICD 未变）。
5. 所有模块迁移完成后，再单独提交删除 compat 的决策；至少留一个发布周期。

验收：

- 导入边界测试通过；
- 公共 API 兼容清单逐项通过；
- 单测数量不减少；
- CLI/HTTP baseline 完全一致；
- 任一子包可独立列出其公开 API。

回滚：`git revert` 单批迁移；compat 模块使后续批次不依赖迁移顺序。

## 6. 风险与处置

| 风险 | 触发场景 | 处置 |
|---|---|---|
| 文件移动打断私有 import | 测试 monkeypatch 了旧模块私有符号 | compat 层保留 `__getattr__` 转发；测试分批迁到新路径 |
| CLI 与 HTTP 行为漂移 | 拆分 router 时改变错误码 | golden snapshot 锁定 payload 与 status |
| host 配置静默变化 | 新旧 profile 同时存在 | `doctor --strict-host` 打印 key 来源；缺键 fail-fast |
| Zephyr workspace 被 `west update` 冲掉 | 板子重新拷进树内 | bootstrap 校验树内残留板即失败 |
| 前端生成物与源码冲突 | 有人手改生成文件 | 生成文件头写 `DO NOT EDIT`，CI diff 守卫 |
| 插件 host TS rootDir 报错 | 直接跨包 import core 源文件 | 采用“同 schema 生成两份目标文件”，不跨 program import |
| 历史工程迁移破坏适配测试 | 项目 YAML 仍引用旧路径 | 先做引用审计，无引用才迁；fixture 单独保留 |
| 大范围重构引入 bug | 移动与修改同时做 | 每次提交只允许移动和转发，不允许改行为 |

## 7. 完成定义

只有以下条件全部满足，才宣称架构优化完成：

- [ ] `git grep -n "C:/Users/" -- '*.yaml'` 对入库 host 配置为零；
- [ ] 不存在隐式 host fallback，profile 选择显式；
- [ ] `manifests/zephyr.west.yml` 锁定 zephyr commit 与已用模块；
- [ ] 干净目录可通过 `kharon bootstrap` 完成 workspace 重建；
- [ ] `services/elab` 按六个 context 分包，旧路径仅剩 compat 转发；
- [ ] `cockpit/server.py` 小于 500 行，HTTP handler 只做路由分发；
- [ ] 步骤定义只有一个事实源；
- [ ] 前端 ICD 由单一 schema 生成，生成物 CI diff 为空；
- [ ] `examples/` 中不再混入无引用的历史工程；
- [ ] `docs/current/` 与 `docs/archive/` 明确分离，板级事实源无矛盾；
- [ ] Python 单测、`elab ci --job host-gate`、插件 `npm test`、`tsc --noEmit`、`npm run build` 全部通过；
- [ ] CLI 与 HTTP 的 dry-run、事件和 API snapshot 与基线一致。

## 8. 明确不做

1. 不把 `applications/` 强行搬进 west workspace；官方允许 freestanding application。
2. 不把 Zephyr 的 DTS/Kconfig 内容抄进 `packs/**`。
3. 不把 `providers/**` 做成可执行插件；它只能继续是声明式数据。
4. 不把板级文件拷回 `west/zephyr/boards/**`。
5. 不在工具层 import 业务层源码；唯一缝隙仍是 loopback HTTP ICD。
6. 不为“看起来统一”而重命名公开 API；所有重命名都要经过兼容期。
7. 不在本方案中顺手修业务 bug；架构提交与行为修改必须分开。

## 9. 阶段顺序

```text
P0 安全网
 └─> P1 host profile + manifest + bootstrap
      └─> P2 flow 单源 + HTTP router 拆分
           └─> P3 services/elab context 分包
                └─> P4 前端 schema 生成
                     └─> P5 历史工程与文档收口
```

执行纪律：**P1 未完成前不做 P3，P0 未完成前不做 P2。**  
每次阶段完成都单独验收、单独提交；不要合并成一次“全仓大重构”。

本方案不授权自动 git commit。实施时应按项目既有流程完成验证、更新改动记录，再由用户明确指示提交。
