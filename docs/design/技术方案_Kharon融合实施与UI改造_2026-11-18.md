## 2. 仓库落位：Zephyr 源码怎么住进 elab

### 2.1 目标布局

```
dsh-elab-flow/
├── applications/                          ← 【入库】从 zephyr-learn/apps 提升
│   ├── esp32s31/{korvo_sys,korvo_shell,korvo_lab,korvo_nvs,korvo_periph,korvo_apps}/
│   ├── esp32s3/{s3_wifi_portal,korvo_wifi,blinky_s3,input_btn}/
│   ├── stm32f1/{f103_breath,common}/      stm32f4/{f411_breath,f411_hwpwm,common}/
│   ├── common/{src,include,test}/         _template/
├── boards/                        ← 【入库】boards_local 提升为正式目录（真相）
│   └── esp32s31_function_coreboard/{board.yml,*.dts,*.yaml,support/openocd.cfg}
├── patches/zephyr/*.patch         ← 【入库】上游补丁（mbedtls legacy support）
├── west/                          ← 【不入库】west 工作区（原 zephyr_k）
│   ├── .west/config  zephyr/  modules/  bootloader/
├── .deps/                         ← 【不入库】venv / .tools(cmake,ninja,ccache) / .ccache
├── packs/zephyr/framework/        ← 适配包：board-as-chip + log_profiles + 坑位
├── providers/zephyr/west/         ← 工具链 provider：west 命令模板
├── projects/kharon/*.yaml         ← 工程绑定（app × board）
├── distros/kharon/distro.yaml     ← 发行清单（唯一发行）
├── kharon.host.yaml               ← 主机事实源（取代 env.ps1 的职责）
├── cockpit/  services/elab/  packages/   ← 共享层（见前置文档 §2）
└── docs/{design,reports,教程}/
```

三条归属规则，一条比一条硬：

1. **上游的东西不入库**（`west/`、`.deps/`）——它们是 `kharon deps` 的产物，可重建。
2. **只有"我们的知识"入库**（`applications/`、`boards/`、`patches/`、`packs/`、`projects/`、`providers/`）。
3. **芯片事实只在两处**：dts（Zephyr 的）与 `packs/**/chips/*.yaml`（我们独有的：board 名映射、调试配置、坑位）。**禁止第三处**。

### 2.2 为什么不是「保持 zephyr-learn 原样」

原样保留的代价不是磁盘，是**两套根判据**：`env.ps1` 要求「同层有 `env.ps1` 与 `zephyr_k`」，而 elab 要求「同层有 `cockpit/server.py` 与 `services/elab`」。两个根判据并存，就会出现"在 `zephyr-learn/` 里跑 `west`、在父目录跑 `kharon`，两边看到的世界不一样"——这正是前置文档 §2 说的"第二套真相"。

**处理方式**：`kharon.host.yaml` 取代 `env.ps1` 的职责（路径 + env + PATH 前置都由 provider 声明），`env.ps1` 降级为人类手工 shell 的便捷脚本，由 `kharon env --shell pwsh` 生成（见 T9）。

## 3. 数据模型：芯片 → 工程 二级树

### 3.1 现有 `ProjectCard` 已经够用

`packages/cockpit-ui-core/src/icd.ts:172` 的 `ProjectCard` 已有 `chip`（工程绑定的芯片引用）与 `chip_info`（`icd.ts:160`：`part/core/memory/debug`）。后端在 `cockpit/server.py:1011 project_cards()` 里从 `projects/*.yaml` + `chips/*.yaml` 拼出，`server.py:1166` 组装 `chip_info`。

**所以"按芯片分组"不需要新字段**：`cards` 按 `card.chip` 分桶即可。芯片显示名优先 `chip_info.part`，回退 `chip` 字符串。

### 3.2 唯一的硬墙：`projects` 发现是非递归 glob

```python
# services/elab/config.py:184
for path in sorted((self.root / "projects").glob("*.yaml")):
```

`projects/kharon/*.yaml` **不会被发现**。对比另两个发现根——它们早就是数据驱动的：

| 发现根 | 现状 | 证据 |
|---|---|---|
| packs | ✅ `elab.host.yaml: packs.roots` (+ env 兜底 + `packs/official` 内置) | `pkg.py:106-120` |
| providers | ✅ `elab.host.yaml: providers.roots` + `ELAB_PROVIDER_ROOTS` | `provider.py:115-130` |
| projects | ❌ 硬编码 `root/projects/*.yaml` | `config.py:184` |

改造（T3）：`rglob("*.yaml")` 或读 `elab.host.yaml: projects.roots`，两种都行；**别加 distro 判断**（前置文档红线）。改动量 ~10 行，但 P0 可以绕过（工程 yaml 平铺在 `projects/` 根下）。

### 3.3 board-as-chip 的语义与红线

Zephyr 没有"芯片 yaml"这个概念，它的最小单位是 **board**（`board.yml` + dts + defconfig）。所以 Kharon 的 `chip` 语义 = **board target 字符串**：

| 我们的 chip id | board target（`west -b` 的值） | 段数 |
|---|---|---|
| `zephyr/framework/blackpill_f411ce` | `blackpill_f411ce` | 一段 |
| `zephyr/framework/stm32f103_mini` | `stm32f103_mini/stm32f103xe` | **两段**（qualifier 是 SoC 名） |
| `zephyr/framework/esp32s3_devkitc` | `esp32s3_devkitc/esp32s3/procpu` | 三段 |
| `zephyr/framework/esp32s31_function_coreboard` | `esp32s31_function_coreboard/esp32s31/hpcore` | 三段 |

**红线**：`chips/*.yaml` 只写"elab 独有的知识"——`target`（board 名）、`debug.*`（gdb 键 / openocd cfg）、`serial.baud`、坑位。**不写** `memory` / `core.cpu` / `compiler_defines`：那些是 dts 与 Kconfig 的事实，抄进来就会出现"体检说错、构建是对的"。

好消息：内核所有取用点都做了空值兜底，**不填不会崩**——

```python
doctor.py:330   phys = (plan.chip.get("memory") or {}).get("flash") or None
doctor.py:372   for k, v in (plan.chip.get("memory") or {}).items():
server.py:1166  "core": chip.get("core") or {}, "memory": chip.get("memory") or {},
```

所以 T4（"允许 chip 缺 memory/core"）实际工作量接近 0，要做的只是：**UI 别把空值渲染成"0%"**，改成"未测量"（见 §4.3）。

### 3.4 新增 `matrix:` 分组（唯一的新元数据）

多板对照要知道"哪几个工程是同一台设备的四块板"。可选三种来源：

| 方案 | 判据 | 结论 |
|---|---|---|
| 按 `root` 目录名猜 | `applications/esp32s31/korvo_sys` 与 `applications/stm32f4/korvo_sys` 同名 | ❌ 靠命名约定，改名就散 |
| 按 `applications/<soc>/<app>` 路径解析 | 路径天然带 soc 层 | ⚠ 可行但把目录结构变成语义 |
| **工程 yaml 显式 `matrix: korvo_sys`** | 一行数据 | ✅ 采用 |

```yaml
# projects/kharon/korvo_sys_s31.yaml
name: korvo_sys_s31
chip: zephyr/framework/esp32s31_function_coreboard
root: ${ELAB_ROOT}/applications/esp32s31/korvo_sys
matrix: korvo_sys            # ★ 同组 = 同一次对照
```

**注意一个诚实的事实**：仓库里真正的"一个 app × 多板"只有 `korvo_sys`（`applications/esp32s31/korvo_sys/boards/` 下正好两份 overlay：`esp32s31_function_coreboard_esp32s31_hpcore.overlay` 与 `esp32s3_devkitc_esp32s3_procpu.overlay`）。`f411_breath` 与 `f103_breath` 是**两个独立 app**（`main.c` md5 不同）。所以：
- `matrix: korvo_sys` = 真·一 app 两板（现成）；
- `matrix: breath` = 两个 app 的对照（价值同样成立，但文案要写"同组工程"而不是"同一 app"）。

### 4.1 左栏：从平铺列表改成「芯片 → 工程」二级树

具体改动清单（都在 `ProjectsRail.tsx` 内，不动 App）：

| 项 | 做法 | 依据 |
|---|---|---|
| 分组函数 | 纯函数 `groupByChip(cards): ChipGroup[]`，key = `card.chip`，标题 = `chip_info.part \|\| card.chip`，副标题 = `core.cpu` + 存储 | 零新元数据 |

| 锁定 | `locked` 时**只禁切换工程**，不禁折叠/展开 | 现有纪律："有任务在跑，先取消或等它结束"（第 160 行） |

### 4.2 芯片切换器

不做独立侧栏（会挤掉工程树空间），做成**头部一行紧凑切换条**：

```
[全部芯片 ▾]  ESP32-S31 ×   ESP32-S3 ×   F411
```

- 单选 → 只显示该芯片组（其余组仍列出组头，但灰化 + 显示"3 个工程"），**不隐藏**，避免"我的工程去哪了"。

### 4.3 芯片卡改成两态（未构建 / 已构建）

现状芯片卡（`ProjectsRail.tsx:350-535`）直接读 `chip_info.memory/core`。Zephyr 的 chip yaml 不写这些，所以会显示 `—`。

## 5. 四大差异化能力：实现路径

### 5.1 多板并排对照（一个 app × 4 板）

**已经有的**（这是最关键的发现）：

| 能力 | 证据 |
|---|---|
| 多 run 并发 | `RunManager._active` 是 `dict[run_id]`，每个 run 一个 follower 线程（`server.py:640-663`）；`spawn()`（736 行）**没有**"只允许一个 run"的守卫 |
| 每个 run 独立产物 | `<id>.jsonl` + `<id>.proc.jsonl` + `<id>.log` + `<id>.serial.log`（`events.py:700`） |
| 内存数字 | build 步骤事件里带 `memory` / `size` / `memory_source`（`run.py:651-676`）——**外部 provider 也会从 `.map` 回填** |
| 串口互斥 | `serialmon.open_session` 单会话 + `/api/run` 里的 `_serial_yield_begin`（`server.py:1356 _serial_blocker`）自动让位 |

**缺的三件**：

1. **分组**：`matrix:` 字段（§3.4）。
2. **聚合端点**：`/api/matrix?group=korvo_sys` → 对组内每个 project 取最近一次含 build 的 run，抽出 `memory/size/verdict/elapsed`。一次扫描 + 进程内缓存（`run_meta` 已做过首尾读优化，800 条历史 ~0.6s，见 `events.py:663-668` 的性能注记）。
3. **并发预算**（**必须做，否则必然翻车**）：上游自己的文档实测 `-j18` 触发 cc1 OOM。4 板 × 8 并发 = 32 → 必然 OOM。策略：
   - `matrix.max_parallel: 2`，每路 `jobs = 8 / min(2, n)`；
   - **只并行 build/flash，monitor 一律串行**（串口只有一个）；
   - 排队状态进事件流（`queue/waiting`），UI 显示"第 2/4 板，等待中"。

**工作量**：server ~120 行 + 前端 `MatrixWorkspace.tsx` ~350 行。

**验收判据**（可机械判定）：
- 一次点击 → 四个 run 依次/并发完成，矩阵表 4 行齐全，FLASH/RAM/耗时/结论四列无空、无 `—`；
- 点任意一行 → 落到该工程的证据（该 run 的事件流），**不是**别的工程的日志；
- 断网重进页面 → 矩阵数据仍在（读的是 run 留档，不是内存状态）。

[00:00:21.324,000] <inf> portal_cred: credential remembered: "501A" (2 saved)

| S4 | Zephyr 线程视图（`k_thread` 遍历 + 栈水位） | `rtos.py` | ~200 行（P3） |

S3 的两个具体卡点（行号已核对）：

```python
# plan.py:99-107 —— 二元硬编码
backend = str(dbg.get("backend") or "openocd")
esp_idf = backend in ("esp-idf", "idf")
gdb = (self.host.gdb_riscv or self.host.gdb) if esp_idf else self.host.gdb
openocd = (self.host.openocd_esp32 or self.host.openocd) if esp_idf else self.host.openocd

# flash.py:22 —— 只认 interface + target 两段，且强校验文件在 scripts_dir 下
if not interface or not Path(scripts_dir, interface).exists(): raise ...
if not target or not Path(scripts_dir, target).exists(): raise ...
```

Zephyr 的 `boards_local/.../support/openocd.cfg` 是**整份 cfg**（base + interface + target 混写，内部 `source board/esp32s31-builtin.cfg`），塞不进两段式。所以必须加一条"整份 cfg"通道：`chip.debug.openocd_config` → `openocd -s <scripts_dir> -f <abs cfg>`，并让 `debugsession.py:294` 的 `if not target` 断言在 `openocd_config` 存在时放行。

**同时必须修一个设计缺陷**：`Host` 的工具是一个**属性一把钥匙**（`gdb` / `gdb_riscv` / `openocd` / `openocd_esp32`，`config.py:356-437`）。再加 `gdb_zephyr_arm/riscv/xtensa` 就是 3 个属性，等于把"发行差异"写进内核。正确做法是加一个通用访问器：

```python
# config.py
def tool(self, key: str) -> dict:      # 任意键，返回 {"path","scripts",...}
    return ((self.data.get("tools") or {}).get(key) or {})
```

芯片侧只写键名：`debug: { gdb_key: gdb_zephyr_arm, openocd_key: openocd_esp32 }`。这才是数据驱动，也符合"芯片知识只写适配包"。

## 9.2 关键纠正：调试参数一律读 `runners.yaml`

上一版方案打算在 `chips/*.yaml` 里写 `debug.openocd_config`（整份 cfg 路径），并为此估了 ~45 行改动。
**这个方向错了**，理由在构建产物里：

```yaml
# build/…/zephyr/runners.yaml（configure 阶段由 board.cmake 生成）
runners: [dfu-util, stm32cubeprogrammer, openocd, jlink, blackmagicprobe]
flash-runner: dfu-util
debug-runner: openocd
config:
  gdb: C:/Users/xiao1/zephyr-sdk-1.0.1/gnu/arm-zephyr-eabi/bin/arm-zephyr-eabi-gdb-py.exe
  openocd: C:/Users/xiao1/zephyr-sdk-1.0.1/hosttools/openocd/bin/openocd.exe
  openocd_search: [ …/openocd/share/openocd/scripts ]
args:
  openocd: [--cmd-load, flash write_image erase, --cmd-verify, verify_image]
  jlink:   [--dt-flash=y, --device=STM32F411CE, --speed=4000]
```

GDB、OpenOCD 的**绝对路径**、scripts 搜索路径、每路参数，构建系统全给了。我们在芯片包里再抄一份
= 同一块板两份参数，谁对谁错取决于人 —— 正是方案 §6.1 的红线。

**结论**：Kharon 的调试链应当 `runners.yaml` 优先，芯片包只做覆盖与兜底。这条同时把
`chip.debug.gdb_key` / `openocd_key` 的必要性降级为"runners.yaml 缺失时的兜底"。

顺带一个真实诊断价值：本板 `flash-runner` 默认是 **dfu-util**（F411 需要进 DFU 才认），
而调试 runner 是 openocd —— 面板把它显示出来，"为什么烧不进去"立刻有答案。

### 9.6.1 三条链的分歧被收敛成"一个入口 + 三种形态"

`flash` / `debug_verify` 没有被 Zephyr 分叉成第二套实现，改动全落在既有函数里：

| 形态 | 判据 | 命令 |
|---|---|---|
| classic 两段 cfg | 芯片包有 `debug.openocd_target` | `-f interface/x.cfg -f target/y.cfg`（逐字不变） |
| Zephyr 整份 cfg | 芯片包有 `debug.openocd_config` | `-f <整份 cfg>`（interface+target+reset_config 混写） |
| 非 openocd runner | `flash.runner` ∉ {`""`, `openocd`} | `west flash -d <build> --runner <runner>` |

配套两个小机制：

- `Host.tool(key, field="path")` —— 通用工具访问器。芯片包只写**键名**
  （`gdb_key: gdb_zephyr_arm`），三套架构（ARM / RISC-V / Xtensa）的 gdb 与 addr2line 不再各加一个
  Host 属性。环境变量覆盖沿用 `ELAB_TOOL_<KEY>`。
- provider 的 `native: true` —— "这一步不归我，交回内核"。**不是**缺步骤静默回退
  （缺步骤仍然 `unavailable` 报错，D3 不变），必须在 `provider.yaml` 里写出来才生效，可审计。

### 9.6.2 ★ 真坑：不开 `CONFIG_DEBUG` 时 `continue` 会"假崩"

症状：会话开得起来、能停在 `main`；一按继续，openocd 立刻刷

```
Error: [stm32f4x.cpu] Polling failed, trying to reexamine
Error: Failed to read memory at 0xe000ed04
Error: [stm32f4x.cpu] Examination failed
```

gdb 侧报 `signal-received`、`pc=0x0`、`??`——**看起来像固件崩了**。但同一时刻串口心跳照旧，
`monitor` 步全绿：固件根本没崩。

根因：WFI/STOP 期间内核时钟被门控，AHB-AP 读不到内核寄存器（`0xe000ed04` 是 ICSR，SCB 的入口）；
DP 层还有回应（`SWD DPIDR 0x2ba01477`），所以不是接线问题。降到 500 kHz 也复现，排除速率。

修法：`prj.conf` 加 `CONFIG_DEBUG=y`。STM32 的 SoC 初始化随之置 `DBGMCU_CR` 的
`DBG_SLEEP|DBG_STOP|DBG_STANDBY` 三个冻结位，低功耗态下调试口仍可访问。加完同一操作直接
`breakpoint-hit 0x80006e2 @ main.c:97`。

**这条写进包坑位**（`packs/official/zephyr/framework/pack.yaml#pitfalls`）：它不是 F411 的特性，
是所有 Cortex-M + WFI 的共性，只是"固件看起来崩了"这个假象特别费人。

### 9.6.4 两个产品的边界落在 profile，不落在代码

第一次以 `kharon` 主机起驾驶舱时，左栏是 18 个工程混排（classic 的 CubeMX 工程排在上面、
每个都挂一条「flash / debug_verify 不可用」的红字）——它们不是"坏了"，是 **kharon.host.yaml
的 provider roots 里没有它们的 provider**。产品边界没画在数据里，就成了噪音。

修法是把"看哪些工程"也变成装配数据（`cockpit/profiles/kharon.yaml`）：

```yaml
profile: kharon
workspaces: [debug, build, dash, flash, serial, matrix, west, tools]
projects:
  archetype: [zephyr]        # ← 只此一行决定可见范围
```

`web.yaml` 不写 `projects` 节 → 全可见，classic 行为逐字不变；代码里没有任何厂商分支。
结果：左栏 4 个芯片组 / 7 个工程，芯片卡两态（未构建「待测量」、构建后读 ELF 实测）。

同时补了 `kharon.host.yaml` 的 `probes:` 段。缺它的症状很隐蔽：**CLI 烧录正常、面板全灰**
（`project_cards` 的可用性判定要求 `debug.probe` 在 `probes.list` 里）。声明与执行必须同源，
否则"面板说不行、命令行却行"比不能用更费人。

### 9.7 一键切换：把"两个入口"变成顶栏一个开关（2026-11-18）

到这里两个产品仍是"启动时选一次"（`ELAB_HOST=kharon.host.yaml`）。验收时那句反问很自然：
**既然差别只是两份装配数据，为什么要重启进程才能对比？** 于是把它做成运行期切换。

#### 9.7.1 切的是什么（只有两处）

| 环境变量 | 来源 | 影响 |
|---|---|---|
| `ELAB_HOST` | 目标清单的 `host:` 一行 | 工具链 / 探针 / Zephyr 工作区 / 串口默认 —— **全部** |
| `ELAB_PROFILE` | 目标清单的文件名 | 左栏可见范围、右列工作区顺序、工具启停 |

★ 关键决定：**走环境变量，而不是给每条链路各传一份 Config**。`elab run` 子进程、openocd、
gdb、west、modbus 主站都是派生进程，环境天然被继承 —— 少一处传递就少一处忘传。
证据（同一次 `doctor`，两套 host）：

```text
classic:  [info] host.yaml  .../elab.host.yaml
          [OK  ] toolchain.root  C:/DevEnv/GNU-tools-for-STM32
zephyr :  [tool:doctor] $ .../.deps/venv/Scripts/python.exe -m west --version
          West version: v1.5.0
```

`west_python` 这个键只存在于 `kharon.host.yaml`，classic 那份里没有 —— 读到它才算真换了。

#### 9.7.2 三条把关（缺一条都会变成"看起来切了"）

1. **有活就拒**：闭环在跑 / 调试会话开着 / 串口监视开着 → 400 指名道姓。它们握着按旧 host
   解析出来的工具句柄，中途换 host 的表现是"每个动作都报工具找不到"，而界面上看不出配置换过。
2. **失败回滚**：host 文件缺失时把 `ELAB_HOST` / `ELAB_PROFILE` 复原。半切状态（host 换了、
   profile 没换）会让左栏工程与右列工作区互相矛盾，且没有任何一处能看出是怎么来的。
3. **换就换到底**：`handler.cfg`（每请求读它）、`mgr.cfg`（起 run）、`dbg.cfg`（开调试）
   三份引用 + `mgr.runs_dir` 一起换。只换一份的症状最阴：面板用新 host，一按「跑闭环」
   子进程拿的还是旧 host。（顺带发现 `/api/pkg/*` 与 `/api/adapt` 的重载也漏了 `dbg.cfg`，已一并修。）

#### 9.7.3 不持久化是刻意的

运行期切换只活在本进程。重启后仍由 host 那份静态 `profile:` 决定 —— 否则
`kharon.cmd`（默认 zephyr）与 `cockpit.cmd`（默认 classic）各自的默认会被上一次点击改掉，
"我明明用 kharon 启动的，怎么是 classic"这类幽灵故障迟早出现。

#### 9.7.4 实现落点

| 项 | 位置 |
|---|---|
| 模式表（扫目录 → `label/desc/order/host`） | `cockpit/server.py::_mode_record / _profile_summary` |
| 激活优先级（env → host → web） | `cockpit/server.py::_active_profile_name` |
| 切换 + 回滚 | `cockpit/server.py::switch_mode` |
| 把关 + 三份引用 | `cockpit/server.py::CockpitHandler::_switch_mode` |
| 端点 | `POST /api/mode`（ICD §3.8） |
| 顶栏开关 | `cockpit/web/src/App.tsx`（`SegmentedTabs`，`modes.length > 1` 才渲染） |
| 装配数据 | `cockpit/profiles/{web,kharon}.yaml` 的 `label / desc / host / order` |
| 守卫 | `tests/test_cockpit_mode.py`（8 例：模式表 / 优先级 / 回滚 / 无 host 回落） |

### 9.8 Zephyr 专属调试区（2026-11-19，F411 实机）

参考 Zephyr IDE 在 Zephyr 模式下的调试区，把「通用 GDB 面板看不懂内核态」补齐。
页签只在 `zephyr/` 构建出现（`features` 里的 `zephyr` 由工程判据决定，不是符号探测）。

| 层 | 落点 | 内容 |
|---|---|---|
| 数据 | `services/elab/debug/zephyr.py` | `_kernel` 概览、线程表（复用 `rtos`）、静态内核对象、`.config` 能力事实 |
| 线程 | `services/elab/debug/rtos.py` | 兼容 3.x/4.x 三种线程表：`threads` 单链、`threads` `sys_slist`、`ready_q.runq` 双向链 |
| 接口 | `GET /api/debug/zephyr` | 返回 `kernel / threads / objects / object_groups / config / notes` |
| 前端 | `DebugWorkspace.tsx` 的 `Zephyr` 页签 | 内核概览 + 线程（可选中看栈区间、跳栈内存）+ 对象计数/字段 + 配置告警 |
| 测试 | `tests/test_zephyr_debug.py` | 9 例：配置解析、对象段/字段、两种 4.x 线程表、非 Zephyr 拒绝 |

**三个真机纠正（都会踩第二次）**

1. **`k_thread` 在 4.x ELF 里不是 typedef**：裸 `(k_thread*)0` 真机报
   `No symbol k_thread`，必须 `(struct k_thread*)0`；而 `_mi_expr` 原本会把空格
   压成 `structk_thread`。修法：含 `struct/union/enum` 关键字的表达式整体按 MI
   C 字符串引用（`"(struct k_thread*)0"` 实测可求值）。
2. **`CONFIG_THREAD_MONITOR=n` 时 4.x 没有 `_kernel.threads`**：回落到
   `_kernel.ready_q.runq`（`sys_dlist_t`，节点就是 `&thread->base.qnode_dlist`），
   能看到就绪线程但看不到阻塞/挂起线程；页面把来源与限制写清楚，并给出
   `CONFIG_THREAD_MONITOR=y` 建议。
3. **`CONFIG_INIT_STACKS=n` 时栈里没有 0xAA**：扫描结果必然是"全部已用"。
   现在 `rtos` 接受 `config`，该开关关闭时直接不出水位数字（`—`），
   而不是展示一个必然误报的 100%。

F411 实测：`features` 含 `zephyr`；线程 2 个（main + idle，来源 `readyq`），
prio/状态/栈区间正确；14 类内核对象段全部存在且为空；`notes` 命中
THREAD_MONITOR / THREAD_NAME / INIT_STACKS / OBJ_CORE 四条。
回归：单测 813 OK（skipped=2，新增 9 例），集成 58 OK。
